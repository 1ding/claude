# 1 总则

+   **文档编号**：TW-FMT-PPT-01
+   **文档名称**：Markdown 转 PPT 内容格式规范
+   **文档密级**：【内部资料】 -- 不主动对外公开。
+   **适用对象**：AI 文档转换助手
+   **管理要点**：本规范定义将 Markdown 文档转换为 PPT 内容稿时的格式约束，包括标题层级映射、页面容量、标注系统、内容转换、代码处理等规则。

## 1.1 执行原则

-   **保持逻辑结构**：不改变原文档的章节顺序和核心观点。
-   **保持内容完整性**：不忽略、跳过或删减原文档的内容和要点；单页内容过多时分页展示。
-   **控制页面容量**：每页内容适合一个 PPT 页展示。
-   **优化表达方式**：段落文字转换为结构化要点，精简冗余表述。
-   **提供可视化建议**：以标注形式提供 PPT 可视化建议。

# 2 标题层级规则

## 2.1 层级映射

+   PPT 内容稿的标题层级与 PPT 页面的对应关系如下表所示。

    | 层级     | 语法   | PPT 用途   | 数量 | 说明                                  |
    | -------- | ------ | ---------- | ---- | ------------------------------------- |
    | 文档标题 | `#`    | 封面页     | 1 个 | 包含标题、副标题、日期                |
    | 章节标题 | `##`   | 章节分隔页 | 不限 | 大章节的起始页，仅标题                |
    | 主页面   | `###`  | 标准内容页 | 不限 | 每个 `###` 独立成页                   |
    | 子页面   | `####` | 主题细分   | 可选 | 从属于 `###`，标题显示为"主题/子主题" |

## 2.2 约束

-   最多使用 4 级标题（`#` 至 `####`），不应使用 `#####` 及以下。
-   子页面（`####`）标题显示格式为"父主题/子主题"。

# 3 页面容量规则

## 3.1 容量标准

+   每个 PPT 页面的内容元素应符合以下限制。

    | 元素       | 限制       | 说明                                |
    | ---------- | ---------- | ----------------------------------- |
    | 页面标题   | ≤20 字     | 清晰、可独立理解                    |
    | 要点数量   | 4-6 条     | 最少 3 条，最多 8 条                |
    | 单条要点   | 20-40 字   | 完整表达，保持精炼                  |
    | 页面总字数 | 300-400 字 | 不含代码和标注                      |
    | 代码行数   | ≤50 行     | 单块代码的限制                      |
    | 列表嵌套   | ≤2 层      | 主要点→次要点；避免三层嵌套影响可读 |

## 3.2 字数计算

+   页面字数 = 标题字数 + 所有要点字数 + 补充说明字数。
+   不计入：代码块、标注标签、分隔符。

## 3.3 内容密度参考

-   **标准密度页**（300-400 字）：框架介绍、方法论说明、实施步骤
-   **中密度页**（250-300 字）：要点列举、对比分析、案例说明
-   **低密度页**（200-250 字）：数据展示为主、简单流程、关键结论
-   **极简页**（<200 字）：章节封面、引用金句、单一图表

## 3.4 分页规则

+   当原文内容超出单页容量时，应按以下规则分页展示，不应删减内容。

-   **分页触发条件**：要点数 >8 条，或总字数 >400 字，或单条要点 >40 字且要点数 >5 条。
-   **分页策略**：优先按逻辑维度拆分（概述页 + 详情页，或按维度分组各占一页）；无法按逻辑拆分时，按内容顺序均匀分配。
-   **分页标题**：使用"主题（续）"或按逻辑维度命名（如"主题：组织维度""主题：技术维度"）。
-   **分页关联**：首页末尾可添加"详见下页"提示，帮助读者理解内容连续性。

## 3.5 单条要点精炼规则

+   单条要点超过 40 字时，应按以下优先级精简。

-   **优先级 1：去冗余**：删除"进行""实现""通过...方式"等虚词和冗余结构。
-   **优先级 2：拆分**：一条含多个信息点的要点拆为 2-3 条独立要点。
-   **优先级 3：提炼**：长描述改为"关键词 + 短说明"格式（如"**核心原则**：零信任架构，持续验证每次访问"）。

# 4 标注系统

## 4.1 核心内容标注

+   用于标记页面中的重点信息类型。

    | 标注      | 用途         | 适用场景               |
    | --------- | ------------ | ---------------------- |
    | `[KEY]`   | 核心信息强调 | 关键结论、重要概念     |
    | `[DATA]`  | 数据突出     | 统计数据、百分比、指标 |
    | `[QUOTE]` | 引用         | 权威观点、文献引用     |
    | `[CASE]`  | 实际案例     | 真实案例、应用场景     |
    | `[VS]`    | 对比说明     | 前后对比、优劣对比     |

## 4.2 视觉元素标注

+   用于建议 PPT 中应使用的图表或图片类型。

    | 标注                 | 用途     | 适用场景           |
    | -------------------- | -------- | ------------------ |
    | `[CHART:bar]`        | 柱状图   | 对比数据、排名     |
    | `[CHART:line]`       | 折线图   | 趋势变化、时间序列 |
    | `[CHART:pie]`        | 饼图     | 占比分布、构成     |
    | `[CHART:flow]`       | 流程图   | 步骤、流程、关系   |
    | `[CHART:compare]`    | 对比图   | 方案对比、优缺点   |
    | `[CHART:table]`      | 表格     | 规范数据、矩阵     |
    | `[CHART:timeline]`   | 时间线   | 发展历程、路线图   |
    | `[IMAGE:photo]`      | 实景图片 | 现场照片、产品图   |
    | `[IMAGE:diagram]`    | 示意图   | 架构图、模型图     |
    | `[IMAGE:screenshot]` | 截图     | 界面、操作示例     |
    | `[ICON:类型]`        | 图标建议 | shield/chart/user  |

## 4.3 布局标注

+   用于建议 PPT 页面的排版布局方式。

    | 标注                  | 用途     | 效果                   |
    | --------------------- | -------- | ---------------------- |
    | `[LAYOUT:left-right]` | 左右分栏 | 对比内容、代码与说明   |
    | `[LAYOUT:top-bottom]` | 上下布局 | 原理与应用、问题与方案 |
    | `[LAYOUT:center]`     | 居中突出 | 核心数据、关键结论     |
    | `[LAYOUT:grid]`       | 网格布局 | 多模块并列、分类展示   |
    | `[EMPHASIS:number]`   | 大号数字 | 关键指标、统计结果     |
    | `[PROGRESS:比例]`     | 进度展示 | 完成度、达成率         |

## 4.4 代码标注

+   用于指定代码块在 PPT 中的展示方式。

    | 标注             | 用途       | 说明               |
    | ---------------- | ---------- | ------------------ |
    | `[CODE:single]`  | 单栏代码   | ≤15 行，完整展示   |
    | `[CODE:double]`  | 双栏代码   | 16-30 行，左右分栏 |
    | `[CODE:compare]` | 代码对比   | Before/After 对比  |
    | `[CMD]`          | 命令行示例 | Shell 命令         |
    | `[CONFIG]`       | 配置文件   | YAML/JSON/XML 配置 |
    | `[PSEUDO]`       | 伪代码     | 逻辑说明、算法描述 |

## 4.5 章节页标注

+   用于丰富章节分隔页（`##`）的内容元素，避免章节页过于空白。

    | 标注                    | 用途       | 效果                           |
    | ----------------------- | ---------- | ------------------------------ |
    | `[SECTION:keywords]`    | 关键词预览 | 在章节标题下方展示 3-5 个关键词 |
    | `[SECTION:progress]`    | 进度指示   | 展示"第 N 章 / 共 M 章"       |
    | `[SECTION:outline]`     | 章节目录   | 列出本章包含的 3-4 个子主题    |

# 5 内容转换规则

## 5.1 段落文字

+   将连续段落拆解为 4-6 个结构化要点。
+   每条要点 20-40 字，使用加粗关键词引导。
+   为核心概念添加 `[KEY]`、数据添加 `[DATA]` 标注。

## 5.2 长列表

+   按逻辑维度分组（如"组织与流程维度""管理与监督维度"），每组 3-4 条。
+   每条要点补充具体说明，不应仅列名称。
+   超过 8 条时应分页展示（见第 3.4 节）。

## 5.3 复杂句

+   一句话拆成多个要点，每个要点聚焦一个信息单元。

## 5.4 数据处理

+   数据可视化决策规则如下：

-   单个关键数字 → `[DATA]` + `[EMPHASIS:number]`
-   时间序列数据 → `[CHART:line]`
-   分类对比数据 → `[CHART:bar]`
-   占比构成数据 → `[CHART:pie]`
-   多维度数据 → `[CHART:table]`
-   流程步骤 → `[CHART:flow]`

## 5.5 逻辑结构识别

+   在转换过程中，应识别内容的逻辑结构并选择对应的布局标注。

-   **对比结构**（A vs B、现状 vs 目标、问题 vs 方案）→ `[LAYOUT:left-right]` + `[CHART:compare]`
-   **递进结构**（阶段1→阶段2→阶段3）→ `[CHART:flow]` 或 `[CHART:timeline]`
-   **分类结构**（3-4 个并列模块）→ `[LAYOUT:grid]`
-   **层级结构**（核心要点 + 详细展开）→ `[LAYOUT:top-bottom]`
-   **总分结构**（总述 + 分项说明）→ 首页总述 `[KEY]` + 后续分页详述

# 6 代码块处理

## 6.1 基本要求

-   总行数 ≤50 行，单行长度 ≤80 字符。
-   应指定语言标签（`python`、`yaml`、`bash` 等）。
-   应添加注释说明核心逻辑。

## 6.2 代码标注选择

-   ≤15 行 → `[CODE:single]`
-   16-30 行 → `[CODE:double]`（左右分栏）
-   对比展示 → `[CODE:compare]`（Before/After）
-   配置文件 → `[CONFIG]`
-   命令行 → `[CMD]`

# 7 特殊场景处理

## 7.1 大量表格

-   简单表格（2-3 列）→ 转换为要点列举。
-   复杂表格（4 列以上）→ 标注 `[CHART:table]`。
-   对比表格 → 标注 `[CHART:compare]`。

## 7.2 大量代码

-   每个代码块 ≤50 行。
-   保留核心逻辑代码，移除辅助性代码。
-   根据行数选择对应代码标注。

## 7.3 概念密集

-   每页不超过 3-4 个核心概念。
-   核心概念标注 `[KEY]`。
-   复杂概念补充类比或例子。
-   必要时拆分为多页（见第 3.4 节）。

## 7.4 数据丰富

-   所有关键数据标注 `[DATA]`。
-   核心指标标注 `[EMPHASIS:number]`。
-   根据数据特点选择图表类型（见第 5.4 节）。

# 8 禁止事项

## 8.1 格式禁止

-   单页不应超过 400 字。
-   不应出现超过 3 行的连续段落文字。
-   单句不应超过 40 字。
-   代码块不应超过 50 行。
-   不应使用 Markdown 表格作为 PPT 内容（应标注 `[CHART:table]`）。
-   标题不应超过 4 级。
-   单页要点不应超过 8 条。
-   列表嵌套不应超过 2 层。

## 8.2 内容禁止

-   不应忽略或跳过原文档中的任何章节或要点。
-   不应因字数限制删除原文档的关键信息；内容过多时应分页展示。
-   不应将多个不同主题的内容合并到一页。
-   不应使用模糊表述（"可能""大概""一些"）。
-   不应出现重复内容（标题与要点重复、页面之间重复）。

## 8.3 标注禁止

-   不应滥用标注（不应每条都标 `[KEY]`）。
-   不应标注不准确（普通内容不应标 `[DATA]`）。
-   关键数据不应缺少标注。

# 9 质量检查规则

## 9.1 单页检查

+   每页提交前，逐项核对以下清单。

-   □ 标题清晰且 ≤20 字
-   □ 要点数量 4-6 条（最少 3 条，最多 8 条）
-   □ 每条要点 20-40 字，表达完整
-   □ 总字数 300-400 字（不含代码）
-   □ 添加了适当的标注（KEY/DATA/CHART 等）
-   □ 代码块 ≤50 行且有充分注释
-   □ 无 Markdown 表格
-   □ 无连续段落文字（>3 行）
-   □ 无过长单句（>40 字）
-   □ 视觉元素标注明确
-   □ 列表嵌套 ≤2 层
-   □ 已识别内容逻辑结构并添加布局标注

## 9.2 全文检查

+   结构层面：

-   □ 有且仅有 1 个文档标题（`#`）
-   □ 每章内容页 ≥3 页
-   □ 标题层级不超过 4 级
-   □ 逻辑连贯，章节过渡自然
-   □ 同级标题字数相近、格式统一

+   内容层面：

-   □ 每页都有明确的核心观点
-   □ 重点内容有 `[KEY]` 标注（每章至少 2-3 处）
-   □ 数据信息有 `[DATA]` 标注（有数据的地方必标）
-   □ 至少 60% 的页面有视觉元素建议
-   □ 代码示例有实际价值且注释充分
-   □ 无重复内容（标题与正文、页面之间重复）
-   □ 专业术语有适当解释或上下文
-   □ 超容量页面已按第 3.4 节分页处理

+   视觉层面：

-   □ 页面密度均衡（避免某些页过密或过疏）
-   □ 图表类型选择合理（符合数据特征）
-   □ 布局标注使用得当（双栏、居中、网格等）
-   □ 关键数据使用 `[EMPHASIS:number]`
-   □ 对比内容使用 `[VS]` 或 `[CHART:compare]`
-   □ 流程性内容使用 `[CHART:flow]`
-   □ 每 2-3 页至少有 1 个视觉化标注
-   □ 章节页使用了 `[SECTION:*]` 标注

## 9.3 专项检查

+   代码质量检查：

-   □ 代码逻辑正确或合理
-   □ 有充分的注释说明（关键行、逻辑块、参数）
-   □ 格式规范（缩进、命名、空行）
-   □ 示例简洁且有代表性
-   □ 标注了 `[CODE:single/double]` 或其他代码标注
-   □ 单行长度 ≤80 字符
-   □ 总行数 ≤50 行

+   数据准确性检查：

-   □ 数据有来源说明或合理性
-   □ 百分比总和为 100%（如适用）
-   □ 趋势描述与数据一致
-   □ 对比数据有明确基准
-   □ 数字单位统一且明确
-   □ 关键数据都有 `[DATA]` 标注

+   标注完整性检查：

-   □ 核心概念标注 `[KEY]`（每章 2-4 个）
-   □ 所有数字标注 `[DATA]`
-   □ 建议了合适的图表类型
-   □ 复杂流程标注 `[CHART:flow]`
-   □ 对比内容标注 `[VS]` 或 `[CHART:compare]`
-   □ 大号展示的数据标注 `[EMPHASIS:number]`
-   □ 代码标注 `[CODE]` 系列
-   □ 布局需求标注 `[LAYOUT]` 系列

# 附录A（资料性）内容转换示例

+   本附录给出常见场景的"转换前→转换后"对照，供实现时参照。

## A.1 段落文字转换

+   原文（约 300 字连续段落）：

    ```text
    数字安全治理是企业安全管理的核心环节，它通过建立完善的组织架构、
    明确的职责分工和规范的流程制度，确保信息安全策略能够有效落地。
    治理层需要从战略高度制定安全目标和投资方向，平衡安全投入与业务
    发展的关系。同时，治理层需要定期评估安全风险，监督技术措施的
    实施效果，并根据业务发展及时调整安全策略。有效的安全治理不仅能
    降低安全风险，还能提升整体安全运营效率，为企业的数字化转型提供
    坚实保障。根据行业实践，安全治理应遵循"战略先行、体系保障、
    持续改进"的原则，建立起适应企业规模和业务特点的治理框架。
    ```

+   转换后（PPT 格式，约 350 字，增加结构和标注）：

    ```markdown
    ### 数字安全治理的核心价值

    - **战略定位**：企业安全管理的顶层设计，从战略高度统筹安全工作 [KEY]
    - **核心机制**：组织、职责、流程三大支柱确保安全策略有效落地
    - **治理职能**：制定安全目标、评估风险、监督执行、动态调整
    - **双重价值**：既降低安全风险，又提升安全运营效率 [KEY]
    - **实践原则**：战略先行、体系保障、持续改进 [KEY]
    - **最终目标**：为企业数字化转型提供坚实安全保障

    [CHART:flow]
    ```

+   转换要点：段落拆解为 6 个结构化要点，每条 ≤40 字；核心观点加 `[KEY]` 标注；添加 `[CHART:flow]` 可视化建议。

## A.2 长列表转换

+   原文（10 项逗号分隔）：

    ```text
    安全治理包括：组织架构设计、角色职责定义、决策流程建立、
    风险评估机制、合规性检查、预算管理、人员培训、
    绩效考核、事件响应、持续改进等10个方面。
    ```

+   转换后（按逻辑维度分页，首页总览 + 后续分页展示）：

    ```markdown
    ### 安全治理体系十大要素

    **组织与流程维度**
    - **组织架构设计**：安全委员会、执行团队和协同机制 [KEY]
    - **角色职责定义**：RACI矩阵明确各方职责
    - **决策流程建立**：分级授权，平衡效率与风险
    - **事件响应机制**：预警、处置、恢复、复盘闭环

    **管理与能力维度**
    - **风险评估机制**：定期识别、评估、处置安全风险
    - **合规性检查**：对标法规和行业标准
    - **预算管理**：安全投入通常为IT预算的5-8% [DATA]
    - **人员培训**：分层分类开展培训，年均≥40小时

    [CHART:table]
    [LAYOUT:grid]
    ```

+   转换要点：10 项按维度分组各 4 条，控制在 8 条以内；每条精简至 ≤40 字；添加 `[LAYOUT:grid]` 布局建议。

## A.3 复杂句转换

+   一句话拆成多个要点的示例如下表所示。

## A.7 [CODE:double] 代码示例

+   双栏代码（16-30 行）使用 `[CODE:double]` + `[LAYOUT:left-right]` 标注，左右栏各放一段逻辑相关的代码。

+   Markdown 输入：

    ```markdown
        ### 权限控制实现

        ```python
        # 左栏：权限模型定义
        class Permission:
            """权限类：定义资源和操作"""
            def __init__(self, resource, action):
                self.resource = resource  # 资源标识
                self.action = action      # 操作类型

            def match(self, request):
                """匹配请求是否符合权限"""
                return (request.resource == self.resource and
                        request.action == self.action)

        class Role:
            """角色类：权限集合"""
            def __init__(self, name, permissions):
                self.name = name
                self.permissions = permissions

            def has_permission(self, perm):
                return perm in self.permissions

        # 右栏：权限验证器
        class SecurityManager:
            def __init__(self):
                self.roles = {}
                self.user_roles = {}

            def authorize(self, user, permission):
                roles = self._get_user_roles(user)
                return any(r.has_permission(permission) for r in roles)
        ```

        [LAYOUT:left-right]
    ```
