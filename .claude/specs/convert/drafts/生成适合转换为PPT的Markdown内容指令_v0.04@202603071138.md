# 1 总则

+   **文档编号**：TW-FMT-PPT-01
+   **文档名称**：Markdown 转 PPT 内容格式规范
+   **文档密级**：【内部资料】 -- 不主动对外公开。
+   **适用对象**：AI 文档转换助手
+   **管理要点**：本规范定义将 Markdown 文档转换为 PPT 内容稿时的格式约束，包括标题层级映射、页面容量、标注系统、内容转换、代码处理等规则。

## 1.1 执行原则

-   **保持逻辑结构**：不改变原文档的章节顺序和核心观点。
-   **保持内容完整性**：不忽略、跳过或删减原文档的内容和要点；单页内容过多时分页展示。
-   **控制页面容量**：每页内容适合一个 PPT 页展示。
-   **优化表达方式**：段落文字转换为结构化要点，精简冗余表述。
-   **提供可视化建议**：以标注形式提供 PPT 可视化建议。

# 2 标题层级规则

## 2.1 层级映射

+   PPT 内容稿的标题层级与 PPT 页面的对应关系如下表所示。

    | 层级     | 语法   | PPT 用途   | 数量 | 说明                                  |
    | -------- | ------ | ---------- | ---- | ------------------------------------- |
    | 文档标题 | `#`    | 封面页     | 1 个 | 包含标题、副标题、日期                |
    | 章节标题 | `##`   | 章节分隔页 | 不限 | 大章节的起始页，仅标题                |
    | 主页面   | `###`  | 标准内容页 | 不限 | 每个 `###` 独立成页                   |
    | 子页面   | `####` | 主题细分   | 可选 | 从属于 `###`，标题显示为"主题/子主题" |

## 2.2 约束

-   最多使用 4 级标题（`#` 至 `####`），不应使用 `#####` 及以下。
-   子页面（`####`）标题显示格式为"父主题/子主题"。

# 3 页面容量规则

## 3.1 容量标准

+   每个 PPT 页面的内容元素应符合以下限制。

    | 元素       | 限制       | 说明                                |
    | ---------- | ---------- | ----------------------------------- |
    | 页面标题   | ≤20 字     | 清晰、可独立理解                    |
    | 要点数量   | 4-6 条     | 最少 3 条，最多 8 条                |
    | 单条要点   | 20-60 字   | 完整表达，保留必要上下文            |
    | 页面总字数 | 350-550 字 | 不含代码和标注；目标填充率≥70%      |
    | 代码行数   | ≤50 行     | 单块代码的限制                      |
    | 列表嵌套   | ≤2 层      | 主要点→次要点；避免三层嵌套影响可读 |

## 3.2 字数计算

+   页面字数 = 标题字数 + 所有要点字数 + 补充说明字数。
+   不计入：代码块、标注标签、分隔符。

## 3.3 内容密度参考

-   **标准密度页**（400-550 字）：框架介绍、方法论说明、实施步骤
-   **中密度页**（300-400 字）：要点列举、对比分析、案例说明
-   **低密度页**（250-300 字）：数据展示为主、简单流程、关键结论
-   **极简页**（<250 字）：章节封面、引用金句、单一图表

## 3.4 分页规则

+   当原文内容超出单页容量时，应按以下规则分页展示，不应删减内容。

-   **分页触发条件**：要点数 >8 条，或总字数 >550 字，或单条要点 >60 字且要点数 >5 条。
-   **分页策略**：优先按逻辑维度拆分（概述页 + 详情页，或按维度分组各占一页）；无法按逻辑拆分时，按内容顺序均匀分配。
-   **分页标题**：使用"主题（续）"或按逻辑维度命名（如"主题：组织维度""主题：技术维度"）。
-   **分页关联**：首页末尾可添加"详见下页"提示，帮助读者理解内容连续性。

## 3.5 单条要点精炼规则

+   单条要点超过 60 字时，应按以下优先级精简。

-   **优先级 1：去冗余**：删除"进行""实现""通过...方式"等虚词和冗余结构。
-   **优先级 2：拆分**：一条含多个信息点的要点拆为 2-3 条独立要点。
-   **优先级 3：提炼**：长描述改为"关键词 + 短说明"格式（如"**核心原则**：零信任架构，持续验证每次访问"）。

+   **注意**：不应过度精简。要点应保留足够的上下文和解释，使读者无需参阅原文即可理解。每页视觉填充率（内容实际占用面积 / 可用面积）应 ≥70%。

# 4 标注系统

## 4.1 核心内容标注

+   用于标记页面中的重点信息类型。

    | 标注      | 用途         | 适用场景               |
    | --------- | ------------ | ---------------------- |
    | `[KEY]`   | 核心信息强调 | 关键结论、重要概念     |
    | `[DATA]`  | 数据突出     | 统计数据、百分比、指标 |
    | `[QUOTE]` | 引用         | 权威观点、文献引用     |
    | `[CASE]`  | 实际案例     | 真实案例、应用场景     |
    | `[VS]`    | 对比说明     | 前后对比、优劣对比     |

## 4.2 视觉元素标注

+   用于建议 PPT 中应使用的图表或图片类型。

    | 标注                 | 用途     | 适用场景           |
    | -------------------- | -------- | ------------------ |
    | `[CHART:bar]`        | 柱状图   | 对比数据、排名     |
    | `[CHART:line]`       | 折线图   | 趋势变化、时间序列 |
    | `[CHART:pie]`        | 饼图     | 占比分布、构成     |
    | `[CHART:flow]`       | 流程图   | 步骤、流程、关系   |
    | `[CHART:compare]`    | 对比图   | 方案对比、优缺点   |
    | `[CHART:table]`      | 表格     | 规范数据、矩阵     |
    | `[CHART:timeline]`   | 时间线   | 发展历程、路线图   |
    | `[IMAGE:photo]`      | 实景图片 | 现场照片、产品图   |
    | `[IMAGE:diagram]`    | 示意图   | 架构图、模型图     |
    | `[IMAGE:screenshot]` | 截图     | 界面、操作示例     |
    | `[ICON:类型]`        | 图标建议 | shield/chart/user  |

## 4.3 布局标注

+   用于建议 PPT 页面的排版布局方式。

    | 标注                  | 用途     | 效果                   |
    | --------------------- | -------- | ---------------------- |
    | `[LAYOUT:left-right]` | 左右分栏 | 对比内容、代码与说明   |
    | `[LAYOUT:top-bottom]` | 上下布局 | 原理与应用、问题与方案 |
    | `[LAYOUT:center]`     | 居中突出 | 核心数据、关键结论     |
    | `[LAYOUT:grid]`       | 网格布局 | 多模块并列、分类展示   |
    | `[EMPHASIS:number]`   | 大号数字 | 关键指标、统计结果     |
    | `[PROGRESS:比例]`     | 进度展示 | 完成度、达成率         |

## 4.4 代码标注

+   用于指定代码块在 PPT 中的展示方式。

    | 标注             | 用途       | 说明               |
    | ---------------- | ---------- | ------------------ |
    | `[CODE:single]`  | 单栏代码   | ≤15 行，完整展示   |
    | `[CODE:double]`  | 双栏代码   | 16-30 行，左右分栏 |
    | `[CODE:compare]` | 代码对比   | Before/After 对比  |
    | `[CMD]`          | 命令行示例 | Shell 命令         |
    | `[CONFIG]`       | 配置文件   | YAML/JSON/XML 配置 |
    | `[PSEUDO]`       | 伪代码     | 逻辑说明、算法描述 |

## 4.5 逻辑结构标注

+   用于标记页面内容的语义关系结构，驱动内容组织和布局选择。这是内容稿最重要的标注——决定页面是"有结构的信息"还是"扁平的列表"。

+   **单层标注**：`[LOGIC:type]`，标记整页的主结构。

+   **多层标注**：`[LOGIC:L1→L2]` 或 `[LOGIC:L1→L2→L3]`，标记嵌套结构。箭头左侧为外层关系，右侧为内层关系。最多 3 层，超出应拆页。

    | 类型标识         | 中文   | 语义                               | 典型场景                           |
    | ---------------- | ------ | ---------------------------------- | ---------------------------------- |
    | `cause-effect`   | 因果   | 原因→结果，问题→影响               | 问题诊断、风险分析、政策影响       |
    | `compare`        | 对比   | A vs B，优劣、前后、现状vs目标     | 方案比选、改进前后、差距分析       |
    | `progressive`    | 递进   | 阶段→阶段→阶段，逐步深入           | 实施路线图、成熟度演进、流程步骤   |
    | `classify`       | 分类   | 按维度/类型分组，并列平等           | 职责分工、多模块介绍、分级分类     |
    | `hierarchy`      | 层级   | 核心→支撑，上位→下位               | 战略→战术、原则→措施、总纲→细则   |
    | `total-parts`    | 总分   | 总述→分项展开                       | 执行摘要+详情、框架概述+要素说明   |
    | `condition`      | 条件   | 条件→响应，触发→动作               | 应急预案、决策树、分支策略         |
    | `evolution`      | 演进   | 起点→变化→终点，含时间维度         | 五年规划、技术演进、能力成熟度     |
    | `matrix`         | 矩阵   | 两个维度交叉分析                   | 风险矩阵、RACI、优先级四象限       |
    | `parallel`       | 并列   | 等权重条目，无内在关系             | 清单、检查项（仅在确实无关系时用） |

+   **多层组合示例**：

-   `[LOGIC:cause-effect→classify]`：上区展示因→果流程，下区将"果"按类型分组展示
-   `[LOGIC:classify→compare]`：左右两栏各展示一个分类，栏内对比各要素
-   `[LOGIC:hierarchy→progressive]`：上区核心原则卡片，下区展示递进实施步骤
-   `[LOGIC:total-parts→classify]`：上区总述高亮摘要，下区按维度分组展示各部分
-   `[LOGIC:condition→cause-effect]`：上区条件/触发场景，下区每个触发的因果链

+   **`parallel`（并列）的使用约束**：`parallel` 仅在内容要素之间确实没有内在关系时使用。转换过程中应首先尝试识别更具体的关系类型；只有确认无法归入其他类型时，方可标注 `parallel`。标注 `parallel` 时应同时考虑使用网格或卡片布局，避免退化为纯列表。

## 4.6 章节页标注

+   用于丰富章节分隔页（`##`）的内容元素，避免章节页过于空白。

    | 标注                    | 用途       | 效果                           |
    | ----------------------- | ---------- | ------------------------------ |
    | `[SECTION:keywords]`    | 关键词预览 | 在章节标题下方展示 3-5 个关键词 |
    | `[SECTION:progress]`    | 进度指示   | 展示"第 N 章 / 共 M 章"       |
    | `[SECTION:outline]`     | 章节目录   | 列出本章包含的 3-4 个子主题    |

# 5 内容转换规则

## 5.1 段落文字

+   将连续段落拆解为 4-6 个结构化要点。
+   每条要点 20-60 字，使用加粗关键词引导，保留必要的上下文说明。
+   为核心概念添加 `[KEY]`、数据添加 `[DATA]` 标注。
+   避免过度精简：要点应包含"是什么 + 为什么/怎么做"两层信息，而非仅有名词短语。

## 5.2 长列表

+   按逻辑维度分组（如"组织与流程维度""管理与监督维度"），每组 3-4 条。
+   每条要点补充具体说明，不应仅列名称。
+   超过 8 条时应分页展示（见第 3.4 节）。

## 5.3 复杂句

+   一句话拆成多个要点，每个要点聚焦一个信息单元。

## 5.4 数据处理

+   数据可视化决策规则如下：

-   单个关键数字 → `[DATA]` + `[EMPHASIS:number]`
-   时间序列数据 → `[CHART:line]`
-   分类对比数据 → `[CHART:bar]`
-   占比构成数据 → `[CHART:pie]`
-   多维度数据 → `[CHART:table]`
-   流程步骤 → `[CHART:flow]`

## 5.5 逻辑结构识别与内容组织

+   **逻辑结构识别是内容转换的第一步**，应在拆解要点之前完成。转换流程为：①识别原文逻辑关系 → ②标注 `[LOGIC:*]` → ③按结构组织内容 → ④选择对应布局标注。

+   **禁止先列要点再找结构**：不应将所有内容拍平为并列要点后再标注布局。应先识别内容的语义关系，再按关系结构组织要点的层次和分组。

### 5.5.1 单层结构识别与内容组织

+   每种逻辑类型对应特定的内容组织方式和布局标注。

-   **因果**（`cause-effect`）→ 内容分为"原因/问题"和"结果/影响"两个区块，使用加粗标题分隔 → `[LAYOUT:top-bottom]` 或 `[CHART:flow]`
-   **对比**（`compare`）→ 内容分为 A、B 两组，每组独立成段 → `[LAYOUT:left-right]` + `[CHART:compare]`
-   **递进**（`progressive`）→ 内容按阶段/步骤排列，标注顺序 → `[CHART:flow]` 或 `[CHART:timeline]`
-   **分类**（`classify`）→ 内容按维度分组，每组有标题 → `[LAYOUT:grid]` 或分组列表
-   **层级**（`hierarchy`）→ 核心要点独立突出，支撑要点在其下方 → `[LAYOUT:top-bottom]`，上区 `[KEY]` 卡片
-   **总分**（`total-parts`）→ 总述独立成高亮行，分项在下方 → 首行 `[KEY]` 高亮 + 分项列表
-   **条件**（`condition`）→ 内容分为"触发条件"和"响应措施"，配对展示 → `[LAYOUT:top-bottom]` 或 `[CHART:flow]`
-   **演进**（`evolution`）→ 内容按时间维度排列，强调变化方向 → `[CHART:timeline]`
-   **矩阵**（`matrix`）→ 内容按两个维度交叉组织 → `[CHART:table]` 或 `[LAYOUT:grid]`
-   **并列**（`parallel`）→ 仅在确认无内在关系时使用 → `[LAYOUT:grid]`（卡片）或列表

### 5.5.2 多层结构识别

+   现实内容通常包含嵌套关系。一个页面最多支持 3 层结构，超出应拆分为多页。

+   **识别方法**：先识别页面整体的 L1 关系，再检查 L1 的每个区块内部是否存在 L2 关系，依此类推。

+   **标注格式**：`[LOGIC:L1→L2]` 或 `[LOGIC:L1→L2→L3]`

+   **内容组织方法**：

-   **L1 决定页面整体结构**：按 L1 类型将内容分为 2-4 个主区块，区块之间用加粗标题或分隔线分隔
-   **L2 决定区块内部结构**：每个 L1 区块内部，按 L2 类型组织子要点（分组、排序、配对等）
-   **L3 决定要点内部格式**：要点内部的信息组织方式（加粗、标注、对比短语等）

+   **多层示例**（原文含因果+分类关系）：

+   原文概述："底线思维导致三个后果：合规水平低、能力闲置、评级难提升"

+   错误转换（全部拍平为并列）：

    ```text
    - 底线思维过重
    - 合规水平接近监管最低要求
    - 安全设备能力闲置
    - 评级难以跨档提升
    ```

+   正确转换（识别因果→分类结构）：

    ```text
    [LOGIC:cause-effect→classify]

    **根因：底线思维过重**
    - 各项工作以满足监管最低要求为隐性目标，合规水平普遍接近底线

    **后果一（合规层面）**：等保/密评重在通过而非整改落地
    **后果二（能力层面）**：安全设备超出默认配置的能力被忽略，"已购未用"
    **后果三（评级层面）**：各维度"执行多在边缘"，难以实现跨档提升

    [LAYOUT:top-bottom]
    ```

### 5.5.3 拆页规则

-   **结构层数上限**：单页最多 3 层嵌套。若识别出 4 层以上关系，应将 L3/L4 内容拆分为独立子页面（`####`）。
-   **区块数量上限**：L1 层最多 4 个区块。若 L1 分出 5 个以上区块，应拆为多页或合并相近区块。
-   **内容量触发**：任一 L1 区块内要点超过 4 条时，考虑将该区块独立为子页面。

## 5.6 视觉多样性规则

+   PPT 的核心价值在于视觉传达，纯文字列表页面应作为"最后选择"而非"默认选择"。

-   **连续列表上限**：连续超过 2 页使用纯列表布局时，第 3 页起必须切换为其他布局形式（卡片网格、上下分区、两栏对比、流程图、时间线等）。
-   **每章布局多样性**：每章（`##` 之间）至少有 1 页使用非列表布局。
-   **短列表强制升级**：当要点 ≤4 条且总字数 <300 字时，不应使用纯列表，应切换为以下任一形式：
    -   `[LAYOUT:grid]`：每条要点转为独立卡片，占满页面空间
    -   highlight-row 格式：每条要点使用高亮背景条，增加视觉重量
    -   `[LAYOUT:top-bottom]`：首条要点作为核心摘要卡片，其余列表在下方
-   **上下分区优先**：内容页应积极使用上下分区布局——上区放核心摘要（`[KEY]` 卡片）、关键数据（`[DATA]` 网格）或流程图，下区放详细列表。此布局在保持信息完整的同时显著提升视觉层次感。
-   **数据页强制可视化**：当页面包含 ≥3 个 `[DATA]` 标注时，必须使用 `[EMPHASIS:number]` + 数据卡片网格布局，不应仅用列表展示数据。
-   **每页布局标注**：每个内容页（`###`）必须至少包含 1 个布局标注（`[LAYOUT:*]`、`[CHART:*]`、`[EMPHASIS:*]` 中任一），不允许无标注的纯列表页。

## 5.7 内容充实规则

+   PPT 内容稿应充分利用页面空间，避免大面积留白。

-   **信息完整性**：每条要点应包含"关键词 + 说明"两部分，说明部分应提供足够的上下文（原因、影响、方法、范围等），而非仅有一个名词短语。
-   **补充说明**：当原文提供了背景、原因、影响等上下文信息时，应保留在要点中，不应因追求精简而丢弃。
-   **示例丰富化**：对于抽象概念，应补充具体示例、数据佐证或类比说明，使页面内容更充实。
-   **反模式**：以下模式说明页面内容不足，应补充完善：
    -   4 条要点每条仅 20 字（总计 80 字）→ 页面仅填充 25%
    -   全部要点为"**名词**：短语"格式，缺乏说明 → 信息密度不足
    -   页面无任何视觉元素标注 → 视觉单调

# 6 代码块处理

## 6.1 基本要求

-   总行数 ≤50 行，单行长度 ≤80 字符。
-   应指定语言标签（`python`、`yaml`、`bash` 等）。
-   应添加注释说明核心逻辑。

## 6.2 代码标注选择

-   ≤15 行 → `[CODE:single]`
-   16-30 行 → `[CODE:double]`（左右分栏）
-   对比展示 → `[CODE:compare]`（Before/After）
-   配置文件 → `[CONFIG]`
-   命令行 → `[CMD]`

# 7 特殊场景处理

## 7.1 大量表格

-   简单表格（2-3 列）→ 转换为要点列举。
-   复杂表格（4 列以上）→ 标注 `[CHART:table]`。
-   对比表格 → 标注 `[CHART:compare]`。

## 7.2 大量代码

-   每个代码块 ≤50 行。
-   保留核心逻辑代码，移除辅助性代码。
-   根据行数选择对应代码标注。

## 7.3 概念密集

-   每页不超过 3-4 个核心概念。
-   核心概念标注 `[KEY]`。
-   复杂概念补充类比或例子。
-   必要时拆分为多页（见第 3.4 节）。

## 7.4 数据丰富

-   所有关键数据标注 `[DATA]`。
-   核心指标标注 `[EMPHASIS:number]`。
-   根据数据特点选择图表类型（见第 5.4 节）。

# 8 禁止事项

## 8.1 格式禁止

-   单页不应超过 550 字。
-   不应出现超过 3 行的连续段落文字。
-   单句不应超过 60 字。
-   代码块不应超过 50 行。
-   不应使用 Markdown 表格作为 PPT 内容（应标注 `[CHART:table]`）。
-   标题不应超过 4 级。
-   单页要点不应超过 8 条。
-   列表嵌套不应超过 2 层。

## 8.2 内容禁止

-   不应忽略或跳过原文档中的任何章节或要点。
-   不应因字数限制删除原文档的关键信息；内容过多时应分页展示。
-   不应将多个不同主题的内容合并到一页。
-   不应使用模糊表述（"可能""大概""一些"）。
-   不应出现重复内容（标题与要点重复、页面之间重复）。

## 8.3 标注禁止

-   不应滥用标注（不应每条都标 `[KEY]`）。
-   不应标注不准确（普通内容不应标 `[DATA]`）。
-   关键数据不应缺少标注。

# 9 质量检查规则

## 9.1 单页检查

+   每页提交前，逐项核对以下清单。

-   □ 标题清晰且 ≤20 字
-   □ 要点数量 4-6 条（最少 3 条，最多 8 条）
-   □ 每条要点 20-60 字，包含关键词+说明两部分
-   □ 总字数 350-550 字（不含代码），页面填充率≥70%
-   □ 添加了适当的标注（KEY/DATA/CHART 等）
-   □ 代码块 ≤50 行且有充分注释
-   □ 无 Markdown 表格
-   □ 无连续段落文字（>3 行）
-   □ 无过长单句（>60 字）
-   □ 视觉元素标注明确（每页至少1个布局/图表标注）
-   □ 列表嵌套 ≤2 层
-   □ 已识别 `[LOGIC:*]` 结构并按结构组织内容（非扁平列表）
-   □ 多层结构不超过 3 层，超出已拆页

## 9.2 全文检查

+   结构层面：

-   □ 有且仅有 1 个文档标题（`#`）
-   □ 每章内容页 ≥3 页
-   □ 标题层级不超过 4 级
-   □ 逻辑连贯，章节过渡自然
-   □ 同级标题字数相近、格式统一

+   内容层面：

-   □ 每页都有明确的核心观点
-   □ 重点内容有 `[KEY]` 标注（每章至少 2-3 处）
-   □ 数据信息有 `[DATA]` 标注（有数据的地方必标）
-   □ 至少 60% 的页面有视觉元素建议
-   □ 代码示例有实际价值且注释充分
-   □ 无重复内容（标题与正文、页面之间重复）
-   □ 专业术语有适当解释或上下文
-   □ 超容量页面已按第 3.4 节分页处理

+   视觉层面：

-   □ 页面密度均衡（避免某些页过密或过疏），每页填充率≥70%
-   □ 连续纯列表页面不超过 2 页（第 3 页起必须切换布局）
-   □ 每章至少 1 页使用非列表布局（卡片/网格/流程图/时间线/两栏等）
-   □ 图表类型选择合理（符合数据特征）
-   □ 布局标注使用得当（双栏、居中、网格等）
-   □ 关键数据使用 `[EMPHASIS:number]`
-   □ 每页均已标注 `[LOGIC:*]`（`parallel` 需确认无法归入其他类型）
-   □ 对比内容使用 `[VS]` 或 `[CHART:compare]`
-   □ 流程性内容使用 `[CHART:flow]`
-   □ 因果内容使用 `[LOGIC:cause-effect]` + `[LAYOUT:top-bottom]`
-   □ 多层结构标注正确（`[LOGIC:L1→L2]` 格式）
-   □ 每 2-3 页至少有 1 个视觉化标注
-   □ 章节页使用了 `[SECTION:*]` 标注

## 9.3 专项检查

+   代码质量检查：

-   □ 代码逻辑正确或合理
-   □ 有充分的注释说明（关键行、逻辑块、参数）
-   □ 格式规范（缩进、命名、空行）
-   □ 示例简洁且有代表性
-   □ 标注了 `[CODE:single/double]` 或其他代码标注
-   □ 单行长度 ≤80 字符
-   □ 总行数 ≤50 行

+   数据准确性检查：

-   □ 数据有来源说明或合理性
-   □ 百分比总和为 100%（如适用）
-   □ 趋势描述与数据一致
-   □ 对比数据有明确基准
-   □ 数字单位统一且明确
-   □ 关键数据都有 `[DATA]` 标注

+   标注完整性检查：

-   □ 核心概念标注 `[KEY]`（每章 2-4 个）
-   □ 所有数字标注 `[DATA]`

-   □ 代码标注 `[CODE]` 系列

## A.7 [CODE:double] 代码示例

+   双栏代码（16-30 行）使用 `[CODE:double]` + `[LAYOUT:left-right]` 标注，左右栏各放一段逻辑相关的代码。

+   Markdown 输入：

        ```python
        # 左栏：权限模型定义
        class Permission:
            """权限类：定义资源和操作"""
            def __init__(self, resource, action):
                self.resource = resource  # 资源标识
                self.action = action      # 操作类型

            def match(self, request):
                """匹配请求是否符合权限"""
                return (request.resource == self.resource and
                        request.action == self.action)

        class Role:
            """角色类：权限集合"""
            def __init__(self, name, permissions):
                self.name = name
                self.permissions = permissions

            def has_permission(self, perm):
                return perm in self.permissions

        # 右栏：权限验证器
        class SecurityManager:
            def __init__(self):
                self.roles = {}
                self.user_roles = {}

            def authorize(self, user, permission):
                roles = self._get_user_roles(user)
                return any(r.has_permission(permission) for r in roles)
        ```
