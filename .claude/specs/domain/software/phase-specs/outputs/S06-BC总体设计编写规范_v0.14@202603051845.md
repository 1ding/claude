# 2 BC总体设计综述

## 2.1 整体定位

+   BC总体设计文档是阶段6"BC总体设计"的核心输出物，每个BC对应一份。本文档承接阶段5"BC详细需求"的 Feature / User Story 清单及阶段4"系统设计"的 Enabler Feature 架构约束，为阶段7"BC详细设计"提供子领域划分方案、公共架构决策和跨子领域约束。

+   本文档采用"1+N"文档体系定位——BC总体设计是"骨架"，解决"本BC是什么、做什么、内部怎么分、和外部怎么协作、技术上怎么建"五个核心问题。子领域详细设计是"血肉"，在总体设计骨架下展开各子领域的领域模型、接口契约和数据模型。

+   所有BC均需产出总体设计文档。大BC（含子领域划分）与小BC（无子领域划分）在子领域划分章节的详略程度上有差异，但文档结构一致。

## 3.1 第1章 总则

### 3.1.1 章节综述

### 3.1.2 表达规范

+   **强制元数据清单**（按以下顺序逐行列出）：

## 3.2 第2章 上下文概述

### 3.2.1 章节综述

+   本章采用三段式结构，以"背景→过程→结果"完整呈现阶段6的需求承接：
    +   **2.1 前置背景**：声明上游基线、版本范围和约束假设，回答"在什么条件下开展本次 BC 总体设计"。
    +   **2.2 上下文定义**：确认BC身份、阐明价值定位与职责边界、声明前置约束，回答"本BC是什么、边界在哪、有哪些约束"——是 2.1 到 2.3 的分析过程基础。
    +   **2.3 需求落位**：基于 2.2 的 BC 边界分析，建立 Feature 到设计功能项的承接基线，是阶段6需求演化的权威记录。
+   需求落位在文档结构上位于第2章，但在编写顺序上应在**第3章（业务职责与功能清单）完成后回填**功能清单项编号；编写时先预留表格框架并填入 Feature 清单，功能清单项列待第3章完成后补充。
+   需求落位替代原有"功能清单应与Feature清单一一对应"规则——允许废弃（需留痕说明原因）和新增（需标注来源）。
+   BC归属信息应与阶段3领域设计文档和阶段4系统设计文档保持一致，如需调整应先走变更流程。
+   本章产出向后传递：BC归属信息和边界定义是后续所有章节的基础；前置约束是所有子领域详细设计必须遵循的BC级约束；完整术语表见附录A。

#### 3.4.3.3 子领域职责说明

+   每个子领域输出一个独立段落，包含以下五项：
    -   **核心职责**：该子领域的职责边界描述（一句话）
    -   **核心实体**：该子领域的核心领域对象（含英文类名和关键字段），以列表形式枚举，每项格式：`实体名（EnglishName）：字段1、字段2...`
    -   **核心能力**：归属到该子领域的功能清单（对应第3章功能编号），按版本阶段分组（如 P1 / P2+）
    -   **数据存储方案**：该子领域使用的存储技术及各技术的具体职责（MySQL / Elasticsearch / Redis 等）；与 §7.1 数据隔离架构保持一致
    -   **对外接口**：该子领域对其他子领域或外部BC暴露/依赖的接口摘要（详细接口定义见第5章或子领域详细设计文档）

+   **粒度要求**：核心实体通常1~4个，过多说明子领域职责边界不清晰；数据存储方案在总体设计中只列技术和职责，不展开表结构（表结构在子领域详细设计中定义）。
+   **横切子领域的职责说明要点**（仅适用于横切子领域）：
    -   **核心职责**：应明确横切范围（"横切所有子领域"或"服务SD01~SD04等指定子领域"）
    -   **核心能力**：按"为被服务的各子领域提供X能力"的方式描述，避免与核心子领域的职责重叠
    -   **对外接口**：应明确调用模式——被动型（接收其他子领域的领域事件后写入）或主动型（提供查询接口供其他子领域主动调用）

    -   调用方式选择原因：为什么选择同步/异步

+   应至少覆盖以下五类标准场景：

    -   查询类依赖（只读）：允许同步调用，建议走缓存，必须设置超时和熔断
    -   命令类依赖（写操作）：优先使用领域事件异步通知；如需同步，必须实现Saga补偿
    -   跨BC数据一致性：禁止分布式事务（2PC）；必须采用最终一致性方案
    -   上游模型变更：下游必须通过ACL隔离；禁止直接依赖上游领域模型
    -   双向依赖：原则上禁止；如确需，必须双向ACL，并在架构评审中说明

#### 3.5.3.6 映射模式参考

+   每个映射模式选择应有明确的权衡理由。可选映射模式参考：

    | 映射模式          | 适用场景             | 约束要求                            |
    | ----------------- | -------------------- | ----------------------------------- |
    | OHS + ACL         | 推荐的标准集成方式   | 上游提供OHS，下游实现ACL            |
    | OHS + PL          | 对外提供标准化API    | 必须定义发布语言（如OpenAPI/Proto） |
    | ACL               | 隔离外部系统变化     | 下游必须实现模型转换层              |
    | Conformist        | 下游完全依赖上游模型 | 需评审确认，记录风险                |
    | Partnership       | 两个团队紧密协作     | 需明确协调机制和变更通知流程        |
    | Customer-Supplier | 上游为下游提供服务   | 需明确SLA和变更通知机制             |
    | Separate Ways     | 无集成需求           | 需评审确认，记录决策原因            |
    | Shared Kernel     | 多BC共享核心模型     | 需严格变更管理，不推荐大范围使用    |

    +   映射模式参考

# 5 附录编写规则

+   BC总体设计文档的附录遵循以下规则：
    -   附录编号使用大写字母：附录A、附录B...
    -   附录标题格式：`附录{字母}（{规范性/资料性}）{附录名称}`
    -   规范性附录排在资料性附录之前
    -   修订记录不编号为附录，固定位于文档末尾
    -   附录A（术语表）为必选项，其他附录按实际需要添加

+   常见附录类型参考：

    | 附录类型        | 建议标题     | 必选/可选 | 说明                                             |
    | --------------- | ------------ | --------- | ------------------------------------------------ |
    | 附录A（资料性） | 术语表       | 必选      | 三层术语体系收录，BC总体设计必选                 |
    | 附录B（资料性） | 参考文档     | 推荐      | 列出本文档依赖的上游文档和引用规范，便于追溯     |
    | 附录C（资料性） | Epic映射     | 推荐      | 子领域与Epic的对应关系表，便于需求追溯和进度跟踪 |
    | 附录D（资料性） | 版本规划     | 推荐      | BC各阶段版本的子领域范围和核心功能规划           |
    | 附录E（资料性） | 追溯矩阵     | 可选      | Feature与设计章节的对应关系，大BC推荐            |
    | 附录F（规范性） | 接口变更规范 | 可选      | 对外接口变更流程，涉及外部依赖时添加             |

    +   常见附录类型参考

+   **附录B 参考文档**格式：以列表形式列出，每项格式：`《文档名称》：一句话说明与本文档的关联`。

+   **附录C Epic映射**标准列定义：

    | 字段       | 说明                         |
    | ---------- | ---------------------------- |
    | Epic编号   | Epic的唯一标识               |
    | Epic名称   | Epic的中文名称               |
    | 对应子领域 | 负责该Epic的子领域编号列表   |
    | 核心能力   | 该Epic在本BC中的核心交付能力 |

    +   Epic映射表列定义

+   **附录D 版本规划**标准列定义：

    | 字段       | 说明                       |
    | ---------- | -------------------------- |
    | 版本       | 版本标识（如 P1、V1.0）    |
    | 子领域范围 | 本版本涉及的子领域编号列表 |
    | 核心功能   | 本版本核心交付功能概要     |
    | 里程碑     | 本版本的里程碑标识（可选） |

    +   版本规划表列定义

+   业界通用术语（AI已具备充分理解能力，仅列出名称）：
    -   BC（Bounded Context，限界上下文）
    -   DDD（Domain-Driven Design，领域驱动设计）
    -   ACL（Anti-Corruption Layer，防腐层）
