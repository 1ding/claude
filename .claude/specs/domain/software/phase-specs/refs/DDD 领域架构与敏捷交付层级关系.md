# DDD 领域架构与敏捷交付层级关系

> 本文以透管云（Clarisphere）平台为示例，阐述业务域、业务子域、BC、Theme、Epic、Feature、User Story 之间的完整对应关系。

---

## 1. 核心概念速览

| 概念               | 所属框架    | 所在空间     | 核心作用                      |
| ------------------ | ----------- | ------------ | ----------------------------- |
| 业务域 Domain      | DDD         | 问题空间     | 划定知识疆界                  |
| 业务子域 Subdomain | DDD         | 问题空间     | 职责细分                      |
| 限界上下文 BC      | DDD         | 解决方案空间 | 自治实现单元                  |
| BC子域 SD-xx       | DDD（扩展） | 解决方案空间 | BC 内部职责切割（复杂BC才有） |
| Theme 主题         | 敏捷/SAFe   | 交付空间     | 战略意图方向                  |
| Epic               | 敏捷/SAFe   | 交付空间     | 大粒度交付单元                |
| Feature            | 敏捷/SAFe   | 交付空间     | 单 PI 内可交付功能            |
| User Story         | 敏捷/SAFe   | 交付空间     | 用户可感知最小单元            |
| Task               | 敏捷/SAFe   | 交付空间     | 开发执行单元                  |

## 3. 层级栈详解

### 3.1 完整层级栈

```
业务域（Domain）
  └── 业务子域（Subdomain）
        └──► BC（限界上下文）          ← 问题空间映射解决方案空间的边界
               └── [BC子域 SD-xx]     ← 可选层，复杂BC才有
                     └── 聚合 / 领域服务 / 接口
```

```
Theme（主题）
  └── Epic
        └── [Capability]             ← 可选层，对应BC子域
              └── Feature
                    └── User Story
                          └── Task
```

### 3.2 BC 的两种形态

BC 是否有 BC子域，取决于其自身复杂度：

```
简单 BC                              复杂 BC
──────────────────────               ──────────────────────────────
Epic                                 Epic
  └── BC                               └── BC
        └── Feature                          ├── SD-xx ══► Capability
              └── Story                      │     └── Feature
                                             │           └── Story
                                             ├── SD-xx ══► Capability
                                             │     └── Feature
                                             └── SD-xx ══► Capability
                                                   └── Feature
```

透管云示例对照：

```
BC-12 消息通知（简单BC）             BC-35 租户落地（复杂BC）
  └── Epic                             └── Epic
        └── Feature: 站内消息                 ├── SD-01 资产管理 ══► Capability
        └── Feature: 邮件通知                 ├── SD-02 场景映射 ══► Capability
        └── Feature: 消息模板                 ├── SD-03 控制映射 ══► Capability
                                              ├── SD-04 制度管理 ══► Capability
                                              ├── SD-05 技术方案 ══► Capability
                                              └── SD-06 责任映射 ══► Capability
```

### 3.3 两栈对齐规则

```
业务域                ══════►  Theme        【战略层】跨 PI，无结束时间
  业务子域 = BC        ══════►  Epic         【战术层】跨 Sprint，1~2 个 PI
    BC子域 SD-xx      ══════►  Capability   【能力层】可选，复杂BC才有
      聚合/接口         ══════►  Feature      【功能层】单 PI 内交付
        领域服务         ══════►  User Story   【实现层】单 Sprint 内交付
          代码/配置      ══════►  Task         【执行层】1~2 天完成
```

### 4.2 业务域命名说明

> 业务域采用**架构语言**命名（供给侧域、消费侧A域等），反映系统的架构分层视角，与 Theme 保持一致的表达风格。纯业务视角下可替换为语义更强的名称（如合规治理域、知识管理域）。

## 7. 敏捷交付空间：Theme → Task 完整示例

### 7.1 Theme → 业务域对应

```
┌──────────────────────────────────────────────────────────────┐
│  业务域（问题空间）              Theme（敏捷交付空间）            │
├──────────────────────────────────────────────────────────────┤
│  供给侧域          ══════►  知识内容供给体系建设                  │
│  中台域            ══════►  知识中台能力建设                      │
│  消费侧A域         ══════►  合规治理能力建设                      │
│  消费侧B域         ══════►  知识消费体验提升                      │
│  通用域            ══════►  基础平台能力建设                      │
└──────────────────────────────────────────────────────────────┘

说明：Theme 是业务域在敏捷路线图上的战略表达，
      通常跨多个 PI，没有明确结束时间。
```

```
┌──────────────────────────────────────────────────────────────┐
│  Theme：合规治理能力建设                                         │
│                                                               │
│  BC（解决方案空间）            Epic（敏捷交付空间）               │
├──────────────────────────────────────────────────────────────┤
│  BC-31 合规管理    ══════►  Epic: 合规知识管理能力建设            │
│  BC-32 验证检查    ══════►  Epic: 合规验证检查能力建设            │
│  BC-33 治理监督    ══════►  Epic: 治理监督看板建设               │
│  BC-34 风险管理    ══════►  Epic: 风险识别与评估能力建设          │
│  BC-35 租户落地    ══════►  Epic: 租户合规落地能力建设            │

对比简单BC（无Capability层）：

┌──────────────────────────────────────────────────────────────┐
│  Epic：消息通知能力建设（BC-12）                                  │
│                                                               │
│  BC（无BC子域）                Feature                         │
├──────────────────────────────────────────────────────────────┤

```

## 9. 关键设计原则

### 9.1 边界对齐原则

> **Epic 的业务边界应尽量与 BC 边界对齐。**
> 一个设计良好的 Epic 主要落在单一 BC 内，跨 BC 的 Epic 是架构耦合的信号。

### 9.2 BC子域按需出现原则

> **BC子域（SD-xx）不是每个BC都必须有的。**
> BC复杂度超过阈值时，BC子域自然生长出来；简单BC直接 Epic → Feature，不必强行插入Capability层。
>
> 判断是否需要引入BC子域，应以**语义内聚性**为标准，而非功能数量：
>
> -   **聚合根边界**：一组实体围绕独立的聚合根运转，与其他实体群耦合度低，应独立为BC子域
> -   **业务逻辑自治**：一块业务逻辑有独立的生命周期、状态机或规则体系，应独立为BC子域
> -   **统一语言边界**：同一个词在BC内部出现歧义（需要加定语区分），说明BC子域边界已到
>
> 数量只是结果，不是原因——Feature多是表象，领域概念无法内聚才是引入BC子域的真正信号。

### 9.3 BC子域不跨 BC 原则

> **BC子域（SD-xx）不跨 BC。**
> 若某个 SD 需要跨 BC 协作，应升格为独立业务子域，对应自己的 BC。

### 9.4 Theme 与业务域的正交性

> **业务域是空间维度（稳定），Theme 是时间/战略维度（随业务重心调整）。**
> 两者正交，Epic 是两者的交叉落点。

### 9.5 命名一致性原则

> 同一概念在问题空间、解决方案空间、交付空间中的命名应保持语义一致，
> 避免同一业务能力在三个空间中出现三种不同叫法。
