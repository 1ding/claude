# 1 适用范围

+   文档编号：N00
+   文档名称：软件研发过程规范
+   适用对象：公司所有软件产品的研发项目
+   管辖范围：软件研发过程的阶段划分、各阶段的目标、关键活动、输入输出及交付物要求、过程管理要求（阶段门禁、变更管理、可追溯性、质量保障）
+   不管辖的范围：各类交付物的具体编写规范（见各交付物专用编写规范）、编号体系（见《P01-软件开发编号规范》）、术语定义（见《C99-天帷通用术语规范》）、错误代码（见《P02-软件开发错误代码规范》）
+   本规范与其他规范的关系：本规范定义研发过程框架，各阶段交付物的编写标准由独立的编写规范约束；编号规范和错误代码规范中的阶段划分应与本规范保持一致
+   文档密级：【商密二级】 -- 外发必追责。

# 2 研发过程总览

+   软件研发过程分为8个阶段，各阶段从宏观到微观、从业务到技术逐步细化。

    ```graph
    阶段1 产品战略 → 阶段2 宏观需求 → 阶段3 领域设计 → 阶段4 系统设计 → 阶段5 BC详细需求 → 阶段6 BC总体设计 → 阶段7 BC详细设计 → 阶段8 开发实现
    ```

+   各阶段之间存在顺序依赖关系，实际执行中可根据项目特点迭代和并行。
+   8个阶段与三个需求域的对应关系如下（详见附录B）：

    ```graph
    需求域              对应阶段                        SAFe 需求层级
    ─────────────────────────────────────────────────────────────────────
    业务需求域          阶段1 产品战略                  Strategic Theme
                        阶段2 宏观需求                  Business Epic
    ─────────────────────────────────────────────────────────────────────
    系统架构需求域      阶段3 领域设计                  Enabler Epic
                        阶段4 系统设计                  Capability / Enabler Capability / Enabler Feature
    ─────────────────────────────────────────────────────────────────────
    软件开发需求域      阶段5 BC详细需求                Feature → User Story（由Capability拆分而来）
                        阶段6 BC总体设计
                        阶段7 BC详细设计                Task
                        阶段8 开发实现
    ─────────────────────────────────────────────────────────────────────
    ```

# 3 阶段1：产品战略

## 3.1 阶段目标

+   明确产品的战略定位、目标市场、核心价值主张和商业模式，定义 Strategic Theme（战略主题），为后续研发提供方向性指引。

## 3.2 关键活动

-   市场分析与竞品研究
-   产品愿景与定位确定
-   Strategic Theme 定义：明确投资组合级的战略方向和业务目标
-   商业模式设计与可行性评估
-   产品路线图规划（基于 Strategic Theme 分解中长期演进计划）
-   关键成功指标（KPI）定义

## 3.3 阶段输入

-   市场调研报告
-   公司战略规划
-   客户反馈与需求洞察
-   技术趋势分析

## 3.4 阶段输出

| 交付物       | 说明                                                         |
| ------------ | ------------------------------------------------------------ |
| 产品战略文档 | 含产品愿景、目标市场、价值主张、商业模式、竞争策略、         |
|              | Strategic Theme 清单等，具体格式参见产品战略文档编写规范     |
| 产品路线图   | 分阶段的产品演进计划，标明关键里程碑，各里程碑可追溯到对应的 |
|              | Strategic Theme                                              |

# 4 阶段2：宏观需求

## 4.1 阶段目标

+   从整体业务视角梳理和定义产品的宏观需求，将 Strategic Theme 分解为 Business Epic（业务史诗），识别核心业务流程和关键用户场景，建立需求的全局视图。

## 4.2 关键活动

-   业务流程梳理与建模
-   系统角色与场景分析
-   Business Epic 识别与定义：将 Strategic Theme 分解为端到端的业务目标或价值流；采用三线三级对齐模型（见附录 B.2）：角色线为推导主线，活动线（CL0→CL1→CL2）为场景来源，实体线为完整性验证维度
-   宏观需求完整性验证：按活动线（场景全覆盖）、角色线（角色目标全覆盖）、实体线（实体生命周期全覆盖）三维度交叉核查 Business Epic 清单
-   核心功能需求识别与分类
-   非功能需求（性能、安全、可用性等）初步定义
-   Business Epic 优先级排序
-   需求演化：Business Epic 承接 Strategic Theme 分解；不符合战略方向的 Epic 候选可废弃；允许新增市场洞察或用户访谈驱动的新 Epic

## 4.3 阶段输入

-   产品战略文档（含 Strategic Theme 清单）
-   产品路线图
-   利益相关方访谈记录
-   现有系统分析（如适用）

## 4.4 阶段输出

| 交付物       | 说明                                                                 |
| ------------ | -------------------------------------------------------------------- |
| 宏观需求文档 | 涵盖业务全景、核心流程、用户场景、Business Epic 清单（含优先级与验收 |
|              | 标准）及非功能需求，具体格式参见宏观需求文档编写规范                 |
| 业务流程图   | 核心业务流程的可视化表达                                             |

# 5 阶段3：领域设计

## 5.1 阶段目标

+   运用领域驱动设计方法，对业务领域进行合理划分，识别核心领域、支撑领域和通用领域，建立统一语言。同时识别和定义 Enabler Epic（架构史诗），将跨BC的架构决策显性化管理。

## 5.2 关键活动

-   领域知识获取与统一语言建立
-   领域划分（核心域、支撑域、通用域）
-   限界上下文（BC）识别与边界划定
-   BC间关系与上下文映射（Context Map）设计
-   领域事件识别
-   Enabler Epic 识别与定义：基于 Business Epic 和领域划分结果，识别跨BC的架构决策需求（如领域边界划定的技术约束、BC间通信模式选型、共享内核策略等）
-   需求演化：Business Epic 全量承接，领域划分不废弃业务 Epic；Enabler Epic 为本阶段新识别的架构需求，与业务 Epic 并行管理

## 5.3 阶段输入

-   宏观需求文档（含 Business Epic 清单）
-   业务流程图
-   领域专家知识

## 5.4 阶段输出

| 交付物       | 说明                                                                   |
| ------------ | ---------------------------------------------------------------------- |
| 领域设计文档 | 包括领域划分、BC识别、上下文映射图、统一语言词汇表等，具体格式参见领域 |
|              | 设计文档编写规范。文档中应包含"架构需求分析"章节，记录本阶段识别的     |
|              | Enabler Epic 清单及其与 Business Epic 的追溯关系                       |

# 6 阶段4：系统设计

## 6.1 阶段目标

+   基于领域设计成果，完成系统层面的整体架构设计，确定技术选型、部署架构、集成策略和关键技术方案。将 Enabler Epic 分解为 Enabler Capability（架构能力）和 Enabler Feature（架构特性），形成可落地的架构需求清单。

## 6.2 关键活动

-   系统整体架构设计
-   技术选型与评估
-   BC到服务/模块的映射
-   系统集成方案设计（API网关、消息机制等）
-   基础设施与部署架构设计
-   系统级非功能需求方案设计（安全、性能、可观测性等）
-   Enabler Capability 定义：将 Enabler Epic 分解为跨BC的架构级能力（如统一认证体系、跨服务事件总线、可观测性平台等）
-   Enabler Feature 定义：将 Enabler Capability 进一步分解为具体的架构特性（如具体的技术选型方案、集成接口规范、非功能需求指标要求等），明确验收标准
-   需求演化：Enabler Epic 承接并细化为 Enabler Capability / Enabler Feature；架构约束若影响业务 Epic 范围，反馈至宏观需求文档

## 6.3 阶段输入

-   领域设计文档（含 Enabler Epic 清单）
-   宏观需求文档（非功能需求部分）
-   技术约束与现有架构资产

## 6.4 阶段输出

| 交付物       | 说明                                                                     |
| ------------ | ------------------------------------------------------------------------ |
| 系统设计文档 | 包括系统架构图、技术选型说明、集成方案、部署架构、非功能需求方案等，具体 |
|              | 格式参见系统设计文档编写规范。文档中应包含"架构需求清单"章节，记录       |
|              | Enabler Capability 和 Enabler Feature 列表（含验收标准），并标注与上游   |
|              | Enabler Epic 的追溯关系                                                  |

# 7 阶段5：BC详细需求

## 7.1 阶段目标

+   在宏观需求和领域设计的基础上，将 Business Epic 和 Capability 逐步拆分为 Feature（特性）和 User Story（用户故事），针对每个BC进行细粒度的需求分析和定义，产出可指导设计的详细需求规格。

## 7.2 关键活动

-   Capability 层引入判断（见附录 B.3）：评估是否在 Business Epic 与 Feature 之间引入 Capability 层；跨多个 BC 协作的 Epic 必须引入，BC 与多个 Epic 呈 N:M 横切关系时不引入
-   Capability（含 Enabler Capability）拆分：将跨BC的大粒度能力拆分为各BC可独立交付的 Feature
-   Feature 识别（见附录 B.4）：以业务场景为主线，按业务内聚性对场景分组形成 Feature；以实体状态机线和角色线两个维度交叉验证，确保场景、状态转换、角色目标无遗漏
-   User Story 识别（见附录 B.5）：三线并立推导——场景流程线识别功能型 Story，角色差异线识别角色专属型 Story，实体状态机线识别状态迁移型 Story；每个 Story 须满足 INVEST 原则
-   需求演化：上游 Business Epic / Capability 细化为 Feature / User Story（承接、细化、废弃、新增）；Enabler Feature 约束全量承接并细化为 BC 级非功能需求指标
-   需求验收标准定义：为每个 Feature 和 User Story 定义明确的、可测试的验收标准
-   业务规则详细定义
-   数据需求分析
-   BC级别的非功能需求细化（承接系统设计阶段的 Enabler Feature 约束）
-   BC间交互需求明确

## 7.3 阶段输入

-   宏观需求文档（含 Business Epic 清单）
-   领域设计文档（含 Enabler Epic 清单）
-   系统设计文档（含 Enabler Capability / Enabler Feature 架构需求清单）

## 7.4 阶段输出

| 交付物         | 说明                                                                     |
| -------------- | ------------------------------------------------------------------------ |
| BC详细需求文档 | 每个BC对应一份，包含 Feature 列表、User Story（含验收标准）、业务规则、  |
|                | 数据需求等，具体格式参见BC详细需求文档编写规范。各 Feature 和 User Story |
|                | 应可追溯到上游 Business Epic，并标注受上游 Enabler Feature 约束的        |
|                | 非功能需求                                                               |

# 8 阶段6：BC总体设计

## 8.1 阶段目标

+   针对每个BC，完成总体级别的技术设计。所有BC均需确定BC内部的模块划分、核心领域模型、关键接口和数据存储方案，并将 User Story 分解为初步的 Task（任务），建立需求到设计的追溯关系。
+   大BC：在总体设计共性内容之外，还需完成子领域划分、跨子领域约束定义、公共架构决策。
+   小BC：按传统方式完成总体设计，无需子领域划分。

## 8.2 BC规模判定

+   BC是否需要划分子领域，应在本阶段启动时判定。满足以下任一条件的BC判定为大BC：

-   BC内包含多个可独立演进的业务关注点
-   BC内的 Feature 数量或复杂度导致单份详细设计文档难以维护
-   BC内存在可由不同团队或人员并行设计的独立模块

+   不满足以上任一条件的BC按小BC处理。

## 8.3 关键活动

+   所有BC的共性活动：

-   BC内部模块/层次结构设计
-   聚合根与领域模型总体设计
-   对外接口（API）概要定义
-   数据存储方案设计
-   BC内关键技术方案设计
-   与其他BC的集成接口设计（落实系统设计阶段的 Enabler Feature 集成约束）
-   Task 初步分解：基于 User Story 和总体设计方案，识别主要的实现任务
-   需求演化：Feature / User Story 全量承接并拆分为初步 Task；如设计发现需求冲突或边界问题，应反馈 BC 详细需求文档修订

+   大BC的额外活动：

-   子领域划分：将BC内部按业务关注点划分为若干子领域，明确每个子领域的职责边界
-   跨子领域约束定义：明确子领域之间的依赖关系、数据共享规则、接口契约
-   公共架构决策：确定子领域共享的基础设施选型、公共模块、统一的领域事件规范等

## 8.4 阶段输入

-   BC详细需求文档（含 Feature / User Story 清单）
-   系统设计文档（含架构需求清单中的 Enabler Feature 约束）
-   领域设计文档

## 8.5 阶段输出

| 交付物         | 说明                                                                   |
| -------------- | ---------------------------------------------------------------------- |
| BC总体设计文档 | 每个BC对应一份。小BC：包含模块结构、领域模型概要、接口概要、数据方案、 |
|                | 初步 Task 清单等。大BC：在上述内容基础上，还应包含子领域划分方案、跨子 |
|                | 领域约束、公共架构决策，以及各子领域的概要级设计。设计方案应可追溯到   |
|                | Feature / User Story，并标注对 Enabler Feature 约束的落实方式          |

# 9 阶段7：BC详细设计

## 9.1 阶段目标

+   在总体设计基础上，完成BC的详细技术设计，产出可直接指导编码实现的设计方案。细化 Task 至可分配给开发人员的粒度。
+   大BC：按子领域分别产出详细设计文档，每个子领域一份（共 N 份）。
+   小BC：整个BC产出一份详细设计文档。

## 9.2 关键活动

-   详细领域模型设计（实体、值对象、聚合、领域服务）
-   API详细设计（请求/响应结构、错误码、版本策略）
-   数据模型详细设计（表结构、索引、数据迁移）
-   核心业务逻辑与算法设计
-   异常处理与边界条件设计
-   单元测试策略设计
-   需求落位（详细需求落地）：逐条确定 User Story 的处置方式（承接、细化、废弃、新增），形成 S05 详细需求与详细设计之间的追溯基线
-   Task 细化与工作量估算：将初步 Task 细化为可在迭代内完成的具体实现任务

+   大BC的额外要求：

-   各子领域的详细设计应遵循总体设计中定义的跨子领域约束和公共架构决策
-   子领域之间的接口契约应在各自详细设计文档中同步定义，保持一致

## 9.3 阶段输入

-   BC总体设计文档（含初步 Task 清单；大BC还含子领域划分方案和跨子领域约束）
-   BC详细需求文档（含 User Story 及验收标准）

## 9.4 阶段输出

| 交付物         | 说明                                                                   |
| -------------- | ---------------------------------------------------------------------- |
| BC详细设计文档 | 小BC：每个BC对应一份，包含详细领域模型、API规格、数据模型、算法设计、  |
|                | 细化后的 Task 清单（含工作量估算）等。大BC：每个子领域对应一份，内容   |
|                | 同上，各子领域文档应可追溯到总体设计中的子领域划分方案，并遵循跨子领域 |
|                | 约束。具体格式参见BC详细设计文档编写规范                               |

# 10 阶段8：开发实现

## 10.1 阶段目标

+   依据详细设计文档，按 Task 分配开发工作，完成编码实现、单元测试、集成测试和系统测试，交付可部署的软件产品。

## 10.2 关键活动

-   按 Task 分配开发工作，在迭代内完成编码实现
-   代码审查
-   单元测试与集成测试（验证 User Story 验收标准和 Enabler Feature 非功能需求）
-   持续集成/持续部署（CI/CD）
-   系统测试与验收测试
-   缺陷修复与回归测试
-   部署与发布
-   需求验收：以 User Story 验收标准验证实现完整性；发现需求偏差时通过变更管理流程处理

## 10.3 阶段输入

-   BC详细设计文档（含细化 Task 清单）
-   BC总体设计文档
-   BC详细需求文档（含 User Story 验收标准）
-   系统设计文档（含 Enabler Feature 非功能需求验收标准）

## 10.4 阶段输出

| 交付物            | 说明                                                    |
| ----------------- | ------------------------------------------------------- |
| 源代码            | 经代码审查通过，符合编码规范，可追溯到对应 Task 和      |
|                   | User Story                                              |
| 测试报告          | 包括单元测试、集成测试、系统测试的结果，覆盖 User Story |
|                   | 验收标准和 Enabler Feature 非功能需求                   |
| 部署包与部署文档  | 可部署的软件制品及部署说明                              |
| 用户手册/操作指南 | 如适用                                                  |

# 11 过程管理要求

## 11.1 阶段门禁

+   每个阶段完成后，应进行阶段评审，确认交付物质量和完整性，方可进入下一阶段。评审可根据项目规模和风险等级采取不同形式（正式评审会、同行评审、检查单确认等）。

## 11.2 变更管理

+   各阶段产出物如需变更，应遵循变更管理流程，评估变更影响范围并获得相关方确认。前序阶段的变更需评估对后续阶段的影响并同步更新。

## 11.3 可追溯性

+   各阶段交付物之间应建立可追溯的关联关系，确保从产品战略到代码实现的双向追溯能力。
+   推荐的追溯链路（括号内为对应的SAFe需求层级）：

    ```graph
    Strategic Theme → Business Epic → Enabler Epic → Enabler Capability    → Feature      → User Story → Task
    （产品战略）      （宏观需求）     （领域设计）    / Enabler Feature       （BC详细需求）  （BC详细需求） （设计与实现）
    ```

## B.2 阶段2——Business Epic 识别：三线三级对齐模型

+   Business Epic 识别采用三线三级对齐模型，以角色线为推导主线，活动线为场景来源，实体线为完整性验证维度。

### B.2.1 三线说明

| 线     | 别名     | 职责                                                |
| ------ | -------- | --------------------------------------------------- |
| 活动线 | 场景来源 | 从 CL0 业务场景逐级展开到 CL2 活动，构建场景全景    |
| 角色线 | 推导主线 | 按角色分析其在 CL2 活动中的期望，推导 Epic 候选列表 |
| 实体线 | 验证维度 | 检查核心实体的全生命周期是否被 Epic 覆盖            |

### B.2.2 三线演绎步骤

1.   活动线：梳理 CL0→CL1→CL2 三级活动树，形成业务场景全景
2.   角色线：对每个 CL2 活动，识别参与角色及其期望；合并同质期望，形成 Business Epic 候选清单
3.   实体线：梳理核心实体的生命周期（创建→状态变更→删除），检查每个状态转换是否有 Epic 承载

### B.2.3 完整性验证标准

+   活动线：所有 CL1 场景组均有 Epic 承载；CL2 活动均被某 Epic 覆盖
+   角色线：每个核心角色的关键业务目标均有 Epic 对应
+   实体线：核心实体的创建、状态变更、查询、删除生命周期事件均有 Epic 覆盖

> 详细编写规范见 S02-宏观需求编写规范。

## B.3 Capability 层引入判断准则

### B.3.1 三步判断法

**第一步**：Business Epic 是否需要多个 BC 协作交付？

+   是 → **必须引入 Capability**（Capability 聚合跨 BC 的 Feature，协调多 BC 交付）
+   否 → 进入第二步

**第二步**：该 BC 与 Business Epic 的关系是层级还是横切（N:M）？

+   横切（一个 BC 服务于多个 Epic；同时一个 Epic 涉及多个 BC）→ **不引入 Capability**
+   层级（一个 BC 主要承接特定 Epic 的需求）→ 进入第三步

**第三步**：该 BC 在单个 Epic 下的 Feature 数量是否超过 8 个？

+   超过 → 可选引入 Capability 作为管理分组（非业务分层）
+   不超过 → **不引入 Capability**，直接 Business Epic → Feature

### B.3.2 判断矩阵

| 场景                             | 引入 Capability？ | 说明                                 |
| -------------------------------- | ----------------- | ------------------------------------ |
| Business Epic 需多个 BC 协作交付 | 必须引入          | Capability 聚合跨 BC 的 Feature      |
| BC 与 Epic 呈 N:M 横切关系       | 不引入            | 横切型共享服务 BC，无需中间层        |
| 层级关系，Feature ≤ 8 个         | 不引入            | 直接 Epic → Feature，管理复杂度低    |
| 层级关系，Feature > 8 个         | 可选引入          | 用 Capability 做管理分组，非业务分层 |

## B.4 阶段5——Feature 识别：场景线主导、三线验证模型

### B.4.1 主线（场景线）推导

1.   从上游 Business Epic（或 Capability）出发，识别该 BC 承接的业务场景列表
2.   按业务内聚性对场景分组——满足以下任一条件的场景可归为同一 Feature：
    +   场景共用同一实体的状态转换路径（如文件从"待扫描"到"已激活"）
    +   场景的执行前提与后置结果之间存在依赖关系（前序场景的输出是后续场景的输入）
    +   场景服务于同一角色的同一关键业务目标
3.   每个内聚场景分组对应一个 Feature，命名遵循"[角色] + [业务动词] + [业务对象]"格式（避免使用 API 动词如 upload/download，改用业务动词如提交/审核/发布）
+   业务规则（前置条件、约束条件、计算规则、联动规则等）作为场景内部的约束，随场景归入对应 Feature，不单独构成推导线

### B.4.2 验证维度1：实体状态机线

+   梳理 BC 内核心实体的状态机（所有状态及状态转换事件）
+   检查：每个状态转换事件是否有 Feature 承载
+   若有状态转换未被任何 Feature 覆盖 → 补充 Feature 或扩展现有 Feature 边界

### B.4.3 验证维度2：角色线

+   梳理 BC 内的核心角色清单
+   检查：每个核心角色的关键业务目标是否有 Feature 承载
+   若有角色目标未被任何 Feature 覆盖 → 补充 Feature 或扩展现有 Feature 边界

### B.4.4 Feature 完整性核查清单

+   □ 每个 BC 承接的业务场景都有 Feature 覆盖
+   □ 核心实体的每个状态转换都有 Feature 承载
+   □ 每个核心角色的关键业务目标有 Feature 承载
+   □ 每个 Feature 的业务价值假设可独立表述，不依赖其他 Feature 描述才能理解

## B.5 阶段5——User Story 识别：三线并立推导模型

+   User Story 识别采用三线并立模型，三条推导线各自独立运行，结果合并形成完整 Story 清单。

### B.5.1 三线说明

| 线           | 推导目标                                         | Story 类型       |
| ------------ | ------------------------------------------------ | ---------------- |
| 场景流程线   | 主场景及有独立业务价值的分支场景（含场景内业务规则约束） | 功能型 Story     |
| 角色差异线   | 不同角色的差异化完整操作路径                     | 角色专属型 Story |
| 实体状态机线 | 场景流程线未覆盖的实体状态迁移节点               | 状态迁移型 Story |

### B.5.2 场景流程线推导规则

+   主场景（正常流程）→ **功能型 Story**（一个 Feature 至少一个主 Story）
+   有独立业务价值的分支场景（业务结果与主场景本质不同）→ 独立**功能型 Story**
+   技术性异常 / 边界条件（无独立业务价值）→ 作为相关 Story 的 **AC**，不拆 Story
+   业务规则（前置条件、约束条件、计算规则等）作为场景的内在约束，纳入关联 Story 的 **AC**；不构成独立推导线

### B.5.3 角色差异线推导规则

+   不同角色在该 Feature 下的完整操作路径本质不同（非权限差异）→ **角色专属型 Story**（各角色独立 Story）
+   不同角色仅权限或视图不同，操作路径相同 → 同一 Story，在 AC 中按角色分别描述

### B.5.4 实体状态机线推导规则

+   梳理 BC 内核心实体的状态机（所有状态及状态转换事件）
+   触发状态迁移的操作（如提交、审核、发布、撤销等），若未被场景流程线 Story 覆盖 → 独立**状态迁移型 Story**
+   查询类操作（查看当前状态、生命周期追踪）→ 合入相关场景 Story 的 AC，或 Story 数量充足时独立成 Story
+   若有状态转换完全未被场景流程线覆盖 → 补充**状态迁移型 Story**

### B.5.5 三类 Story 快速参照

| Story 类型       | 触发场景                            | 推荐格式                                                          |
| ---------------- | ----------------------------------- | ----------------------------------------------------------------- |
| 功能型 Story     | 主场景 / 有独立业务价值的分支       | As [角色]，I want [功能]，so that [业务价值]                      |
| 角色专属型 Story | 不同角色操作路径本质不同            | As [专属角色]，I want [专属操作]，so that [角色专属业务价值]      |
| 状态迁移型 Story | 实体状态转换未被场景流程线覆盖      | 当 [触发条件/角色操作]，系统完成 [状态迁移]，结果为 [新状态/业务效果] |

### B.5.6 INVEST 质量门禁

+   **I**ndependent：Story 之间无强依赖，可任意排序交付
+   **N**egotiable：实现细节可协商，业务意图明确不变
+   **V**aluable：每个 Story 对用户有可感知的独立业务价值
+   **E**stimable：团队可以合理估算工作量
+   **S**mall：一个迭代内可完成
+   **T**estable：有明确、可执行的验收标准（AC）

### B.5.7 User Story 完整性核查清单

+   □ 每个 Feature 有至少一个主流程功能型 Story
+   □ 核心实体的重要状态转换有 Story 或 AC 覆盖
+   □ 不同角色的差异化操作路径有独立 Story 区分
+   □ 每个 Story 满足 INVEST 原则
+   □ 每个 Story 的 AC 明确、可执行、可验证

## B.6 追溯链完整性

+   需求追溯链全景：

    ```graph
    Strategic Theme → Business Epic → [Capability] → Feature → User Story → Task
    （阶段1）          （阶段2）        （阶段5，可选） （阶段5）   （阶段5）     （阶段6～7）
    ```

+   各层级完整性验证标准：

    | 层级          | 完整性要求                                                        |
    | ------------- | ----------------------------------------------------------------- |
    | Business Epic | 可追溯到 Strategic Theme；三线（活动/角色/实体）均已验证          |
    | Capability    | 可追溯到 Business Epic；聚合的 Feature 均可拆分到各自 BC 独立交付 |

## B.7 各阶段需求演化处置模式

+   各阶段对需求的处置分为四类操作：**承接**（直接沿用上游需求）、**细化**（拆分或补充细节）、**废弃**（超出边界或需求变更，须记录原因）、**新增**（本阶段新发现，须标注来源）。

+   各阶段典型演化模式：

    | 阶段               | 承接来源                                    | 本阶段产出                       | 常见演化操作                                               |

    | 阶段2 宏观需求     | Strategic Theme                             | Business Epic                    | 承接拆分；废弃不符战略的候选；新增洞察或访谈驱动的 Epic   |
    | 阶段3 领域设计     | Business Epic                               | Enabler Epic                     | 承接：Business Epic 全量保留；新增：架构需求（Enabler Epic） |

    | 阶段5 BC详细需求   | Business Epic / Capability, Enabler Feature | Feature / User Story             | 承接；细化为 Feature / Story；废弃 BC 边界外需求；新增边界场景 |
    | 阶段6 BC总体设计   | Feature / User Story                        | Task（初步）                     | 承接；拆分为 Task；设计发现冲突时反馈至 BC 详细需求文档   |
    | 阶段7 BC详细设计   | User Story（S05）                           | 设计方案 + Task 细化             | 承接/细化/废弃/新增；形成 S05 与设计之间的追溯基线        |
    | 阶段8 开发实现     | Task + User Story AC                        | 可交付软件                       | 验收：以 AC 验证完整性；偏差走变更管理流程                 |

+   "废弃"操作应在阶段文档中明确记录废弃原因，并通知上游文档维护者。
+   "新增"操作应标注来源（用户反馈、技术约束、设计发现等），并与上游文档建立追溯关系。

# 附录C（资料性）追溯链全景

+   各阶段产出物之间应建立如下追溯关系：

    ```graph
    产品战略文档
      └── 宏观需求文档
            ├── 业务流程图
            └── 领域设计文档
                  ├── 上下文映射图
                  └── 系统设计文档
                        └── BC详细需求文档 (per BC)
                              └── BC总体设计文档 (per BC)
                                    ├── [小BC] BC详细设计文档 (1份/BC)
                                    │         ├── 源代码
                                    │         └── 测试用例
                                    └── [大BC] 子领域详细设计文档 (N份/BC)
                                              ├── 源代码
                                              └── 测试用例
    ```

+   正向追溯：从产品战略出发，可追踪到每一行代码和测试用例所支撑的业务目标。
+   反向追溯：从任意代码或缺陷出发，可回溯到其对应的设计决策、需求来源和战略依据。
+   变更影响分析：当某一层级的产出物发生变更时，可快速识别受影响的下游产出物。
+   宜在项目管理工具中为各层级产出物建立关联关系，实现自动化的追溯与变更影响分析。
