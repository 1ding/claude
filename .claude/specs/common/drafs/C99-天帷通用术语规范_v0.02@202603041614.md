# 2 术语定义

## 2.1 业务分析术语

**业务价值生态 (Business Value Ecosystem)**
产品所处的业务生态系统全景，是推导业务域、实体、利益相关方的共同源头。

**业务域 (Business Domain, DOM)**
系统按业务职能划分的顶层分区，按业务价值链或职能域划分。

**业务环节 (Business Segment, BS)**
客观发生的业务节点，不依赖系统存在；描述业务域内"在什么情境下发生什么"，是活动线最细粒度。

**工作场景 (Work Scenario, WS)**
角色进入系统的切入点；分直接作业场景（关联业务环节）和间接作业场景（管理/分析/协调）。

**关键实体 (Key Entity, EN)**
价值生态中的核心业务对象，具有明确业务含义、归属和生命周期状态流转。

## 2.2 需求分析术语

**困境 (Dilemma, DLM)**
业务层面达成目标的系统性障碍，描述"为什么目标难以实现"，是宏观需求分析的输入。

**痛点 (Pain Point, PP)**
角色在工作中面临的具体问题，是 Epic 推导的直接输入。

**期望 (Expectation, EXP)**
系统角色对理想工作状态的正向描述，与痛点互补，共同作为 Epic 推导输入。

**关键旅程触点 (Key Journey Touchpoint, TP)**
角色与系统/业务流程交互的关键节点，是工作场景的进一步细化。

**业务验收场景 (Business Acceptance Scenario, BAS)**
从业务视角定义 Epic"完成"的端到端验收场景。

**宏观需求 (Macro Requirements)**
产品全局视角的需求，定义 Epic 级业务能力，不涉及具体交付。

**基础性需求 (Foundation Requirements, FR)**
跨 BC 的通用能力需求（认证/权限/审计等），是功能性横切关注点。

**需求域 (Requirements Domain)**
按抽象层级划分：业务需求域（StRS）、系统架构需求域（SyRS）、软件开发需求域（SRS）。

**Epic**
史诗级用户故事，代表一个完整的业务能力或价值单元，是宏观需求的核心交付物。

**三线演绎 (Three-Line Deduction)**
宏观需求分析方法论，通过活动线、角色线、实体线推导和验证 Epic。

**抽象过滤 (Abstraction Filtering)**
Epic 推导中将候选需求按粒度分类：Epic 级保留，Feature 级降级为候选项。

## 2.3 角色与利益相关方

**特定利益相关方 (Specific Stakeholder, SH)**
从利益相关方中识别的具体人员群体或组织，按组织维度定位。

**系统角色 (System Role, SROLE)**
按业务职能对系统使用者分类的身份标签，携带预设权限集合，独立于 GRC 制度。

**业务角色 (Business Role, BROLE)**
GRC 制度文档中显式定义的职责承担者，独立于平台权限体系。

## 2.4 标识体系

**语义 ID (Semantic ID)**
条目的正式标识符，由类型前缀+语义片段组成，表达业务含义。

**短号 (Short Code)**
条目的便捷引用标识符，由类型前缀+递增数字组成，无业务含义。

**双轨标识 (Dual-Track Identification)**
同一条目同时拥有语义 ID 和短号，两者一一对应。

**类型前缀 (Type Prefix)**
语义 ID 和短号的首段，标识条目所属类型（如 EPIC/US/API）。

**语义片段 (Semantic Segment)**
语义 ID 中类型前缀之后的各组成部分，表达业务含义。

## 2.5 架构设计术语

**大 BC (Large Bounded Context)**
涉及多个子领域的复杂 BC，总体设计阶段需进行子领域划分。

**小 BC (Small Bounded Context)**
业务范围单一、无需子领域划分的 BC。

**BC 总体设计 (BC High-Level Design)**
BC 层面的高层技术方案设计。

**BC 详细设计 (BC Detailed Design)**
BC/子领域层面的细粒度技术设计。

**条目 (Item)**
软件开发过程中需要唯一标识和追溯的工作产物或管理对象。

## 2.6 合规管理术语

**控制点 (Control Point, CP)**
合规管理的最小控制单元，定义了"要做什么"的规范性要求，是外规要求映射到企业内部的标准化表达。

**技术方案 (Technical Solution, TS)**
控制点的具体实现方法，定义了"怎么做"的技术细节，包含配置参数、操作步骤、验证方法等。

**执行记录 (Execution Record, EXR)**
控制点在特定场景下实际执行的历史记录，记录了谁、在什么时间、执行了什么、结果如何。

**证据 (Evidence, EVD)**
证明控制点已执行且有效的客观材料，可以是配置文件、日志、截图、报告等。

**责任点 (Responsibility Point, RSP)**
控制点在特定场景下的责任落实单元，明确了谁负责、在什么场景下、执行什么控制点。

**场景点 (Scenario Point, SP)**
业务场景的具体实例，描述了控制点在什么情况下需要执行。

**合规包 (Compliance Package)**
面向特定行业或监管要求的控制点集合，封装了外规解析、控制点映射、技术方案的完整方案。

## 2.7 产品术语

**6 链 (Six Chains)**
透管云产品的 6 条核心业务链条：治理穿透链（L1）、合规落地链（L2）、制度溯源链（L3）、技术落地链（L4）、责任落实链（L5）、风险防控链（L6）。

**4 大中心 (Four Centers)**
透管云产品的 4 个核心功能中心：治理中心、合规中心、验证中心、风险中心。

**版本规划 (Version Planning)**
产品按时间和功能划分的交付计划，透管云采用 P1-P6 命名，每期对应一个版本。

## 2.8 通用原则

**知识单点定义原则**
每个知识点只在一个位置完整定义，其他位置通过精确引用指向。

# 3 易混淆术语区分

| 术语 A | 术语 B | 区别说明 |
| ------ | ------ | -------- |
| 业务域（DOM） | 限界上下文（BC） | DOM 是编号体系顶层分区标识；BC 是 DDD 业务边界划分单元。一个 DOM 可含多个 BC |
| 业务域 | 领域（DDD） | 业务域是编号体系概念；领域是 DDD 分析概念（核心域/支撑域/通用域） |
| 事件（EVT） | 领域事件（Domain Event） | EVT 是宏观需求中触发实体状态流转的动作；领域事件是 DDD 中 BC 间通信机制 |
| 关键实体（EN） | 实体（Entity/DDD） | EN 是宏观需求的核心业务对象（业务建模）；Entity 是 DDD 详设的领域对象（技术建模） |
| 系统角色（SROLE） | 业务角色（BROLE） | SROLE 按业务职能分类、携带权限；BROLE 是 GRC 制度中的职责承担者 |
| 宏观需求 | 详细需求 | 宏观是产品全局 Epic 级业务能力定义；详细是 BC 内 Feature/US/AC 级实现定义 |
| 控制点（CP） | 技术方案（TS） | CP 定义"要做什么"的规范要求；TS 定义"怎么做"的技术实现细节 |
| 责任点（RSP） | 场景点（SP） | RSP 是控制点在特定场景下的责任落实；SP 是业务场景的具体实例 |
| 执行记录（EXR） | 证据（EVD） | EXR 是执行的历史记录；EVD 是证明执行有效的客观材料 |
