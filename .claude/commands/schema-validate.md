# Schema 验证与修正

比对 schema 文件与原规范文档的一致性，检测遗漏、偏差或过时内容，并修正 schema。

## 适用场景

-   规范文档更新后，验证 schema 是否同步
-   怀疑 schema 与规范存在不一致
-   定期检查 schema 的准确性

## 不适用场景（请改用对应 skill）

-   从规范生成新 schema → `/spec-to-schema`
-   检查规范文档质量 → `/doc-review`
-   修订规范文档 → `/doc-revise`

## 输入

$ARGUMENTS

### 参数格式

```
/schema-validate <规范文档路径>
```

### 参数说明

-   **规范文档路径**（必需）：规范文档路径，自动定位对应的 schema 文件

### 使用示例

```
/schema-validate .claude/specs/common/C01-内容表达规范_v0.22@202602241415.md
```

### 文件定位规则

-   从规范文档路径自动推导 schema 文件路径
-   Schema 文件名 = 规范文档完整文件名（含版本号、时间戳、`.md` 后缀）+ `.schema.yaml`
-   规范文档：`.claude/specs/common/C01-内容表达规范_v0.22@202602241415.md`
  → Schema 文件：`.claude/specs/schema/C01-内容表达规范_v0.22@202602241415.md.schema.yaml`

## 先决条件检查

**在执行任何步骤前，先完成以下检查：**

**参数解析（规范文档）**

若 $ARGUMENTS 提供了规范文档路径（含 `/` 或以 `.md` 结尾）：
1.  提取文件路径和可选章节参数（格式 `N` 或 `N-M`，置于路径之后）
2.  读取规范文档（有章节参数时按 `# ` 一级标题切分，只加载指定章节）
3.  输出 `[LOADED target] {文件路径} | ~{tokens} tokens`

若 $ARGUMENTS 未提供路径 → 扫描当前会话历史中的 `[LOADED *]` 记录，确认：
-   [ ] 已存在 `[LOADED target]` 记录（规范文档已加载）

如两者均不满足，输出以下提示并**立即中止**，不执行后续任何步骤：

> ⚠️ 请提供规范文档路径：
> ```
> /schema-validate /path/to/规范文档.md
> /schema-validate /path/to/规范文档.md 3       # 只加载第3章
> /schema-validate /path/to/规范文档.md 1-2     # 只加载第1、2章
> ```

## 执行步骤

### 1. 确认文件路径

-   规范文档路径已在先决条件检查中确定（来自 $ARGUMENTS 或会话历史 `[LOADED target]` 记录）
-   从规范文档路径推导 schema 文件路径：
    -   提取规范文档目录（如 `.claude/specs/common/`）
    -   构建 schema 路径：`{规范文档目录}/../schema/{规范文档完整文件名（含.md）}.schema.yaml`
    -   示例：规范 `outputs/N00-规范_v0.23@202603051007.md` → schema `schema/N00-规范_v0.23@202603051007.md.schema.yaml`
-   读取规范文档内容
-   查找 schema 文件：
    -   若精确路径存在 → 正常加载
    -   若精确路径不存在 → 在 schema 目录搜索同文档前缀的其他版本 schema（glob `{文档编号}-*schema.yaml`）
        -   找到旧版本 → 加载旧版本，并在验证报告中将**文件名版本不匹配**列为 [!!] 严重问题，在步骤4修正时将 schema 文件重命名为新版本名
        -   完全找不到 → 提示用户先执行 `/spec-to-schema`

### 2. 执行一致性检查

按以下维度逐项检查：

#### 2.1 结构完整性检查

-   规范文档的核心章节是否在 schema 中有对应分组
-   规范文档的强制性规则是否在 schema 中完整覆盖
-   schema 中的规则分组是否与规范文档结构对应

#### 2.2 规则准确性检查

-   schema 中的规则描述是否与规范文档一致
-   schema 中的规则是否存在理解偏差或表述错误
-   schema 中的规则是否过时（规范已更新但 schema 未同步）

#### 2.3 示例有效性检查

-   schema 中的示例是否来自规范文档
-   示例是否准确反映规则要求
-   示例是否存在错误或误导

#### 2.4 遗漏检查

-   规范文档中新增的规则是否在 schema 中缺失
-   规范文档中的关键约束是否被遗漏

#### 2.5 冗余检查

-   schema 中是否包含规范文档中已删除的规则
-   schema 中是否存在重复或冗余的规则描述

### 3. 输出验证报告

```
---Schema 验证报告---

Schema 文件：{schema 文件路径}
规范文档：{规范文档路径}
验证日期：{日期}

检查结果汇总：
| 检查维度       | 结果   | 问题数 | 说明       |
| -------------- | ------ | ------ | ---------- |
| 结构完整性     | [OK]   | 0      |            |
| 规则准确性     | [!]    | 2      | 见详情     |
| 示例有效性     | [OK]   | 0      |            |
| 遗漏检查       | [!!]   | 3      | 见详情     |
| 冗余检查       | [!]    | 1      | 见详情     |

[!!] 严重问题（须立即修正）：
1. 规范文档第X章新增规则"..."未在 schema 中体现
2. Schema 中规则"..."与规范文档第Y章描述不一致
3. ...

[!] 一般问题（建议处理）：
1. Schema 中包含规范文档已删除的规则"..."
2. ...

总体评价：{一句话结论}
```

### 4. 执行修正（如有问题）

如检查发现 [!!] 严重问题，立即修正 schema 文件：

-   补充遗漏的规则
-   修正不一致的规则描述
-   删除过时或冗余的规则
-   更新示例
-   **若存在文件名版本不匹配**：使用 Bash `mv` 将 schema 文件重命名为正确的版本名（`{规范文档完整文件名}.schema.yaml`），并更新 schema 文件头部的 `来源规范` 注释

修正后：
-   保存修正后的 schema 文件，立即输出 `[CAP DELTA]` 标记（见容量管理规范）
-   在 schema 文件头部注释中更新修订日期
-   输出修正说明

### 5. 输出最终报告

```
---Schema 修正完成---

修正内容：
- 补充规则：{数量} 条
- 修正规则：{数量} 条
- 删除规则：{数量} 条
- 更新示例：{数量} 个

建议后续操作：
- 在编写流程中使用修正后的 schema
- 定期执行 /schema-validate 保持 schema 与规范同步
```

## 不执行

-   **不修改**原规范文档
-   **不执行**规范文档的质量检查
-   **不加载**关联文档
-   **不生成**新的 schema 文件（仅修正现有 schema）
