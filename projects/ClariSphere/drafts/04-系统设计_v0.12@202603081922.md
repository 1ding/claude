## 3.3 映射模式选型指南

    | 映射模式                | 适用场景                                | 约束要求                                   | 耦合程度 | 推荐优先级 |
    | ----------------------- | --------------------------------------- | ------------------------------------------ | -------- | ---------- |
    | OHS（开放主机服务）     | 上游BC提供标准化API，支持多个下游BC接入 | 上游需提供稳定API；下游通过API调用         | 低       | 最高       |
    | CS（客户-供应商）       | 下游BC依赖上游BC，上游优先满足下游需求  | 上游需响应下游需求；下游可影响上游接口设计 | 中       | 高         |
    | Partnership（合作关系） | 两个BC紧密协作，共同演进                | 双方需同步变更；需建立协调机制             | 高       | 中         |
    | SK（共享内核）          | 两个BC共享部分模型，需同步变更          | 共享代码需双方评审；MAJOR版本需同步发布    | 高       | 低         |
    | ACL（防腐层）           | 下游BC通过转换层隔离上游BC的模型差异    | 下游需实现适配器；需处理模型转换           | 低       | 高         |
    | Conformist（遵奉者）    | 下游BC完全遵从上游BC的模型，无议价能力  | 下游无法影响上游；需完全适应上游模型       | 高       | 最低       |

## 3.5 API网关设计

+   API网关职责：统一入口、身份认证、租户路由、限流熔断、协议转换、安全审计
+   路由规则规范：
    -   供给侧：`/api/provider/**` → 供给侧BFF
    -   消费侧A：`/api/tenant/**` → 消费侧A BFF（需租户上下文）
    -   消费侧B：`/api/consumer/**` → 消费侧B BFF（需用户认证）
    -   通用服务：`/api/common/**` → 通用服务直连
+   限流熔断策略：
    -   全局限流：10000 QPS
    -   租户级限流：单租户 1000 QPS
    -   用户级限流：单用户 100 QPS
    -   熔断阈值：错误率 > 50% 或 P99延迟 > 3s 触发熔断

## 3.6 事件驱动架构

### 3.6.1 消息中间件选型

+   主选：RocketMQ（支持事务消息、延迟消息、顺序消息）
+   备选：Kafka（高吞吐场景）
+   消息可靠性：至少一次投递（At Least Once）
+   消费模式：集群消费
+   死信处理：死信队列 + 人工干预

### 3.6.2 全局事件规范

+   Topic命名规范：`{domain}.{bc}.{event-type}`

## 3.8 全局依赖治理原则

    | 治理场景   | 治理规则                                                         | 违规后果                       |
    | ---------- | ---------------------------------------------------------------- | ------------------------------ |
    | 查询类依赖 | 禁止直接访问其他BC数据库；必须通过API调用；超时3秒；支持熔断降级 | 数据不一致、级联故障           |
    | 命令类依赖 | 禁止同步调用链超过3层；必须支持幂等；必须有超时和重试机制        | 性能下降、雪崩效应             |
    | 数据一致性 | 禁止跨BC分布式事务（2PC/XA）；采用最终一致性；使用Saga或事件驱动 | 数据不一致、性能瓶颈           |
    | 模型变更   | 上游模型变更时下游应通过ACL隔离；共享内核变更需双方评审          | 下游被迫跟随变更、耦合度增加   |
    | 循环依赖   | 禁止BC间循环依赖；如需双向协作使用Partnership模式+事件解耦       | 无法独立部署、变更影响范围扩大 |

### 8.1.3 动态数据源路由

+   消费侧A采用动态数据源路由实现Schema级隔离：

```java
// 租户上下文
public class TenantContext {
    private static final ThreadLocal<String> TENANT_CODE = new ThreadLocal<>();
    
    public static void setTenantCode(String tenantCode) {
        TENANT_CODE.set(tenantCode);
    }
    
    public static String getTenantCode() {
        return TENANT_CODE.get();
    }
    
    public static void clear() {
        TENANT_CODE.remove();
    }
}

// 动态数据源路由
public class TenantDataSourceRouter extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        String tenantCode = TenantContext.getTenantCode();
        return tenantCode != null ? "tenant_" + tenantCode : "default";
    }
}
```

## ADR-007 采用微服务架构

+   **状态**：已接受
+   **日期**：2026-01-31
+   **决策者**：架构团队

### 背景

+   ClariSphere 需要支持多租户、高并发、快速迭代的业务需求，需要选择合适的架构风格。

### 决策

+   采用微服务架构，按照 BC 划分微服务，每个 BC 对应一个微服务。

### 理由

+   **支持独立部署**：各 BC 可独立部署，互不影响
+   **支持独立扩展**：各 BC 可根据负载独立扩展
+   **支持技术异构**：各 BC 可选择最适合的技术栈
+   **支持团队自治**：各 BC 可由独立团队负责

### 后果

+   **正面影响**：
    -   提高系统可扩展性和可维护性
    -   支持快速迭代和持续交付
    -   降低单点故障风险
+   **负面影响**：
    -   增加分布式系统复杂度（事务、一致性、追踪）
    -   增加运维成本（监控、部署、故障排查）
    -   需要处理服务间通信开销

### 缓解措施

+   采用 Saga 模式处理分布式事务
+   采用事件驱动架构实现最终一致性
+   采用 SkyWalking 实现分布式链路追踪
+   采用 K8s 简化部署和运维

## ADR-008 知识中台采用 CQRS 模式

+   **状态**：已接受
+   **日期**：2026-01-31
+   **决策者**：架构团队

### 背景

+   知识中台（DOM40/41数据视图域）需要支持高频查询和复杂图谱遍历，同时保证写入性能。

### 决策

+   知识中台采用 CQRS 模式，读写分离：
+   **写模型**：BC-40 知识实体（MySQL + ES）
+   **读模型**：BC-41 知识图谱（Neo4j）

### 理由

+   **优化查询性能**：Neo4j 专为图查询优化，支持高性能图谱遍历
+   **优化写入性能**：MySQL + ES 支持高并发写入
+   **分离关注点**：写模型关注数据完整性，读模型关注查询性能

### 后果

+   **正面影响**：
    -   查询性能提升 10 倍以上
    -   写入性能不受查询影响
    -   支持独立扩展读写能力
+   **负面影响**：
    -   读写模型需要同步，存在延迟
    -   增加系统复杂度
    -   需要处理数据一致性

### 缓解措施

+   采用共享内核模式（SK），BC-40/41 共享节点 ID
+   采用事件驱动同步，保证最终一致性
+   读写延迟控制在 3 秒以内

## ADR-009 消费侧A采用 Schema 级租户隔离

+   **状态**：已接受
+   **日期**：2026-01-31
+   **决策者**：架构团队

### 背景

+   消费侧A（BC-31~36）需要支持 100+ 企业租户，需要选择合适的租户隔离方案。

### 决策

+   采用 Schema 级租户隔离，每个租户独立 Schema，共享数据库实例。

### 理由

+   **隔离级别高**：Schema 级隔离，租户间数据零泄漏
+   **成本可控**：共享数据库实例，成本低于独立数据库
+   **扩展性好**：支持 1000+ 租户
+   **运维友好**：统一数据库实例，运维成本低

### 后果

+   **正面影响**：
    -   满足企业租户的数据隔离要求
    -   成本低于独立数据库方案
    -   支持租户独立升级
+   **负面影响**：
    -   Schema 变更需要全租户同步
    -   单库容量有上限（1000+ 租户）
    -   需要动态数据源路由

### 缓解措施

+   采用 Flyway 统一管理 Schema 变更
+   采用动态数据源路由实现租户隔离
+   预留分库分表能力（P4）

## ADR-010 禁止使用 2PC/XA 分布式事务

+   **状态**：已接受
+   **日期**：2026-01-31
+   **决策者**：架构团队

### 背景

+   微服务架构下需要处理跨 BC 的分布式事务。

### 决策

+   禁止使用 2PC/XA 分布式事务，采用 Saga 模式和事件驱动架构保证最终一致性。

### 理由

+   **性能问题**：2PC 需要全局锁，性能差
+   **可用性问题**：2PC 需要协调者，存在单点故障
+   **扩展性问题**：2PC 不适合大规模分布式系统

### 后果

+   **正面影响**：
    -   提高系统性能和可用性
    -   支持大规模分布式系统
+   **负面影响**：
    -   需要处理最终一致性
    -   需要设计补偿机制
    -   增加业务复杂度

### 缓解措施

+   采用 Saga 模式，每步定义补偿操作
+   采用事件溯源，保证完整审计轨迹
+   采用幂等性设计，支持重试

## ADR-011 采用 RocketMQ 作为消息队列

+   **状态**：已接受
+   **日期**：2026-01-31
+   **决策者**：架构团队

### 背景

+   事件驱动架构需要选择合适的消息队列。

### 决策

+   采用 RocketMQ 作为消息队列。

### 理由

+   **支持事务消息**：保证消息可靠投递
+   **支持延迟消息**：支持定时任务场景
+   **支持顺序消息**：保证消息顺序
+   **社区活跃**：阿里开源，社区活跃

### 后果

+   **正面影响**：
    -   满足事件驱动架构需求
    -   支持复杂消息场景
+   **负面影响**：
    -   需要运维 RocketMQ 集群
    -   学习成本

### 缓解措施

+   采用 Docker 部署，简化运维
+   提供统一消息封装，降低学习成本
