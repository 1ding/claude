# 1 概述

+   文档编号：GUIDE-REG-001
+   文档名称：监管条文结构化拆解指南
+   文档密级：内部资料

## 1.1 目的

+   本指南定义监管条文结构化拆解的字段体系、填写规则及操作步骤，用于将法规原文转换为可跨法规聚合的结构化记录。
+   本指南以《法规条款原子化拆解模型》（以下简称"拆解模型"）为基础依据，字段定义与词库以拆解模型为准，并在此基础上补充操作层面的填写规则、示例与 JSON 格式。
+   适用场景：

-   对单部法规全文进行批量结构化拆解
-   跨法规汇总同一领域的全部监管要求
-   基于结构化记录开展合规差距分析与要求映射
-   将监管义务映射到安全目标体系，识别覆盖关系

## 1.2 核心模型

+   拆解基于拆解模型的维度体系，以"主体对客体执行行为"为语义核心，附加场景条件、控制要求、义务约束等维度。一条监管义务的完整语义结构如下图所示：

```graph
┌────────────────────────────────────────────────────────────────────────┐
│                          监管义务语义结构                              │
│                                                                        │
│  [主体]  ──[义务模态]──▶  [行为]  ──▶  [客体(A/S/N/H/P/R)]           │
│                                                                        │
│  场景层：在 [环境/区域] 下  /  经由 [通道/途径]  /  涉及 [协作方]     │
│  条件层：[适用条件（静态）]  /  当 [触发事件（动态）] 时              │
│  控制层：采取 [T/M/G 控制手段]                                        │
│  约束层：满足 [时限] [覆盖范围] [量化指标] [审批层级] [证据要求]      │
│  目的层：为了 [保护法益]                                               │
│  映射层：对应 [COAST 安全目标]                                         │
└────────────────────────────────────────────────────────────────────────┘
```

+   每条条文按上述结构拆解为一条或多条**义务记录**，一条记录对应一个独立的监管义务。

# 2 字段体系

## 2.1 字段定义

下表列出全部字段及其说明：

| 字段      | 必填 | 分组       | 说明                                                                 |
| --------- | ---- | ---------- | -------------------------------------------------------------------- |
| 来源      | 是   | 法规元数据 | 法规名称 + 条款编号，如：数据安全法§27                               |
| 义务类别  | 是   | 语义结构   | 操作性 / 结构性 / 资格性 / 责任归属，见 2.2 节                       |
| 主体      | 是   | 场景条件   | 被约束的责任方，标注类型（组织/岗位/角色），使用归一化类型，见 4.1 节|
| 行为      | 是   | 语义结构   | 主体作用于客体的动词，使用归一化动词，见 4.7 节                      |
| 客体      | 否   | 场景条件   | 行为作用的实体对象，使用统一实体词库编码（A/S/N/H/P/R），见 4.2 节   |
| 环境/区域 | 否   | 场景条件   | 条款适用的场景边界，见 4.3 节                                        |
| 通道/途径 | 否   | 场景条件   | 行为经由的方式或介质，见 4.4 节                                      |
| 协作方    | 否   | 场景条件   | 条款涉及的外部关系方，见 4.5 节                                      |
| 控制手段  | 否   | 控制要求   | 具体控制措施，T/M/G 三类，见 4.6 节                                  |
| 适用条件  | 否   | 控制要求   | 限定主体范围或场景的静态前置条件                                     |
| 触发事件  | 否   | 控制要求   | 驱动义务生效的特定动态事件                                           |
| 义务模态  | 是   | 控制要求   | 应 / 不得 / 可以 / 宜，见 3.1 节                                     |
| 规则内容  | 是   | 控制要求   | 具体合规要求列表，每项为一个可独立验证的合规动作                     |
| 时限      | 否   | 控制程度   | 立即 / 及时 / 定期 / N 日内 / 无                                     |
| 覆盖范围  | 否   | 控制程度   | 义务的适用面限定，如：全量、等保三级及以上、涉及个人信息的           |
| 量化指标  | 否   | 控制程度   | 具体数值约束，如：密码长度≥8位、日志留存≥6个月                      |
| 审批层级  | 否   | 控制程度   | 授权/审批要求；参考值：操作员级、管理员级、管理层级、监管机构级      |
| 证据要求  | 否   | 控制程度   | 文档化与可追溯性要求，如：留存记录、向主管部门备案、出具报告         |
| 保护法益  | 否   | 补充说明   | 条文明确表述的保护目的                                               |
| 目标      | 否   | 补充说明   | 对应 COAST 安全目标，格式：{一级} > {二级} > {三级}，见 4.8 节       |
| 例外      | 否   | 补充说明   | 豁免条件，如"依法不予公开的除外"                                     |
| 法律后果  | 否   | 补充说明   | 违规处罚，通常引用法律责任章节条款                                   |

## 2.2 义务类别

+   每条义务记录按其结构特征归入以下四类：

| 义务类别 | 特征                       | 行为词示例               |
| -------- | -------------------------- | ------------------------ |
| 操作性   | 主体执行一个具体的动作     | 处理、监测、报告、配合   |
| 结构性   | 主体建立某个组织架构或制度 | 建立、设置、明确（机构） |
| 资格性   | 主体须具备某种状态或资质   | 取得、具备、持有         |
| 责任归属 | 某主体承担某项职责或责任   | 承担、负责、担任         |

# 3 填写规则

## 3.1 义务模态判断

+   根据条文关键词判断义务模态：

| 关键词                 | 模态 | 含义             |
| ---------------------- | ---- | ---------------- |
| 应、应当、须、必须     | 应   | 强制作为         |
| 不得、不应、禁止、严禁 | 不得 | 强制不作为       |
| 可以、可               | 可以 | 授权许可，非强制 |
| 宜、鼓励、支持         | 宜   | 推荐做法，非强制 |

## 3.2 适用条件与触发事件的区分

+   **适用条件**：静态范围限定，主体满足条件则持续适用该义务。
    +   示例："关键信息基础设施运营者……"→ 适用条件 = 主体为关键信息基础设施运营者
+   **触发事件**：动态事件驱动，事件发生时义务才生效。
    +   示例："发现数据安全缺陷或漏洞时……"→ 触发事件 = 发现安全风险
+   两者可同时存在，也可均为空（表示无条件持续义务）。

## 3.3 规则内容的粒度

+   每项规则内容应为**一个独立可验证的合规动作**，用①②③列举。
+   不可验证的抽象表述保留原文，不拆解过细。
+   示例（数据安全法§27）：

    -   ①建立健全全流程数据安全管理制度
    -   ②组织开展数据安全教育培训
    -   ③采取相应技术措施和其他必要措施

## 3.4 责任归属类条文的处理

+   中文监管条文常用"是……"代替"应当承担……"，须还原隐含动词后再填写行为字段。

| 原文句式           | 隐含义务动词 | 还原示例                   |
| ------------------ | ------------ | -------------------------- |
| X 是安全第一责任人 | 承担         | X 应当承担安全第一责任     |
| 应当明确安全负责人 | 建立         | 主体应建立安全职能岗位     |
| 应当具备相应资质   | 取得         | 主体应取得相应资质         |
| 应当取得行政许可   | 取得         | 主体应取得行政许可         |

## 3.5 一条条文拆分为多条记录的情形

+   出现以下任一情形时，拆分为多条独立义务记录：

-   条文涉及多个不同主体，每个主体单独一条记录
-   条文中义务模态混合（"应"与"不得"并存），按模态分别单独一条记录
-   条文中存在不同触发事件，每个触发事件单独一条记录

## 3.6 目标字段的填写

+   目标字段用于将监管义务与 COAST 安全目标体系建立映射，格式为 `{一级} > {二级} > {三级}`。
+   填写原则：

-   **尽量填到三级**；只有义务确实跨越多个三级目标时，才停留在二级
-   一条义务可对应多个目标，用分号分隔
-   处罚性条款（法律责任章节）通常不填目标

## 3.7 语法主语辨别

+   部分条文以**活动名称**作为语法主语（如"变更管理应当……"、"开发应当……"），此时：

    -   **活动本身是控制手段（M类）**，不是主体，也不是客体
    -   **真正的主体**是负责该活动的组织或岗位，需根据上下文识别
    -   若上下文未明确指定，填写最贴近的归一化角色

+   示例：

| 原文                 | 错误理解       | 正确拆解                                                     |
| -------------------- | -------------- | ------------------------------------------------------------ |
| 变更管理应当确保……   | 主体=变更管理  | 主体=负责变更管理的组织，控制手段(M)=变更管理                |
| 开发应当遵循安全规范 | 主体=开发      | 主体=开发团队（组织/岗位），控制手段(T)=开发安全/代码安全    |

## 3.8 客体字段标注

+   客体字段使用统一实体词库编码，格式：`{代码} {名称}`，如 `A3 重要数据`、`S1 业务应用系统`。
+   多个客体用分号分隔，如 `A1 个人信息; S1 业务应用系统`。
+   若条文仅要求采取管理或治理措施，无明确实体对象，客体字段留空，措施通过控制手段字段体现。
+   标注时优先使用条款原文表述对应的最具体分类（颗粒度就高）。
+   A/S/N/H/P/R 完整分类体系见 4.2 节。

## 3.9 控制手段字段标注

+   控制手段字段标注条款要求采取的具体控制措施，分 T（技术措施）、M（管理措施）、G（治理措施）三类，词库见 4.6 节。
+   标注原则与拆解模型一致：

-   T 词库默认标到第一层（安全能力大类）；仅在条款原文明确指定具体手段时才标注第二层
-   一条义务可同时涉及多类控制手段，格式：`T: 密码/加密; M: 跨境传输管理`
-   义务类别（操作性/结构性等）描述条文结构特征；控制手段（T/M/G）描述要求采取的措施类型；两者独立标注，不互斥

## 3.10 场景条件字段标注

+   **环境/区域**：描述条款适用的场景边界；无显式环境限定时留空，表示"不限环境"。典型值见 4.3 节。
+   **通道/途径**：描述行为经由的方式或介质；出现频率低，多数条款不显式指定，无则留空。典型值见 4.4 节。
+   **协作方**：描述条款涉及的外部关系方；在数据共享、出境、外包管理等场景为高频字段。同一角色可同时出现在主体字段和协作方字段中。典型值见 4.5 节。
+   留空规则：未显式指定时一律留空，不得填写"全部"或"不限"等文字。

## 3.11 控制程度约束字段

+   **时限**：条款明确规定的时间约束，无则留空。常见值：立即、及时、定期（注明周期）、N 日内。
+   **覆盖范围**：条款明确规定的适用面，无则留空。示例：全量、等保三级及以上、涉及个人信息的系统。
+   **量化指标**：条款包含的具体数值要求，无则留空。示例：密码长度≥8位、日志留存≥6个月、RPO≤4小时。
+   **审批层级**：条款规定的授权或审批要求，无则留空。参考值：操作员级、管理员级、管理层级、监管机构级。
+   **证据要求**：条款要求的文档化或可追溯性措施，无则留空。示例：留存操作记录、向主管部门备案、出具评估报告。

# 5 拆解步骤

+   按以下步骤对每条条文执行拆解：

-   **Step 1　识别是否需拆解**：判断条文是否属于不拆类型（见 5.1 节）。属于则跳过，不属于则继续。
-   **Step 2　识别主体**：条文中有几个主体？注意辨别语法主语（见 3.7 节），多个主体则准备生成多条记录。
-   **Step 3　确定义务类别**：该义务是操作性、结构性、资格性，还是责任归属？
-   **Step 4　还原行为动词**：如条文为"是……"句式，还原隐含动词（见 3.4 节）。
-   **Step 5　确定行为和客体**：主体对什么实体对象执行什么动词？若无明确实体对象，客体留空。
-   **Step 6　标注场景条件**：有无特定环境/区域、通道/途径、协作方？分别填入对应字段，无则留空。
-   **Step 7　判断义务模态**：关键词归类，见 3.1 节。
-   **Step 8　判断条件类型**：有无适用条件（静态）或触发事件（动态）？
-   **Step 9　标注控制手段**：条款要求采取何种 T/M/G 控制措施？见 4.6 节词库；无明确指定则留空。
-   **Step 10　拆解规则内容**：逐项列举可独立验证的合规动作，用①②③标注。
-   **Step 11　填写控制程度约束**：时限、覆盖范围、量化指标、审批层级、证据要求，有则填，无则留空。
-   **Step 12　映射目标**：对照 4.8 节词表，选取 COAST 安全目标，尽量到三级。
-   **Step 13　归一化**：对照 4.1～4.7 节词表，标注主体类型，映射客体编码，规范控制手段表达。

## 5.1 不拆的条文类型

| ---------- | ----------------------- | ---------------------------- |

## 7.2 字段说明

+   各字段与第 2 章字段体系的对应关系及取值规则如下：

| JSON 字段                 | 对应字段   | 类型            | 必填 | 取值规则                                                                     |
| ------------------------- | ---------- | --------------- | ---- | ---------------------------------------------------------------------------- |
| `source`                  | 来源       | string          | 是   | 法规名称 + 条款编号，如 `数据安全法§29`                                      |
| `obligation_type`         | 义务类别   | string          | 是   | `"操作性"` / `"结构性"` / `"资格性"` / `"责任归属"`                         |
| `subject.normalized_type` | 主体       | string          | 是   | 见 4.1 节归一化类型                                                          |
| `subject.category`        | 主体类型   | string          | 是   | `"组织"` / `"岗位"` / `"角色"`                                               |
| `subject.type_class`      | 主体专属性 | string          | 是   | `"通用"` / `"专属"`，见 GUIDE-REG-002 第 2.3 节                              |
| `action`                  | 行为       | string          | 是   | 见 4.7 节归一化动词                                                          |
| `object`                  | 客体       | array \| null   | 否   | 多客体时含多项，格式 `[{"code":"A3","name":"重要数据"}]`；无实体客体填 null  |
| `environment`             | 环境/区域  | string \| null  | 否   | 见 4.3 节；无则 null                                                         |
| `channel`                 | 通道/途径  | string \| null  | 否   | 见 4.4 节；无则 null                                                         |
| `collaborator`            | 协作方     | array \| null   | 否   | 多协作方时含多项；无则 null；见 4.5 节                                       |
| `controls.T`              | 控制手段-T | array\<string\> | 否   | T词库一级名称，如 `["密码/加密"]`；空则填 `[]`                               |
| `controls.M`              | 控制手段-M | array\<string\> | 否   | M词库名称，如 `["风险评估"]`；空则填 `[]`                                    |
| `controls.G`              | 控制手段-G | array\<string\> | 否   | G词库名称，如 `["岗位/角色设置"]`；空则填 `[]`                               |
| `applicable_condition`    | 适用条件   | string \| null  | 否   | 无则 null                                                                    |
| `trigger_event`           | 触发事件   | string \| null  | 否   | 无则 null                                                                    |
| `modality`                | 义务模态   | string          | 是   | `"应"` / `"不得"` / `"可以"` / `"宜"`                                       |
| `rules`                   | 规则内容   | array\<string\> | 是   | 每项一个独立可验证的合规动作，保留 `①②③` 前缀                               |
| `deadline`                | 时限       | string \| null  | 否   | `"立即"` / `"及时"` / `"定期"` / `"N日内"` / null                           |
| `coverage_scope`          | 覆盖范围   | string \| null  | 否   | 无则 null                                                                    |
| `quantitative_indicator`  | 量化指标   | string \| null  | 否   | 无则 null                                                                    |
| `approval_level`          | 审批层级   | string \| null  | 否   | `"操作员级"` / `"管理员级"` / `"管理层级"` / `"监管机构级"` / null          |
| `evidence_requirement`    | 证据要求   | string \| null  | 否   | 无则 null                                                                    |
| `legal_interest`          | 保护法益   | string \| null  | 否   | 无则 null                                                                    |
| `targets`                 | 目标       | array\<object\> | 否   | 多目标时含多项；只到二级时省略 `level3`；处罚条款填空数组 `[]`               |
| `exception`               | 例外       | string \| null  | 否   | 无则 null                                                                    |
| `legal_consequence`       | 法律后果   | string \| null  | 否   | 无则 null                                                                    |

## 7.3 内规侧记录的差异

+   内规记录复用监管侧同一 schema，额外增加两个字段；`subject.type_class` 字段不适用于内规侧（主体专属性由监管侧记录携带）：

| 附加字段  | 类型   | 说明                                                             |
| --------- | ------ | ---------------------------------------------------------------- |
| `doc_ref` | string | 内规来源文件编号，如 `DSP-OPS-012`                               |
| `scope`   | string | 内规适用范围，如 `"全公司"` / `"信息科技部"` / `"核心业务系统"` |

+   内规主体覆盖判断不依赖内规记录中的主体字段，而由监管侧 `subject.type_class` 驱动，见 GUIDE-REG-002 第 2.3 节。
+   `legal_interest` 和 `legal_consequence` 在内规记录中通常为 null。
