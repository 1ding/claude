+   文档密级：内部资料

## 1.1 目的与定位

+   本指南是监管条文结构化拆解的唯一操作参考，涵盖维度体系、词库体系、拆解步骤、字段说明与示例，形成一站式操作文档。
+   适用场景：

    -   跨法规汇总同一领域的全部监管要求
    -   基于结构化记录开展合规差距分析与义务映射

# 2 基础

## 2.1 拆解思路

### 2.1.1 拆解的目的价值

+   监管条文往往在单一条款中含有多个并列义务或复合义务。**原子化**的目标是将每条条款拆分为可独立理解且可独立落地的单条要求（原子要求），使义务可跨法规聚合、可直接映射到控制措施。

### 2.1.2 拆解的基准

+   **原子要求**是基本记录单元，定义为：一个条款中包含的、可独立理解且可独立落地的单条要求。
+   若一个法条包含多个并列要求，则拆分为多条原子记录；每条原子记录独立标注全部字段。
+   **拆解基准**：以可独立定位的最小编号节点为读入单元（处理单元），一个处理单元可产出 1..N 条原子记录；条款编号是溯源定位符，同一条款派生的所有原子记录共享相同的条款编号。

+   不同文本类型的引用粒度：

    | 文本类型               | 引用层级                     | 说明                                    |
    | ---------------------- | ---------------------------- | --------------------------------------- |
    | 法律/行政法规/部门规章 | 条（第X条）                  | 款无独立编号，不作为引用粒度            |
    | 国家/行业标准          | 最小数字编号节（如 8.1.4.1） | 字母编号（a)/b)）在段落之下，不独立定位 |
    | 通知/发文              | 最小编号层级                 | 随文本结构取最细可编号层级              |

### 2.1.3 三层九维——拆解的方法

+   对任意一条合规义务，可从三类问题入手系统性分解：

    -   **"它从哪里来、旨在实现什么、违反会怎样"**：法规溯源记录出处，目标标注安全意图，后果记录违规处罚。
    -   **"谁对什么执行什么操作、在哪里、何时触发"**：主体描述参与方，客体描述操作对象，行为描述具体动作，环境描述基础设施上下文，条件描述触发时机与豁免情形。
    -   **"用什么约束、以什么强度"**：控制描述控制机制及其义务模态和时限要求。

+   三类问题对应三个逻辑层次，共展开为九个维度组：

    -   **元数据层**（法规溯源、目标、后果）：描述条款本身的来源、安全分类和法律后果，不涉及义务内容。
    -   **业务语义层**（主体、客体、行为、环境、条件）：描述义务的业务场景——谁、对什么、做什么、在哪里、什么条件下。
    -   **约束层**（控制）：描述对业务行为施加的约束——用什么控制机制、什么模态、达到什么程度。

+   控制的约束对象从结构自动推导：有行为时约束行为；无行为时约束所有已标注的主体和客体。

+   每组内，字段分为**维度**和**属性**两种层级——属性是对维度的进一步展开与限定：

    -   **维度**：实体身份标识，可独立成立，具有独立检索/查询价值。
    -   **属性**：对维度的进一步限定，须依附维度才有意义，自身独立存在不具备价值。

+   属性以结构化数组存储，每个属性项包含 `attr`（属性名）、`value`（值）、`required`（是否必填）三个字段；属性各组独立定义，不跨组通用；所有属性字段均有对应词库（固定枚举/参考词库），仅阈值型数值字段保留自由文本。

+   三层九维结构与各维度组中的维度/属性字段详见 2.2 节总览表，以下为结构示意：

    ```graph
    ┌─────────────┬─────────────┬────────────────────────────────────────────────────┐
    │ 元数据层    │ 法规溯源    │ 出处、效力、适用行业                    → # 3      │
    │             │ 目标        │ 安全目标                                → # 4      │
    │             │ 后果        │ 法律后果                                → # 5      │
    ├─────────────┼─────────────┼────────────────────────────────────────────────────┤
    │             │ 主体        │ 身份 × 属性（职责·规模·属地）           → # 6      │
    │ 业务语义层  │ 客体        │ 资产 × 属性（状态·规模·分级·属地）      → # 7      │
    │             │ 行为        │ 动词 + 资源域（IT/R）/事项域（IT/M · IT/G） → # 8  │
    │             │ 环境        │ 资源域（IT/R）× 部署属性               → # 9      │
    │             │ 条件        │ 触发事件 · 例外                         → # 10     │
    ├─────────────┼─────────────┼────────────────────────────────────────────────────┤
    │ 约束层      │ 控制        │ 控制机制 × 属性（义务模态·时限·量化指标）→ # 11    │
    └─────────────┴─────────────┴────────────────────────────────────────────────────┘
    ```

## 2.2 维度总览

+   全部标注字段分为九组，每组对应一条原子记录中的一个 JSON 对象。各组内字段分为**维度**（实体身份标识，可独立成立）和**属性**（对该维度的限定，须依附维度才有意义）两种层级；属性各组独立定义，不跨组通用。

    | 组别     | 层级 | 字段     | 词库来源         | 说明                                                     | 详见 |
    | -------- | ---- | -------- | ---------------- | -------------------------------------------------------- | ---- |
    | 法规溯源 | 维度 | 法规名称 | —                | 条款所在法规或标准的全称                                 | # 3  |
    |          | 维度 | 条款编号 | —                | 条款在法规中的唯一层级定位符，规则因文本类型而异         | # 3  |
    |          | 维度 | 效力层级 | 固定枚举         | 法规的法律位阶，决定义务的强制力来源                     | # 3  |
    |          | 维度 | 适用行业 | 行业清单树       | 法规明确限定的适用行业范围，引用行业清单树节点           | # 3  |
    | 目标     | 维度 | 安全目标 | COAST 词库       | 该条款旨在达成的安全目标，按 COAST 体系分类              | # 4  |
    | 后果     | 维度 | 法律后果 | —                | 违反该义务时适用的处罚，通常引用法律责任条款             | # 5  |
    | 主体     | 维度 | 身份     | 身份词库         | 条款中的参与方类型（执行者、监管机构、数据主体等）       | # 6  |

    |          | 属性 | 规模     | 自由文本         | 组织体量或数据处理量（阈值型，无法枚举）                 | —    |
    |          | 属性 | 属地     | 固定枚举         | 参与方的地理管辖归属                                     | # 6  |

## 2.3 JSON 基准格式

+   每条原子记录存储为一个 JSON 对象，结构与九维度组一一对应。

+   **数据库存储模型**：条款在数据库中独立存储（每条条款一行）。原子记录通过 `clause_id` 外键引用条款表，条款表再通过 `law_id` 引用法规主表。JSON 的 `regulation` 对象为展示形态，存储时只保留 `clause_id`，其余字段由数据库根据外键展开。

+   **JSON 基准（展示形态）**：

    ```json
    {
    "regulation": {
        "clause_id": "",              // 存储键：条款表主键
        "clause_code": "",            // 展示键：可读定位符，如 "数据安全法§29"
        "law_name": "",               // 展示键：法规全称（来自法规主表）
        "effect_level": "",           // 展示键：效力层级（来自法规主表）
        "applicable_industry": null   // 展示键：行业清单树节点 id 列表（来自法规主表）
    },
    "target": {
        "security_targets": []
    },
    "consequence": {
        "legal_consequence": []
    },
    "stakeholders": [
        {
        "identity": "",
        "category": "",
        "type_class": "",
        "attributes": [
            { "attr": "职责", "value": ["R"], "required": true }
        ]
        }
    ],
    "object": null,
    "action": {
        "verb": null,
        "domain": null,
        "matter": null
    },
    "environment": {
        "resource_env": null,
        "deployment_env": null
    },
    "condition": {
        "trigger_event": null,
        "exception": null
    },
    "control": {
        "mechanisms": { "T": [], "M": [], "G": [] },
        "attributes": [
        { "attr": "义务模态", "value": "应", "required": true }
        ]
    }
    }
    ```

+   各维度组的详细取值规则见对应章节（# 3～# 11）。内规侧记录在此基础上额外增加 `doc_ref`（来源文件编号）和 `scope`（适用范围）两个字段；`stakeholders[].type_class` 不适用于内规侧。

# 3 法规溯源

## 3.1 概述

+   法规溯源组描述原子记录所属条款的法律来源。由于条款在数据库中独立存储，原子记录的法规溯源信息通过 `clause_id` 外键链接到条款/法规主表，而非冗余存储在每条记录中。

## 3.2 字段说明

+   `regulation` 对象的各字段如下：

    | 字段名                | 存/展 | 说明                                           | 取值规则                                          |
    | --------------------- | ----- | ---------------------------------------------- | ------------------------------------------------- |
    | `clause_id`           | 存储  | 条款表主键，唯一标识一条条款                   | 系统生成整数 ID                                   |
    | `clause_code`         | 展示  | 人工可读的条款定位符，拆解时手工填写           | 见 2.1.2 节，如 `数据安全法§29`                   |
    | `law_name`            | 展示  | 法规/标准全称                                  | 来自法规主表，如"中华人民共和国数据安全法"        |
    | `effect_level`        | 展示  | 法规的法律位阶                                 | 法律/行政法规/部门规章/国家标准/行业标准/团体标准 |
    | `applicable_industry` | 展示  | 法规明确限定的适用行业范围，引用行业清单树节点 | 节点 id 数组；全行业通用填 `["通用"]`；无则 null  |

+   行业清单树的结构和节点列表见附录A。

## 3.3 标注规则

+   拆解时在 `clause_code` 字段填写可读定位符；`clause_id` 由系统在条款入库后回填。
+   `applicable_industry` 标注法规整体适用范围，通用法规填 `["通用"]`，行业专属法规引用对应行业节点。

# 4 目标

## 4.1 概述

+   目标组标注条款旨在达成的安全目标，使用 COAST 安全目标词库分类。安全目标是分析性标注，用于跨法规的合规分析和义务汇总，而非条文原文内容。

## 4.2 字段说明

+   **安全目标**（`security_targets`）：从 COAST 词库（见附录C）选取，格式 `{一级} > {二级} > {三级}`。尽量填到三级；跨多个三级目标时可停留二级; 根据原文语义，确有必要的，可以填写一级目标。
+   security_targets： 数据格式为字符串数组，支持多目标。

## 4.3 标注规则

+   处罚性条款通常不填（无安全目标，只有法律后果）。
+   声明性安全目标条款（如"应当保障数据的保密性"）在此字段填写目标，控制机制可留空。

# 5 后果

## 5.1 概述

+   后果组标注违反义务时适用的法律处罚，作为溯源引用而非内容描述。

## 5.2 字段说明

+   **法律后果**（`legal_consequence`）：违规处罚的条款引用，通常指向法律责任条款，如 `"数据安全法§48"`。无则为 null。
+   legal_consequence： 展示时，为对应的具体条款，存储时，为对应条款的id。数组格式，支持多后果条款。

# 6 主体

## 6.1 概述

+   主体组描述条款中所有参与方，采用**身份**（维度）+ **属性**（限定条件）结构。一条原子要求可包含多个主体，每个主体独立标注身份和属性。

### 6.2.2 职责属性（RACISV 枚举）

| 值  | 含义   | 说明                                    | 责任类型      | 责任程度 |
| --- | ------ | --------------------------------------- | ------------- | -------- |
| R   | 执行者 | 实际执行任务的人                        | 直接责任      | 主要责任 |
| A   | 负责人 | 最终对结果负责的人（每条义务只能有1个） | 管理责任      | 主要责任 |
| C   | 顾问   | 需要征询意见的人（双向沟通）            | 技术/建议责任 | 次要责任 |
| I   | 知情者 | 需要被告知的人（单向沟通）              | 无            | 无问责   |
| S   | 审批者 | 审批和签字批准的人（含会签和终审）      | 管理/领导责任 | 次要责任 |
| V   | 验证者 | 验证执行结果的人                        | 监督责任      | 次要责任 |

+   S（审批者）含两个子类型：会签（流程中间环节把关，管理责任）、终审（最终决策，领导责任；制度体系缺陷严重时可升级为主要责任）。

## 6.3 字段说明

+   **身份**（`identity`）：从身份词库选取归一化类型，格式 `{归一化类型}【{类型}】`，如 `数据处理者【组织】`。
+   **类别**（`category`）：`"组织"` / `"岗位"` / `"角色"`。
+   **主体专属性**（`type_class`）：`"通用"` / `"专属"`，见 GUIDE-REG-002 第 2.3 节；内规侧不适用。
+   **属性**（`attributes`）：

    | 属性名 | required | 词库来源    | 取值规则                      |
    | ------ | -------- | ----------- | ----------------------------- |
    | 职责   | true     | RACISV 枚举 | R / A / C / I / S / V，可多值 |
    | 规模   | false    | 自由文本    | 条款未限定时不填（阈值型）    |
    | 属地   | false    | 固定枚举    | 见 6.2.3 节；条款未限定时不填 |

## 6.4 标注规则

+   同一实体可承担多个 RACISV 角色（如监管机构同时是 I 和 V）。
+   职责由条文语境判定，与身份类型无关——同一身份词库类型在不同条款中可承担不同职责。
+   条文常见省略：主体省略时从章节标题或适用范围条款推断；"X是安全第一责任人"句式还原为"X应当承担安全责任"；活动名称作主语时还原真正的执行者（如"变更管理应当……"→ 负责变更管理的组织）。

# 7 客体

## 7.1 概述

+   客体组描述义务作用的信息资产，采用**资产**（维度）+ **属性**（限定条件）结构。资产使用 DASPR 五层编码标识（词库见附录B）。

## 7.2 词库

### 7.2.1 分级参考词库

+   标注时注明所用分级体系，格式：`{体系}: {值}`，如 `等保: 等保三级`、`数安: 重要数据`。

+   数据安全分级（数据安全法）：

    | 值       | 说明                                 |
    | -------- | ------------------------------------ |
    | 核心数据 | 关系国家安全、国民经济命脉、重要民生 |
    | 重要数据 | 法规定义的重要数据目录中列明的数据   |
    | 一般数据 | 不属于核心或重要数据的业务数据       |

+   信息系统安全等级（GB/T 22239）：等保一级 / 等保二级 / 等保三级 / 等保四级
+   个人信息敏感度（GB/T 35273 及个人信息保护法）：敏感个人信息 / 一般个人信息
+   （词库随实际适用标准扩展）

### 7.2.2 属地枚举（客体）

| 值   | 说明                 |
| ---- | -------------------- |
| 境内 | 数据存储或产生于境内 |
| 境外 | 数据存储或产生于境外 |

## 7.3 字段说明

+   **资产**（`object[].code` + `object[].name`）：DASPR 编码，如 `D3 重要数据`。允许多值；无资产客体时为 null。资产状态集见附录B。
+   **属性**（`object[].attributes`）：

    | 属性名 | required | 词库来源   | 取值规则                            |
    | ------ | -------- | ---------- | ----------------------------------- |
    | 状态   | false    | 资产状态集 | 从附录B各资产状态集选取；不填时不限 |
    | 规模   | false    | 自由文本   | 条款未限定时不填（阈值型）          |
    | 分级   | false    | 参考词库   | 见 7.2.1 节，注明分级体系           |
    | 属地   | false    | 固定枚举   | 见 7.2.2 节；条款未限定时不填       |

## 7.4 标注规则

+   **颗粒度就高**：原文为"敏感个人信息"时，不应标注 D1，应标注 D2。
+   **客体 vs 资源环境**：同一 DASPR 资产在不同条文中可充当客体（义务作用的对象）或资源环境（义务发生的基础设施上下文），判定方式见 9.4 节。

# 8 行为

## 8.1 概述

+   拆解操作围绕三个域组织词库和标注逻辑，域划分决定事项选取和控制机制（T/M/G）归类：

    | 域          | 全称          | 覆盖范围               | 对应标注维度             |
    | ----------- | ------------- | ---------------------- | ------------------------ |
    | IT/R 资源域 | IT Resource   | 信息资产（DASPR 五层） | 客体（# 7）、环境（# 9） |
    | IT/M 管理域 | IT Management | 管理关注事项           | 行为·事项（见 8.2.2 节） |
    | IT/G 治理域 | IT Governance | 治理关注事项           | 行为·事项（见 8.2.3 节） |

    | 域   | 事项（做什么事）        | 控制机制（用什么约束）             |
    | ---- | ----------------------- | ---------------------------------- |
    | IT/R | DASPR 信息资产          | T 技术机制：加密、访问控制、审计…… |
    | IT/M | 管理事项（见 8.2.2 节） | M 管理机制：审批、四眼原则……       |
    | IT/G | 治理事项（见 8.2.3 节） | G 治理机制：职责分离、授权矩阵……   |

+   行为组描述义务的动作内容，由**动词**（必要时）和**事项**（IT/M、IT/G 域时）两个维度组成。行为域（IT/R / IT/M / IT/G）由作用对象决定。

# 10 条件

## 10.1 概述

+   条件组描述义务的生效边界——何时激活（触发事件）、何时豁免（例外）。条件是自由文本，描述状态变化的开关，与部署环境（描述持续存在的基础设施特征）有本质区别。

## 10.2 字段说明

+   **触发事件**（`condition.trigger_event`）：义务激活的动态事件条件，事件发生时义务从休眠变为激活。如 `"发现数据安全缺陷或漏洞"`。无则为 null。
+   **例外**（`condition.exception`）：义务的豁免条件，满足则义务不适用。如 `"经中华人民共和国主管机关批准的除外"`。无则为 null。

## 10.3 标注规则

+   同一条文中存在不同触发事件时，应拆分为多条原子记录，每条对应一个触发事件。

# 11 控制

    | -------- | -------- | -------- | ------------------------------------------------- |
    | 义务模态 | true     | 固定枚举 | 见 11.2.4 节：应/不得/可以/宜                     |
    | 时限     | false    | 固定枚举 | 见 11.2.5 节；无时限约束时不填                    |
    | 量化指标 | false    | 自由文本 | 具体数值要求，如 `"密码≥8位"`；无则不填（数值型） |

## 11.4 标注规则

+   T 机制默认标到一级；仅在条文明确指定具体手段时才标二级。
+   声明性安全目标条款（如"应当保障数据的保密性"）：控制机制可为空数组，义务模态仍需填写，安全目标字段填写对应 COAST 词条。
+   内规侧记录复用此 schema，增加 `doc_ref` 和 `scope` 两个字段。

# 12 拆解步骤

## 12.1 识别与前置处理

+   **不拆类型**：以下条文跳过，不产出原子记录：

    | 类型       | 示例                    | 原因                   |
    | ---------- | ----------------------- | ---------------------- |
    | 定义条款   | 第3条 数据的定义        | 无义务，仅定义术语     |
    | 政策宣示   | 第7条 国家保护数据权益  | 无可验证合规动作       |
    | 立法目的   | 第1条 制定本法目的      | 无义务                 |
    | 纯授权条款 | 第54条 军事数据另行制定 | 义务在子法规中，待拆解 |

+   **省略还原**：拆解前先从条文上下文还原隐含要素：

    | 省略类型     | 还原方法                         |
    | ------------ | -------------------------------- |
    | 主体省略     | 从章节标题或适用范围条款推断     |
    | 客体省略     | 从动词和上下文推断处理对象       |
    | 语法主语偏移 | 活动名称作主语时还原真正的执行者 |
    | 隐含义务动词 | "是……"句式还原为"应当承担……"     |

## 12.2 九维展开

+   将还原后的条文按九个维度组逐一映射。展开框架：

```text
[主体·身份(职责)] 在 [环境] 中，
当 [条件·触发事件] 时，
对 [客体] 执行 [行为]，
[控制·义务模态] [控制机制] [控制·时限/量化]。
```

+   展开示例：

```text
原文："所有变更都应经过审批。"

还原："（运维团队）对（IT/R资源）进行变更前，
       应经（变更审批负责人）审批。"

维度映射：
  主体 → 运维人员【岗位】(R)；变更审批负责人【岗位】(S)
  客体   → 具体资产（由上下文确定，如 A1/A2/S6 等）
  行为   → 变更（IT/R 域）
  条件   → 变更执行前（触发事件：变更申请发起）
  控制   → M: 审批/授权；义务模态=应
```

## 12.3 拆分规则

+   以下任一情形须拆分为多条独立原子记录：

-   条文涉及多个不同 R 角色（执行者）→ 每个执行者单独一条
-   义务模态混合（"应"与"不得"并存）→ 按模态各一条
-   存在不同触发事件 → 每个触发事件一条
-   含证据要求（如"留存操作记录"）→ 证据要求单独一条

## 12.4 归一化检查

+   归一化身份类型（对照身份词库）
+   映射客体编码至 DASPR（颗粒度就高）
+   属性值匹配对应枚举词库
+   规范控制机制表达（T/M/G 前缀 + 一级词条）
