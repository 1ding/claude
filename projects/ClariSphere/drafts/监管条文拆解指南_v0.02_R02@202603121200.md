# 1 概述

+   文档编号：GUIDE-REG-001
+   文档名称：监管条文结构化拆解指南
+   文档密级：内部资料

## 1.1 目的与定位

+   本指南是监管条文结构化拆解的唯一操作参考，内容基于《法规条款原子化拆解模型》，将模型的维度体系、词库体系完整融合，并补充拆解步骤、字段说明与示例，形成一站式操作文档。
+   适用场景：

-   对单部法规全文进行批量结构化拆解
-   跨法规汇总同一领域的全部监管要求
-   基于结构化记录开展合规差距分析与义务映射

## 1.2 原子要求的定义与结构

+   **原子要求**是本模型的基本记录单元，定义为：一个条款中包含的、可独立理解且可独立落地的单条要求。
+   若一个法条包含多个并列要求，则拆分为多条原子记录；每条原子记录独立标注全部字段。
+   每条原子要求的语义结构为：

```graph
场景条件（谁 + 针对什么 + 在什么环境下 + 经由什么途径 + 涉及哪些协作方）
  → 控制要求（做什么 + 属于什么类型 + 达到什么控制程度）
  → 目标与溯源（服务哪个安全目标 + 条款出处 + 适用范围）
```

# 3 词库体系

## 3.1 统一实体词库

+   客体、环境、通道三个维度共用一套统一实体词库。同一实体在不同条款中可充当不同角色，角色由各对应字段分别标注。
+   操作编码规则：客体字段使用 A/S/N/H/P/R 前缀；环境与通道字段使用实体名称文本（不用编码）。T/M/G 字母专用于控制手段分类，不用于实体编码。

## 4.2 法规元数据字段

+   **法规名称**：法规/标准全称，如"中华人民共和国数据安全法"。
+   **条款编号**：原始条款的层级定位，如"第三章第二十一条第一款"；操作简写格式：`数据安全法§21`。
+   **效力层级**：法律、行政法规、部门规章、国家标准、行业标准、团体标准。
+   **适用行业**：金融、电信、医疗、能源、政务、通用等；通用时可省略。
+   **适用条件**：触发该法规适用的前置条件，如"CII运营者"、"处理100万人以上个人信息"。

## 4.3 场景条件字段

+   **责任主体**：条款的义务承担者，格式 `{归一化类型}【{类型}】`，如 `数据处理者【组织】`。允许多值。
+   **客体/资产**：行为作用的实体对象，使用 A/S/N/H/P/R 编码，如 `A3 重要数据[传输]`。允许多值；无实体客体时留空。
+   **环境/区域**：条款适用的场景边界，使用实体词库的"环境"角色，如"互联网/外网"、"云环境"。无显式限定时留空（表示不限环境，不得填"不限"）。
+   **通道/途径**：行为经由的方式或介质，使用实体词库的"通道"角色，如"专线/VPN"、"移动存储介质"。多数条款不显式指定，无则留空。
+   **协作方**：条款涉及的外部关系方，使用角色词库，如"境外接收方"、"第三方服务商/外包"。在数据共享、出境、外包场景为高频字段；同一角色可同时出现在责任主体和协作方中。

## 4.4 控制要求字段

+   **义务类别**：条款的法律结构特征，四取一：

| 值       | 特征                       | 行为词示例               |
| -------- | -------------------------- | ------------------------ |
| 操作性   | 主体执行一个具体的动作     | 处理、监测、报告、配合   |
| 结构性   | 主体建立某个组织架构或制度 | 建立、设置、明确（机构） |
| 资格性   | 主体须具备某种状态或资质   | 取得、具备、持有         |
| 责任归属 | 某主体承担某项职责或责任   | 承担、负责、担任         |

+   **行为**：主体对客体执行的动词，使用归一化动词，见 3.5 节。
+   **要求类型**：控制措施的性质分类，五取一（或混合）：

| 值  | 含义        | 说明                           | 控制手段词库 |
| --- | ----------- | ------------------------------ | ------------ |
| OBJ | 目标/原则   | 声明性安全目标或原则           | OBJ 词汇     |
| DOC | 制度/文档   | 要求制定某类文档或制度         | DOC 词汇     |
| T   | 技术措施    | 具体技术控制要求               | T 词库       |
| M   | 管理措施    | 具体管理活动要求               | M 词库       |
| G   | 治理措施    | 组织/治理结构要求              | G 词库       |

+   **控制手段**：具体的控制措施，根据要求类型选对应词库，见 3.3 节。允许多类型混合，格式：`T: 密码/加密; M: 跨境传输管理`。
+   **触发事件**：动态事件驱动，事件发生时义务生效，如"发现数据安全缺陷或漏洞"、"数据安全事件发生"。与适用条件（静态前置条件）区分，见 5.2 节。
+   **义务模态**：条款的义务性质：

| 值   | 关键词                   | 含义             |
| ---- | ------------------------ | ---------------- |
| 应   | 应、应当、须、必须       | 强制作为         |
| 不得 | 不得、不应、禁止、严禁   | 强制不作为       |
| 可以 | 可以、可                 | 授权许可，非强制 |
| 宜   | 宜、鼓励、支持           | 推荐做法，非强制 |

+   **规则内容**：可独立验证的合规动作列表，用①②③列举。每项为一个独立可执行动作，不可验证的抽象表述保留原文不过度拆解。

## 4.5 控制程度字段

+   **时限**：条款明确的时间约束。参考值：立即、及时、定期（注明周期，如"每年一次"）、N 日内。无则留空。
+   **覆盖范围**：条款明确的适用面限定。示例：全量、等保三级及以上系统、涉及个人信息的系统。无则留空。
+   **量化指标**：条款包含的具体数值约束。示例：密码长度≥8位、日志留存≥6个月、RPO≤4小时。无则留空。
+   **审批层级**：条款规定的授权或审批要求。参考值：操作员级、管理员级、管理层级、监管机构级。无则留空。
+   **证据要求**：条款要求的文档化或可追溯性措施。示例：留存操作记录、向主管部门备案、出具评估报告、留存审批文件。无则留空。

## 4.6 目标与法益字段

+   **安全目标**：条款要求达成的 COAST 安全目标，直接从 3.4 节词库中选取，格式 `{一级} > {二级} > {三级}`。尽量填到三级；跨多个三级目标时可停留二级；多个目标用分号分隔。处罚性条款通常不填。
+   **保护法益**：条文原文明确表述的保护目的，如"数据安全"、"国家安全"、"个人信息权益"。

## 4.7 法律信息字段

+   **例外**：条款的豁免条件，如"经中华人民共和国主管机关批准的除外"。无则留空。
+   **法律后果**：违规处罚，通常引用法律责任章节，如"数据安全法§48"。无则留空。

# 5 标注规则

## 5.1 多值、留空与推断规则

+   **多值标注**：所有维度均允许多值。责任主体、客体、协作方、控制手段、安全目标均可标注多项，用分号分隔。
+   **留空规则**：当条款未显式指定某维度时，该维度留空，表示"不限/未指定"。不得填写"全部"、"不限"等文字。
+   **推断克制**：标注忠实于条款原文。仅当上下文逻辑关系明确时允许推断，不做过度解读。
+   **颗粒度就高**：标注优先使用原文表述对应的最具体分类。如原文为"敏感个人信息"，不应标注上位概念"个人信息"（A1），应标注 A2。

## 5.2 适用条件与触发事件的区分

+   **适用条件**：静态范围限定，主体满足条件则持续适用该义务。
    +   示例："关键信息基础设施运营者……" → 适用条件 = 主体为关键信息基础设施运营者
+   **触发事件**：动态事件驱动，事件发生时义务生效。
    +   示例："发现数据安全缺陷或漏洞时……" → 触发事件 = 发现安全风险
+   两者可同时存在，也可均为空（表示无条件持续义务）。

## 5.3 实体词库的角色机制

+   同一实体在不同条款中可充当不同角色：

| 实体         | 作为客体（A/S/N/H/P/R 编码） | 作为环境          | 作为通道        |
| ------------ | ---------------------------- | ----------------- | --------------- |
| 防火墙       | N5（边界/DMZ 相关设备）      | 边界/DMZ          | —               |
| 互联网       | N2                           | 互联网/外网       | 互联网          |
| 专线/VPN     | N3                           | —                 | 专线/VPN        |
| 移动存储介质 | H4                           | —                 | 移动存储介质    |

+   当实体作为**被管理的对象**（条款要求对其进行保护、部署、维护）时，标注为客体。
+   当实体描述**条款的适用背景**时，标注为环境。
+   当实体描述**数据传输的经过路径**时，标注为通道。

## 5.4 角色词库的双重身份

+   同一角色可在同一条款中同时出现在责任主体和协作方字段：
    +   示例："第三方服务商应在合同约定范围内处理数据" → 责任主体=第三方服务商，协作方=第三方服务商

## 5.5 T 词库分层标注规则

+   技术措施默认标到第一层（安全能力大类），如"密码/加密"。
+   仅在条款原文明确指定具体技术手段时才标注第二层，如"传输层加密(TLS)"。
+   场景条件（客体状态、环境等）已编码"传输"/"存储"等信息，T 词库不重复编码这些场景维度。

## 5.6 语法主语辨别

+   部分条文以**活动名称**作为语法主语（如"变更管理应当……"），此时活动本身是控制手段（M类），不是主体也不是客体，真正的主体是负责该活动的组织或岗位。

| 原文                 | 错误理解       | 正确拆解                                                  |
| -------------------- | -------------- | ---------------------------------------------------------- |
| 变更管理应当确保……   | 主体=变更管理  | 主体=负责变更管理的组织，控制手段(M)=变更管理              |
| 开发应当遵循安全规范 | 主体=开发      | 主体=开发团队，控制手段(T)=开发安全/代码安全               |

## 5.7 责任归属类条文的处理

+   中文监管条文常用"是……"代替"应当承担……"，须还原隐含动词。

| 原文句式           | 隐含义务动词 | 还原后                     |
| ------------------ | ------------ | -------------------------- |
| X 是安全第一责任人 | 承担         | X 应当承担安全第一责任     |
| 应当明确安全负责人 | 建立         | 主体应建立安全职能岗位     |
| 应当具备相应资质   | 取得         | 主体应取得相应资质         |

## 5.8 条文拆分规则

+   出现以下任一情形时，拆分为多条独立原子记录：

-   条文涉及多个不同主体，每个主体单独一条记录
-   条文中义务模态混合（"应"与"不得"并存），按模态分别单独一条记录
-   条文中存在不同触发事件，每个触发事件单独一条记录

## 5.9 不拆的条文类型

+   以下类型条文跳过，不纳入原子记录：

| 类型       | 示例                    | 原因                         |
| ---------- | ----------------------- | ---------------------------- |
| 定义条款   | 第3条 数据的定义        | 无义务，仅定义术语           |
| 政策宣示   | 第7条 国家保护数据权益  | 无可验证合规动作             |
| 立法目的   | 第1条 制定本法目的      | 无义务                       |
| 纯授权条款 | 第54条 军事数据另行制定 | 义务在子法规中，待子法规拆解 |

# 6 拆解步骤

+   按以下步骤对每条条文执行拆解：

-   **Step 1　识别是否需拆解**：判断条文是否属于不拆类型（见 5.9 节）。属于则跳过。
-   **Step 2　识别主体**：条文中有几个主体？注意辨别语法主语（见 5.6 节）；多个主体则准备生成多条记录。
-   **Step 3　确定义务类别**：该义务是操作性、结构性、资格性，还是责任归属？如为"是……"句式，还原隐含动词（见 5.7 节）。
-   **Step 4　确定行为和客体**：主体对什么实体对象（A/S/N/H/P/R）执行什么动词？有无状态？若无明确实体对象，客体留空。
-   **Step 5　标注场景条件**：有无特定环境/区域、通道/途径、协作方？分别填入，无则留空（见 5.3 节角色机制）。
-   **Step 6　判断义务模态**：关键词归类，见 4.4 节。
-   **Step 7　判断条件类型**：有无适用条件（静态）或触发事件（动态）？见 5.2 节。如有不同触发事件，准备拆分多条记录。
-   **Step 8　确定要求类型**：OBJ / DOC / T / M / G，见 4.4 节。
-   **Step 9　标注控制手段**：根据要求类型从对应词库选取，见 3.3 节；T 词库默认到一级（见 5.5 节）；无明确指定则留空。
-   **Step 10　拆解规则内容**：逐项列举可独立验证的合规动作，用①②③标注。
-   **Step 11　填写控制程度约束**：时限、覆盖范围、量化指标、审批层级、证据要求，有则填，无则留空。
-   **Step 12　填写安全目标**：从 3.4 节 COAST 词库选取，尽量到三级。
-   **Step 13　填写法规元数据**：法规名称、条款编号、效力层级、适用行业、适用条件。
-   **Step 14　归一化**：对照 3.1～3.5 节词表，标注主体类型、映射客体编码、规范控制手段表达。

## 8.3 内规侧记录的差异

+   内规记录复用监管侧同一 schema，额外增加两个字段；`subject.type_class` 字段不适用于内规侧：

| 附加字段  | 类型   | 说明                                                             |
| --------- | ------ | ---------------------------------------------------------------- |
| `doc_ref` | string | 内规来源文件编号，如 `DSP-OPS-012`                               |
| `scope`   | string | 内规适用范围，如 `"全公司"` / `"信息科技部"` / `"核心业务系统"` |

+   内规主体覆盖判断由监管侧 `subject.type_class` 驱动，见 GUIDE-REG-002 第 2.3 节。
+   `legal_interest` 和 `legal_consequence` 在内规记录中通常为 null。
