## 2.2 上下文价值定位

+   **核心价值**：将知识中台的标准化合规知识落地到租户真实业务环境，实现"要求→落实→责任到人"的完整合规追溯链。

+   **业务目标**：
    1.   帮助租户完成 IT 资产登记、场景/控制/制度/岗位角色的标准化映射，快速建立自身合规基线
    2.   通过双向追溯机制，确保合规要求与租户执行之间的可见性与可审计性
    3.   为下游合规管理（BC-31）、验证检查（BC-32）、安全管理（BC-36）提供可信数据底座

+   **服务对象**：租户侧安全架构师（UR-02）、制度编写者（UR-03）、方案制定者（UR-04）、制度管理员（UR-10）、租户管理员（UR-09），以及下游 BC-31/BC-32/BC-36。

+   **核心能力**：租户资产管理、知识映射（场景/控制/责任）、制度库管理、技术方案管理、岗位角色映射。

## 2.3 上下文边界

+   **核心职责**：
    -   管理租户IT资产的登记、分类与场景关联
    -   建立标准场景点、控制点到租户实际场景、控制的映射关系
    -   管理租户制度库（导入、入库、版本管理、作废）
    -   管理技术安全方案与配置基线
    -   建立标准角色点到租户岗位/人员的映射，生成责任点

+   **扩展职责**（P2+ 实现）：
    -   在线起草制度、发布审批流程
    -   AI 辅助映射推荐

+   **明确排除**：

+   **R-01 租户资产管理职责详情**：
    -   业务场景：租户接入合规管理流程时，首先需要建立本租户IT资产台账
    -   触发条件：安全架构师（UR-02）或租户管理员（UR-09）发起资产录入操作
    -   预期结果：资产完整登记并分类，可与租户场景建立关联

+   **R-02 知识映射落地职责详情**：
    -   业务场景：租户订阅合规包后，需要将标准知识（场景点/控制点）映射到自身业务实际环境
    -   触发条件：BC-53 推送合规包数据后，安全架构师手动发起或系统自动初始化映射
    -   预期结果：租户场景/控制映射关系建立并激活，支撑合规评估数据来源
    -   关联功能：F-16、F-17（P2 实现）

+   **R-03 制度库管理职责详情**：
    -   业务场景：租户需要维护内部管理制度库，P1 执行库管生命周期，P2+ 执行在线起草和发布审批
    -   触发条件：制度编写者（UR-03）或制度管理员（UR-10）上传制度文件或发起制度管理操作
    -   预期结果：制度入库并可检索，版本可追溯，支撑合规追溯
    -   关联功能：F-05~F-12，F-21~F-22

+   **R-04 技术方案管理职责详情**：
    -   业务场景：租户需要制定技术安全方案（如操作系统基线、数据库基线）并关联技术控制点
    -   触发条件：方案制定者（UR-04）发起方案制定或导入操作
    -   预期结果：技术方案与配置基线建立，关联到租户技术控制（P2+），支撑技术落地链
    -   关联功能：F-13~F-15，F-18

+   **R-05 岗位责任映射职责详情**：
    -   业务场景：租户完成场景/控制映射后，需要将责任落实到具体岗位和人员
    -   触发条件：场景/控制映射激活后，安全架构师发起角色映射，系统自动生成责任点
    -   预期结果：责任点生成并关联到具体人员，实现"谁在什么场景下负责什么控制措施"的责任可视化
    -   关联功能：F-19、F-20

# 4 子领域划分

## 4.1 子领域划分总览

+   BC-35 租户落地按业务内聚性和数据内聚性，划分为 6 个子领域。划分遵循以下原则：
    -   **业务内聚**：同一子领域内的功能服务于同一业务目标
    -   **数据内聚**：同一子领域内的实体具有强关联关系
    -   **职责单一**：每个子领域有明确的职责边界，避免职责重叠
    -   **依赖清晰**：子领域间的依赖关系清晰，避免循环依赖

+   BC-35 子领域清单如下表所示

    | 子领域编号 | 子领域名称 | 英文缩写 | 核心关注问题 | 归属功能 | 文档编号 |
    | ---------- | ---------- | -------- | ------------ | -------- | -------- |

## 4.2 各子领域职责说明

### SD-01 资产管理子领域

+   **核心职责**：管理租户IT资产的完整登记、分类、场景关联及批量导入导出生命周期。

+   **核心实体**：
    -   租户资产（TenantAsset）：资产编号、资产名称、资产类型、所属租户、生命周期状态、创建时间、操作人
    -   资产分类（AssetCategory）：分类编号、分类名称、父分类ID、层级（支持多级分类树）
    -   资产场景关联（AssetSceneMapping）：资产ID、场景ID、关联类型（直接关联/间接关联）、关联状态

+   **核心能力**：
    -   P1：F-01 资产登记（手工录入/API对接）、F-02 资产分类管理、F-03 资产场景关联、F-04 资产批量导入导出（含导入前校验）

+   **数据存储方案**：
    -   MySQL（租户独立库）：存储资产主表（t_tenant_asset）、资产分类表（t_asset_category）、资产场景关联表（t_asset_scene_mapping）
    -   Redis：资产列表查询缓存（Key: `td:asset:list:{tenantId}:{queryHash}`），TTL 30分钟

+   **对外接口**：
    -   提供资产查询接口给 SD-02、SD-05（场景关联/方案关联时查询资产）
    -   提供租户资产数据给 BC-32 验证检查（OHS）
    -   依赖 BC-13 文件管理进行 Excel/CSV 导入导出

### SD-02 场景映射子领域

+   **核心职责**：建立并维护标准场景点到租户实际场景的映射关系，管理映射激活状态，支撑合规评估的场景数据来源。

+   **核心实体**：
    -   租户场景（TenantScene）：场景ID、场景名称、标准场景点ID、租户ID、定制内容、映射状态（DRAFT/ACTIVE/INACTIVE/ARCHIVED）
    -   场景映射关系（SceneMapping）：标准场景点ID、租户场景ID、映射类型（DIRECT/CUSTOMIZED/MERGED/SPLIT/DISABLED）、映射状态

+   **核心能力**：
    -   P2：F-16 标准场景点到租户场景的映射管理（创建/激活/停用/定制）

+   **数据存储方案**：
    -   MySQL（租户独立库）：存储租户场景表（t_tenant_scene）、场景映射关系表（t_scene_mapping）
    -   Redis：场景映射关系缓存（Key: `td:scene:mapping:{tenantId}`），高频查询低频变更，TTL 1小时

+   **对外接口**：
    -   依赖 BC-40 知识实体获取标准场景点数据（OHS+ACL）
    -   提供租户场景数据给 BC-31 合规管理、BC-32 验证检查（OHS）

### SD-03 控制映射子领域

+   **核心职责**：建立并维护标准控制点（管理控制+技术控制）到租户控制的映射关系，管理映射激活状态，区分管理控制和技术控制。

+   **核心实体**：
    -   租户控制（TenantControl）：控制ID、控制名称、控制类型（MANAGEMENT/TECHNICAL）、标准控制点ID、租户ID、定制内容、映射状态（DRAFT/ACTIVE/INACTIVE/ARCHIVED）
    -   控制映射关系（ControlMapping）：标准控制点ID、租户控制ID、映射类型、映射状态

+   **核心能力**：
    -   P2：F-17 标准控制点到租户控制的映射管理（含管理控制/技术控制分类，激活/停用/定制）
    -   P2：F-18 技术方案与租户技术控制的关联管理

+   **数据存储方案**：
    -   MySQL（租户独立库）：存储租户控制表（t_tenant_control）、控制映射关系表（t_control_mapping）
    -   Redis：控制映射关系缓存（Key: `td:control:mapping:{tenantId}`），TTL 1小时

+   **对外接口**：
    -   依赖 BC-40 知识实体获取标准控制点数据（OHS+ACL）
    -   提供租户控制数据给 BC-31 合规管理、BC-32 验证检查（OHS）
    -   提供管理控制清单给 SD-04（制度与控制关联，P2+）
    -   提供技术控制清单给 SD-05（技术方案关联）

### SD-04 制度管理子领域

+   **核心职责**：管理租户制度在库中的两个生命周期——P1 库管生命周期（导入、入库、版本替换、作废、检索）；P2+ 运营生命周期（在线起草、审批、发布）。P1 以库管生命周期为主，运营生命周期在 P2+ 阶段实现。

+   **核心实体**：
    -   导入任务（PolicyImportTask）：聚合根，封装制度文件导入的完整过程，含文件信息及7态状态机（CREATED/CONVERTING/PENDING_CONFIRM/IMPORTING/COMPLETED/FAILED/CANCELLED）
    -   制度库条目（TenantPolicy）：聚合根，制度ID、名称、分类、当前版本号、状态（DRAFT/ACTIVE/DEPRECATED/DELETED）、归属部门（owner_dept_id）、入库时间、租户ID
    -   制度章节（PolicyChapter）：TenantPolicy 聚合内实体，章节编号、标题、层级（1-5层）、内容（仅存 ES）、排序号
    -   制度附件（PolicyAttachment）：TenantPolicy 聚合内值对象，附件文件引用信息

+   **核心能力**：
    -   P1 库管生命周期：F-05 制度文件导入（含异步格式转换和确认入库）、F-06 制度清单管理（多维度筛选）、F-07 全文检索（章节级）、F-08 制度阅读、F-09 制度替换、F-10 制度作废、F-11 制度永久删除（DRAFT）、F-12 退回待确认
    -   P2+ 运营生命周期：F-21 制度在线起草、F-22 发布审批

+   **数据存储方案**：
    -   MySQL（租户独立库）：存储导入任务表（t_policy_import_task）、制度主表（t_tenant_policy）、制度附件表（t_policy_attachment）
    -   Elasticsearch（租户独立索引）：idx_policy_chapter_{tenant_id}（制度章节内容，仅写 ES 不写 MySQL）、idx_tenant_policy_{tenant_id}（制度列表辅助索引）
    -   Redis：导入任务状态缓存、制度列表查询缓存、单租户并发解析限制信号量（最大3个并发）

+   **对外接口**：
    -   提供制度库数据给 BC-31 合规管理（OHS）：PolicyImportedEvent/PolicyDeprecatedEvent 异步事件 + 同步查询接口
    -   依赖 BC-13 文件管理进行制度文件上传下载

### SD-05 技术方案管理子领域

+   **核心职责**：管理技术安全方案的制定、导入和配置基线，建立技术方案与技术控制的关联（P2 实现），支撑技术落地链（L4）。

+   **核心实体**：
    -   技术方案（TechnicalSolution）：方案ID、方案名称、方案内容、方案类型（操作系统/数据库/网络等）、租户ID、状态（DRAFT/ACTIVE）
    -   方案基线（SolutionBaseline）：基线ID、基线名称、配置项列表（JSON）、适用资产类型
    -   方案模板（SolutionTemplate）：从 BC-40 获取的只读数据（不存本地），技术类型、模板内容

+   **核心能力**：
    -   P1：F-13 技术方案制定（基于模板或手工，含格式校验）、F-14 基线配置管理（关联租户资产）、F-15 技术方案文件导入（Excel/JSON）
    -   P2：F-18 技术方案与租户技术控制关联

+   **数据存储方案**：
    -   MySQL（租户独立库）：存储技术方案表（t_technical_solution）、方案基线表（t_solution_baseline）
    -   Redis：方案列表查询缓存（Key: `td:solution:list:{tenantId}`）

+   **对外接口**：
    -   依赖 BC-40 知识实体获取技术方案模板数据（OHS+ACL）
    -   依赖 SD-01 获取租户资产清单（方案关联资产时）
    -   依赖 SD-03 获取租户技术控制清单（P2，方案关联控制时）
    -   提供技术方案数据给 BC-32 验证检查（OHS）
    -   依赖 BC-13 文件管理进行文件上传下载

### SD-06 责任映射子领域

+   **核心职责**：建立标准角色点到租户岗位/人员的映射，基于 BC-41 责任分配基准图和已激活的控制/场景映射，自动生成责任点，实现责任到人。

+   **核心实体**：
    -   岗位角色映射（RoleMapping）：标准角色点ID、租户岗位ID（来自 BC-10）、租户人员ID、映射类型、映射状态（DRAFT/ACTIVE）
    -   责任点（ResponsibilityPoint）：责任点ID、控制ID、场景ID、角色ID、RACISV角色类型、分配人员ID、责任点状态

+   **核心能力**：
    -   P3：F-19 岗位角色映射（标准角色点→租户岗位/人员）、F-20 责任点自动生成

+   **数据存储方案**：
    -   MySQL（租户独立库）：存储岗位角色映射表（t_role_mapping）、责任点表（t_responsibility_point）
    -   Redis：责任点查询缓存（Key: `td:responsibility:point:{tenantId}`），TTL 1小时

+   **对外接口**：
    -   依赖 BC-41 知识图谱获取责任分配基准图数据（OHS+ACL）
    -   依赖 BC-10 用户管理获取租户组织架构/岗位/人员数据（OHS+ACL）
    -   提供责任点数据给 BC-32 验证检查（OHS）

+   BC-35 协作设计决策汇总

    | 决策编号 | 协作关系 | 映射模式 | 调用方式 | 决策原因 | 风险与缓解 |

    | CTX-002 | BC-35 → BC-40 | OHS+ACL | Feign 同步 | 知识节点数据通过 OHS 标准接口获取；ACL 防止 BC-35 与知识实体领域模型强耦合 | 超时熔断：降级返回 Redis 缓存节点数据（TTL 5分钟） |
    | CTX-003 | BC-35 → BC-41 | OHS+ACL | Feign 同步 | 责任分配图仅在责任点生成时需要，调用频率低，同步调用足够 | 不可用时责任点生成任务标记为 PENDING，支持重试 |
    | CTX-004 | BC-35 → BC-10 | OHS+ACL | Feign 同步 | 组织架构数据需实时获取以确保角色映射准确；OHS 接口已标准化 | 超时熔断：降级返回缓存的组织架构（TTL 10分钟） |
    | CTX-005 | BC-31 → BC-35 | OHS | Feign同步+领域事件 | BC-31 合规评估需要实时场景/控制数据（同步）；制度状态变更用事件及时通知 BC-31 | 事件丢失：Kafka At-least-once + eventId 幂等消费；Feign 超时配置 3s |
    | CTX-006 | BC-32 → BC-35 | OHS | Feign 同步 | 证据采集需要实时资产/控制/责任点数据，同步接口满足及时性要求 | BC-32 应设置 3s 超时+熔断；BC-35 查询接口走缓存 |
    | CTX-007 | BC-36 → BC-35 | OHS | Feign 同步 | 安全策略数据变更频率低，同步查询满足需求 | BC-36 可缓存策略数据降低请求频率 |

+   **CTX-002 协作设计决策详情（BC-40 知识实体，代表性案例）**：
    -   协作场景：BC-35 在执行场景映射/控制映射/角色映射时，需查询 BC-40 的标准节点数据作为映射源；节点数据变更（新增/停用标准节点）时，BC-35 的映射候选集需同步更新
    -   模式选择原因：BC-40 以 OHS 暴露6库数据查询接口，接口稳定且有版本管理；BC-35 通过 infrastructure 层 ACL 适配器隔离 BC-40 的领域模型，将知识实体 DTO 转换为 BC-35 的 StandardNodeVO，防止上游领域模型变更影响 BC-35 领域层
    -   调用方式选择原因：节点数据查询为只读操作，Feign 同步调用足够；变更频率低，配合 Redis 缓存（TTL 5分钟）可大幅降低高频调用
    -   风险与缓解策略：①接口超时（P99 > 500ms）→ Feign 超时 3s + Resilience4j 熔断，降级返回缓存数据；②节点数据不一致（BC-40 更新但缓存未刷新）→ BC-40 发布知识更新事件，BC-35 订阅后主动清除对应 Redis 缓存

## 7.1 数据隔离架构

+   BC-35 采用 Database per Tenant 物理库隔离方案，数据隔离策略如下表所示

# 8 安全与权限设计

## 8.1 认证方案

+   BC-35 采用以下认证方案：
    -   **认证方式**：JWT（JSON Web Token）。用户登录后由统一认证服务签发 JWT，BC-35 接口层通过 Spring Security + JWT Filter 验证 Token 有效性和签名
    -   **Token 管理策略**：Access Token 有效期 2小时；Refresh Token 有效期 7天；BC-35 本身不签发 Token，Token 刷新由认证服务处理
    -   **内部服务间认证**：Feign 调用其他 BC 时，在请求头中透传当前用户 JWT（Gateway 注入或 Feign Interceptor 传递，AS-05）
    -   **用户群差异化认证**：BC-35 仅服务租户侧用户，无多个独立用户群，不涉及差异化认证路径

## 8.6 前端权限控制策略

+   **路由权限**：前端应用（Vue 3）在 Router beforeEach 守卫中检查当前用户权限列表，无权限时重定向至 403 页面。路由定义中通过 meta.permissions 数组声明所需权限码，满足任一权限即可访问（OR 逻辑）。

+   **按钮权限**：使用 `v-permission` 自定义指令控制按钮级权限（如"导入制度""作废制度"等操作按钮）。v-permission 指令接收权限码或权限码数组，在指令绑定时检查用户权限列表，无权限时通过 v-if 逻辑移除 DOM（而非禁用，防止绕过）。

+   **权限数据来源**：用户登录成功后，后端（BC-10 或统一认证服务）返回用户在当前租户下的权限码列表（`permissions: string[]`）。前端将权限列表存储在 Pinia Store（`usePermissionStore`），路由守卫和 v-permission 指令均从 Store 读取。

+   安全策略覆盖范围

    | 安全领域 | 规范内容 |

    | 敏感数据加密 | 制度章节内容（ES存储）应用字段级加密（AS-03，算法待安全策略确认）；密码类字段禁止明文（bcrypt）；API 响应中手机号/邮箱执行脱敏（中间位替换为 *） |

## 9.4 链路追踪

+   BC-35 链路追踪策略：
    -   **追踪框架**：OpenTelemetry（遵循系统基线，AS-09）
    -   **Span 命名规范**：`{layer}.{operation}`；示例：`api.importPolicy`（接口层）、`app.confirmPolicyImport`（应用层）、`repo.findTenantPolicyById`（仓储层）、`acl.getStandardNodes`（ACL 层）
    -   **采样策略**：默认按比例采样（10%）；错误请求和慢请求（响应时间 > 对应 P99 目标值）强制采样（100%）
    -   **跨服务传播**：traceId/spanId 通过 HTTP Header（W3C TraceContext 标准：`traceparent` header）在 Feign 调用中自动传播；Kafka 消息通过自定义消息头（`X-Trace-Id`）传播

+   **天帷通用术语**（引用 C99 术语规范，不重复定义）：
    -   租户、合规包、场景点、控制点、角色点、标准节点、知识中台、供给侧域、技术落地链（L4）

+   **文档专有术语**：
    -   **租户落地**：将知识中台的标准化合规知识（场景点/控制点/角色点）映射到租户的实际业务环境的过程，是 BC-35 的核心定位
    -   **租户资产**（TenantAsset）：租户已登记在册的 IT 资产，包括服务器/数据库/应用系统等，是合规场景化的基础数据
    -   **租户场景**（TenantScene）：由标准场景点映射而来的租户实际业务场景，处于 BC-35 SD-02 管辖范围
    -   **租户控制**（TenantControl）：由标准控制点映射而来的租户实际控制措施（含管理控制和技术控制）
    -   **租户制度**（TenantPolicy）：租户内部管理制度，在 P2+ 阶段与租户控制建立关联
    -   **责任点**（ResponsibilityPoint）：控制点/场景点/角色点的组合，明确"谁在什么场景下负责什么控制措施"
    -   **导入任务**（PolicyImportTask）：封装制度文件导入完整过程的聚合根，含7态状态机（CREATED→CONVERTING→PENDING_CONFIRM→IMPORTING→COMPLETED）
    -   **库管生命周期（P1）**：制度在租户制度库中以"导入→入库→替换/作废"为主线的管理周期，不要求关联控制点
    -   **运营生命周期（P2+）**：制度从在线起草→审批→发布的完整运营过程，制度需关联控制点
    -   **owner_dept_id**：制度归属部门ID，用于支撑制度管理员（data_scope=2）的部门级数据权限过滤
    -   **data_scope**：数据权限范围枚举，定义于 BC-10 用户管理，取值 1-5，控制用户在租户内部可见的数据范围
    -   **1+N文档体系**：BC总体设计是"骨架"（1），各子领域详细设计（07-BC详细设计-BC35-SDxx）是"血肉"（N）
    -   **Database per Tenant**：每个租户拥有独立数据库（clarisphere_{tenant_code}）的多租户物理隔离方案，是 BC-35 的核心数据架构
