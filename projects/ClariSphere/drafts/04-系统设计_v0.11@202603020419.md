## 2.7 领域划分与BC清单（承接阶段3缺失内容）

+   由于阶段3领域设计文档缺失（假设 AS-01、AS-02），本节基于 DDD 方法论自行定义领域划分和 BC 清单，作为系统设计的基础。

### 2.7.1 领域划分

+   **核心域**（Core Domain）：承载核心竞争力，最高优先级
    -   **知识工程域**：管理8库6图1包核心数据资产，提供知识查询、图谱遍历、版本管理服务
    -   **合规管理域**：实现从外规要求到控制措施的映射落地，管理合规评估与差距分析
    -   **验证检查域**：管理证据采集、自动化验证、持续监测，实现控制点的技术验证

+   **支撑域**（Supporting Domain）：支撑核心业务，中等优先级
    -   **治理监督域**：支撑 CISO、风险经理等决策者的战略监控、绩效汇报、审计监督
    -   **风险管理域**：支撑风险识别、风险评估、风险应对的全流程管理
    -   **安全管理域**：支撑安全策略制定、安全事件管理、安全运营监控、应急响应
    -   **内容生产域**：支撑供给侧的外规采集、解析映射、方案封装、质检发布
    -   **知识消费域**：支撑个人用户的知识检索、图谱浏览、模板下载、付费转化

+   **通用域**（Generic Domain）：通用能力，可外购或复用
    -   **用户管理域**：统一身份认证、用户管理、权限管理、组织架构、审计日志（IAM）
    -   **租户管理域**：租户生命周期管理，开通、配置、计费、数据源管理、AD/LDAP同步
    -   **消息通知域**：统一消息通知，支持站内信、邮件、短信、企业微信等多渠道推送
    -   **文件管理域**：统一文件管理，上传下载、版本控制、预览、病毒扫描
    -   **支付计费域**：统一支付管理，订阅计费与账单
    -   **系统运维域**：任务调度、系统监控告警、数据备份恢复、数据字典管理

## 3.5 API网关设计

+   API网关职责：统一入口、身份认证、租户路由、限流熔断、协议转换、安全审计
+   路由规则规范：
    -   供给侧：`/api/provider/**` → 供给侧BFF
    -   消费侧A：`/api/tenant/**` → 消费侧A BFF（需租户上下文）
    -   消费侧B：`/api/consumer/**` → 消费侧B BFF（需用户认证）
    -   通用服务：`/api/common/**` → 通用服务直连
+   限流熔断策略：
    -   全局限流：10000 QPS
    -   租户级限流：单租户 1000 QPS
    -   用户级限流：单用户 100 QPS
    -   熔断阈值：错误率 > 50% 或 P99延迟 > 3s 触发熔断

### 8.1.3 动态数据源路由

+   消费侧A采用动态数据源路由实现Schema级隔离：

```java
// 租户上下文
public class TenantContext {
    private static final ThreadLocal<String> TENANT_CODE = new ThreadLocal<>();
    
    public static void setTenantCode(String tenantCode) {
        TENANT_CODE.set(tenantCode);
    }
    
    public static String getTenantCode() {
        return TENANT_CODE.get();
    }
    
    public static void clear() {
        TENANT_CODE.remove();
    }
}

// 动态数据源路由
public class TenantDataSourceRouter extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        String tenantCode = TenantContext.getTenantCode();
        return tenantCode != null ? "tenant_" + tenantCode : "default";
    }
}
```

# 附录B 架构决策记录（ADR）

## ADR-001 采用微服务架构

+   **状态**：已接受
+   **日期**：2026-01-31
+   **决策者**：架构团队

### 背景

ClariSphere 需要支持多租户、高并发、快速迭代的业务需求，需要选择合适的架构风格。

### 决策

采用微服务架构，按照 BC 划分微服务，每个 BC 对应一个微服务。

### 理由

+   **支持独立部署**：各 BC 可独立部署，互不影响
+   **支持独立扩展**：各 BC 可根据负载独立扩展
+   **支持技术异构**：各 BC 可选择最适合的技术栈
+   **支持团队自治**：各 BC 可由独立团队负责

### 后果

+   **正面影响**：
    -   提高系统可扩展性和可维护性
    -   支持快速迭代和持续交付
    -   降低单点故障风险
+   **负面影响**：
    -   增加分布式系统复杂度（事务、一致性、追踪）
    -   增加运维成本（监控、部署、故障排查）
    -   需要处理服务间通信开销

### 缓解措施

+   采用 Saga 模式处理分布式事务
+   采用事件驱动架构实现最终一致性
+   采用 SkyWalking 实现分布式链路追踪
+   采用 K8s 简化部署和运维

## ADR-002 知识中台采用 CQRS 模式

+   **状态**：已接受
+   **日期**：2026-01-31
+   **决策者**：架构团队

### 背景

知识中台（BC-40/41）需要支持高频查询和复杂图谱遍历，同时保证写入性能。

### 决策

知识中台采用 CQRS 模式，读写分离：
+   **写模型**：BC-40 知识实体（MySQL + ES）
+   **读模型**：BC-41 知识图谱（Neo4j）

### 理由

+   **优化查询性能**：Neo4j 专为图查询优化，支持高性能图谱遍历
+   **优化写入性能**：MySQL + ES 支持高并发写入
+   **分离关注点**：写模型关注数据完整性，读模型关注查询性能

### 后果

+   **正面影响**：
    -   查询性能提升 10 倍以上
    -   写入性能不受查询影响
    -   支持独立扩展读写能力
+   **负面影响**：
    -   读写模型需要同步，存在延迟
    -   增加系统复杂度
    -   需要处理数据一致性

### 缓解措施

+   采用共享内核模式（SK），BC-40/41 共享节点 ID
+   采用事件驱动同步，保证最终一致性
+   读写延迟控制在 3 秒以内

## ADR-003 消费侧A采用 Schema 级租户隔离

+   **状态**：已接受
+   **日期**：2026-01-31
+   **决策者**：架构团队

### 背景

消费侧A（BC-31~36）需要支持 100+ 企业租户，需要选择合适的租户隔离方案。

### 决策

采用 Schema 级租户隔离，每个租户独立 Schema，共享数据库实例。

### 理由

+   **隔离级别高**：Schema 级隔离，租户间数据零泄漏
+   **成本可控**：共享数据库实例，成本低于独立数据库
+   **扩展性好**：支持 1000+ 租户
+   **运维友好**：统一数据库实例，运维成本低

### 后果

+   **正面影响**：
    -   满足企业租户的数据隔离要求
    -   成本低于独立数据库方案
    -   支持租户独立升级
+   **负面影响**：
    -   Schema 变更需要全租户同步
    -   单库容量有上限（1000+ 租户）
    -   需要动态数据源路由

### 缓解措施

+   采用 Flyway 统一管理 Schema 变更
+   采用动态数据源路由实现租户隔离
+   预留分库分表能力（P4）

## ADR-004 禁止使用 2PC/XA 分布式事务

+   **状态**：已接受
+   **日期**：2026-01-31
+   **决策者**：架构团队

### 背景

微服务架构下需要处理跨 BC 的分布式事务。

### 决策

禁止使用 2PC/XA 分布式事务，采用 Saga 模式和事件驱动架构保证最终一致性。

### 理由

+   **性能问题**：2PC 需要全局锁，性能差
+   **可用性问题**：2PC 需要协调者，存在单点故障
+   **扩展性问题**：2PC 不适合大规模分布式系统

### 后果

+   **正面影响**：
    -   提高系统性能和可用性
    -   支持大规模分布式系统
+   **负面影响**：
    -   需要处理最终一致性
    -   需要设计补偿机制
    -   增加业务复杂度

### 缓解措施

+   采用 Saga 模式，每步定义补偿操作
+   采用事件溯源，保证完整审计轨迹
+   采用幂等性设计，支持重试
