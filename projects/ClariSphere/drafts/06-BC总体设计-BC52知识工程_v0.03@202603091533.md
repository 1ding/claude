### 2.2.2 上下文价值定位

+   **核心价值**：将外规原文转化为结构化、可落地的合规知识资产
+   **业务目标**：
    -   将依赖专家经验、耗时2-3周的外规解析系统化为AI辅助+人工确认的标准化流程
    -   将碎片化的控制架构知识沉淀为可复用的结构化资产（场景点、控制点、验证规则、责任点）
    -   将人工拼凑的合规方案升级为模板化、可审视的标准化合规包封装
+   **服务对象**：UP02控制架构师、UP03外规解析师、UP04方案设计师；下游BC-31合规管理、BC-32验证检查、BC-33治理监督、BC-11租户管理
+   **核心能力**：
    -   外规解析与要求点提取（AI辅助+人工确认）
    -   T/M/G三空间场景架构维护
    -   控制点架构维护（含方案设计与方法论框架审视）
    -   责任点动态批量生成（控制点×场景点×RACISV）
    -   合规包标准化封装与发布

## 4.2 各子领域职责说明

### SD01 场景管理

+   **核心职责**：管理T/M/G三空间场景树的创建、维护和版本管理，为控制点和责任点提供场景定位基础
+   **核心实体**：
    -   ScenarioPoint（场景点）：code、name、spaceType(T/M/G)、parentId、levelPath、version、status
+   **核心能力**：
    -   P1：场景点CRUD、场景树层级调整、关键字检索、版本管理
    -   P2+：场景模板库、跨行业场景预置
+   **数据存储方案**：MySQL（场景点表、场景版本表）；Redis（场景树缓存）
+   **对外接口**：
    -   提供场景点查询接口供SD-06映射管理和SD-03责任管理调用
    -   无跨BC接口（场景点数据不直接对外暴露）

### SD02 控制管理

+   **核心职责**：管理控制点的创建与方法论属性配置、方案组合设计、验证规则定义，沉淀控制架构知识资产
+   **核心实体**：
    -   ControlPoint（控制点）：code、name、spaceType(T/M/G)、timing、mechanism、degree、version、status
    -   Solution（方案）：name、targetDesc、controlPointIds[]、coverageSummary
    -   VerificationRule（验证规则）：name、ruleType(AUTO/MANUAL)、frequency、expectedResult、controlPointIds[]
+   **核心能力**：
    -   P1：控制点CRUD与属性配置、方案组合与覆盖度对比、验证规则配置、版本管理
    -   P2+：控制点模板库、行业控制架构预置
+   **数据存储方案**：MySQL（控制点表、方案表、验证规则表）；ES（控制点全文检索）；Redis（热点控制点缓存）
+   **对外接口**：
    -   提供控制点查询API供BC-31合规管理调用（OHS+PL）
    -   提供验证规则查询API供BC-32验证检查调用（OHS+PL）
    -   提供控制点数据供SD-06映射管理和SD-03责任管理调用

### SD03 责任管理

+   **核心职责**：管理RACISV配置参数和责任点批量生成引擎，自动化职责分配
+   **核心实体**：
    -   ResponsibilityPoint（责任点）：controlPointId、scenarioPointId、racisvType(R/A/C/I/S/V)、status
    -   GenerationConfig（生成配置）：controlPointScope、scenarioPointScope、racisvRoles[]、estimatedCount
+   **核心能力**：
    -   P1：RACISV配置、全量/增量批量生成（75000条<30分钟）、多维度筛选查询
    -   P2+：生成规则模板化、生成结果统计分析
+   **数据存储方案**：MySQL（责任点表、生成配置表、生成日志表）；Redis（分布式锁、生成进度缓存）
+   **对外接口**：
    -   发布DE-05事件（责任点已批量生成）通知BC-33治理监督
    -   提供责任点查询接口供BC-31调用

### SD04 要求管理

+   **核心职责**：管理外规条文两步拆解（识别要求→定位场景）、归一化去重和要求点全生命周期
+   **核心实体**：
    -   RequirementPoint（要求点）：code、regulationClauseRef、nature(TARGET/MEASURE)、objective、sceneLocation、version、status
+   **核心能力**：
    -   P1：两步法条文拆解、归一化（主键：资源/活动+资源状态+要求目标）、元数据标注、废止管理
    -   P2+：跨外规要求点关联分析
+   **数据存储方案**：MySQL（要求点表、归一化日志表）；ES（要求点全文检索）
+   **对外接口**：
    -   发布DE-03事件（要求点已提取）
    -   提供要求点查询API供BC-31合规管理调用（OHS+PL）
    -   提供要求点数据供SD-06映射管理调用

### SD05 外规解析

+   **核心职责**：管理事件驱动的解析任务创建与调度、AI辅助解析和人工审核流程
+   **核心实体**：
    -   ParseTask（解析任务）：regulationId、status(PENDING/PARSING/CONFIRMING/COMPLETED)、progress、assigneeId
+   **核心能力**：
    -   P1：DE-01事件驱动任务创建、AI辅助拆解、人工审核、进度追踪
    -   P2+：AI准确率提升、解析效率优化
+   **数据存储方案**：MySQL（解析任务表、AI解析结果表）；Redis（事件幂等去重）
+   **对外接口**：
    -   入站：消费DE-01（外规已采集）和DE-15（外规已更新）事件
    -   出站：解析产出的条文数据传递给SD-04进行拆解

### SD06 映射管理

+   **核心职责**：管理要求点与控制点、场景点之间的映射关系建立，提供方法论框架覆盖度审视和完整性分析
+   **核心实体**：
    -   MappingRelation（映射关系）：requirementPointId、controlPointId、scenarioPointId、confidence、confirmStatus、confirmedBy
+   **核心能力**：
    -   P1：AI推荐映射、人工确认调整、时机/机制/程度三视角覆盖度审视、完整性报告
    -   P2+：映射规则学习优化
+   **数据存储方案**：MySQL（映射关系表、覆盖度快照表）
+   **对外接口**：
    -   提供映射关系数据供SD-07合规包管理调用
    -   UP02和UP03双角色协作入口

### SD07 合规包

+   **核心职责**：管理合规包的设计封装、内容配置、依赖检查、审核发布和下架的全生命周期
+   **核心实体**：
    -   CompliancePack（合规包）：name、industryTags[]、applicableRegIds[]、status(DRAFT/REVIEWING/PUBLISHED/RETIRED)、version
    -   PackItem（合规包条目）：packId、requirementPointRef、controlPointRef、scenarioPointRef、templateRef
+   **核心能力**：
    -   P1：草稿创建、内容配置、依赖检查、审核提交、发布（触发DE-06）、下架（触发DE-16）
    -   P2+：合规包模板化、跨行业合规包
+   **数据存储方案**：MySQL（合规包表、合规包条目表、合规包版本表）
+   **对外接口**：
    -   出站：发布DE-06事件（合规包已发布）通知BC-11租户管理
    -   出站：发布DE-16事件（合规包已下架）通知BC-11和BC-35

### SD08 目标管理

+   **核心职责**：管理基础目标受控词表和具体目标的全生命周期，为 SD04 要求管理和 SD02 控制管理提供目标分类基础
+   **核心实体**：
    -   BasicObjective（基础目标）：code、name、category(CIA/EXTENDED/MANAGEMENT/GOVERNANCE)、definition、status(ACTIVE/DEPRECATED)
    -   ContextualObjective（具体目标）：code、basicObjectiveId、sceneSpace(T/M/G)、resourceType、specificMeaning、typicalMetrics、status(DRAFT/PUBLISHED/DEPRECATED)、createdBy
+   **核心能力**：
    -   P1：基础目标受控词表维护（预置+扩展）、具体目标创建与发布、具体目标搜索（按 basicObjective+sceneSpace+resourceType）、目标缺口接收与处理
    -   P2+：目标覆盖度分析、目标词表版本管理
+   **数据存储方案**：MySQL（基础目标表、具体目标表、缺口申请表）；Redis（基础目标词表缓存）
+   **设计决策**：resourceType 为 SD08 自维护枚举，对照 SD01 场景树设计但不强依赖（方案B）；SD01 场景树变更不触发 SD08 级联更新
+   **对外接口**：
    -   提供具体目标搜索接口供 SD04 要求管理调用（拆解时匹配目标）
    -   提供具体目标查询接口供 SD02 控制管理调用（控制点关联目标）
    -   提供具体目标查询接口供 SD06 映射管理调用（按目标维度审视覆盖度）
    -   接收 SD04 发起的目标缺口申请（内部调用）

## 5.4 协作设计决策

+   协作设计决策如下表所示

    | 决策编号 | 协作关系    | 映射模式          | 调用方式    | 决策原因                            | 风险与缓解                  |
    | -------- | ----------- | ----------------- | ----------- | ----------------------------------- | --------------------------- |
    | CTX-001  | BC-51→BC-52 | Customer-Supplier | 异步事件    | 采集与解析解耦，允许延迟            | 事件丢失：事件重试+死信队列 |
    | CTX-002  | BC-52→BC-31 | OHS+PL            | 同步查询API | 合规管理需实时获取最新要求点/控制点 | 超时：熔断降级+缓存兜底     |
    | CTX-003  | BC-52→BC-32 | OHS+PL            | 同步查询API | 验证检查需实时获取验证规则定义      | 超时：熔断降级+缓存兜底     |
    | CTX-004  | BC-52→BC-33 | Customer-Supplier | 异步事件    | 责任点生成与督办初始化解耦          | 事件丢失：事件重试+死信队列 |
    | CTX-005  | BC-52→BC-11 | Customer-Supplier | 异步事件    | 合规包发布与租户推送解耦            | 推送失败：Saga补偿+人工介入 |
    | CTX-006  | BC-52→BC-53 | Customer-Supplier | 异步事件    | 质量回馈与生产流程解耦              | 事件丢失：事件重试          |

    +   表 协作设计决策

+   **CTX-001 BC-51→BC-52**
    -   协作场景：BC-51外规采集完成后，BC-52自动创建解析任务
    -   模式选择原因：采集和解析是独立流程，无需同步等待
    -   调用方式选择原因：异步事件允许采集侧快速响应，解析侧按能力消费
    -   风险与缓解：事件丢失导致解析任务未创建——RocketMQ事务消息保证投递，消费端幂等处理

+   **CTX-002 BC-52→BC-31**
    -   协作场景：合规管理实时查询要求点和控制点内容用于差距分析
    -   模式选择原因：OHS+PL提供标准化API，下游通过发布语言解耦
    -   调用方式选择原因：差距分析需要实时最新数据，不允许延迟
    -   风险与缓解：BC-52不可用导致查询失败——Sentinel熔断+Redis缓存兜底（缓存有效期30分钟）

+   **CTX-005 BC-52→BC-11**
    -   协作场景：合规包发布后触发租户订阅推送
    -   模式选择原因：发布与推送是独立事务，跨4个BC的长链路
    -   调用方式选择原因：异步事件解耦，推送失败不影响发布
    -   风险与缓解：推送链路中断——Saga编排，BC-11接收DE-06后触发推送流程，失败时补偿重试

# 附录A（资料性）术语表

+   **业界通用术语**：BC（Bounded Context，限界上下文）、DDD（Domain-Driven Design，领域驱动设计）、ACL（Anti-Corruption Layer，防腐层）、OHS（Open Host Service，开放主机服务）、Feature、User Story、CQRS
+   **天帷通用术语**（引用C99）：控制点、场景点、责任点、合规包、RACISV、6链、五重映射、要求点、验证规则、七层级编码
+   **文档专有术语**：
    -   知识生产链路：BC-52核心业务流程，从外规条文输入到合规包输出的完整链路（SD-05→SD-04→SD-06→SD-07），架构侧（SD-01/SD-02→SD-03）提供支撑，SD-08提供目标分类基础
    -   两步拆解法：要求管理中将条文拆解为结构化要求的方法——第一步识别要求(What，性质+目标)，第二步定位场景(空间+资源+状态)，两步不可颠倒
    -   归一化主键：要求归一化的判定依据——"资源/活动+资源状态+要求目标"三者相同的条文归为同一要求
    -   What/How边界：要求与方案的分界——说"做到什么"是要求(What)，说"怎么做到"是方案(How)
    -   方法论框架：时机×机制×程度三个维度的分析工具，用于审视方案对要求的覆盖充分性
    -   T/M/G场景空间：场景点的三类空间——T(技术场景，管技术资源)、M(管理场景，管管理活动)、G(治理场景，管治理活动)
    -   基础目标：与场景无关的抽象安全目标概念，来自受控词表（CIA三性/扩展属性/管理目标/治理目标），全局唯一，由SD08维护
    -   具体目标：基础目标在特定场景空间+资源类型下的实例化定义，明确业务含义和典型度量指标；同一基础目标在不同资源类型下有不同的具体目标（如"可用性"在信息系统下为服务SLA，在数据场景下为数据可检索访问率）
    -   目标缺口：SD04拆解要求点时，SD08中无对应具体目标的情况；拆解师提交缺口申请，触发SD08补充流程，补充发布后回填要求点
