## 2.3 业务价值

+   **解决的核心问题**：
    -   知识中台的标准化知识（场景点、控制点、角色点）如何落地到租户的实际环境
    -   租户的IT资产、组织架构、制度体系如何与标准知识建立映射关系
    -   如何实现"要求→落实→责任到人"的完整追溯链

+   **业务价值**：
    -   **管理透明化**：租户的资产、场景、控制、制度、责任全部可视化
    -   **双向追溯**：标准知识→租户实例的正向映射，租户实例→标准知识的反向溯源
    -   **责任到人**：通过岗位角色映射，实现责任点到具体人员的精确定位
    -   **快速落地**：基于标准模板和最佳实践，快速完成租户环境的合规配置

## 2.4 范围边界

+   **范围内**：
    -   租户资产管理（IT资产登记、分类、场景关联）
    -   租户场景映射（标准场景点→租户场景的映射与定制）
    -   租户控制映射（标准控制点→租户控制的映射与定制）
    -   租户制度管理（制度入库、发布审批、版本管理、制度与控制点关联）
    -   岗位角色映射（标准角色点→租户岗位/人员的映射）
    -   安全策略基础配置（策略模板、策略与制度关联）

+   **范围外**：
    -   知识中台数据管理（由 BC-40 知识实体、BC-41 知识图谱负责）
    -   合规评估与差距分析（由 BC-31 合规管理负责）
    -   证据采集与技术验证（由 BC-32 验证检查负责）
    -   安全策略运营执行（由 BC-36 安全管理负责）

# 3 子领域划分方案

## 3.1 子领域划分概述

+   BC-35 租户落地按照业务能力和数据内聚性，划分为 6 个子领域
+   子领域划分遵循以下原则：
    -   **业务内聚**：同一子领域内的功能服务于同一业务目标
    -   **数据内聚**：同一子领域内的实体具有强关联关系
    -   **职责单一**：每个子领域有明确的职责边界，避免职责重叠
    -   **依赖清晰**：子领域间的依赖关系清晰，避免循环依赖

+   BC-35 子领域划分如下表所示

    | 子领域编号 | 子领域名称   | 核心职责                                       | 核心实体                     | 对应Epic    |
    | ---------- | ------------ | ---------------------------------------------- | ---------------------------- | ----------- |
    | SD-01      | 资产管理     | 租户IT资产登记、分类、场景关联、批量导入导出   | 租户资产、资产分类、资产场景 | EP-PL-01    |
    | SD-02      | 场景映射     | 标准场景点→租户场景的映射与定制                | 租户场景、场景映射关系       | EP-PL-01    |
    | SD-03      | 控制映射     | 标准控制点（管理+技术）→租户控制的映射与定制   | 租户控制、控制映射关系       | EP-PL-01    |
    | SD-04      | 制度管理     | 租户制度库生命周期管理（入库、清单、检索、展示、替换、作废）及发布审批 | 制度库条目、制度版本 | EP-BD-01/02 |
    | SD-05      | 技术方案管理 | 技术方案制定、导入、基线配置（技术控制实现）   | 技术方案、方案基线、方案模板 | EP-BD-03    |
    | SD-06      | 责任映射     | 标准角色点→租户岗位/人员的映射                 | 岗位角色映射、责任点         | EP-PL-01    |

    +   表 BC-35 子领域划分

## 3.2 SD-01 资产管理子领域

+   **核心职责**：租户IT资产登记、资产分类、资产与场景关联、批量导入导出

+   **核心实体**：
    -   租户资产（TenantAsset）：资产编号、资产名称、资产类型、所属租户、创建时间
    -   资产分类（AssetCategory）：分类编号、分类名称、父分类、层级
    -   资产场景关联（AssetSceneMapping）：资产ID、场景ID、关联类型

+   **核心能力**：
    -   资产登记：支持手工录入、批量导入、API对接等多种方式
    -   资产分类：按照行业标准（如ISO 27001资产分类）进行分类管理
    -   资产场景关联：将资产与租户场景建立关联，支撑场景化控制
    -   批量导入：支持从 Excel、CSV 批量导入租户资产数据
    -   批量导出：支持将租户资产导出为 Excel、CSV 格式
    -   导入校验：导入前校验数据格式、必填字段、资产编号唯一性

+   **对外接口**：
    -   提供资产查询接口给 SD-02 场景映射子领域
    -   提供资产数据给 BC-32 验证检查（用于证据采集）
    -   依赖 BC-13 文件管理进行文件上传下载

## 3.3 SD-02 场景映射子领域

+   **核心职责**：标准场景点→租户场景的映射与定制

+   **核心实体**：
    -   租户场景（TenantScene）：场景ID、场景名称、标准场景点ID、租户ID、定制内容
    -   场景映射关系（SceneMapping）：标准场景点ID、租户场景ID、映射类型、映射状态

+   **核心能力**：
    -   场景映射：将知识中台的标准场景点映射到租户的实际场景
    -   场景定制：支持租户对标准场景进行定制（增加属性、调整描述等）
    -   场景激活：租户可选择性激活需要的场景，未激活场景不参与合规评估

+   **对外接口**：
    -   依赖 BC-40 知识实体获取标准场景点数据
    -   提供租户场景数据给 BC-31 合规管理、BC-32 验证检查

## 3.4 SD-03 控制映射子领域

+   **核心职责**：标准控制点（管理+技术）→租户控制的映射与定制

+   **核心实体**：
    -   租户控制（TenantControl）：控制ID、控制名称、控制类型（管理/技术）、标准控制点ID、租户ID、定制内容
    -   控制映射关系（ControlMapping）：标准控制点ID、租户控制ID、映射类型、映射状态

+   **核心能力**：
    -   控制映射：将知识中台的标准控制点（管理控制+技术控制）映射到租户的实际控制措施
    -   控制定制：支持租户对标准控制进行定制（调整实施方式、补充说明等）
    -   控制分类：区分管理控制和技术控制，为后续实现提供依据
    -   控制激活：租户可选择性激活需要的控制，未激活控制不参与验证

+   **对外接口**：
    -   依赖 BC-40 知识实体获取标准控制点数据
    -   提供租户控制数据给 BC-31 合规管理、BC-32 验证检查
    -   提供管理控制清单给 SD-04 制度管理（制度关联）
    -   提供技术控制清单给 SD-05 技术方案管理（方案关联）

## 3.5 SD-04 制度管理子领域

+   **核心职责**：管理租户制度的两个生命周期，均由 SD-04 内部完成：
    -   **库管生命周期（P1）**：制度在租户制度库中的全过程管理——文件导入、格式转换、章节解析、确认入库、清单维护、检索展示、版本替换、作废归档、永久删除
    -   **运营生命周期（P2+）**：制度从起草、审批到正式发布的完整运营过程
    -   P1 仅实现库管生命周期；运营生命周期在 P2+ 阶段实现

+   **核心实体**：
    -   导入任务（PolicyImportTask）：聚合根，记录一次制度文件导入的完整过程，包含文件信息、解析状态（7 态状态机）和转换结果
    -   制度库条目（TenantPolicy）：聚合根，制度ID、制度名称、分类、当前版本号、状态（4 态：DRAFT/ACTIVE/DEPRECATED/DELETED）、归属部门（owner_dept_id）、入库时间、操作人、租户ID
    -   制度章节（PolicyChapter）：TenantPolicy 聚合内实体，章节编号、标题、层级（1-5 层）、内容、排序号
    -   制度附件（PolicyAttachment）：TenantPolicy 聚合内值对象，附件文件引用信息

+   **核心能力**（P1 · 库管生命周期）：
    -   制度导入：上传 Word/Excel 文件 → 异步格式转换（转 MD）→ MD 比对确认 → MD 转 JSON → 确认入库，全流程由导入任务聚合驱动
    -   制度清单：维护租户有效制度列表，支持按部门、状态、分类、版本筛选，支持多维度展示
    -   制度检索：基于 Elasticsearch 实现全文检索，支持章节级内容搜索
    -   制度阅读：查看制度详情、章节树结构及历史版本列表
    -   制度替换：手动发起新版本入库，旧版本自动归入版本历史
    -   制度作废：手动将制度标记为废止，移出有效清单，保留归档
    -   制度永久删除：仅对 DRAFT 状态制度可永久删除
    -   退回待确认：将已入库制度退回到 DRAFT 状态重新编辑

+   **核心能力**（P2+ · 运营生命周期）：
    -   制度起草：基于模板在线起草制度内容，保存为草稿
    -   发布审批：UR-10 制度管理员审批，通过后自动入库为有效版本
    -   制度修订：对已发布制度发起修订，经完整审批流程后替换原版本

+   **数据存储方案**：
    -   MySQL（租户独立库）：存储导入任务表（t_policy_import_task）、制度主表（t_tenant_policy）、制度附件表（t_policy_attachment）
    -   Elasticsearch（租户独立索引）：存储制度章节内容（idx_policy_chapter_{tenant_id}）和制度索引（idx_tenant_policy_{tenant_id}），制度章节内容仅写入 ES，不写入 MySQL
    -   Redis：导入任务状态缓存、制度列表查询缓存

+   **权限与数据权限**：
    -   功能权限：四段式权限码 `tenant:policy:{resource}:{action}`，通过 RBAC 控制
    -   数据权限：UR-10（制度管理员）data_scope = 2（本部门及以下），通过 owner_dept_id 过滤；UR-03（制度编写者）data_scope = 4（仅本人创建），通过 created_by 过滤；UR-02/UR-09 data_scope = 1（全部数据，只读）
    -   详见 §5.3 SD-04 权限与数据权限设计

+   **对外接口**：
    -   提供制度库数据给 BC-31 合规管理（制度追溯），通过 OHS 同步查询接口 + PolicyImportedEvent/PolicyDeprecatedEvent 异步事件
    -   依赖 BC-13 文件管理进行制度文件上传下载
    -   详细接口定义见《07-BC详细设计-BC35租户落地-SD04制度管理》第 6 章

## 3.6 SD-05 技术方案管理子领域

+   **核心职责**：技术方案制定、导入、基线配置（技术控制的实现）

+   **核心实体**：
    -   技术方案（TechnicalSolution）：方案ID、方案名称、方案内容、租户ID、状态
    -   方案基线（SolutionBaseline）：基线ID、基线名称、配置项、适用资产
    -   方案模板（SolutionTemplate）：模板ID、模板名称、模板内容、技术类型

+   **核心能力**：
    -   方案制定：基于模板制定技术方案（如操作系统基线、数据库基线等）
    -   方案导入：支持从 Excel、JSON 导入技术方案和基线配置
    -   基线配置：配置技术基线参数，关联到租户资产
    -   方案关联：将技术方案与租户控制（技术控制）建立关联，支撑技术落地链（L4）
    -   导入校验：导入前校验方案格式、配置项完整性、参数有效性

    -   依赖 BC-13 文件管理进行文件上传下载

## 3.7 SD-06 责任映射子领域

+   **核心职责**：标准角色点→租户岗位/人员的映射

+   **核心实体**：
    -   岗位角色映射（RoleMapping）：标准角色点ID、租户岗位ID、租户人员ID、映射类型
    -   责任点（ResponsibilityPoint）：责任点ID、控制ID、场景ID、角色ID、RACISV角色

+   **核心能力**：
    -   岗位映射：将知识中台的标准角色点映射到租户的实际岗位
    -   人员映射：将岗位映射到具体人员，实现责任到人

# 5 公共架构决策

## 5.1 技术架构决策

### 5.1.1 微服务归属

+   BC-35 租户落地归属于微服务 `svc-tenant-deployment`

+   微服务职责：
    -   提供租户资产、场景、控制、制度、责任映射的 CRUD 服务
    -   提供租户落地数据的查询接口给下游 BC
    -   提供租户落地数据的同步接口给上游 BC

### 5.1.2 数据存储决策

+   **关系型数据库**：MySQL
+   **选型理由**：
    -   租户落地数据具有明确的关系结构（资产-场景、控制-制度、角色-人员等）
    -   需要支持复杂的关联查询和事务一致性
    -   数据量适中（单租户数据量预估在 10 万条以内）

+   **全文检索**：Elasticsearch
+   **适用子领域**：SD-04 制度管理
+   **用途**：制度章节内容存储与全文检索，制度列表辅助索引。制度章节内容（PolicyChapter）仅写入 ES，不写入 MySQL

+   **数据隔离方案**：
    -   采用 Database per Tenant 物理库隔离方案，每个租户拥有独立数据库（clarisphere_{tenant_code}）
    -   BC-35 所有子领域的数据均存储在租户独立库中
    -   ES 按租户创建独立索引（如 idx_policy_chapter_{tenant_id}），实现物理隔离
    -   所有表保留 `tenant_id` 字段，由应用层查询条件注入作为兜底校验，并非主要隔离手段
    -   数据源路由通过 DynamicDataSource（AbstractRoutingDataSource）按 tenant_id 路由至对应数据库

### 5.1.3 缓存策略

+   **缓存层**：Redis
+   **缓存对象**：
    -   租户场景映射关系（高频查询，低频变更）
    -   租户控制映射关系（高频查询，低频变更）
    -   岗位角色映射关系（高频查询，低频变更）

+   **缓存失效策略**：
    -   写操作时主动失效相关缓存
    -   设置 TTL 为 1 小时，防止缓存雪崩

### 5.1.4 API 设计原则

+   **RESTful API**：
    -   资源命名：`/api/v1/tenant-deployment/{resource}`
    -   HTTP 方法：GET（查询）、POST（创建）、PUT（更新）、DELETE（删除）

+   **分页查询**：
    -   支持 `page` 和 `page_size` 参数
    -   默认 `page_size=20`，最大 `page_size=100`

+   **过滤与排序**：
    -   支持通用过滤参数（如 `tenant_id`、`status`、`created_at` 等）
    -   支持排序参数 `sort_by` 和 `order`（asc/desc）

### 5.2.2 映射关系设计

+   **映射类型枚举**：
    -   `DIRECT`：直接映射（1:1）
    -   `CUSTOMIZED`：定制映射（1:1，但有定制内容）
    -   `MERGED`：合并映射（N:1，多个标准节点合并为一个租户节点）
    -   `SPLIT`：拆分映射（1:N，一个标准节点拆分为多个租户节点）
    -   `DISABLED`：禁用映射（标准节点在租户环境中不适用）

+   **映射状态枚举**：
    -   `DRAFT`：草稿（映射关系已创建，但未激活）
    -   `ACTIVE`：激活（映射关系生效，参与合规评估）
    -   `INACTIVE`：停用（映射关系暂时停用，不参与合规评估）
    -   `ARCHIVED`：归档（映射关系已废弃，仅保留历史记录）

### 5.2.3 版本管理设计

+   **版本控制策略**：
    -   租户场景、租户控制、租户制度均支持版本管理
    -   每次修改创建新版本，保留历史版本
    -   版本号格式：`v{major}.{minor}`（如 v1.0、v1.1、v2.0）

+   **版本状态**：
    -   `DRAFT`：草稿版本
    -   `PUBLISHED`：已发布版本
    -   `DEPRECATED`：已废弃版本

    | 4          | 仅本人       | 制度编写者、只能看自己创建/负责的数据  | created_by = 当前用户ID      |
    | 5          | 自定义范围   | 跨部门协作、项目组、临时授权等场景     | 查询授权表                   |

    +   表 data_scope 定义（引用 BC-10）

### 5.3.2 SD-04 权限与数据权限设计

+   SD-04 制度管理是 BC-35 中首个落地权限模型的子领域，其设计同时为其他子领域提供参照模式

+   **SD-04 角色-权限码映射**：

    | 角色编号 | 角色名称   | 功能权限                                                                               | 数据权限       |
    | -------- | ---------- | -------------------------------------------------------------------------------------- | -------------- |
    | UR-10    | 制度管理员 | tenant:policy:import:\*、tenant:policy:policy:\*（全部操作，含作废、删除、退回）       | 本部门及以下   |
    | UR-03    | 制度编写者 | tenant:policy:import:create/read/confirm/cancel、tenant:policy:policy:list/read/update  | 仅本人创建     |
    | UR-02    | 安全架构师 | tenant:policy:policy:list、tenant:policy:policy:read                                   | 全部数据（只读）|
    | UR-09    | 租户管理员 | tenant:policy:policy:list、tenant:policy:policy:read                                   | 全部数据（只读）|

    +   表 SD-04 角色-权限码映射（P1 阶段）
    +   UR-01 CISO、安全经理等管理层角色的制度权限在 P2+ 运营生命周期中定义
    +   完整权限码清单和接口权限矩阵见《07-BC详细设计-BC35租户落地-SD04制度管理》§11

+   **制度的部门归属设计**：
    -   TenantPolicy 实体包含 `owner_dept_id` 字段，记录制度归属部门
    -   制度入库时，`owner_dept_id` 默认取操作人所属部门（从 BC-10 用户上下文获取）
    -   `owner_dept_id` 支持在入库确认阶段或入库后由制度管理员手动调整

+   **数据权限过滤规则**：

    | 角色         | 过滤维度     | 过滤条件                                            | 说明                                         |
    | ------------ | ------------ | --------------------------------------------------- | -------------------------------------------- |
    | UR-10 制度管理员 | 部门级   | owner_dept_id IN (当前用户部门及所有下级部门)       | 只能管理本部门及下级部门的制度               |
    | UR-03 制度编写者 | 个人级   | created_by = 当前用户ID（导入任务）                 | 只能操作自己创建的导入任务                   |
    | UR-02 安全架构师 | 无过滤   | 无                                                  | 全局只读视角                                 |
    | UR-09 租户管理员 | 无过滤   | 无                                                  | 全局只读，用于问题定位和用户支持             |

    +   所有角色的数据均受租户级物理隔离保护（Database per Tenant + ES 独立索引）

+   **多维度列表展示**：

### 5.3.3 数据权限模式推广

+   SD-04 建立的数据权限模式（owner_dept_id + created_by + data_scope）可推广到其他子领域：
    -   SD-01 资产管理：资产可设置 owner_dept_id，资产管理员按部门级管理
    -   SD-05 技术方案管理：方案可设置 created_by，方案制定者按个人级管理
    -   其他子领域在详细设计时参照 SD-04 模式落地

+   **审计内容**：

# 6 跨子领域约束

## 6.1 数据一致性约束

### 6.1.1 映射关系一致性

+   **约束规则**：
    -   租户场景必须映射到有效的标准场景点（来自 BC-40）
    -   租户控制必须映射到有效的标准控制点（来自 BC-40）
    -   岗位角色映射必须映射到有效的标准角色点（来自 BC-41）

+   **校验时机**：
    -   创建映射关系时，校验标准节点是否存在
    -   激活映射关系时，校验标准节点是否仍然有效

### 6.1.2 制度控制关联一致性

+   **约束规则**：
    -   租户制度只能关联到本租户的租户控制（P2+ 功能，P1 不实现制度-控制关联）
    -   制度控制关联必须在制度发布前完成（P2+）
    -   P1 阶段制度入库不要求关联控制点，制度以独立库管状态存在

+   **校验时机**：
    -   创建制度控制关联时，校验控制是否属于同一租户（P2+）
    -   提交制度审批时，校验制度是否已关联控制（P2+）

### 6.1.3 责任点生成一致性

+   **约束规则**：
    -   责任点必须基于有效的租户控制、租户场景、岗位角色映射生成
    -   责任点的 RACISV 角色必须映射到实际人员

+   **校验时机**：
    -   生成责任点时，校验控制、场景、角色映射是否有效
    -   激活责任点时，校验角色是否已映射到人员

## 6.2 业务流程约束

### 6.2.1 租户开通流程

+   **流程顺序**：
    1.   BC-53 运营分发推送合规包数据到 BC-35
    2.   BC-35 初始化租户的场景、控制映射（默认为 DRAFT 状态）
    3.   UR-02 安全架构师审核并激活场景、控制映射
    4.   BC-35 生成责任点（基于责任分配基准图）
    5.   UR-02 安全架构师完成岗位角色映射

+   **约束规则**：
    -   场景、控制映射必须激活后，才能生成责任点
    -   责任点必须生成后，才能进行岗位角色映射

### 6.2.2 制度入库流程（P1 · 库管生命周期）

+   **流程顺序**：
    1.   UR-03 制度编写者或 UR-10 制度管理员上传制度文件（Word/Excel），创建导入任务
    2.   系统异步执行格式转换（转 MD），导入任务状态：CREATED → CONVERTING
    3.   转换完成后进入 MD 比对确认阶段，导入任务状态：CONVERTING → PENDING_CONFIRM
    4.   用户确认章节解析结果，可编辑调整章节结构和元数据
    5.   用户确认入库，系统执行 MD → JSON 转换并写入 ES + MySQL，导入任务状态：PENDING_CONFIRM → IMPORTING → COMPLETED
    6.   SD-04 发布 `PolicyImportedEvent` 事件

+   **约束规则**：
    -   导入任务为异步处理，上传接口即时返回任务 ID
    -   单租户并发解析限制为 3 个任务（Redis 分布式信号量）
    -   解析超时 60 秒，超时后自动标记 FAILED
    -   同一文件（fileId）不可重复创建活跃导入任务（幂等保护）
    -   P1 阶段制度入库后直接进入 DRAFT 状态，不要求关联控制点

+   **详细流程**：见《07-BC详细设计-BC35租户落地-SD04制度管理》§3

### 6.2.3 制度编写流程（P2+ · 运营生命周期）

+   **流程顺序**：
    1.   UR-03 制度编写者基于模板编写制度
    2.   UR-03 制度编写者将制度与租户控制建立关联
    3.   UR-03 制度编写者提交制度审批申请（在 BC-35 内部）
    4.   UR-10 制度管理员完成发布审批
    5.   SD-04 更新制度状态为 PUBLISHED，发布 `TenantPolicyPublished` 事件

+   **约束规则**：
    -   制度必须关联至少一个租户控制，才能提交审批
    -   制度提交审批后，不能再修改内容（需创建新版本）

## 6.3 性能约束

### 6.3.1 批量操作限制

+   **批量导入**：
    -   单次批量导入资产数量不超过 1000 条
    -   单次批量创建映射关系不超过 500 条

+   **批量查询**：
    -   单次批量查询结果不超过 10000 条
    -   超过限制时，使用分页查询

### 6.3.2 响应时间要求

+   **查询操作**：
    -   单条查询：< 100ms
    -   列表查询：< 500ms
    -   复杂关联查询：< 1s

+   **写操作**：
    -   单条创建/更新：< 200ms
    -   批量操作：< 5s

## 6.4 扩展性约束

### 6.4.1 子领域扩展

+   **扩展原则**：
    -   新增子领域不影响现有子领域的功能
    -   新增子领域通过事件与现有子领域协作
    -   新增子领域遵循统一的数据模型和 API 设计原则

### 6.4.2 映射类型扩展

+   **扩展原则**：
    -   新增映射类型通过枚举值扩展
    -   新增映射类型不破坏现有映射关系的语义
    -   新增映射类型需在文档中明确定义语义和使用场景

# 7 附录

## 7.1 术语表

+   **租户落地**：将知识中台的标准化知识（场景点、控制点、角色点）映射到租户的实际环境
+   **租户资产**：租户的 IT 资产，包括服务器、数据库、应用系统等
+   **租户场景**：租户实际业务场景，由标准场景点映射而来
+   **租户控制**：租户实际控制措施，由标准控制点映射而来
+   **租户制度**：租户内部管理制度，与租户控制建立关联
+   **岗位角色映射**：将标准角色点映射到租户的实际岗位和人员
+   **责任点**：控制点、场景点、角色点的组合，明确"谁在什么场景下负责什么控制"
+   **RACISV**：责任分配矩阵，包括 Responsible（执行者）、Accountable（负责人）、Consulted（咨询者）、Informed（知情者）、Support（支持者）、Verify（验证者）
+   **导入任务**（PolicyImportTask）：记录一次制度文件导入的完整过程，包含文件信息、解析状态和转换结果，是 SD-04 P1 的核心聚合根之一
+   **制度章节**（PolicyChapter）：从制度文件中解析出的层级化章节结构，存储在 Elasticsearch 中，支持全文检索
+   **owner_dept_id**：制度归属部门 ID，用于支撑制度管理员的部门级数据权限过滤（data_scope = 2）
+   **data_scope**：数据权限范围枚举，定义于 BC-10 用户管理，取值 1-5，详见 §5.3.1
