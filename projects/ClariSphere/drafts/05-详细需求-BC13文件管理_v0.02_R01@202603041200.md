## 2.3 BC定位与核心价值

BC-13文件管理（FileManagement）是ClariSphere平台通用服务层的基础设施BC，承担统一文件存储、版本控制、病毒扫描与访问控制职责，以OHS（Open Host Service）模式（CM-25上下文映射）向平台所有业务BC提供文件管理能力，避免各业务BC重复构建文件处理逻辑。

BC-13的核心业务能力包括：（1）文件上传——支持单文件上传（≤100MB），含文件类型/大小预校验、幂等保护和覆盖版本递增；（2）文件访问——支持签名URL模式和流式模式下载，以及独立签名URL签发（有效期15m/1h/24h）；（3）文件元数据与版本管理——提供文件元数据查询和版本历史列表查询；（4）文件删除——软删除机制，含状态守卫约束；（5）文件安全——异步病毒扫描（SD03文件安全子领域执行）与管理员释放隔离。

BC-13的核心价值体现在：对于业务BC调用方（BC-R01），提供标准化文件操作REST API（OHS），消除各BC重复开发文件管理逻辑的成本；对于普通用户（BC-R02）和管理员（BC-R03/BC-R04），在业务BC透传场景下保障文件操作的安全合规——所有上传文件经异步病毒扫描（SCANNING→ACTIVE/QUARANTINED）后才开放访问，误判隔离文件由SUPER_ADMIN（BC-R04）通过专属接口审核处理。

### 4.2.1 SC-13-01 上传文件

+   上传文件场景定义如下表所示。

    | 字段     | 内容                                                                                           |
    | -------- | ---------------------------------------------------------------------------------------------- |
    | 场景编号 | SC-13-01                                                                                       |
    | 场景名称 | 上传文件                                                                                       |
    | 来源活动 | 02-宏观需求 FR-09；PL2节点 BA-CP-01（外规原文）、BA-EX-02（证据材料）、BA-BD-01（制度文档）、BA-AU-01（审计报告）、BA-CM-04（评估报告）上传时触发 |
    | 触发条件 | 业务BC调用 POST /v1/files 接口，携带文件和 X-Client-File-Id 请求头                             |
    | 前置条件 | 业务BC已通过Sa-Token鉴权；调用方具有 file:file:create 权限码                                   |
    | 参与角色 | BC-R01 业务BC调用方                                                                            |
    | 业务价值 | 为所有业务BC提供统一的文件上传入口，消除重复建设，保障文件上传的幂等性、合规性和病毒安全       |
    | 后置条件 | 文件元数据持久化至数据库，OBS对象已写入，文件状态为SCANNING；FileUploadedEvent已发布至RocketMQ |
    | 关联Epic | EP-CP-01, EP-EX-02, EP-BD-01                                                                   |

    +   表4.2.1-1 SC-13-01 场景定义

**主流程**：

1.   业务BC携带文件（multipart/form-data）和 X-Client-File-Id 发起 POST /v1/files 请求（Sa-Token鉴权通过）
2.   BC-13接口层校验文件大小（≤100MB）和文件类型（扩展名+Magic Number双重校验，白名单由SD03维护）
3.   BC-13应用层查询Redis检查 clientFileId 幂等性（TTL=24h）——若命中则执行分支流程A
4.   BC-13领域层通过ObjectStoragePort（OBS防腐层）将文件写入OBS（S3 PutObject）
5.   BC-13领域层持久化文件元数据至数据库（File聚合，status=SCANNING，currentVersionNo=1）
6.   BC-13应用层向RocketMQ发布 FileUploadedEvent（fileId、storageKey、tenantId）
7.   BC-13接口层返回 HTTP 201，响应体包含 fileId 和 status=SCANNING

**分支流程A（幂等上传）**：

从主流程第3步分支：当Redis命中相同 clientFileId 时——
1.   BC-13直接返回 HTTP 409，响应体包含 E-4091301（IDEMPOTENT_FILE_EXISTS）和已有 fileId
2.   不执行OBS写入，不新增数据库记录，不发布消息事件

**分支流程B（覆盖上传版本递增）**：

从主流程第5步分支：当同一业务语义下再次上传同名文件（非幂等场景，clientFileId不同）时——
1.   BC-13创建新 FileVersion 记录（versionNo=currentVersionNo+1，storageKey指向新OBS对象）
2.   更新 File.currentVersionNo 为新版本号
3.   继续主流程第6步（发布事件，返回已有fileId和新版本号）

**异常流程**：

-   当文件大小 >100MB 时 → 返回 HTTP 400（E-4000011 FILE_SIZE_EXCEEDED），终止流程
-   当文件类型不在白名单时 → 返回 HTTP 422（E-4221304 FILE_TYPE_NOT_ALLOWED），终止流程
-   当OBS写入失败时 → 回滚数据库记录，返回 HTTP 500（E-5000005 DEPENDENCY_SERVICE_FAILED），终止流程
-   当数据库持久化失败时 → 触发OBS对象异步清理，返回 HTTP 500，终止流程

4.   BC-13通过ObjectStoragePort生成OBS预签名URL（默认有效期15m）

    | 后置条件 | 文件状态标记为DELETED；Redis元数据缓存已失效；审计日志已记录；OBS对象保留至异步清理 |

1.   业务BC携带 fileId 调用 DELETE /v1/files/{fileId}
2.   BC-13查询文件元数据，校验文件状态——若非ACTIVE或QUARANTINED则执行异常流程
3.   BC-13校验操作人权限——若文件为QUARANTINED且操作人非SUPER_ADMIN则执行异常流程B
4.   BC-13通过乐观锁（version字段）更新文件状态为DELETED（并发冲突时执行异常流程C）
5.   BC-13主动失效Redis缓存（DEL file:meta:{fileId}）

从主流程第3步分支：当操作人为SUPER_ADMIN且文件状态为QUARANTINED时——
1.   BC-13允许操作，继续执行主流程第4步

**异常流程**：

-   当文件状态为SCANNING时 → 返回 HTTP 422（E-4221302 FILE_STATUS_DELETE_NOT_ALLOWED），终止流程
-   当文件状态已为DELETED时 → 返回 HTTP 422（E-4221302），终止流程（异常流程A）
-   当操作人非SUPER_ADMIN且文件为QUARANTINED时 → 返回 HTTP 403（E-4030001 PERMISSION_DENIED）（异常流程B）
-   当乐观锁冲突时 → 返回 HTTP 409（E-4090001 OPTIMISTIC_LOCK_CONFLICT），提示刷新后重试（异常流程C）

3.   SD03从OBS读取文件字节流，调用病毒扫描引擎执行扫描
4.   扫描结果为SAFE → SD03通过 FileRepository 接口将文件状态更新为ACTIVE
5.   BC-13主动失效Redis缓存（DEL file:meta:{fileId}）
6.   业务BC下次查询元数据时获得 status=ACTIVE，文件可访问

**分支流程（扫描发现威胁）**：

从主流程第4步分支：当扫描结果为THREAT时——
1.   SD03通过 FileRepository 接口将文件状态更新为QUARANTINED
2.   BC-13主动失效Redis缓存
3.   （可选）通知BC-14消息通知BC向SUPER_ADMIN发送告警

**异常流程**：

-   当RocketMQ消息发送失败时 → 不回滚上传事务，通过本地重试队列保证消息最终送达（引用EF-BC13-01）
-   当SD03消费失败时 → RocketMQ重试机制保证至少一次消费（引用EF-BC13-02），文件保持SCANNING状态直至扫描完成
