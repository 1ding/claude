## 1  概述

### 1.1  背景与目的

在ITGRC合规实践中，存在两个长期混淆：

+   **要求与控制的混淆**："应使用AES-256加密"到底是要求还是控制措施？
+   **What与How的混淆**："必须防范恶意代码"和"部署防病毒软件"是同一层的东西吗？

本文档定义控制点的要素模型，明确What（要求）和How（方案/控制点）的边界，并提供连接两者的方法论框架。

### 1.2  核心模型

```
要求（What）─── 必须做到什么
  │
  │  方法论框架（时机 × 机制 × 程度）
  │  检验方案对要求的覆盖是否全面、闭环、达标
  │
  ▼
方案（How）─── 打算怎么做到（一组控制点的组合）
  │
  ▼
控制点 ─── 可单独落地的最小措施单元
```

+   **要求**：必须做到什么，来自外规或内部策略，是刚性的。
+   **方法论框架**：时机×机制×程度，用来评价和设计方案，检验方案是否充分回应了要求。
+   **方案**：打算怎么做到，可替换，有多种选择，是一组控制点的组合。
+   **控制点**：方案中可单独落地的最小措施单元。

## 2  要求（What）

### 2.1  定义

要求是对"必须做到什么"的规定，回答What。要求不关心怎么做到，只关心做到什么。不管方案怎么换，要求不变。

### 2.2  要求的两种性质

+   **目标类要求**：描述期望达到的状态，连措施方向都没指定。如"应保障系统安全运行"。
+   **措施类要求**：指定了措施方向，但不指定具体实现。如"必须防范恶意代码"、"董事长应为网络安全第一责任人"。

判断标准：**只要还在说"做到什么"就是要求，一旦开始说"怎么做到"就跨入了方案。**

### 2.3  要求的粒度

要求的粒度独立于性质，可以逐层细化，形成父子关系：

```
目标类：应保障系统安全运行
  └── 措施类（粗）：必须防范恶意代码
        └── 措施类（中）：终端应部署恶意代码防护措施
              └── 措施类（细）：终端应部署具备实时监控能力的防病毒软件
```

每一层都是要求，都是What。不同粒度的要求都是有效的，应保留层级结构。

要求可以带有场景归属——作用于技术场景(T)、管理场景(M)还是治理场景(G)。例如"必须防范恶意代码"作用于T，"应每年开展风险评估"作用于M，"董事长应为第一责任人"作用于G。

### 2.4  监管条文的要求拆解

监管条文的拆解分两步：识别要求（What）和定位场景。

#### 2.4.1  第一步：识别要求

从条文中提取"必须做到什么"，区分要求性质和要求目标。

以等保条文为例："应采用密码技术保证重要数据在传输过程中的保密性"

+   **要求性质**：措施类（指定了"密码技术"这个措施方向）
+   **要求目标**：保密性

要求目标采用受控词表，典型的目标词表包括但不限于：

+   CIA三性：保密性、完整性、可用性
+   扩展属性：可追溯性、不可否认性、真实性
+   管理目标：合规性、有效性、及时性
+   治理目标：权责明确、决策透明、问责可溯

#### 2.4.2  第二步：定位场景

从条文中提取场景信息，明确要求作用于什么对象、什么状态。

同一条文："应采用密码技术保证**重要数据**在**传输过程**中的保密性"

+   **场景空间**：T（技术场景）
+   **资源**：重要数据
+   **资源状态**：传输中

资源状态是技术场景(T)特有的维度，描述资源所处的阶段：

| 资源状态 | 英文       | 说明                   |
| -------- | ---------- | ---------------------- |
| 存储中   | at rest    | 数据持久化存储在介质上 |
| 传输中   | in transit | 数据在网络上流动       |
| 使用中   | in use     | 数据在内存中被处理     |

#### 2.4.3  拆解产出的结构化记录

每条监管条文拆解后，产出一条结构化记录：

```
场景侧:
  场景空间:   T | M | G
  资源/活动:  （场景路径，如"重要数据"、"生产变更"、"安全责任体系"）
  资源状态:   存储中 | 传输中 | 使用中（T场景特有）

要求侧:
  要求性质:   目标类 | 措施类
  要求目标:   保密性 | 完整性 | 可用性 | ...（受控词表）
  要求内容:   原文或规范化表述

溯源:
  来源条文:   [条文编号列表]
```

**拆解示例：**

| 条文来源      | 条文原文                                       | 场景空间 | 资源/活动     | 资源状态 | 要求性质 | 要求目标 |
| ------------- | ---------------------------------------------- | -------- | ------------- | -------- | -------- | -------- |
| 等保-8.1.4.2  | 应采用密码技术保证重要数据在传输过程中的保密性 | T        | 重要数据      | 传输中   | 措施类   | 保密性   |
| 数安法-第27条 | 应当采取加密等安全技术措施                     | T        | 数据          | —        | 措施类   | 保密性   |
| 网安法-第21条 | 应确定网络安全负责人                           | G        | 安全责任体系  | —        | 措施类   | 权责明确 |
| 等保-8.1.2.1  | 应对登录的用户进行身份标识和鉴别               | T        | 应用系统-登录 | 使用中   | 措施类   | 真实性   |
| 银保监指引    | 应每年开展一次信息科技风险评估                 | M        | 风险评估      | —        | 措施类   | 合规性   |

### 2.5  要求的归一化

不同监管条文经常用不同的话说同一件事。归一化的目的是将来源不同但本质相同的要求合并到同一个位置，避免重复落实。

**归一的主键**：**资源/活动 + 资源状态 + 要求目标**

三者相同的条文，不管原文怎么表述，归为同一个要求，来源条文合并到溯源列表中。

**归一示例：**

以下三条来自不同监管要求，归一后是同一个要求：

| 来源          | 条文原文                                       |
| ------------- | ---------------------------------------------- |
| 等保-8.1.4.2  | 应采用密码技术保证重要数据在传输过程中的保密性 |
| 数安法-第27条 | 应当采取加密等安全技术措施                     |
| 银保监指引    | 传输敏感数据应使用加密通道                     |

归一结果：

```
{
  资源/活动:  重要数据/敏感数据
  资源状态:   传输中
  要求目标:   保密性
  要求性质:   措施类
  规范化表述: 重要数据在传输过程中应保障保密性
  来源条文:   [等保-8.1.4.2, 数安法-第27条, 银保监-第X条]
}
```

归一化过程中需要注意：

+   **资源/活动的同义词处理**："重要数据"和"敏感数据"在不同法规中含义可能不同，需要根据企业自身分类标准判断是否归为同一对象。
+   **要求目标的受控词表**：必须使用统一的词表，否则"保密性"、"加密"、"传输保护"会被当成不同目标。
+   **程度差异的处理**：不同条文对同一要求可能有不同程度的规定（如等保要求AES-256，行业规范要求国密SM4），归一后取最严格的程度要求，或保留多个程度要求并标注来源。

## 3  方法论框架（时机 × 机制 × 程度）

### 3.1  定义与定位

方法论框架是连接要求(What)与方案(How)的桥梁。它不属于要求，也不属于方案，而是用来**评价和设计方案**的分析工具。

拿到一个要求后，用方法论框架去审视方案：

+   **时机**：方案覆盖了哪些介入时点？只有预防没有检测？是否全面？
+   **机制**：方案靠什么原理生效？是否过于单一？是否闭环？
+   **程度**：方案管到什么标准？是否达标？

三个视角中，时机和程度相互独立，机制按时机归类。

### 3.2  时机

措施的介入时点。时机的枚举值因被管控问题的性质不同而有所差异——技术领域面对攻击事件，管理和治理领域面对持续运作偏差：

**技术场景(T)——四分：**

| 编码 | 名称 | 说明               |
| ---- | ---- | ------------------ |
| PREV | 预防 | 事前，阻止威胁发生 |
| DETC | 检测 | 事中，发现威胁存在 |
| RESP | 响应 | 事中，处置威胁影响 |
| RECV | 恢复 | 事后，恢复正常状态 |

**管理场景(M)和治理场景(G)——三分：**

| 编码 | 名称 | 说明                 |
| ---- | ---- | -------------------- |
| PREV | 预防 | 事前，确保条件就绪   |
| DETC | 检测 | 事中，发现偏差和失灵 |
| CORR | 纠正 | 事后，纠偏并改进     |

### 3.3  机制

措施生效的底层原理。机制**按时机归类**，每个时机下有自己的机制枚举。

在DSCF框架中，技术场景的机制可以进一步细分为原理类和原理项，这种细分对安全产品研究有价值，但对一般企业落地未必需要展开到那个粒度。

#### 3.3.1  技术场景(T)机制

**T-PREV 预防机制：**

| 编码 | 名称     | 说明                 |
| ---- | -------- | -------------------- |
| RCHB | 不可达   | 使攻击者无法到达目标 |
| FSBL | 不可行   | 使攻击路径不可执行   |
| XPLT | 不可利用 | 使漏洞无法被利用     |
| INFR | 不可推断 | 使信息无法被推导获取 |

**T-DETC 检测机制：**

| 编码 | 名称     | 说明                         |
| ---- | -------- | ---------------------------- |
| OBSV | 可观测性 | 使系统状态可被观察           |
| REPR | 表征构造 | 将观察数据构造为可分析的特征 |
| CONS | 一致判定 | 判定观察到的状态是否异常     |
| CAUS | 因果归因 | 追溯异常的根本原因           |

**T-RESP 响应机制：**

| 编码 | 名称     | 说明                           |
| ---- | -------- | ------------------------------ |
| DISB | 结构失效 | 使攻击结构失去效力             |
| TRNS | 状态转移 | 将系统从受损状态转移到安全状态 |
| CAUS | 因果切断 | 切断攻击的因果传播链           |

**T-RECV 恢复机制：**

| 编码 | 名称     | 说明                     |
| ---- | -------- | ------------------------ |
| SUBS | 空间替代 | 用备用资源替代受损资源   |
| REVS | 时间回溯 | 将系统回滚到已知良好状态 |
| GNSS | 可信重建 | 从可信基线重新构建系统   |

#### 3.3.2  治理场景(G)机制

**G-PREV 预防机制：**

| 编码 | 名称     | 说明                                 |
| ---- | -------- | ------------------------------------ |
| ASGN | 权责落位 | 确保每项职责有明确的承担主体         |
| SEPR | 权责分离 | 确保决策、执行、监督不集中于同一主体 |
| TRNS | 决策透明 | 使治理决策过程可被审视，防止暗箱操作 |

**G-DETC 检测机制：**

| 编码 | 名称     | 说明                         |
| ---- | -------- | ---------------------------- |
| ACNT | 问责可溯 | 使治理行为可追溯到具体责任人 |
| AUDT | 治理审计 | 检查治理机制是否在按设计运转 |

**G-CORR 纠正机制：**

| 编码 | 名称     | 说明                               |
| ---- | -------- | ---------------------------------- |
| OVRD | 权力覆写 | 上级机构否决或纠正下级决策         |
| ESCL | 升级通道 | 风险和问题逐级上报到有决策权的层级 |
| RSTK | 权责重置 | 重新指定责任人、重建问责链条       |

#### 3.3.3  管理场景(M)机制

**M-PREV 预防机制：**

| 编码 | 名称     | 说明                                   |
| ---- | -------- | -------------------------------------- |
| NORM | 规则明确 | 流程和制度已成文、已发布、已传达       |
| QUAL | 能力胜任 | 执行人具备所需能力（培训、认证、资质） |
| RSRC | 资源保障 | 执行所需资源已到位（人力、预算、工具） |

**M-DETC 检测机制：**

| 编码 | 名称     | 说明                         |
| ---- | -------- | ---------------------------- |
| CMPL | 合规核查 | 检查执行是否符合已定义的规则 |
| PERF | 绩效度量 | 度量管理活动的实际效果       |

**M-CORR 纠正机制：**

| 编码 | 名称     | 说明                       |
| ---- | -------- | -------------------------- |
| CORR | 纠正执行 | 将偏离的执行拉回正确轨道   |
| REVW | 制度修订 | 根据失灵经验修订流程和制度 |
| RETR | 能力重建 | 针对能力缺口重新培训或换人 |

### 3.4  程度

管控力度和约束条件。一个方案可以同时具备多个程度要求，不同类别可组合，同类别内也可并存。

#### 3.4.1  过程类

对行为执行过程的伴随性约束：

+   **留痕**: 执行过程必须记录（审计日志、操作记录、变更记录）
+   **见证**: 执行过程必须有人在场（双人操作、四眼原则、监督岗）
+   **审批**: 执行之前必须经过批准流程（逐级审批、会签、变更委员会审议）

#### 3.4.2  度量类

可量化的约束指标：

+   **频次**: 多久执行一次（每年、每季度、每日）
+   **时长**: 保持多长时间（日志保留6个月、备份保留1年）
+   **阈值**: 达到什么数值（密码长度≥8位、可用性≥99.9%）
+   **等级**: 达到什么级别（AES-256、TLS 1.2+、等保三级）

### 3.5  方法论框架的使用方式

以"必须防范恶意代码"这个要求为例，用方法论框架审视方案的充分性：

| 视角 | 审视问题                       | 审视示例                                                                       |
| ---- | ------------------------------ | ------------------------------------------------------------------------------ |
| 时机 | 方案覆盖了哪些时机？是否全面？ | 只有预防（防病毒拦截）没有检测（行为分析）？缺恢复（感染后清除）？             |
| 机制 | 方案靠什么原理生效？是否单一？ | 只靠特征匹配（一致判定）？有没有行为分析（因果归因）？有没有沙箱（不可利用）？ |
| 程度 | 方案管到什么标准？是否达标？   | 实时扫描还是定期扫描？病毒库更新频次？日志保留多久？                           |

## 4  场景维度

### 4.1  总体说明

场景定位措施的作用对象，回答"管什么"。场景分为三个独立的空间：

| 编码 | 名称     | 定位           | 说明                                                                        |
| ---- | -------- | -------------- | --------------------------------------------------------------------------- |
| T    | 技术场景 | 管什么技术资源 | 以技术设施、软硬件设施为主（含物理设施），直接承载业务                      |
| M    | 管理场景 | 管什么管理活动 | 流程、制度、规范所约束的管理行为，回答How（怎么做）                         |
| G    | 治理场景 | 管什么治理活动 | 组织架构、决策机制、权责分配相关的治理行为，回答Why/What（为什么做/做什么） |

三个场景空间完全独立，各自有自己的层级结构。

### 4.2  治理场景(G)与管理场景(M)的划分原则

| 对比维度 | G 治理场景                      | M 管理场景       |
| -------- | ------------------------------- | ---------------- |
| 核心问题 | Why（为什么做）/ What（做什么） | How（怎么做）    |
| 关注层面 | 战略、方向、原则                | 流程、执行、操作 |
| 输出形式 | 政策、框架、标准                | 制度、规程、记录 |
| 决策主体 | 董事会、高管层                  | 管理层、执行层   |
| 评估方式 | 有效性、符合性                  | 效率、完成度     |
| 时间跨度 | 长期（年度及以上）              | 短期（日/周/月） |
| 变化频率 | 相对稳定                        | 根据需要调整     |

治理层的每个领域通常都有对应的管理层执行落地。

### 4.3  命名规则

所有场景节点必须是**纯名词性**描述，**不能混入任何措施语义**。

+   ✓ "数据"、"数据库"、"表空间" / "变更管理"、"生产变更" / "安全责任体系"
+   ✗ "数据安全" / "数据库加密" / "数据存储保护"

### 4.4  层级规则

+   **层数不固定**：按复杂度按需展开。
+   **逐层收敛**：每一层是对上一层的范围收窄。
+   **允许跳过**：简单场景不需要展开所有层级。
+   **结构不限于树**：场景之间可能存在交叉引用和多维组合。

### 4.5  技术场景(T)示例

```
T 技术场景
├── 数据
│   ├── 结构化数据
│   │   ├── 数据库 → 表空间 → 字段
```

## 5  方案（How）

### 5.1  定义

方案是对"打算怎么做到"的回答，回答How。方案是一组控制点的组合，用来实现一个或多个要求。

同一个要求可以有多种方案。方案可替换，要求不因方案更换而改变。

### 5.2  方案与要求的边界

判断标准：**What/How边界**。

+   "必须防范恶意代码" → What → 要求
+   "部署终端防病毒软件系统" → How → 方案
+   "终端应部署具备实时监控能力的防病毒软件" → 仍是What → 要求（虽然具体，但说的是"做到什么"，不是"怎么做到"）

### 5.3  方案示例

**要求**：必须防范恶意代码

| 方案              | 控制点组合                                 |
| ----------------- | ------------------------------------------ |
| 方案A：终端防病毒 | 防病毒客户端、防病毒管理端、病毒库更新服务 |
| 方案B：应用白名单 | 白名单管理平台、白名单代理                 |
| 方案C：组合防护   | 防病毒系统 + 应用白名单 + 网关恶意流量检测 |

## 6  控制点

### 6.1  定义

控制点是方案中**可单独落地的最小措施单元**。

+   T场景：可独立部署的技术措施（终端恶意代码检测、网络访问控制、存储加密）
+   M场景：可独立执行的管理措施（风险评估、变更审批、补丁管理）
+   G场景：可独立建立的治理措施（最高责任人指定、权责分离）

判断标准：**能否独立落地？** 能→控制点。

### 6.2  控制点与载体

控制点是措施本身，载体是控制点落地时产生或依赖的介质。载体不是控制点。

| 控制点           | 典型载体（介质）                   |
| ---------------- | ---------------------------------- |
| 风险评估         | 风险评估规程、评估报告、风险登记册 |
| 补丁管理         | 补丁管理平台、补丁测试报告         |
| 最高责任人指定   | 任命文件、职责清单                 |
| 变更审批         | 变更审批流程文件、变更记录         |
| 终端恶意代码检测 | 防病毒客户端软件、策略配置文件     |
| 存储加密         | keystore文件、加密配置脚本         |

载体的常见类型：

+   **制度载体**：规程、规范、指南、操作手册
+   **工具载体**：平台、系统、软件
+   **文档载体**：任命文件、报告、记录、清单
+   **配置载体**：策略文件、配置脚本、模板

### 6.3  控制点的落实

> **控制点的落实，一定表现为可验证的状态变化。**

控制点是抽象的、可复用的。控制点落实到具体场景后，产生可验证的状态变化：

| 控制点（抽象）   | 场景                      | 落实（可验证的状态变化）                               |
| ---------------- | ------------------------- | ------------------------------------------------------ |
| 终端恶意代码检测 | T：主机/终端 → 生产服务器 | 生产服务器已部署防病毒客户端，实时扫描已启用           |
| TDE加密          | T：数据 → 数据库 → 表空间 | 客户信息表空间已启用AES-256加密，keystore状态为OPEN    |
| 最高责任人指定   | G：安全组织 → 权责划分    | 董事长已被正式任命为网络安全第一责任人，任命文件已签发 |
| 变更审批         | M：工程活动 → 变更管理    | 生产变更已纳入审批流程，未经审批的变更无法执行         |

### 6.4  控制点示例

| 控制点           | 说明                           | 典型场景                          |
| ---------------- | ------------------------------ | --------------------------------- |
| 终端恶意代码检测 | 终端层面的恶意代码检测与清除   | T：主机/终端                      |
| 网络访问控制     | 基于规则的网络流量访问控制     | T：网络 → 边界网络                |
| 补丁管理         | 补丁的测试、审批与分发         | M：工程活动 → 运维安全            |
| 变更审批         | 变更实施前的审批管控           | M：工程活动 → 运维安全 → 变更管理 |
| 风险评估         | 资产、威胁、脆弱性的识别与评估 | M：风险合规 → 风险管理            |
| 最高责任人指定   | 明确网络安全最高责任人         | G：安全组织 → 权责划分            |

## 7  参考/依据

### 7.1  定义

参考/依据是支撑要求来源和方案决策的理论来源和实践参考，回答"为什么有这个要求"和"为什么选这个方案"。

### 7.2  范围

+   **国际标准**: ISO 27005、NIST CSF、COBIT
+   **行业规范**: 等保要求、银保监指引
+   **监管要求**: 《网络安全法》、《数据安全法》
+   **内部规范**: 公司安全基线、操作手册
+   **厂商文档**: Oracle TDE最佳实践指南、MySQL审计插件配置手册
+   **技术实践**: 社区最佳实践、架构兼容性分析
+   **评估结论**: 风险评估报告、审计发现、渗透测试结果

## 8  完整示例

### 8.1  恶意代码防护

```
要求：必须防范恶意代码（What）
  │
  │  方法论框架审视：
  │  ├── 时机：需要覆盖预防+检测+恢复
  │  ├── 机制：需要一致判定（特征匹配）+ 因果归因（行为分析）
  │  └── 程度：实时扫描、病毒库每日更新、日志保留180天
  │
  ▼
方案：终端防病毒 + 网关检测（How）
  │
  ├── 控制点：终端恶意代码检测
  │     场景 → T：主机/终端 → 生产服务器
  │     载体 → 防病毒客户端软件
  │     落实 → 生产服务器已部署防病毒客户端，实时扫描已启用
  │
  ├── 控制点：恶意代码集中管控
  │     场景 → T：应用系统 → 安全管理区
  │     载体 → 防病毒管理端平台
  │     落实 → 管理端已部署，所有终端已纳入统一管控
  │
  ├── 控制点：病毒特征库更新
  │     场景 → T：应用系统 → 安全管理区
  │     载体 → 病毒库更新服务
  │     落实 → 病毒库已配置每日自动更新，更新成功率可监控
  │
  └── 控制点：网关恶意流量检测
        场景 → T：网络 → 边界网络
        载体 → 网关防病毒设备/模块
        落实 → 边界网关已启用恶意流量检测，日志已转发至SIEM
  │
  参考/依据：等保三级恶意代码防范要求、CIS Controls v8
```

## 10  版本演进对照

| 维度           | V1.0           | V2.x                | V3.0                                   |
| -------------- | -------------- | ------------------- | -------------------------------------- |
| 核心模型       | 四要素线性     | 场景×措施交叉       | 要求→方案→控制点三层                   |
| What/How       | 未区分         | 未区分              | 明确分离                               |
| 时机×机制×程度 | 控制点的属性   | 措施的属性/视角     | 方法论框架（连接What与How的桥梁）      |
| 场景           | 控制点第一要素 | 独立维度（T/M/G）   | 控制点实施时的上下文                   |
| 方案           | 无             | 无                  | 一组控制点的组合，可替换               |
| 控制点         | 四要素的整体   | 落实点（场景×措施） | 可单独落地的最小措施单元               |
| 落实点         | 无             | 核心产出物          | 取消（控制点的实施状态，不单独成概念） |
| 控制包         | 无             | 无                  | 取消（方案层自然处理组合关系）         |
| 方法/参考      | 实现手段       | 参考/依据           | 参考/依据（支撑要求来源和方案决策）    |

## 11  术语索引

| 术语        | 定义                                                                                      |
| ----------- | ----------------------------------------------------------------------------------------- |
| 要求        | 必须做到什么（What），来自外规或内部策略，可以是目标类或措施类，粒度不固定                |
| 方法论框架  | 时机×机制×程度，连接要求(What)与方案(How)的分析工具，用于评价方案的全面性、闭环性、达标性 |
| 时机        | 措施的介入时点，T四分（预防/检测/响应/恢复），MG三分（预防/检测/纠正）                    |
| 机制        | 措施生效的底层原理，按时机归类，枚举值跟随场景空间变化                                    |
| 程度        | 管控力度和约束条件：过程类（留痕/见证/审批）、度量类（频次/时长/阈值/等级），可组合       |
| 方案        | 打算怎么做到（How），一组控制点的组合，可替换                                             |
| 控制点      | 方案中可单独落地的最小措施单元                                                            |
| 载体        | 控制点落地时产生或依赖的介质（制度、工具、文档、配置），不是控制点本身                    |
| 技术场景(T) | 以技术设施、软硬件设施为主的场景定位                                                      |
| 管理场景(M) | 定位被管控的管理活动，回答How                                                             |
| 治理场景(G) | 定位被管控的治理活动，回答Why/What                                                        |
| 参考/依据   | 支撑要求来源和方案决策的理论来源和实践参考                                                |
