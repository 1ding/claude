### 2.2.4 问题空间全景

+   透管云以「合规知识生产」（供给侧）和「企业合规治理闭环」（消费侧A）、「个人知识消费」（消费侧B）构成三大业务价值生态
+   供给侧的核心业务问题是：如何将海量分散的外部监管法规，经由标准化的解析-映射-封装流程，转化为可被企业直接落地的结构化合规知识产品
+   消费侧A的核心业务问题是：如何建立从合规要求到管理制度、技术方案、执行行动的全链路穿透可见性，使企业真正做到要求↔落实不脱节
+   消费侧B提供低门槛的个人合规知识获取渠道，并作为企业客户的引流漏斗
+   三大生态通过8库6图1包的数据架构和6链穿透验证模型（L1治理穿透/L2合规落地/L3制度溯源/L4技术落地/L5责任落实/L6风险防控）在技术层面打通
+   四大困境（DLM001新规比对地狱、DLM002监管检查拷问、DLM003管理汇报哑口、DLM004员工执行茫然）是问题空间的顶层框架，指引核心域边界划定和优先级决策

# 3 领域划分与子域分类

+   本章从《02-宏观需求》v0.13 的业务域出发（9个有场景域 + 7个基础/数据域），通过合并、拆分、重划识别出12个子域，并按核心域/支撑域/通用域三类进行分类和定义

## 3.1 子域识别方法

+   以阶段2的业务域为起点，应用以下规则：
    -   **合并**：内聚性高、变更频率相近、无独立部署需求的相邻业务域合并为一个子域（如DOM33治理监督域与DOM35的规划部分合并为治理督办子域）
    -   **拆分**：单一业务域内存在明显语言边界或不同变更频率的能力，拆分为多个子域（如DOM52知识工程域拆出解析映射能力为SD-02、控制架构能力为SD-03、方案封装为SD-04）
    -   **重划**：跨业务域的同类能力归入同一子域（如DOM53运营分发域的质量审核部分并入SD-03控制架构子域）
    -   **新增**：基础性需求识别出无对应业务域的横切能力（用户权限子域SD-12来自FR-01~07）
+   识别步骤：以业务能力内聚性为主判据，以变更频率和数据所有权为辅助判据
+   最终从16个业务域识别出12个子域

# 4 限界上下文识别与定义

+   本章从12个子域出发，识别和定义15个限界上下文（BC），确认已有BC（BC-10/BC-11/BC-51）的边界，并完成BC与子域、Business Epic的映射关系及BC内聚性验证

## 4.1 BC识别方法

+   以子域为起点，以**统一语言边界**为首要划定因素：同一BC内部，同一术语在所有上下文中含义完全相同
+   已有BC（BC-10/BC-11/BC-51）在本章确认边界，保持原有编号和命名，不重新命名
+   BC编号分区策略：BC-1X（用户权限）、BC-2X（消费侧A体系执行）、BC-3X（消费侧A GRC中心）、BC-4X（消费侧B知识消费）、BC-5X（供给侧知识生产）、BC-6X（平台运维）
+   本次共识别15个BC

## 4.2 BC边界划定原则

+   五因素优先级：语言边界 > 数据所有权 > 业务能力内聚 > 变更频率 > 团队边界
+   BC边界划定原则如下表所示

    | 划定因素     | 定义                                                         | 应用规则                                                             | 优先级 |
    | ------------ | ------------------------------------------------------------ | -------------------------------------------------------------------- | ------ |
    | 语言边界     | 同一术语在两个BC中含义不同时，必须划分为不同BC               | 不可强行合并含义不同的术语                                           | 最高   |
    | 数据所有权   | 聚合根由且仅由一个BC拥有                                     | 不允许多BC共同维护同一聚合                                           | 高     |
    | 业务能力内聚 | 职责高度内聚、低耦合的能力集合划入同一BC                     | 依据职责单一原则                                                     | 中     |
    | 变更频率     | 变更频率差异显著的能力宜分属不同BC                           | 避免联动变更                                                         | 中低   |
    | 团队边界     | BC边界尽量与组织团队边界对齐                                 | 不以此为主要判据                                                     | 低     |

# 6 领域事件全景

+   本章识别和定义35个领域事件，包括跨域事件（触发其他BC响应）和域内事件（驱动本BC聚合状态流转），建立事件流转全景图

## 6.1 事件识别方法

+   **来源**：EventStorming工作坊产出（KA-01计划）+ 实体生命周期状态转换（阶段2成果SI-03）+ 跨BC异步集成场景（第5章CM关系）
+   **命名规范**：英文PascalCase + 过去时态（`{Entity}{Action}ed`）；中文"{实体}已{动作}"
+   **事件分类**：跨域事件（触发其他BC响应）、域内事件（BC内部消费）
+   **版本策略**：事件载荷采用向后兼容设计，新增字段可选，删除字段需版本升级

## 6.2 事件分类

+   **跨域事件**：由一个BC发布，被其他BC订阅并响应；是异步集成的核心机制
+   **域内事件**：在同一BC内部触发聚合状态流转或工作流推进；不对外发布

## 7.2 聚合识别方法

+   **主要判据**：事务一致性边界——同一事务中必须保持一致的实体，划入同一聚合
+   **辅助判据**：实体生命周期独立性——生命周期独立的实体可考虑独立聚合
+   **设计原则**：聚合应尽量小（Small Aggregates），跨聚合引用只允许通过聚合根ID

# 附录A（规范性）统一语言

+   本附录定义 ClariSphere 透管云领域设计统一语言，适用于本文档及所有下游阶段文档

## A.1 统一语言原则

+   **唯一性**：全文同一术语名称含义唯一，禁止同义词混用
+   **边界性**：同一术语在不同BC中含义不同时，必须拆分为不同术语（如"用户"在BC-10和BC-40的含义不同，须明确区分"登录账号"和"知识消费用户"）
+   **显示性**：新术语首次出现必须在本附录注册，并提供定义；下游文档不可自行引入未在本附录注册的领域术语
+   **治理性**：术语变更须通知所有关联BC的负责团队，并更新下游文档

## A.3 术语治理规则

+   **新增**：提交领域设计评审，双周同步全团队；新增后在本附录登记，并通知下游阶段文档负责人
+   **变更**：记录变更原因和影响范围，通知所有引用该术语的BC负责团队；下游文档须同步更新
+   **冲突解决**：同一术语在不同BC含义不同时，拆分为不同术语并在本附录分别注册；不允许同一术语名称在不同BC中具有不同定义
+   **废弃**：废弃术语保留在本附录（标记状态为"废弃"），不可删除，须注明替代术语
