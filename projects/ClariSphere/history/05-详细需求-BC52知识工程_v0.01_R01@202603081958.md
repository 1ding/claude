### 2.2.3 BC定位与核心价值

+   BC-52知识工程是透管云合规知识生产链路的核心引擎，负责将BC-51采集的外规原文转化为结构化、可落地的合规知识资产，并通过合规包机制向下游BC传递。

+   BC-52提供六项核心业务能力：外规原子化拆解与结构化（SD-04/05）、控制点与场景点架构维护（SD-01/02）、要求到控制点到场景点的映射建立与审视（SD-06）、责任点动态生成（SD-03）、验证规则配置（SD-02）、合规包封装与发布（SD-07）。

+   BC-52为供给侧运营人员（UP02控制架构师、UP03外规解析师、UP04方案设计师）提供核心价值：将原本依赖专家经验、耗时2-3周的外规解析过程系统化为AI辅助+人工确认的标准化流程，将碎片化的控制架构知识沉淀为可复用的结构化资产，将人工拼凑的合规包升级为模板化、可审视的标准化封装。

+   INVEST原则速查表如下表所示

    | ---- | ----------- | ---------------------------------------- | ---------------------------------- |
    | I    | Independent | 能否独立交付，不依赖其他未完成的Story？  | 拆除依赖或调整交付顺序             |
    | N    | Negotiable  | 实现方式是否可协商？                     | 移除技术实现细节，回归用户目标     |
    | V    | Valuable    | 对用户有明确价值吗？                     | 重写价值描述或合并至有价值的Story  |
    | E    | Estimable   | 能否估算工作量？                         | 补充信息或拆分至可估算粒度         |
    | S    | Small       | 能否在1~3天内完成？                      | 拆分为更小的Story                  |
    | T    | Testable    | 有明确的验收标准吗？                     | 补充AC                             |

# 附录A 术语速查

+   本附录汇总BC-52详细需求中使用的核心术语，引用C99天帷通用术语规范和控制点要素模型V3.0

    | 术语             | 定义                                                                                           | 来源               |
    | ---------------- | ---------------------------------------------------------------------------------------------- | ------------------ |
    | 要求             | 必须做到什么（What），来自外规或内部策略，可以是目标类或措施类，粒度不固定                     | 控制点要素模型 §2  |
    | 方案             | 打算怎么做到（How），一组控制点的组合，可替换                                                  | 控制点要素模型 §5  |
    | 控制点           | 方案中可单独落地的最小措施单元                                                                 | 控制点要素模型 §6  |
    | 方法论框架       | 时机×机制×程度，连接要求(What)与方案(How)的分析工具，用于评价方案的全面性、闭环性、达标性       | 控制点要素模型 §3  |
    | 时机             | 措施的介入时点；T四分（预防/检测/响应/恢复），M/G三分（预防/检测/纠正）                        | 控制点要素模型 §3.2 |
    | 机制             | 措施生效的底层原理，按时机归类，枚举值跟随场景空间变化                                         | 控制点要素模型 §3.3 |
    | 程度             | 管控力度和约束条件；过程类（留痕/见证/审批）、度量类（频次/时长/阈值/等级），可组合             | 控制点要素模型 §3.4 |
    | 技术场景(T)      | 以技术设施、软硬件设施为主的场景定位，管什么技术资源                                           | 控制点要素模型 §4.1 |
    | 管理场景(M)      | 定位被管控的管理活动，回答How                                                                  | 控制点要素模型 §4.1 |
    | 治理场景(G)      | 定位被管控的治理活动，回答Why/What                                                             | 控制点要素模型 §4.1 |
    | 载体             | 控制点落地时产生或依赖的介质（制度、工具、文档、配置），不是控制点本身                         | 控制点要素模型 §6.2 |
    | 归一化           | 将来源不同但本质相同的要求合并到同一位置；主键为资源/活动+资源状态+要求目标                    | 控制点要素模型 §2.5 |
    | 资源状态         | T场景特有维度，描述资源所处的阶段：存储中(at rest)/传输中(in transit)/使用中(in use)            | 控制点要素模型 §2.4 |
    | 要求性质         | 目标类（描述期望状态）或措施类（指定措施方向但不指定实现）                                     | 控制点要素模型 §2.2 |
    | 要求目标         | 受控词表；CIA三性+扩展属性（可追溯性/不可否认性/真实性）+管理目标+治理目标                     | 控制点要素模型 §2.4 |
    | 场景点           | 业务场景的最小定位单元（场景视角：在哪里执行）                                                 | C99 §terms         |
    | 要求点           | 外规拆解的原子化要求（要求视角：需达成什么目标）                                               | C99 §terms         |
    | 验证规则         | 自动化检查规则，验证控制点执行状态                                                             | C99 §terms         |
    | 责任点           | 由控制点×场景点×RACISV筛选有效组合后动态生成并持久化存储的职责单元                             | C99 §terms         |
    | 合规包           | 面向特定合规目标的解决方案封装，将知识侧内容针对性打包传递到企业落地侧                         | C99 §terms         |
    | RACISV           | Responsible/Accountable/Consulted/Informed/Support/Verify 六种角色类型                         | 02-宏观需求        |
    | 知识工程(BC-52)  | 管理外规解析映射、控制架构维护、合规包封装发布的全知识生产链路                                 | 03-领域设计 §4.3   |
    | Capability       | BC内部的子域分层，对应DDD解决方案空间的BC子域（SD-xx）；引入Capability的BC即为大BC             | C99 §terms         |
    | What/How边界     | 判断标准：说"做到什么"是要求(What)，说"怎么做到"是方案(How)                                    | 控制点要素模型 §5.2 |
