# 1 概述

+   文档编号：GUIDE-REG-001
+   文档名称：监管条文结构化拆解指南
+   文档密级：内部资料

## 1.1 目的与定位

+   本指南是监管条文结构化拆解的唯一操作参考，内容基于《法规条款原子化拆解模型》，将模型的维度体系、词库体系完整融合，并补充拆解步骤、字段说明与示例，形成一站式操作文档。
+   适用场景：

-   对单部法规全文进行批量结构化拆解
-   跨法规汇总同一领域的全部监管要求
-   基于结构化记录开展合规差距分析与义务映射

## 1.2 原子要求的定义与结构

+   **原子要求**是本模型的基本记录单元，定义为：一个条款中包含的、可独立理解且可独立落地的单条要求。
+   若一个法条包含多个并列要求，则拆分为多条原子记录；每条原子记录独立标注全部字段。
+   每条原子要求由八个维度组描述：

    ```graph
    ┌──────────────────────────────────────────────────────┐
    │                    原子要求                          │
    ├─────────────┬────────────────────────────────────────┤
    │ 法规溯源    │ 出处、效力、适用行业                   │
    │ 条款特征    │ 安全目标、法益、后果                   │
    ├─────────────┼────────────────────────────────────────┤
    │ 相关方      │ 角色 × RACISV（R/A/C/I/S/V）           │
    │ 客体        │ DASPR 编码 + 状态 + 属性               │
    │ 行为        │ 动词 + 事项域（IT/R · IT/M · IT/G）    │
    ├─────────────┼────────────────────────────────────────┤
    │ 环境        │ 计算环境 · 边界 · 通信通道             │
    │ 条件        │ 触发事件 · 例外                        │
    ├─────────────┼────────────────────────────────────────┤
    │ 控制        │ 控制机制(T/M/G) · 义务模态 · 程度      │
    └─────────────┴────────────────────────────────────────┘

    控制的约束对象 ──→ 相关方 / 客体 / 行为 中的一项或多项
                    （从结构自动推导，无需显式标注）
    ```

## 2.2 设计说明

### 2.2.1 八维度结构

+   原子要求的八个维度组分为三个层次：

-   **元数据层**（法规溯源、条款特征）：描述条款本身的来源和分类属性，不涉及义务内容。
-   **业务语义层**（相关方、客体、行为、环境、条件）：描述义务的业务场景——谁、对什么、做什么、在哪里、什么条件下。
-   **约束层**（控制）：描述对业务行为施加的约束——用什么控制机制、什么模态、达到什么程度。

+   控制的约束对象不限于行为，可以是相关方、客体、行为中的一项或多项。约束对象从结构自动推导：有行为时约束行为，无行为时约束唯一存在的相关方或客体。

### 2.2.2 相关方与 RACISV

+   相关方维度统一描述条款涉及的所有参与方，每个参与方标注 RACISV 角色：

| 角色 | 含义   | 说明                                    | 责任类型      | 责任程度 |
| ---- | ------ | --------------------------------------- | ------------- | -------- |
| R    | 执行者 | 实际执行任务的人                        | 直接责任      | 主要责任 |
| A    | 负责人 | 最终对结果负责的人（每条义务只能有1个） | 管理责任      | 主要责任 |
| C    | 顾问   | 需要征询意见的人（双向沟通）            | 技术/建议责任 | 次要责任 |
| I    | 知情者 | 需要被告知的人（单向沟通）              | 无            | 无问责   |
| S    | 审批者 | 审批和签字批准的人（含会签和终审）      | 管理/领导责任 | 次要责任 |
| V    | 验证者 | 验证执行结果的人                        | 监督责任      | 次要责任 |

+   设计依据：原模型将参与方分为"责任主体"和"协作方"两个字段，角色语义模糊。RACISV 提供了更精确的角色分类，同一实体可在同一条款中承担多个角色（如监管机构同时是 I 和 V）。
+   S（审批者）包含两个子类型：

-   **会签**：在流程中间环节把关，属于管理责任。
-   **终审**：最终决策环节，属于领导责任。视制度体系缺陷程度，领导责任可能升级为主要责任。

### 2.2.3 环境三要素

+   环境维度按纵深防御模型分为三个子维度：

| 子维度   | 含义                | 示例                                         |
| -------- | ------------------- | -------------------------------------------- |
| 计算环境 | 数据/系统运行的场所 | 生产环境、测试环境、云环境、境内、境外、机房 |
| 边界     | 不同环境之间的分界  | DMZ、网络边界、内外网边界、跨境              |
| 通信通道 | 数据跨越边界的路径  | 互联网、专线/VPN、无线网络、移动存储介质     |

+   三者形成完整链条：**计算环境 → 边界 → 通信通道 → 计算环境**。
+   信息资产词库中的同一实体可在不同条文中充当不同角色（客体、计算环境、边界或通信通道），角色判定规则见 5.4 节。

### 2.2.4 三域行为架构

+   行为由**动词**和**事项**两部分组成。动词描述"做什么动作"，事项描述"关注什么领域"。行为所涉及的领域分为三个域：

| 域          | 事项来源         | 事项性质           | 行为示例                         |
| ----------- | ---------------- | ------------------ | -------------------------------- |
| IT/R 资源域 | DASPR 信息资产   | 资产实体（→客体）  | 处理 + D1个人信息 = 处理个人信息 |
| IT/M 管理域 | 管理事项词库     | 管理关注事项       | 开展 + 风险评估 = 开展风险评估   |
| IT/G 治理域 | 治理事项词库     | 治理关注事项       | 建立 + 岗位/角色 = 建立岗位     |

+   **IT/R 资源域**：事项即 DASPR 实体，已由客体字段承载，行为字段只需填动词。
+   **IT/M 管理域 / IT/G 治理域**：事项由管理/治理事项词库提供，行为字段需同时填写动词和事项。
+   行为的存在性仍取决于条文结构：相关方(R) + 客体共现时必填，否则可无（见 R05 设计）。
+   **设计依据**：管理/治理词条（如"风险评估"、"岗位设置"）是关注的**事项**，不是**行为**本身。"风险评估"是你关注的事情，"开展风险评估"才是行为。事项与动词的分离使行为表达更精确，也避免了事项与控制机制的混淆。

### 2.2.5 控制机制与事项域的分离

+   原 T/M/G 词库混合了两类语义：

| 原词条           | 实际语义 | 应归属         |
| ---------------- | -------- | -------------- |
| 加密             | 技术工具 | T 控制机制 ✓   |
| 访问控制         | 技术工具 | T 控制机制 ✓   |
| 变更管理         | 管理事项 | IT/M 事项域    |
| 风险评估         | 管理事项 | IT/M 事项域    |
| 岗位/角色设置    | 治理事项 | IT/G 事项域    |
| 组织架构         | 治理事项 | IT/G 事项域    |

+   拆分后，T/M/G 词库只保留真正的**控制机制**——用来约束行为的工具/手段：

| 类型 | 含义       | 控制机制示例                       | 类比           |
| ---- | ---------- | ---------------------------------- | -------------- |
| T    | 技术机制   | 加密、访问控制、审计、IDS          | 技术工具       |
| M    | 管理机制   | 审批/授权、四眼原则、合同约束      | 管理工具       |
| G    | 治理机制   | 职责分离、授权矩阵、考核问责       | 治理工具       |

+   三类控制机制的对称结构（参考 NIST 800-53 控制族/控制项两层结构、COSO 控制活动类型）：

| 维度     | 事项域（做什么事） | 控制机制（用什么约束） |
| -------- | ------------------ | ---------------------- |
| 技术(T)  | DASPR 信息资产     | 加密、访问控制、审计…… |
| 管理(M)  | 管理事项           | 审批、四眼原则、合同…… |
| 治理(G)  | 治理事项           | 职责分离、授权矩阵……   |

+   每一类都是：**事项域（场景/对象） + 控制机制（手段/工具）**。事项域归入行为或客体维度，控制机制归入控制维度。

### 2.2.6 条件独立

+   条件维度（触发事件、例外）独立于其他维度，理由：

-   **与环境的区别**：环境使用信息资产词库，描述持续存在的空间背景；条件是自由文本，描述状态变化的开关。
-   **触发事件与例外的关系**：两者是义务生效边界的正反两面——触发事件划入（满足则激活），例外划出（满足则豁免）。

### 2.2.7 控制维度的精简历程

+   控制维度经过多轮精简，最终只保留四个子维度（控制机制、义务模态、时限、量化指标）：

-   **审批层级删除**：由相关方 S 角色 + 属性词承载。
-   **证据要求删除**：拆为独立原子要求。
-   **覆盖范围删除**：被属性词机制吸收。
-   **义务类别删除**：可从行为动词推导，且存在多值问题。
-   **要求类型删除**：控制机制已自带 T/M/G 前缀。
-   **规则内容删除**：行为 + 控制机制 + 程度已完整表达。
-   **控制手段重定义**：M/G 活动域词条拆出为事项域，T/M/G 只保留控制机制。

### 2.2.8 属性词机制

+   相关方、客体、环境三个维度组均可附带**属性词**，用于限定要素的特征。
+   设计依据：监管条文中的"适用条件"本质上是对各要素的特征限定（如"系统重要性银行"限定相关方，"数据总量超过100万条"限定客体）。将这些条件拆解到各要素的属性词中，消除了"适用条件"作为独立字段的必要性。

| 维度组 | 典型属性维度           | 属性词示例                                              |
| ------ | ---------------------- | ------------------------------------------------------- |
| 相关方 | 规模、级别、资质、性质 | 系统重要性银行、CII运营者、持牌机构、大型数据处理者     |
| 客体   | 数量、敏感度、分类分级 | 数据量超过100万条、涉及敏感个人信息、等保三级及以上系统 |
| 环境   | 位置、性质、安全等级   | 境内、跨境、互联网暴露、加密通道                        |

+   属性词为自由文本，不设固定词库；标注时忠实于条文原文表述。

### 2.2.9 信息资产词库（DASPR）的分层设计

+   信息资产词库按五层架构分类，每层对应一个编码前缀：

| 层       | 编码前缀 | 覆盖范围                                       |
| -------- | -------- | ---------------------------------------------- |
| 数据层   | D        | 个人信息、重要数据、日志、凭证、配置等信息资产 |
| 应用层   | A        | 业务系统、数据库、中间件、接口、CII            |
| 系统层   | S        | 网络、服务器、终端、IoT、存储介质              |
| 物理层   | P        | 机房、办公场所、灾备中心                       |
| 文档层   | R        | 策略文件、方案报告、预案、操作记录             |

+   五层按信息安全管理的经典分层组织，每层内的实体在同一抽象层级上。
+   客体、计算环境、边界、通信通道四个字段共用同一套信息资产词库，同一实体在不同条款中可充当不同角色。

# 3 词库体系

## 3.1 信息资产词库（DASPR）

+   客体、计算环境、边界、通信通道四个字段共用一套信息资产词库。同一实体在不同条款中可充当不同角色，角色由各对应字段分别标注。
+   操作编码规则：客体字段使用 D/A/S/P/R 前缀编码；计算环境、边界与通信通道字段使用实体名称文本（不用编码）。

**D 类：数据层**

| 代码 | 名称         | 说明                                       | 适用状态集                                    |
| ---- | ------------ | ------------------------------------------ | --------------------------------------------- |
| D1   | 个人信息     | 与可识别自然人相关的各类信息               | 采集、传输、存储、使用、共享、出境、删除/销毁 |
| D2   | 敏感个人信息 | 生物识别、金融账户、行踪轨迹等特殊类别信息 | 同 D1                                         |
| D3   | 重要数据     | 法规定义的重要数据目录中列明的数据         | 同 D1                                         |
| D4   | 核心数据     | 关系国家安全、国民经济命脉、重要民生的数据 | 同 D1                                         |
| D5   | 政务数据     | 国家机关在履行法定职责中收集和产生的数据   | 同 D1                                         |
| D6   | 一般业务数据 | 企业经营中产生的一般商业及业务数据         | 同 D1                                         |
| D7   | 日志数据     | 操作日志、安全日志、审计日志等记录型数据   | 生成、存储、分析、归档、删除                  |
| D8   | 鉴别信息     | 口令、密钥、证书、令牌等身份凭据           | 生成、传输、存储、使用、变更、销毁            |
| D9   | 配置数据     | 系统配置参数、安全基线参数等配置型数据     | 创建、变更、存储、备份、恢复                  |

**A 类：应用层**

| 代码 | 名称             | 说明                                       | 适用状态集                               |
| ---- | ---------------- | ------------------------------------------ | ---------------------------------------- |
| A1   | 业务应用系统     | 直接支撑业务运营的应用软件系统             | 规划、开发、测试、部署、运行、变更、下线 |
| A2   | 基础设施平台     | 云平台、操作系统、虚拟化平台等基础运行环境 | 同 A1                                    |
| A3   | 数据库           | 结构化或非结构化数据的存储管理系统         | 部署、运行、维护、备份、迁移、下线       |
| A4   | 中间件与接口     | 系统间通信与集成的中间层组件及 API         | 同 A1                                    |
| A5   | 关键信息基础设施 | 依法认定的关键信息基础设施                 | 同 A1                                    |

**S 类：系统层**

| 代码 | 名称         | 说明                               | 角色说明                                   |
| ---- | ------------ | ---------------------------------- | ------------------------------------------ |
| S1   | 内部网络     | 组织内部局域网及专网               | 作客体时标 S1；作计算环境时填"内部网络"    |
| S2   | 互联网       | 对外互联网出口及相关边界设施       | 作客体时标 S2；作通信通道时填"互联网"      |

| S5   | 边界/DMZ     | 网络边界区及非军事化区             | 作客体时标 S5；作边界时填"DMZ"或"网络边界" |
| S6   | 服务器       | 数据中心及机房内的物理或虚拟服务器 | 采购、部署、运行、维护、报废               |
| S7   | 用户终端     | PC、工作站等办公终端               | 同 S6                                      |
| S8   | 移动设备     | 手机、平板等移动办公设备           | 注册、使用、回收                           |
| S9   | 移动存储介质 | U盘、移动硬盘等可移动存储设备      | 采购、登记、使用、销毁                     |
| S10  | IoT 设备     | 工控、传感、摄像头等物联网设备     | 部署、运行、维护、报废                     |

**P 类：物理层**

| 代码 | 名称          | 说明                             | 适用状态集                   |
| ---- | ------------- | -------------------------------- | ---------------------------- |
| P1   | 机房/数据中心 | 承载 IT 系统运行的专用物理空间   | 规划、建设、运行、扩容、退役 |
| P2   | 办公场所      | 日常办公区域                     | —                            |

## 4.2 法规溯源字段

+   **法规名称**：法规/标准全称，如"中华人民共和国数据安全法"。
+   **条款编号**：原始条款的层级定位，如"第三章第二十一条第一款"；操作简写格式：`数据安全法§21`。
+   **效力层级**：法律、行政法规、部门规章、国家标准、行业标准、团体标准。
+   **适用行业**：金融、电信、医疗、能源、政务、通用等；通用时可省略。

## 4.3 条款特征字段

+   **安全目标**：条款要求达成的 COAST 安全目标，直接从 3.5 节词库中选取，格式 `{一级} > {二级} > {三级}`。尽量填到三级；跨多个三级目标时可停留二级；多个目标用分号分隔。处罚性条款通常不填。声明性安全目标条款（如"应当保障数据完整性"）在此字段填写目标，控制机制可留空。
+   **保护法益**：条文原文明确表述的保护目的，如"数据安全"、"国家安全"、"个人信息权益"。
+   **法律后果**：违规处罚，通常引用法律责任章节，如"数据安全法§48"。无则留空。

## 4.4 相关方字段

+   **角色**：条款涉及的参与方，从角色词库选取归一化类型，格式 `{归一化类型}【{类型}】`，如 `数据处理者【组织】`。一条原子要求可包含多个相关方。
+   **RACISV**：该参与方在本条义务中的职责类型，见 2.2.2 节。每个相关方标注一个或多个 RACISV 角色。
+   **相关方属性**：限定相关方特征的条件词，如"处理100万人以上个人信息的"、"系统重要性银行"。条款未显式限定时留空。

## 4.5 客体字段

+   **实体**：行为作用的实体对象，使用 DASPR 编码，如 `D3 重要数据`。允许多值；无实体客体时留空。
+   **状态**：客体的处理阶段，从实体适用状态集中选取，如 `[传输]`、`[存储]`。编码与状态的组合格式：`D1 个人信息[传输]`。
+   **客体属性**：限定客体特征的条件词，如"数据量超过100万条"、"涉及国家秘密的"。条款未显式限定时留空。

## 4.6 行为字段

+   **动词**：相关方对客体/事项执行的动作，使用归一化动词，见 3.3.1 节。必填条件：当同一条原子要求中同时存在相关方（R角色）和客体时必填，否则可留空。
+   **事项**：行为所关注的管理/治理领域，从 IT/M 或 IT/G 事项域选取（见 3.3.2、3.3.3 节）。IT/R 资源域行为不填事项（资产实体由客体字段承载）。

| 行为域  | 动词示例 | 事项示例         | 组合后的行为     |
| ------- | -------- | ---------------- | ---------------- |
| IT/R    | 处理     | —（客体承载）    | 处理个人信息     |
| IT/M    | 开展     | 风险评估         | 开展风险评估     |
| IT/G    | 建立     | 岗位/角色设置    | 建立岗位         |

## 4.7 环境字段

+   **计算环境**：数据/系统处理或存储发生的场所，如"生产环境"、"云环境"、"境内"。无显式限定时留空。
+   **边界**：不同环境之间的分界，如"DMZ"、"网络边界"、"内外网边界"。无显式限定时留空。
+   **通信通道**：数据跨越边界流转的路径，如"互联网"、"专线/VPN"、"无线网络"、"移动存储介质"。无显式限定时留空。
+   **环境属性**：限定环境特征的条件词，如"跨境"、"互联网暴露的"。条款未显式限定时留空。

## 4.8 条件字段

+   **触发事件**：动态事件驱动的义务激活条件——事件发生时义务从休眠变为激活。如"发现数据安全缺陷或漏洞"、"数据安全事件发生"。无则留空。
+   **例外**：义务的豁免条件——满足该条件时义务不适用。如"经中华人民共和国主管机关批准的除外"。无则留空。

## 4.9 控制字段

+   **控制机制**：具体的控制工具/手段，从 T/M/G 机制词库选取，见 3.4 节。使用前缀标明类型，格式：`T: 密码/加密; M: 审批/授权`。允许多类型混合。条文未指定具体机制时留空。
+   **义务模态**：条款的义务性质：

| 值   | 关键词                 | 含义             |
| ---- | ---------------------- | ---------------- |
| 应   | 应、应当、须、必须     | 强制作为         |
| 不得 | 不得、不应、禁止、严禁 | 强制不作为       |
| 可以 | 可以、可               | 授权许可，非强制 |
| 宜   | 宜、鼓励、支持         | 推荐做法，非强制 |

+   **时限**：条款明确的时间约束。参考值：立即、及时、定期（注明周期，如"每年一次"）、N 日内。无则留空。
+   **量化指标**：条款包含的具体数值约束。示例：密码长度≥8位、日志留存≥6个月、RPO≤4小时。无则留空。

# 5 标注规则

## 5.1 多值、留空与推断规则

+   **多值标注**：所有维度均允许多值。相关方、客体、控制机制、安全目标均可标注多项，用分号分隔。
+   **留空规则**：当条款未显式指定某维度时，该维度留空，表示"不限/未指定"。不得填写"全部"、"不限"等文字。
+   **推断克制**：标注忠实于条款原文。仅当上下文逻辑关系明确时允许推断，不做过度解读。
+   **颗粒度就高**：标注优先使用原文表述对应的最具体分类。如原文为"敏感个人信息"，不应标注上位概念"个人信息"（D1），应标注 D2。

## 5.2 属性词标注规则

+   **属性词的来源**：属性词提取自条文中对要素的限定性描述。当条文使用"……的"定语结构修饰相关方、客体或环境时，该定语即为属性词的候选。
+   **属性词与要素的绑定**：属性词应挂在其直接限定的要素上，不应集中堆放。

| 条文片段                       | 要素   | 属性词                   |
| ------------------------------ | ------ | ------------------------ |
| 关键信息基础设施运营者         | 相关方 | 关键信息基础设施运营者   |
| 处理100万人以上个人信息的      | 客体   | 数据量超过100万条        |
| 存储于中华人民共和国境内的数据 | 环境   | 境内                     |
| 通过互联网提供服务的系统       | 环境   | 互联网暴露               |
| 未通过安全评估的境外机构       | 相关方 | 未通过安全评估的；境外的 |

## 5.3 省略还原规则

+   监管条文常省略要素，拆解时需从上下文还原：

| 省略类型     | 还原方式                       | 示例                                      |
| ------------ | ------------------------------ | ----------------------------------------- |
| 主体省略     | 从章节标题、适用范围条款推断   | "所有变更必须经过审批" → 还原执行者       |
| 客体省略     | 从行为动词推断变更/处理的对象  | "应当加强风险监测" → 还原监测对象         |
| 环境省略     | 从文档上下文推断适用的环境     | 通常默认不限环境                          |
| 隐含义务动词 | "是……"句式还原为"应当承担……"   | "X是安全第一责任人" → X应当承担安全责任   |
| 语法主语偏移 | 活动名称作主语时还原真正的主体 | "变更管理应当确保……" → 负责变更管理的组织 |

+   还原依据为**条文显式提及的上下文**，不做过度推断。

## 5.4 信息资产词库的角色机制

+   同一实体在不同条款中可充当不同角色：

| 实体          | 作为客体 | 作为计算环境 | 作为边界 | 作为通信通道 |
| ------------- | -------- | ------------ | -------- | ------------ |
| 云平台        | A2       | 云环境       | —        | —            |
| 互联网        | S2       | —            | —        | 互联网       |
| 专线/VPN      | S3       | —            | —        | 专线/VPN     |
| 移动存储介质  | S9       | —            | —        | 移动存储介质 |
| 机房/数据中心 | P1       | 机房         | —        | —            |
| 边界/DMZ      | S5       | —            | DMZ      | —            |
| 内部网络      | S1       | 内部网络     | —        | —            |

+   判定规则：

-   当实体作为**被管理的对象**时，标注为客体。
-   当实体描述**处理/存储发生的场所**时，标注为计算环境。
-   当实体描述**不同环境之间的分界**时，标注为边界。
-   当实体描述**数据流转的经过路径**时，标注为通信通道。

## 5.5 RACISV 标注规则

+   同一角色在不同条款中可承担不同 RACISV 职责，职责由条文语境判定：

| 条文片段                           | 角色           | RACISV |
| ---------------------------------- | -------------- | ------ |
| 数据处理者应当采取加密措施         | 数据处理者     | R      |
| 应当明确数据安全负责人             | 数据安全负责人 | A      |
| 经安全评估机构评估后方可           | 评估/认证机构  | C      |
| 及时告知用户                       | 用户           | I      |
| 经中华人民共和国主管机关批准       | 监管机构       | S      |
| 向有关主管部门报告                 | 监管机构       | I; V   |
| 第三方服务商应在合同范围内处理数据 | 第三方服务商   | R      |

+   同一角色可在同一条款中承担多个 RACISV 职责（如监管机构同时是 I 和 V）。

## 5.6 T 机制分层标注规则

+   技术控制机制默认标到第一层（安全能力大类），如"密码/加密"。
+   仅在条款原文明确指定具体技术手段时才标注第二层，如"传输层加密(TLS)"。
+   环境字段（通信通道等）已编码"传输"/"存储"等信息，T 机制不重复编码这些场景维度。

## 5.7 行为域判定规则

+   条文中的动作属于哪个域，取决于其作用对象：

| 条文                               | 动词 | 作用对象     | 域   | 事项           |
| ---------------------------------- | ---- | ------------ | ---- | -------------- |
| 数据处理者应当加密传输个人信息     | 处理 | D1 个人信息  | IT/R | —（客体承载）  |
| 应当定期开展风险评估               | 开展 | 风险评估     | IT/M | 风险评估       |
| 应当明确数据安全负责人             | 建立 | 岗位/角色    | IT/G | 岗位/角色设置  |
| 运维人员对生产环境的所有变更应审批 | 变更 | 生产环境系统 | IT/R | —（客体承载）  |

+   判断标准：作用对象是 DASPR 信息资产 → IT/R 域；作用对象是管理活动 → IT/M 域；作用对象是治理结构 → IT/G 域。

## 5.8 条文拆分规则

+   出现以下任一情形时，拆分为多条独立原子记录：

-   条文涉及多个不同的 R 角色（执行者），每个执行者单独一条记录
-   条文中义务模态混合（"应"与"不得"并存），按模态分别单独一条记录
-   条文中存在不同触发事件，每个触发事件单独一条记录
-   条文中包含证据要求（如"留存操作记录"），证据要求拆为独立的原子要求

## 5.9 不拆的条文类型

+   以下类型条文跳过，不纳入原子记录：

| 类型       | 示例                    | 原因                         |
| ---------- | ----------------------- | ---------------------------- |
| 定义条款   | 第3条 数据的定义        | 无义务，仅定义术语           |
| 政策宣示   | 第7条 国家保护数据权益  | 无可验证合规动作             |
| 立法目的   | 第1条 制定本法目的      | 无义务                       |
| 纯授权条款 | 第54条 军事数据另行制定 | 义务在子法规中，待子法规拆解 |

# 6 拆解步骤

+   按以下步骤对每条条文执行拆解：

-   **Step 1　识别是否需拆解**：判断条文是否属于不拆类型（见 5.9 节）。属于则跳过。
-   **Step 2　识别相关方**：条文中有哪些参与方？注意辨别语法主语偏移（见 5.3 节）。为每个参与方标注 RACISV 角色。多个 R 角色则准备生成多条记录。
-   **Step 3　识别客体与行为域**：条文针对什么？判断属于 IT/R（信息资产）、IT/M（管理事项）还是 IT/G（治理事项）。IT/R 域标注 DASPR 编码和状态；IT/M 或 IT/G 域标注事项名称。
-   **Step 4　确定动词**：相关方和客体/事项共现时确定归一化动词。
-   **Step 5　标注环境**：有无特定计算环境、边界、通信通道？分别填入，无则留空（见 5.4 节角色机制）。
-   **Step 6　标注属性词**：检查条文中是否有对相关方、客体、环境的限定性描述，有则提取为对应的属性词（见 5.2 节）。
-   **Step 7　标注条件**：有无触发事件？有无例外？分别填入。如有不同触发事件，准备拆分多条记录。
-   **Step 8　标注控制**：判断义务模态（见 4.9 节）；从 T/M/G 机制词库选取控制机制（见 3.4 节）；填写时限、量化指标。
-   **Step 9　填写条款元数据**：安全目标（从 3.5 节 COAST 词库选取，尽量到三级）、保护法益、法律后果、法规溯源。
-   **Step 10　归一化与检查**：对照词表归一化角色类型、映射客体编码至 DASPR 体系、规范控制机制表达。检查是否有证据要求需拆为独立记录。

    },

## 8.3 内规侧记录的差异

+   内规记录复用监管侧同一 schema，额外增加两个字段；`stakeholders[].type_class` 字段不适用于内规侧：

| 附加字段  | 类型   | 说明                                                            |
| --------- | ------ | --------------------------------------------------------------- |
| `doc_ref` | string | 内规来源文件编号，如 `DSP-OPS-012`                              |
| `scope`   | string | 内规适用范围，如 `"全公司"` / `"信息科技部"` / `"核心业务系统"` |

+   内规主体覆盖判断由监管侧 `stakeholders[].type_class` 驱动，见 GUIDE-REG-002 第 2.3 节。
+   `clause.legal_interest` 和 `clause.legal_consequence` 在内规记录中通常为 null。
