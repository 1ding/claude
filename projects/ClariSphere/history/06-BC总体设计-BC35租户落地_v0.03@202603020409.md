## 2.3 业务价值

+   **解决的核心问题**：
    -   知识中台的标准化知识（场景点、控制点、角色点）如何落地到租户的实际环境
    -   租户的IT资产、组织架构、制度体系如何与标准知识建立映射关系
    -   如何实现"要求→落实→责任到人"的完整追溯链

+   **业务价值**：
    -   **管理透明化**：租户的资产、场景、控制、制度、责任全部可视化
    -   **双向追溯**：标准知识→租户实例的正向映射，租户实例→标准知识的反向溯源
    -   **责任到人**：通过岗位角色映射，实现责任点到具体人员的精确定位
    -   **快速落地**：基于标准模板和最佳实践，快速完成租户环境的合规配置

## 2.4 范围边界

+   **范围内**：
    -   租户资产管理（IT资产登记、分类、场景关联）
    -   租户场景映射（标准场景点→租户场景的映射与定制）
    -   租户控制映射（标准控制点→租户控制的映射与定制）
    -   租户制度编写（制度内容编写、制度与控制点关联、制度模板管理）
    -   岗位角色映射（标准角色点→租户岗位/人员的映射）
    -   安全策略基础配置（策略模板、策略与制度关联）

+   **范围外**：
    -   知识中台数据管理（由 BC-40 知识实体、BC-41 知识图谱负责）
    -   合规评估与差距分析（由 BC-31 合规管理负责）

    -   制度发布审批与版本管理（由 BC-37 制度管理负责）

# 3 子领域划分方案

## 3.1 子领域划分概述

+   BC-35 租户落地按照业务能力和数据内聚性，划分为 6 个子领域
+   子领域划分遵循以下原则：
    -   **业务内聚**：同一子领域内的功能服务于同一业务目标
    -   **数据内聚**：同一子领域内的实体具有强关联关系
    -   **职责单一**：每个子领域有明确的职责边界，避免职责重叠
    -   **依赖清晰**：子领域间的依赖关系清晰，避免循环依赖

+   BC-35 子领域划分如下表所示

    | 子领域编号 | 子领域名称   | 核心职责                                     | 核心实体                     | 对应Epic      |
    | ---------- | ------------ | -------------------------------------------- | ---------------------------- | ------------- |
    | SD-01      | 资产管理     | 租户IT资产登记、分类、场景关联、批量导入导出 | 租户资产、资产分类、资产场景 | EP-PL-01      |
    | SD-02      | 场景映射     | 标准场景点→租户场景的映射与定制              | 租户场景、场景映射关系       | EP-PL-01      |
    | SD-03      | 控制映射     | 标准控制点（管理+技术）→租户控制的映射与定制 | 租户控制、控制映射关系       | EP-PL-01      |
    | SD-04      | 制度管理     | 租户制度编写、导入、关联控制点（管理控制实现）| 租户制度、制度控制关联       | EP-BD-01/02   |
    | SD-05      | 技术方案管理 | 技术方案制定、导入、基线配置（技术控制实现） | 技术方案、方案基线、方案模板 | EP-BD-03      |
    | SD-06      | 责任映射     | 标准角色点→租户岗位/人员的映射               | 岗位角色映射、责任点         | EP-PL-01      |

    +   表 BC-35 子领域划分

## 3.2 SD-01 资产管理子领域

+   **核心职责**：租户IT资产登记、资产分类、资产与场景关联、批量导入导出

+   **核心实体**：
    -   租户资产（TenantAsset）：资产编号、资产名称、资产类型、所属租户、创建时间
    -   资产分类（AssetCategory）：分类编号、分类名称、父分类、层级
    -   资产场景关联（AssetSceneMapping）：资产ID、场景ID、关联类型

+   **核心能力**：
    -   资产登记：支持手工录入、批量导入、API对接等多种方式
    -   资产分类：按照行业标准（如ISO 27001资产分类）进行分类管理
    -   资产场景关联：将资产与租户场景建立关联，支撑场景化控制
    -   批量导入：支持从 Excel、CSV 批量导入租户资产数据
    -   批量导出：支持将租户资产导出为 Excel、CSV 格式
    -   导入校验：导入前校验数据格式、必填字段、资产编号唯一性

+   **对外接口**：
    -   提供资产查询接口给 SD-02 场景映射子领域
    -   提供资产数据给 BC-32 验证检查（用于证据采集）
    -   依赖 BC-13 文件管理进行文件上传下载

## 3.3 SD-02 场景映射子领域

+   **核心职责**：标准场景点→租户场景的映射与定制

+   **核心实体**：
    -   租户场景（TenantScene）：场景ID、场景名称、标准场景点ID、租户ID、定制内容
    -   场景映射关系（SceneMapping）：标准场景点ID、租户场景ID、映射类型、映射状态

+   **核心能力**：
    -   场景映射：将知识中台的标准场景点映射到租户的实际场景
    -   场景定制：支持租户对标准场景进行定制（增加属性、调整描述等）
    -   场景激活：租户可选择性激活需要的场景，未激活场景不参与合规评估

+   **对外接口**：
    -   依赖 BC-40 知识实体获取标准场景点数据
    -   提供租户场景数据给 BC-31 合规管理、BC-32 验证检查

## 3.4 SD-03 控制映射子领域

+   **核心职责**：标准控制点（管理+技术）→租户控制的映射与定制

+   **核心实体**：
    -   租户控制（TenantControl）：控制ID、控制名称、控制类型（管理/技术）、标准控制点ID、租户ID、定制内容
    -   控制映射关系（ControlMapping）：标准控制点ID、租户控制ID、映射类型、映射状态

+   **核心能力**：
    -   控制映射：将知识中台的标准控制点（管理控制+技术控制）映射到租户的实际控制措施
    -   控制定制：支持租户对标准控制进行定制（调整实施方式、补充说明等）
    -   控制分类：区分管理控制和技术控制，为后续实现提供依据
    -   控制激活：租户可选择性激活需要的控制，未激活控制不参与验证

+   **对外接口**：
    -   依赖 BC-40 知识实体获取标准控制点数据
    -   提供租户控制数据给 BC-31 合规管理、BC-32 验证检查
    -   提供管理控制清单给 SD-04 制度管理（制度关联）
    -   提供技术控制清单给 SD-05 技术方案管理（方案关联）

## 3.5 SD-04 制度管理子领域

+   **核心职责**：租户制度编写、导入、制度与控制点关联（管理控制的实现）

+   **核心实体**：
    -   租户制度（TenantPolicy）：制度ID、制度名称、制度内容、租户ID、状态
    -   制度控制关联（PolicyControlMapping）：制度ID、控制ID、关联类型
    -   制度模板（PolicyTemplate）：模板ID、模板名称、模板内容、适用场景

+   **核心能力**：
    -   制度编写：基于模板和外规要求编写租户内部制度
    -   制度导入：支持从 Word、PDF 导入制度内容，自动解析章节结构
    -   制度关联：将制度与租户控制（管理控制）建立关联，支撑制度溯源链（L3）
    -   制度提交：编写完成的制度提交到 BC-37 制度管理进行发布审批
    -   导入校验：导入前校验制度格式、章节结构、必填字段

+   **对外接口**：
    -   依赖 BC-40 知识实体获取外规要求点数据
    -   依赖 SD-03 控制映射获取租户控制（管理控制）数据
    -   提供制度数据给 BC-37 制度管理（发布审批）
    -   提供制度数据给 BC-31 合规管理（制度追溯）
    -   依赖 BC-13 文件管理进行文件上传下载

## 3.6 SD-05 技术方案管理子领域

+   **核心职责**：技术方案制定、导入、基线配置（技术控制的实现）

+   **核心实体**：
    -   技术方案（TechnicalSolution）：方案ID、方案名称、方案内容、租户ID、状态
    -   方案基线（SolutionBaseline）：基线ID、基线名称、配置项、适用资产
    -   方案模板（SolutionTemplate）：模板ID、模板名称、模板内容、技术类型

+   **核心能力**：
    -   方案制定：基于模板制定技术方案（如操作系统基线、数据库基线等）
    -   方案导入：支持从 Excel、JSON 导入技术方案和基线配置
    -   基线配置：配置技术基线参数，关联到租户资产
    -   方案关联：将技术方案与租户控制（技术控制）建立关联，支撑技术落地链（L4）
    -   导入校验：导入前校验方案格式、配置项完整性、参数有效性

+   **对外接口**：
    -   依赖 BC-40 知识实体获取技术方案模板数据
    -   依赖 SD-01 资产管理获取租户资产数据
    -   依赖 SD-03 控制映射获取租户控制（技术控制）数据
    -   提供技术方案数据给 BC-32 验证检查（技术验证）
    -   依赖 BC-13 文件管理进行文件上传下载

## 3.7 SD-06 责任映射子领域

+   **核心职责**：标准角色点→租户岗位/人员的映射

+   **核心实体**：
    -   岗位角色映射（RoleMapping）：标准角色点ID、租户岗位ID、租户人员ID、映射类型
    -   责任点（ResponsibilityPoint）：责任点ID、控制ID、场景ID、角色ID、RACISV角色

+   **核心能力**：
    -   岗位映射：将知识中台的标准角色点映射到租户的实际岗位
    -   人员映射：将岗位映射到具体人员，实现责任到人
    -   责任点生成：基于控制点、场景点、角色点的组合，自动生成责任点

+   **对外接口**：
    -   依赖 BC-41 知识图谱获取责任分配基准图数据
    -   依赖 BC-10 用户管理获取租户组织架构、岗位、人员数据
    -   提供责任点数据给 BC-32 验证检查、BC-33 治理监督

# 5 公共架构决策

## 5.1 技术架构决策

### 5.1.1 微服务归属

+   BC-35 租户落地归属于微服务 `svc-tenant-deployment`

+   微服务职责：
    -   提供租户资产、场景、控制、制度、责任映射的 CRUD 服务
    -   提供租户落地数据的查询接口给下游 BC
    -   提供租户落地数据的同步接口给上游 BC

### 5.1.2 数据存储决策

+   **数据库选型**：PostgreSQL（关系型数据库）
+   **选型理由**：
    -   租户落地数据具有明确的关系结构（资产-场景、控制-制度、角色-人员等）
    -   需要支持复杂的关联查询和事务一致性
    -   数据量适中（单租户数据量预估在 10 万条以内）

+   **数据隔离方案**：
    -   采用租户 ID 字段进行逻辑隔离
    -   所有表均包含 `tenant_id` 字段，作为分区键
    -   通过数据库行级安全策略（RLS）强制租户隔离

### 5.1.3 缓存策略

+   **缓存层**：Redis
+   **缓存对象**：
    -   租户场景映射关系（高频查询，低频变更）
    -   租户控制映射关系（高频查询，低频变更）
    -   岗位角色映射关系（高频查询，低频变更）

+   **缓存失效策略**：
    -   写操作时主动失效相关缓存
    -   设置 TTL 为 1 小时，防止缓存雪崩

### 5.1.4 API 设计原则

+   **RESTful API**：
    -   资源命名：`/api/v1/tenant-deployment/{resource}`
    -   HTTP 方法：GET（查询）、POST（创建）、PUT（更新）、DELETE（删除）

+   **分页查询**：
    -   支持 `page` 和 `page_size` 参数
    -   默认 `page_size=20`，最大 `page_size=100`

+   **过滤与排序**：
    -   支持通用过滤参数（如 `tenant_id`、`status`、`created_at` 等）
    -   支持排序参数 `sort_by` 和 `order`（asc/desc）

### 5.2.2 映射关系设计

+   **映射类型枚举**：
    -   `DIRECT`：直接映射（1:1）
    -   `CUSTOMIZED`：定制映射（1:1，但有定制内容）
    -   `MERGED`：合并映射（N:1，多个标准节点合并为一个租户节点）
    -   `SPLIT`：拆分映射（1:N，一个标准节点拆分为多个租户节点）
    -   `DISABLED`：禁用映射（标准节点在租户环境中不适用）

+   **映射状态枚举**：
    -   `DRAFT`：草稿（映射关系已创建，但未激活）
    -   `ACTIVE`：激活（映射关系生效，参与合规评估）
    -   `INACTIVE`：停用（映射关系暂时停用，不参与合规评估）
    -   `ARCHIVED`：归档（映射关系已废弃，仅保留历史记录）

### 5.2.3 版本管理设计

+   **版本控制策略**：
    -   租户场景、租户控制、租户制度均支持版本管理
    -   每次修改创建新版本，保留历史版本
    -   版本号格式：`v{major}.{minor}`（如 v1.0、v1.1、v2.0）

+   **版本状态**：
    -   `DRAFT`：草稿版本
    -   `PUBLISHED`：已发布版本
    -   `DEPRECATED`：已废弃版本

## 5.3 安全与权限决策

### 5.3.1 权限模型

+   **基于角色的访问控制（RBAC）**：

    -   UR-03 制度编写者：拥有制度编写和制度控制关联的权限

    -   操作时间、操作人、操作类型、操作对象、操作前后数据

# 6 跨子领域约束

## 6.1 数据一致性约束

### 6.1.1 映射关系一致性

+   **约束规则**：
    -   租户场景必须映射到有效的标准场景点（来自 BC-40）
    -   租户控制必须映射到有效的标准控制点（来自 BC-40）
    -   岗位角色映射必须映射到有效的标准角色点（来自 BC-41）

+   **校验时机**：
    -   创建映射关系时，校验标准节点是否存在
    -   激活映射关系时，校验标准节点是否仍然有效

### 6.1.2 制度控制关联一致性

+   **约束规则**：
    -   租户制度只能关联到本租户的租户控制
    -   制度控制关联必须在制度发布前完成

+   **校验时机**：
    -   创建制度控制关联时，校验控制是否属于同一租户
    -   提交制度发布时，校验制度是否已关联控制

### 6.1.3 责任点生成一致性

+   **约束规则**：
    -   责任点必须基于有效的租户控制、租户场景、岗位角色映射生成
    -   责任点的 RACISV 角色必须映射到实际人员

+   **校验时机**：
    -   生成责任点时，校验控制、场景、角色映射是否有效
    -   激活责任点时，校验角色是否已映射到人员

## 6.2 业务流程约束

### 6.2.1 租户开通流程

+   **流程顺序**：
    1.  BC-53 运营分发推送合规包数据到 BC-35
    2.  BC-35 初始化租户的场景、控制映射（默认为 DRAFT 状态）
    3.  UR-02 安全架构师审核并激活场景、控制映射
    4.  BC-35 生成责任点（基于责任分配基准图）
    5.  UR-02 安全架构师完成岗位角色映射

+   **约束规则**：
    -   场景、控制映射必须激活后，才能生成责任点
    -   责任点必须生成后，才能进行岗位角色映射

### 6.2.2 制度编写流程

+   **流程顺序**：
    1.  UR-03 制度编写者基于模板编写制度
    2.  UR-03 制度编写者将制度与租户控制建立关联
    3.  UR-03 制度编写者提交制度到 BC-37 制度管理
    4.  BC-37 制度管理完成发布审批
    5.  BC-35 更新制度状态为 PUBLISHED

+   **约束规则**：
    -   制度必须关联至少一个租户控制，才能提交发布
    -   制度提交后，不能再修改内容（需创建新版本）

## 6.3 性能约束

### 6.3.1 批量操作限制

+   **批量导入**：
    -   单次批量导入资产数量不超过 1000 条
    -   单次批量创建映射关系不超过 500 条

+   **批量查询**：
    -   单次批量查询结果不超过 10000 条
    -   超过限制时，使用分页查询

### 6.3.2 响应时间要求

+   **查询操作**：
    -   单条查询：< 100ms
    -   列表查询：< 500ms
    -   复杂关联查询：< 1s

+   **写操作**：
    -   单条创建/更新：< 200ms
    -   批量操作：< 5s

## 6.4 扩展性约束

### 6.4.1 子领域扩展

+   **扩展原则**：
    -   新增子领域不影响现有子领域的功能
    -   新增子领域通过事件与现有子领域协作
    -   新增子领域遵循统一的数据模型和 API 设计原则

### 6.4.2 映射类型扩展

+   **扩展原则**：
    -   新增映射类型通过枚举值扩展
    -   新增映射类型不破坏现有映射关系的语义
    -   新增映射类型需在文档中明确定义语义和使用场景

## 7.1 术语表

+   **租户落地**：将知识中台的标准化知识（场景点、控制点、角色点）映射到租户的实际环境
+   **租户资产**：租户的 IT 资产，包括服务器、数据库、应用系统等
+   **租户场景**：租户实际业务场景，由标准场景点映射而来
+   **租户控制**：租户实际控制措施，由标准控制点映射而来
+   **租户制度**：租户内部管理制度，与租户控制建立关联
+   **岗位角色映射**：将标准角色点映射到租户的实际岗位和人员
+   **责任点**：控制点、场景点、角色点的组合，明确"谁在什么场景下负责什么控制"
+   **RACISV**：责任分配矩阵，包括 Responsible（执行者）、Accountable（负责人）、Consulted（咨询者）、Informed（知情者）、Support（支持者）、Verify（验证者）
