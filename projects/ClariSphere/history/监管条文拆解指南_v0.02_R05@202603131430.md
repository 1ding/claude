# 1 概述

+   文档编号：GUIDE-REG-001
+   文档名称：监管条文结构化拆解指南
+   文档密级：内部资料

## 1.1 目的与定位

+   本指南是监管条文结构化拆解的唯一操作参考，内容基于《法规条款原子化拆解模型》，将模型的维度体系、词库体系完整融合，并补充拆解步骤、字段说明与示例，形成一站式操作文档。
+   适用场景：

-   对单部法规全文进行批量结构化拆解
-   跨法规汇总同一领域的全部监管要求
-   基于结构化记录开展合规差距分析与义务映射

## 1.2 原子要求的定义与结构

+   **原子要求**是本模型的基本记录单元，定义为：一个条款中包含的、可独立理解且可独立落地的单条要求。
+   若一个法条包含多个并列要求，则拆分为多条原子记录；每条原子记录独立标注全部字段。
+   每条原子要求由八个维度组描述：

    ```graph
    ┌───────────────────────────────────────────────────┐
    │                   原子要求                        │
    ├─────────────┬─────────────────────────────────────┤
    │ 法规溯源    │ 出处、效力、适用行业                │
    │ 条款特征    │ 义务类别、安全目标、法益、后果      │
    ├─────────────┼─────────────────────────────────────┤
    │ 相关方      │ 角色 × RACISV（R/A/C/I/S/V）        │
    │ 客体        │ 实体编码 + 状态 + 属性              │
    │ 行为        │ 归一化动词（相关方+客体共现时必填） │
    ├─────────────┼─────────────────────────────────────┤
    │ 环境        │ 计算环境 · 边界 · 通信通道          │
    │ 条件        │ 触发事件 · 例外                     │
    ├─────────────┼─────────────────────────────────────┤
    │ 控制        │ 手段(T/M/G) · 义务模态 · 程度       │
    └─────────────┴─────────────────────────────────────┘

    控制的约束对象 ──→ 相关方 / 客体 / 行为 中的一项或多项
                    （从结构自动推导，无需显式标注）
```

## 2.2 设计说明

### 2.2.1 八维度结构

+   原子要求的八个维度组分为三个层次：

-   **元数据层**（法规溯源、条款特征）：描述条款本身的来源和分类属性，不涉及义务内容。
-   **业务语义层**（相关方、客体、行为、环境、条件）：描述义务的业务场景——谁、对什么、做什么、在哪里、什么条件下。
-   **约束层**（控制）：描述对业务行为施加的约束——用什么手段、什么模态、达到什么程度。

+   控制的约束对象不限于行为，可以是相关方、客体、行为中的一项或多项。约束对象从结构自动推导：有行为时约束行为，无行为时约束唯一存在的相关方或客体。

### 2.2.2 相关方与 RACISV

+   相关方维度统一描述条款涉及的所有参与方，每个参与方标注 RACISV 角色：

| 角色 | 含义   | 说明                                    | 责任类型      | 责任程度 |
| ---- | ------ | --------------------------------------- | ------------- | -------- |
| R    | 执行者 | 实际执行任务的人                        | 直接责任      | 主要责任 |
| A    | 负责人 | 最终对结果负责的人（每条义务只能有1个） | 管理责任      | 主要责任 |
| C    | 顾问   | 需要征询意见的人（双向沟通）            | 技术/建议责任 | 次要责任 |
| I    | 知情者 | 需要被告知的人（单向沟通）              | 无            | 无问责   |
| S    | 审批者 | 审批和签字批准的人（含会签和终审）      | 管理/领导责任 | 次要责任 |
| V    | 验证者 | 验证执行结果的人                        | 监督责任      | 次要责任 |

+   设计依据：原模型将参与方分为"责任主体"和"协作方"两个字段，角色语义模糊。RACISV 提供了更精确的角色分类，同一实体可在同一条款中承担多个角色（如监管机构同时是 I 和 V）。
+   S（审批者）包含两个子类型：

-   **会签**：在流程中间环节把关，属于管理责任。
-   **终审**：最终决策环节，属于领导责任。视制度体系缺陷程度，领导责任可能升级为主要责任。

### 2.2.3 环境三要素

+   环境维度按纵深防御模型分为三个子维度：

| 子维度   | 含义                | 示例                                         |
| -------- | ------------------- | -------------------------------------------- |
| 计算环境 | 数据/系统运行的场所 | 生产环境、测试环境、云环境、境内、境外、机房 |
| 边界     | 不同环境之间的分界  | DMZ、网络边界、内外网边界、跨境              |
| 通信通道 | 数据跨越边界的路径  | 互联网、专线/VPN、无线网络、移动存储介质     |

+   三者形成完整链条：**计算环境 → 边界 → 通信通道 → 计算环境**。
+   统一实体词库中的同一实体可在不同条文中充当不同角色（客体、计算环境、边界或通信通道），角色判定规则见 5.4 节。

### 2.2.4 行为的条件性

+   行为是相关方与客体之间的**关系谓语**，其存在性取决于条文结构：

| 有相关方(R) | 有客体 | 行为 | 控制约束的对象           | 示例                           |
| ----------- | ------ | ---- | ------------------------ | ------------------------------ |
| ✓           | ✗      | 可无 | 相关方                   | 应当设置数据安全负责人         |
| ✗           | ✓      | 可无 | 客体                     | 日志留存不少于6个月            |
| ✓           | ✓      | 必填 | 行为（连接相关方与客体） | 数据处理者应当加密传输个人信息 |

+   行为不是每条原子要求都有的独立维度，而是相关方-客体共现时才必须出现的连接词。

### 2.2.5 条件独立

+   条件维度（触发事件、例外）独立于其他维度，理由：

-   **与环境的区别**：环境使用实体词库，描述持续存在的空间背景；条件是自由文本，描述状态变化的开关。
-   **触发事件与例外的关系**：两者是义务生效边界的正反两面——触发事件划入（满足则激活），例外划出（满足则豁免）。

### 2.2.6 控制的精简

+   控制维度经过以下精简：

-   **审批层级删除**：审批信息由相关方的 S（审批者）角色承载，审批层级通过 S 角色的属性词表达（如"管理层级"、"监管机构级"）。
-   **证据要求删除**：证据要求（如"留存操作记录"、"出具评估报告"）本身是完整的独立义务（有行为、有客体、有控制手段），应拆为独立的原子要求而非作为主控制的子字段。
-   **义务类别移出**：义务类别描述条款的法律结构特征，属于条款级别的分类属性，移入条款特征组。
-   **要求类型删除**：控制手段已通过 `T:`/`M:`/`G:` 前缀自带类型信息，要求类型是冗余字段。DOC（制度/文档要求）并入 M 词库，OBJ（声明性安全目标）由安全目标字段承载。
-   **规则内容删除**：行为 + 控制手段 + 控制程度已完整表达结构化信息，规则内容沦为自然语言复述。

### 2.2.7 属性词机制

+   相关方、客体、环境三个维度组均可附带**属性词**，用于限定要素的特征。
+   设计依据：监管条文中的"适用条件"本质上是对各要素的特征限定（如"系统重要性银行"限定相关方，"数据总量超过100万条"限定客体）。将这些条件拆解到各要素的属性词中，消除了"适用条件"作为独立字段的必要性。

| 维度组 | 典型属性维度           | 属性词示例                                              |
| ------ | ---------------------- | ------------------------------------------------------- |
| 相关方 | 规模、级别、资质、性质 | 系统重要性银行、CII运营者、持牌机构、大型数据处理者     |
| 客体   | 数量、敏感度、分类分级 | 数据量超过100万条、涉及敏感个人信息、等保三级及以上系统 |
| 环境   | 位置、性质、安全等级   | 境内、跨境、互联网暴露、加密通道                        |

+   属性词为自由文本，不设固定词库；标注时忠实于条文原文表述。

# 3 词库体系

## 3.1 统一实体词库

+   客体、计算环境、边界、通信通道四个字段共用一套统一实体词库。同一实体在不同条款中可充当不同角色，角色由各对应字段分别标注。
+   操作编码规则：客体字段使用 A/S/N/H/P/R 前缀；计算环境、边界与通信通道字段使用实体名称文本（不用编码）。T/M/G 字母专用于控制手段分类，不用于实体编码。

| 代码 | 名称         | 说明                                       | 适用状态集                                    |
| ---- | ------------ | ------------------------------------------ | --------------------------------------------- |

+   行为字段的必填条件：当同一条原子要求中同时存在相关方（R角色）和客体时，行为为必填。

## 4.2 法规溯源字段

+   **法规名称**：法规/标准全称，如"中华人民共和国数据安全法"。
+   **条款编号**：原始条款的层级定位，如"第三章第二十一条第一款"；操作简写格式：`数据安全法§21`。
+   **效力层级**：法律、行政法规、部门规章、国家标准、行业标准、团体标准。
+   **适用行业**：金融、电信、医疗、能源、政务、通用等；通用时可省略。

## 4.3 条款特征字段

+   **义务类别**：条款的法律结构特征，四取一：

| 值       | 特征                         | 行为词示例               |
| -------- | ---------------------------- | ------------------------ |
| 操作性   | 相关方执行一个具体的动作     | 处理、监测、报告、配合   |
| 结构性   | 相关方建立某个组织架构或制度 | 建立、设置、明确（机构） |
| 资格性   | 相关方须具备某种状态或资质   | 取得、具备、持有         |
| 责任归属 | 某方承担某项职责或责任       | 承担、负责、担任         |

+   **安全目标**：条款要求达成的 COAST 安全目标，直接从 3.4 节词库中选取，格式 `{一级} > {二级} > {三级}`。尽量填到三级；跨多个三级目标时可停留二级；多个目标用分号分隔。处罚性条款通常不填。声明性安全目标条款（如"应当保障数据完整性"）在此字段填写目标，控制手段可留空。
+   **保护法益**：条文原文明确表述的保护目的，如"数据安全"、"国家安全"、"个人信息权益"。
+   **法律后果**：违规处罚，通常引用法律责任章节，如"数据安全法§48"。无则留空。

## 4.4 相关方字段

+   **角色**：条款涉及的参与方，从角色词库选取归一化类型，格式 `{归一化类型}【{类型}】`，如 `数据处理者【组织】`。一条原子要求可包含多个相关方。
+   **RACISV**：该参与方在本条义务中的职责类型，见 2.2.2 节。每个相关方标注一个或多个 RACISV 角色。
+   **相关方属性**：限定相关方特征的条件词，如"处理100万人以上个人信息的"、"系统重要性银行"。条款未显式限定时留空。当属性词恰好等于角色词库中的归一化类型时（如"关键信息基础设施运营者"），角色字段直接使用该归一化类型，属性词留空以避免冗余。

## 4.5 客体字段

+   **实体**：行为作用的实体对象，使用 A/S/N/H/P/R 编码，如 `A3 重要数据`。允许多值；无实体客体时留空。
+   **状态**：客体的处理阶段，从实体适用状态集中选取，如 `[传输]`、`[存储]`。编码与状态的组合格式：`A1 个人信息[传输]`。
+   **客体属性**：限定客体特征的条件词，如"数据量超过100万条"、"涉及国家秘密的"。条款未显式限定时留空。

## 4.6 行为字段

+   **行为**：相关方对客体执行的动作，使用归一化动词，见 3.5 节。
+   必填条件：当同一条原子要求中同时存在相关方（R角色）和客体时必填，否则可留空。
+   同一动词在不同条文中可能是行为或控制手段（见 5.9 节），需根据条文语境判定。

## 4.7 环境字段

+   **计算环境**：数据/系统处理或存储发生的场所，如"生产环境"、"云环境"、"境内"。无显式限定时留空。
+   **边界**：不同环境之间的分界，如"DMZ"、"网络边界"、"内外网边界"。无显式限定时留空。
+   **通信通道**：数据跨越边界流转的路径，如"互联网"、"专线/VPN"、"无线网络"、"移动存储介质"。无显式限定时留空。
+   **环境属性**：限定环境特征的条件词，如"跨境"、"互联网暴露的"。可同时修饰计算环境、边界或通信通道中的任一项。条款未显式限定时留空。

## 4.8 条件字段

+   **触发事件**：动态事件驱动的义务激活条件——事件发生时义务从休眠变为激活。如"发现数据安全缺陷或漏洞"、"数据安全事件发生"。无则留空（表示持续性义务，无需事件触发）。
+   **例外**：义务的豁免条件——满足该条件时义务不适用。如"经中华人民共和国主管机关批准的除外"。无则留空。

## 4.9 控制字段

+   **控制手段**：具体的控制措施，从 T/M/G 词库选取，见 3.3 节。使用前缀标明类型，格式：`T: 密码/加密; M: 跨境传输管理`。允许多类型混合。条文未指定具体措施时留空。
+   **义务模态**：条款的义务性质：

| 值   | 关键词                 | 含义             |
| ---- | ---------------------- | ---------------- |
| 应   | 应、应当、须、必须     | 强制作为         |
| 不得 | 不得、不应、禁止、严禁 | 强制不作为       |
| 可以 | 可以、可               | 授权许可，非强制 |
| 宜   | 宜、鼓励、支持         | 推荐做法，非强制 |

+   **时限**：条款明确的时间约束。参考值：立即、及时、定期（注明周期，如"每年一次"）、N 日内。无则留空。
+   **覆盖范围**：条款明确的适用面限定。示例：全量、等保三级及以上系统、涉及个人信息的系统。无则留空。
+   **量化指标**：条款包含的具体数值约束。示例：密码长度≥8位、日志留存≥6个月、RPO≤4小时。无则留空。

# 5 标注规则

## 5.1 多值、留空与推断规则

+   **多值标注**：所有维度均允许多值。相关方、客体、控制手段、安全目标均可标注多项，用分号分隔。
+   **留空规则**：当条款未显式指定某维度时，该维度留空，表示"不限/未指定"。不得填写"全部"、"不限"等文字。
+   **推断克制**：标注忠实于条款原文。仅当上下文逻辑关系明确时允许推断，不做过度解读。
+   **颗粒度就高**：标注优先使用原文表述对应的最具体分类。如原文为"敏感个人信息"，不应标注上位概念"个人信息"（A1），应标注 A2。

## 5.2 属性词标注规则

+   **属性词的来源**：属性词提取自条文中对要素的限定性描述。当条文使用"……的"定语结构修饰相关方、客体或环境时，该定语即为属性词的候选。
+   **属性词与要素的绑定**：属性词应挂在其直接限定的要素上，不应集中堆放。

| 条文片段                       | 要素   | 属性词                   |
| ------------------------------ | ------ | ------------------------ |
| 关键信息基础设施运营者         | 相关方 | 关键信息基础设施运营者   |
| 处理100万人以上个人信息的      | 客体   | 数据量超过100万条        |
| 存储于中华人民共和国境内的数据 | 环境   | 境内                     |
| 通过互联网提供服务的系统       | 环境   | 互联网暴露               |
| 未通过安全评估的境外机构       | 相关方 | 未通过安全评估的；境外的 |

## 5.3 省略还原规则

+   监管条文常省略要素，拆解时需从上下文还原：

| 省略类型     | 还原方式                       | 示例                                      |
| ------------ | ------------------------------ | ----------------------------------------- |
| 主体省略     | 从章节标题、适用范围条款推断   | "所有变更必须经过审批" → 还原执行者       |
| 客体省略     | 从行为动词推断变更/处理的对象  | "应当加强风险监测" → 还原监测对象         |
| 环境省略     | 从文档上下文推断适用的环境     | 通常默认不限环境                          |
| 隐含义务动词 | "是……"句式还原为"应当承担……"   | "X是安全第一责任人" → X应当承担安全责任   |
| 语法主语偏移 | 活动名称作主语时还原真正的主体 | "变更管理应当确保……" → 负责变更管理的组织 |

+   还原依据为**条文显式提及的上下文**，不做过度推断。

## 5.4 实体词库的角色机制

+   同一实体在不同条款中可充当不同角色：

| 实体          | 作为客体 | 作为计算环境 | 作为边界 | 作为通信通道 |
| ------------- | -------- | ------------ | -------- | ------------ |
| 云平台        | S2       | 云环境       | —        | —            |
| 互联网        | N2       | —            | —        | 互联网       |
| 专线/VPN      | N3       | —            | —        | 专线/VPN     |
| 移动存储介质  | H4       | —            | —        | 移动存储介质 |
| 机房/数据中心 | P1       | 机房         | —        | —            |
| 边界/DMZ      | N5       | —            | DMZ      | —            |
| 内部网络      | N1       | 内部网络     | —        | —            |

+   判定规则：

-   当实体作为**被管理的对象**（条款要求对其进行保护、部署、维护）时，标注为客体。
-   当实体描述**处理/存储发生的场所**时，标注为计算环境。
-   当实体描述**不同环境之间的分界**时，标注为边界。
-   当实体描述**数据流转的经过路径**时，标注为通信通道。

## 5.5 RACISV 标注规则

+   同一角色在不同条款中可承担不同 RACISV 职责，职责由条文语境判定：

| 条文片段                           | 角色           | RACISV |
| ---------------------------------- | -------------- | ------ |
| 数据处理者应当采取加密措施         | 数据处理者     | R      |
| 应当明确数据安全负责人             | 数据安全负责人 | A      |
| 经安全评估机构评估后方可           | 评估/认证机构  | C      |
| 及时告知用户                       | 用户           | I      |
| 经中华人民共和国主管机关批准       | 监管机构       | S      |
| 向有关主管部门报告                 | 监管机构       | I; V   |
| 第三方服务商应在合同范围内处理数据 | 第三方服务商   | R      |

+   同一角色可在同一条款中承担多个 RACISV 职责（如监管机构同时是 I 和 V）。

## 5.6 T 词库分层标注规则

+   技术措施默认标到第一层（安全能力大类），如"密码/加密"。
+   仅在条款原文明确指定具体技术手段时才标注第二层，如"传输层加密(TLS)"。
+   环境字段（通信通道等）已编码"传输"/"存储"等信息，T 词库不重复编码这些场景维度。

## 5.7 行为与控制手段的辨别

+   同一动词在不同条文中可能是行为或控制手段，区分标准：**该动词是被约束的对象，还是约束的工具？**

| 条文                       | 动词 | 角色     | 判定依据                     |
| -------------------------- | ---- | -------- | ---------------------------- |
| 要监控服务器的性能         | 监控 | 行为     | 主体对客体做的事，被控制约束 |
| 对管理员的所有操作进行监控 | 监控 | 控制手段 | 用来约束"管理员操作"的方式   |
| 应当对数据传输进行加密     | 加密 | 控制手段 | 约束"传输"行为的方式         |
| 定期开展加密算法评估       | 评估 | 行为     | 主体对客体（加密算法）做的事 |

## 5.8 条文拆分规则

+   出现以下任一情形时，拆分为多条独立原子记录：

-   条文涉及多个不同的 R 角色（执行者），每个执行者单独一条记录
-   条文中义务模态混合（"应"与"不得"并存），按模态分别单独一条记录
-   条文中存在不同触发事件，每个触发事件单独一条记录
-   条文中包含证据要求（如"留存操作记录"），证据要求拆为独立的原子要求

## 5.9 不拆的条文类型

+   以下类型条文跳过，不纳入原子记录：

| 类型       | 示例                    | 原因                         |
| ---------- | ----------------------- | ---------------------------- |
| 定义条款   | 第3条 数据的定义        | 无义务，仅定义术语           |
| 政策宣示   | 第7条 国家保护数据权益  | 无可验证合规动作             |
| 立法目的   | 第1条 制定本法目的      | 无义务                       |
| 纯授权条款 | 第54条 军事数据另行制定 | 义务在子法规中，待子法规拆解 |

# 6 拆解步骤

+   按以下步骤对每条条文执行拆解：

-   **Step 1　识别是否需拆解**：判断条文是否属于不拆类型（见 5.9 节）。属于则跳过。
-   **Step 2　识别相关方**：条文中有哪些参与方？注意辨别语法主语偏移（见 5.3 节）。为每个参与方标注 RACISV 角色。多个 R 角色则准备生成多条记录。
-   **Step 3　识别客体**：条文针对什么实体对象（A/S/N/H/P/R）？有无状态？若无明确实体对象，客体留空。
-   **Step 4　判断行为**：相关方和客体是否共现？是则确定行为动词（注意辨别行为与控制手段，见 5.7 节）。
-   **Step 5　标注环境**：有无特定计算环境、边界、通信通道？分别填入，无则留空（见 5.4 节角色机制）。
-   **Step 6　标注属性词**：检查条文中是否有对相关方、客体、环境的限定性描述，有则提取为对应的属性词（见 5.2 节）。
-   **Step 7　标注条件**：有无触发事件（动态激活条件）？有无例外（豁免条件）？分别填入，无则留空。如有不同触发事件，准备拆分多条记录。
-   **Step 8　标注控制**：判断义务模态（见 4.9 节）；从 T/M/G 词库选取控制手段（见 3.3 节，T 词库默认到一级）；填写时限、覆盖范围、量化指标。
-   **Step 9　填写条款元数据**：义务类别（见 4.3 节）、安全目标（从 3.4 节 COAST 词库选取，尽量到三级）、保护法益、法律后果、法规溯源。
-   **Step 10　归一化与检查**：对照 3.1～3.5 节词表，归一化角色类型、映射客体编码、规范控制手段表达。检查是否有证据要求需拆为独立记录。

## 8.3 内规侧记录的差异

+   内规记录复用监管侧同一 schema，额外增加两个字段；`stakeholders[].type_class` 字段不适用于内规侧：

| 附加字段  | 类型   | 说明                                                            |
| --------- | ------ | --------------------------------------------------------------- |
| `doc_ref` | string | 内规来源文件编号，如 `DSP-OPS-012`                              |
| `scope`   | string | 内规适用范围，如 `"全公司"` / `"信息科技部"` / `"核心业务系统"` |

+   内规主体覆盖判断由监管侧 `stakeholders[].type_class` 驱动，见 GUIDE-REG-002 第 2.3 节。
+   `clause.legal_interest` 和 `clause.legal_consequence` 在内规记录中通常为 null。
