#### 2.2.5.1 DLM001 新规落地的"比对地狱"

+   困境描述：每当监管发布新规，合规团队需要人工逐条比对新规与现有制度的差异
+   典型场景如下所示

    ```text
    收到新规：《金融数据安全管理办法》共 8 章 72 条
        ↓
    开始比对：翻遍 23 份内部制度、156 个系统文档
        ↓
    痛苦分析：• 第 15 条，我们有类似规定吗？在哪个制度里？
            • 第 23 条，现有流程覆盖了吗？有偏差吗？
            • 第 47 条，这个要求我们做到什么程度了？
        ↓
    2 周后...：勉强完成分析，但心里没底
    ```

+   困境表现如下表所示

    | 困境表现     | 具体问题                             | 时间成本 | 质量风险 |
    | ------------ | ------------------------------------ | -------- | -------- |
    | 人工逐条分析 | 需要人工阅读新规每一条，理解监管意图 | 3-5天    | 理解偏差 |
    | 翻找历史制度 | 在几十份制度文档中查找相关条款       | 5-7天    | 遗漏风险 |
    | 差距识别困难 | 难以判断现有措施是否满足新要求       | 3-5天    | 判断不准 |
    | 整改方案模糊 | 不清楚需要新增哪些措施，修改哪些流程 | 2-3天    | 执行偏差 |

    +   表 新规比对困境

+   **根本原因**：要求与落实之间缺乏透明的映射关系，无法快速追溯

#### 2.2.5.2 DLM002 监管检查的"灵魂拷问"

+   困境描述：监管检查现场，面对检查方的连环追问，往往无法快速、准确地给出答案
+   典型场景如下所示

    ```text
    检查方："你们的 xxxx 是怎么落实的？"
    对接人："我们...有相关制度..."（翻找文件夹）
    检查方："具体在哪些系统实施了？"
    对接人："这个...我需要问一下..."（紧急打电话）
    检查方："实施效果怎么样？有审计记录吗？"
    对接人："应该有...我找找看..."（满头大汗）
    结果：明明做了很多工作，却因为找不到、说不清，被判定为"落实不力"
    ```

+   困境表现如下表所示

    | 困境表现     | 具体问题                               | 典型后果       |
    | ------------ | -------------------------------------- | -------------- |
    | 找不到证据   | 制度、流程、系统分散，难以快速定位     | 被判定"无证据" |
    | 说不清关联   | 无法清晰说明制度要求如何落实到具体系统 | 被判定"脱节"   |
    | 证明不了效果 | 缺乏执行记录和审计数据                 | 被判定"未落实" |
    | 准备时间长   | 临时准备材料需要1-2周，检查方等不了    | 现场尴尬       |
    | 口径不一致   | 不同部门对同一问题的回答不一致         | 失去信任       |

    +   表 监管检查应对困境

+   **根本原因**：落实无法反向追溯到要求，证据链断裂

+   典型场景如下所示

    ```text
    领导问："我们在 XXX 方面做了哪些工作？"
    你回答："发了 5 个制度，做了 3 次培训..."
    领导再问："与监管要求相比，还有哪些差距？"
    你沉默："需要时间整理一下..."
    领导追问："与同业相比，我们处于什么水平？"
    你犹豫："这个...应该还可以..."
    最怕听到："这些基本情况都不清楚，怎么做管理？"
    ```

+   困境表现如下表所示

    | 缺失视图 | 领导关注问题                               | 现状困境           |
    | -------- | ------------------------------------------ | ------------------ |
    | 全景图   | 我们整体水平如何？哪些是强项？哪些是弱项？ | 数据分散，难以汇总 |
    | 差距分析 | 与要求相比，还有哪些差距？轻重缓急如何？   | 人工分析，周期长   |
    | 趋势分析 | 我们的管理水平是在提升还是下降？           | 缺乏历史数据       |
    | 风险预警 | 未来3-6个月可能面临哪些风险？              | 被动应对，无预警   |
    | 资源配置 | 投入是否合理？哪些领域需要加强？           | 凭感觉，无数据支撑 |

    +   表 管理视图缺失

+   **根本原因**：管理不透明，无法从全局视角看清现状

#### 2.2.5.4 DLM004 一线员工的"无所适从"

+   困境描述：制度文件如雪片般飞来，员工却越来越迷茫
+   典型场景如下所示

    ```text
    员工内心 OS：
    周一："又发新制度了，这是第几个了？"
    周二："这个操作到底按哪个制度来？"
    周三："为什么要这么做？监管要求还是领导拍脑袋？"
    周四："上个月的制度和这个月的有冲突吧？"
    周五："算了，还是问问老张怎么做的..."
    最终结果：该做的没做，不该做的做了一堆
    ```

+   困境表现如下表所示

    | 困境表现 | 具体问题                             | 执行后果           |
    | -------- | ------------------------------------ | ------------------ |
    | 制度轰炸 | 每月接收数十份制度文件，无法全部消化 | 选择性忽略         |
    | 不知为何 | 不清楚某个操作背后的监管要求和目的   | 机械执行，容易偏离 |
    | 不知怎做 | 制度规定抽象，不知道具体操作步骤     | 执行不到位         |
    | 不知后果 | 不清楚不合规的风险和后果             | 侥幸心理           |
    | 制度冲突 | 新旧制度存在冲突，不知道以哪个为准   | 执行混乱           |

    +   表 一线员工困境

+   **根本原因**：要求与执行者之间缺乏透明的传导机制

# 7 基础性宏观需求分析

+   本章定义跨Epic的基础性需求，即各业务能力共同依赖的通用能力
+   基础性需求是"横切关注点"，在概要设计阶段将映射到平台能力模块
+   基础性需求的完整性直接影响系统的可用性、安全性和可维护性

## 7.1 基础性需求概述

### 7.1.1 基础性需求的定义

+   基础性需求是指：
    -   跨多个Epic使用的通用能力
    -   不直接产生业务价值，但缺失会导致业务无法正常运行
    -   通常在需求分析阶段容易被遗漏，但在开发阶段必须实现

## 10.3 排序策略

### 10.3.1 排序方法

+   透管云采用两级排序机制，分别对应宏观需求和详细需求两个阶段
+   两级排序机制如下表所示

    | 排序级别 | 排序对象 | 排序方法                     | 决策产出          | 所在阶段       |
    | -------- | -------- | ---------------------------- | ----------------- | -------------- |
    | 版本规划 | Epic     | WSJF加权评估→版本分配(P1-P6) | Epic到版本的映射  | 阶段2 宏观需求 |
    | 迭代规划 | Story    | Sprint排序（版本内迭代排序） | Story到迭代的映射 | 阶段4 BC级需求 |

    +   表 两级排序机制

+   版本规划排序说明：
    -   Epic通过WSJF评估得出综合得分，依据得分高低分配到P1-P6各版本
    -   版本分配同时考虑技术依赖关系（10.4节）和版本容量约束
    -   版本本身即体现交付顺序，版本内的Epic不再进行额外排序
+   迭代规划排序说明：
    -   在阶段4 BC级详细需求阶段，Epic拆解为Story后，在版本内按Sprint进行迭代排序
    -   迭代排序由各BC的产品负责人在Sprint Planning中决定
    -   本文档（宏观需求）不涉及迭代级排序

### 10.3.2 WSJF评估维度

+   Epic的版本分配采用WSJF（Weighted Shortest Job First）方法进行评估
+   WSJF得分计算：WSJF = (业务价值 + 时间紧迫性 + 风险降低) / 实现成本
+   WSJF评估维度如下表所示

    | 维度       | 评分范围 | 说明                                             |
    | ---------- | -------- | ------------------------------------------------ |
    | 业务价值   | 1-10     | 该Epic对业务目标的贡献程度                       |
    | 时间紧迫性 | 1-10     | 延迟实现的代价（如法规截止日期、竞争窗口）       |
    | 风险降低   | 1-10     | 该Epic对技术风险或业务风险的降低程度             |
    | 实现成本   | 1-10     | 预估的实现工作量（相对值），得分越高表示成本越大 |

    +   表 WSJF评估维度

+   各维度的锚定标准如下表所示

    | 维度       | 1-3分（低）                         | 4-6分（中）                              | 7-9分（高）                                    | 10分（极高）                                 |
    | ---------- | ----------------------------------- | ---------------------------------------- | ---------------------------------------------- | -------------------------------------------- |
    | 业务价值   | 锦上添花，对业务目标无直接贡献      | 有明确的效率提升或体验改善               | 直接影响核心业务指标（如转化率、留存率）       | 不做则无法达成战略目标                       |
    | 时间紧迫性 | 无时间约束，延迟半年以上影响可忽略  | 有内部期望时间，延迟一个季度会影响竞争力 | 有外部截止日期，延迟一个月会导致合同违约或处罚 | 存在硬性法规生效日，逾期将导致业务不合规     |
    | 风险降低   | 不涉及风险降低                      | 降低中等技术风险或验证关键技术假设       | 显著降低架构风险或消除核心业务不确定性         | 不做则存在系统性风险（如数据安全、合规风险） |
    | 实现成本   | 工作量极小（1-2人周），技术方案明确 | 工作量中等（1-2人月），需一定技术预研    | 工作量较大（1-2个季度），涉及多团队协作        | 工作量巨大（半年以上），需重大架构调整       |

    +   表 WSJF评分锚定标准

+   [待补充] 40个Epic的WSJF评分明细将在成本估算完成后补充

# 附录B 文档说明

+   本文档采用"三线演绎，角色驱动，两维验证"方法论组织
+   三线：活动线（PL0→PL1→PL2）、角色线（RL0→RL1→RL2）、实体线（EL0→EL1→EL2）
+   推导主线：角色(RL2)的痛点/期望 → 候选Epic → 抽象过滤 → Epic
+   两维验证：业务环节(PL2)覆盖度 + 实体生命周期(EL2)覆盖度
+   追溯链：业务目标 → 困境 → 业务环节 → 角色 → Epic → 版本
+   文档框架遵循 S02-宏观需求编写规范 v0.16 的章节结构要求
+   需求层级体系遵循 SAFe 框架：Strategic Theme → Business Epic / Enabler Epic → Feature → User Story → Task
