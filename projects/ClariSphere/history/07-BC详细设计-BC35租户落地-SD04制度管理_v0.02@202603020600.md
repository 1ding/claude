## 2.6 并发与幂等策略

+   乐观锁方案：PolicyImportTask 和 TenantPolicy 均含 `version` 字段（整型），更新时使用 WHERE version=? 检测冲突，冲突返回 E-40935003（CONCURRENT_CONFLICT）。

+   下表说明各写接口的幂等保证策略。

    | 接口类型     | 幂等键生成规则                             | 存储方式       | 有效期 | 重复请求处理      |
    | ------------ | ------------------------------------------ | -------------- | ------ | ----------------- |
    | 创建导入任务 | `tenantId + fileId`（BC-13 返回）          | 数据库唯一索引 | 持久   | 返回已存在任务 ID |
    | 确认导入     | `taskId`（一个任务只能确认一次）           | 数据库业务约束 | 持久   | 返回 E-40935002   |
    | 创建制度草稿 | 由确认导入内部触发，通过任务 ID 唯一性保证 | 数据库约束     | 持久   | 返回 E-40935002   |

    +   表 幂等性保证策略

+   长流程防重入：导入任务进入 PARSING 状态后申请 Redis 分布式锁（key 为 `task_lock:{taskId}`），防止同一任务重复解析。锁随解析完成（成功或失败）释放；超时时间 70 秒（解析超时 60 秒 + 10 秒余量）。

## 3.4 FL-PM-03 导入失败处理流程

+   **流程目标**：用户查看失败原因，选择重新上传（创建新任务）或放弃本次导入。
+   **触发条件**：用户轮询发现任务状态为 FAILED。
+   **结束条件**：用户创建新导入任务（进入 FL-PM-01）或不再操作。

+   下表说明 FL-PM-03 的步骤。

    | 步骤号 | 步骤名称           | 执行者           | 输入         | 输出                      | 业务规则引用 |
    | ------ | ------------------ | ---------------- | ------------ | ------------------------- | ------------ |
    | 1      | 查询失败任务详情   | 应用服务（查询） | taskId       | 任务状态 FAILED、错误原因 | -            |
    | 2      | 展示失败原因给用户 | 前端             | errorMessage | 用户界面展示              | -            |
    | 3a     | 用户选择重新上传   | UR-03            | 新文件       | 触发 FL-PM-01             | -            |
    | 3b     | 用户选择放弃       | UR-03            | -            | 操作结束                  | -            |

    +   表 FL-PM-03 步骤表

+   重试策略：失败任务保持 FAILED 状态不可修改。重新上传时创建全新导入任务（新 taskId），原失败任务保留供审计。

## 4.6 值对象定义

+   **ParseStatus 枚举**（在 PolicyImportTask 中使用）：UPLOADING / PARSING / PENDING_CONFIRM / COMPLETED / FAILED / EXPIRED / CANCELLED。完整语义见 4.3 节状态枚举表。

+   **PolicyStatus 枚举**：
    -   DRAFT：草稿（P1 使用，可修改和删除）
    -   REVIEWING：审批中（P2+）
    -   PUBLISHED：已发布（P2+）
    -   DEPRECATED：已废弃（P2+）

+   **FileType 枚举**：DOCX（Word .docx 格式）/ PDF（.pdf 格式）。

+   **SourceType 枚举**：IMPORT（从文件导入，P1 使用）/ MANUAL（手工编写，P2+）。

+   **ChapterTree 值对象**：
    -   属性：`List<ChapterNode>`，树形结构，每个节点含 chapterNo、chapterTitle、chapterContent、level、children。
    -   序列化：以 JSONB 格式存储在 t_policy_import_task.parse_result 列。
    -   生命周期：由 PolicyImportTask 聚合根管理，确认导入时展开为 PolicyChapter 实体列表。

# 5 应用层设计

## 5.1 应用层职责说明

+   应用层承担以下职责：用例编排（协调领域对象完成业务用例）、事务管理（定义事务边界）、权限前置校验（调用权限服务）、DTO 转换（入参转 Command，出参转 DTO）、领域事件发布（事务提交后收集并发布）。

+   应用层不承担以下职责：业务规则校验（归属领域层，由聚合根或领域服务执行）、数据持久化（归属基础设施层，由 Repository 实现）、HTTP 处理（归属接口层，由 Controller 执行）。

## B.2 解析性能设计

+   Word/PDF 解析为异步任务，通过 RocketMQ 消息队列或内部 `@Async` 线程池执行，不阻塞导入任务创建的 HTTP 响应。
+   解析超时设置为 60 秒，超时后标记任务 FAILED 并释放分布式锁。
+   单租户最多 3 个并发导入任务并行解析，通过 Redis 分布式信号量（`semaphore:parse:{tenantId}`，许可数=3）控制，避免大文件并发解析导致 CPU 和内存压力。
