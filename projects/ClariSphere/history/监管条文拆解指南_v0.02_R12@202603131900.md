# 1 概述

+   文档编号：GUIDE-REG-001
+   文档名称：监管条文结构化拆解指南
+   文档密级：内部资料

## 1.1 目的与定位

+   本指南是监管条文结构化拆解的唯一操作参考，内容基于《法规条款原子化拆解模型》，将模型的维度体系、词库体系完整融合，并补充拆解步骤、字段说明与示例，形成一站式操作文档。
+   适用场景：

-   对单部法规全文进行批量结构化拆解
-   跨法规汇总同一领域的全部监管要求
-   基于结构化记录开展合规差距分析与义务映射

## 1.2 原子要求的定义与结构

+   **原子要求**是本模型的基本记录单元，定义为：一个条款中包含的、可独立理解且可独立落地的单条要求。
+   若一个法条包含多个并列要求，则拆分为多条原子记录；每条原子记录独立标注全部字段。
+   每条原子要求由九个维度组描述：

    ```graph
    ┌──────────────────────────────────────────────────────────────┐
    │                          原子要求                            │
    ├─────────────┬────────────────────────────────────────────────┤
    │ 法规溯源    │ 出处、效力、适用行业                           │
    │ 目标        │ 安全目标                                       │
    │ 后果        │ 法律后果                                       │
    ├─────────────┼────────────────────────────────────────────────┤
    │ 相关方      │ 身份 × 属性（职责·规模·属地）                  │
    │ 客体        │ 资产 × 属性（状态·规模·分级·属地）             │
    │ 行为        │ 动词 + 事项域（IT/R · IT/M · IT/G）            │
    ├─────────────┼────────────────────────────────────────────────┤
    │ 环境        │ 资产 × 属性（属地）                            │
    │ 条件        │ 触发事件 · 例外                                │
    ├─────────────┼────────────────────────────────────────────────┤
    │ 控制        │ 控制机制(T/M/G) · 义务模态 · 程度              │
    └─────────────┴────────────────────────────────────────────────┘

    控制的约束对象 ──→ 相关方 / 客体 / 行为 中的一项或多项
                    （从结构自动推导，无需显式标注）
    ```

## 1.3 拆解基准单元

+   拆解以**可独立定位的最小编号节点**为读入单元（处理单元），一个处理单元可产出 1..N 条原子记录。
+   条款编号是溯源定位符——同一条款派生的所有原子记录共享相同的条款编号；条款与原子记录是 **1:N 的派生关系**。

+   不同文本类型的引用粒度：

| 文本类型               | 引用层级                     | 说明                                    |
| ---------------------- | ---------------------------- | --------------------------------------- |
| 法律/行政法规/部门规章 | 条（第X条）                  | 款无独立编号，不作为引用粒度            |
| 国家/行业标准          | 最小数字编号节（如 8.1.4.1） | 字母编号（a)/b)）在段落之下，不独立定位 |
| 通知/发文              | 最小编号层级                 | 随文本结构取最细可编号层级              |

# 2 维度体系

## 2.1 维度总览

+   全部标注字段分为九组，每组对应一条原子记录（见 1.2、1.3 节）中的一个 JSON 对象。各组内字段分为**维度**（实体身份标识）和**属性**（对该实体的限定条件）两种层级；属性各组独立定义，不跨组通用。

| 组别     | 层级 | 字段     | 词库来源         | 说明                                                     | 详见       |
| -------- | ---- | -------- | ---------------- | -------------------------------------------------------- | ---------- |
| 法规溯源 | 维度 | 法规名称 | —                | 条款所在法规或标准的全称                                 | —          |
|          | 维度 | 条款编号 | —                | 条款在法规中的唯一层级定位符，规则因文本类型而异         | 1.3 节     |
|          | 维度 | 效力层级 | 固定枚举         | 法规的法律位阶，决定义务的强制力来源                     | 4.2 节     |
|          | 维度 | 适用行业 | 行业清单树       | 法规明确限定的适用行业范围，引用行业清单树节点           | 4.2 节     |
| 目标     | 维度 | 安全目标 | COAST 词库       | 该条款旨在达成的安全目标，按 COAST 体系分类              | 3.5 节     |
| 后果     | 维度 | 法律后果 | —                | 违反该义务时适用的处罚，通常引用法律责任章节             | —          |
| 相关方   | 维度 | 身份     | 角色词库         | 条款中的参与方类型（执行者、监管机构、数据主体等）       | 3.2 节     |
|          | 属性 | 职责     | RACISV 枚举      | 该参与方在本条义务中承担的责任类型（必填）               | 2.2.2 节   |
|          | 属性 | 规模     | 自由文本         | 组织体量或数据处理量（如"处理100万人以上个人信息的"）    | —          |
|          | 属性 | 属地     | 自由文本         | 参与方的地理管辖归属（如"境内"、"境外"）                 | —          |
| 客体     | 维度 | 资产     | IT/R 资源域词库  | 义务作用的信息资产，用 DASPR 五层编码标识                | 3.1 节     |
|          | 属性 | 状态     | 资产状态集       | 义务发生时资产所处的处理阶段（如采集、传输、存储）       | 3.1 节     |
|          | 属性 | 规模     | 自由文本         | 数据量级或资产数量（如"超过100万条"）                    | —          |
|          | 属性 | 分级     | 自由文本         | 资产的安全分级或敏感度标识（如"等保三级"）               | —          |
|          | 属性 | 属地     | 自由文本         | 数据存储或产生的地理位置（如"境内存储的"）               | —          |
| 行为     | 维度 | 动词     | 行为词表         | 相关方对客体或事项执行的归一化动作                       | 3.3.1 节   |
|          | 维度 | 事项     | IT/M·IT/G 事项域 | IT/M 或 IT/G 域的管理/治理关注点；IT/R 域不填            | 3.3.2/3 节 |
| 环境     | 维度 | 资产     | IT/R 资源域词库  | 义务发生的背景场所或网络路径（环境角色）                 | 2.2.5 节   |
|          | 属性 | 属地     | 自由文本         | 环境的地理位置（如"境内"、"境外"、"跨境"）               | —          |
| 条件     | 维度 | 触发事件 | 自由文本         | 使义务从休眠变为激活的动态事件                           | 2.2.6 节   |
|          | 维度 | 例外     | 自由文本         | 满足后义务不适用的豁免条件                               | 2.2.6 节   |
| 控制     | 维度 | 控制机制 | T/M/G 机制词库   | 约束行为的具体技术/管理/治理工具                         | 3.4 节     |
|          | 维度 | 义务模态 | 固定枚举         | 条款的强制性质（应/不得/可以/宜）                        | 4.10 节    |
|          | 维度 | 时限     | —                | 条款明确的执行时间约束                                   | —          |
|          | 维度 | 量化指标 | 自由文本         | 条款中的具体数值要求                                     | —          |

## 2.2 设计说明

### 2.2.1 九维度与三层架构

+   原子要求的九个维度组分为三个层次：

-   **元数据层**（法规溯源、目标、后果）：描述条款本身的来源、安全分类和法律后果，不涉及义务内容。
-   **业务语义层**（相关方、客体、行为、环境、条件）：描述义务的业务场景——谁、对什么、做什么、在哪里、什么条件下。
-   **约束层**（控制）：描述对业务行为施加的约束——用什么控制机制、什么模态、达到什么程度。

+   控制的约束对象可以是相关方、客体、行为中的一项或多项。约束对象从结构自动推导：有行为时约束行为；无行为时约束所有已标注的相关方和客体。

### 2.2.2 相关方与 RACISV

+   相关方组由**身份**（维度）和**属性**（限定条件）两部分构成。身份标识参与方类型，属性进一步限定该参与方的特征和职责。
+   **职责**属性使用 RACISV 枚举，描述参与方在本条义务中承担的责任类型，为必填属性：

    | 值 | 含义   | 说明                                    | 责任类型      | 责任程度 |
    | -- | ------ | --------------------------------------- | ------------- | -------- |
    | R  | 执行者 | 实际执行任务的人                        | 直接责任      | 主要责任 |
    | A  | 负责人 | 最终对结果负责的人（每条义务只能有1个） | 管理责任      | 主要责任 |
    | C  | 顾问   | 需要征询意见的人（双向沟通）            | 技术/建议责任 | 次要责任 |
    | I  | 知情者 | 需要被告知的人（单向沟通）              | 无            | 无问责   |
    | S  | 审批者 | 审批和签字批准的人（含会签和终审）      | 管理/领导责任 | 次要责任 |
    | V  | 验证者 | 验证执行结果的人                        | 监督责任      | 次要责任 |

+   同一实体可在同一条款中承担多个 RACISV 角色（如监管机构同时是 I 和 V）。
+   S（审批者）包含两个子类型：

-   **会签**：在流程中间环节把关，属于管理责任。
-   **终审**：最终决策环节，属于领导责任。视制度体系缺陷程度，领导责任可能升级为主要责任。

### 2.2.3 三域体系（IT/R · IT/M · IT/G）

+   模型围绕三个域组织词库和标注逻辑：

    | 域          | 全称          | 覆盖范围               | 对应的标注维度 |
    | ----------- | ------------- | ---------------------- | -------------- |
    | IT/R 资源域 | IT Resource   | 信息资产（DASPR 五层） | 客体、环境     |
    | IT/M 管理域 | IT Management | 管理关注事项           | 行为·事项      |
    | IT/G 治理域 | IT Governance | 治理关注事项           | 行为·事项      |

+   每个域同时关联一组控制机制，用于约束该域内的行为：

    | 域   | 事项域（做什么事） | 控制机制（用什么约束）                 |
    | ---- | ------------------ | -------------------------------------- |
    | IT/R | DASPR 信息资产     | T 技术机制：加密、访问控制、审计……     |
    | IT/M | 管理事项           | M 管理机制：审批、四眼原则、合同约束…… |
    | IT/G | 治理事项           | G 治理机制：职责分离、授权矩阵……       |

+   IT/R 资源域词库（DASPR）按五层架构分类：

    | 层     | 编码前缀 | 覆盖范围                                       |
    | ------ | -------- | ---------------------------------------------- |
    | 数据层 | D        | 个人信息、重要数据、日志、凭证、配置等信息资产 |
    | 应用层 | A        | 业务系统、数据库、中间件、接口、CII            |
    | 系统层 | S        | 网络、服务器、终端、IoT、存储介质              |
    | 物理层 | P        | 机房、办公场所、灾备中心                       |
    | 文档层 | R        | 策略文件、方案报告、预案、操作记录             |

### 2.2.4 行为的结构

+   行为由**动词**和**事项**两部分组成。动词描述"做什么动作"，事项描述"关注什么领域"：

    | 行为域 | 动词示例 | 事项                | 组合后的行为 |
    | ------ | -------- | ------------------- | ------------ |
    | IT/R   | 处理     | —（客体字段已承载） | 处理个人信息 |
    | IT/M   | 开展     | 风险评估            | 开展风险评估 |
    | IT/G   | 建立     | 岗位/角色设置       | 建立岗位     |

+   IT/R 资源域行为的事项即 DASPR 资产，已由客体字段承载，行为字段只需填动词。IT/M 和 IT/G 域行为需同时填写动词和事项。
+   事项是相关方关注的**领域/议题**，不是行为本身。"风险评估"是事项，"开展风险评估"才是行为。
+   行为的存在性取决于条文结构：相关方(R) + 客体共现时动词必填，否则可无。

### 2.2.5 环境与 IT/R 资源域的关系

+   环境维度描述条款适用的背景场所/路径，其词库来源与客体相同（IT/R 资源域词库）。同一 DASPR 资产在不同条文中可充当客体或环境，取决于条文语境：

-   当资产作为**被管理的对象**（条款要求对其进行保护、部署、维护）时，标注为客体。
-   当资产描述**义务发生的背景**（场所、分界、路径）时，标注为环境。

+   环境字段为多值字段，可同时标注多个资产。标注时使用资产名称文本（不用 DASPR 编码）。

    | 资产          | 作为客体 | 作为环境     |
    | ------------- | -------- | ------------ |
    | 云平台        | A2       | 云环境       |
    | 互联网        | S2       | 互联网       |
    | 专线/VPN      | S3       | 专线/VPN     |
    | 移动存储介质  | S9       | 移动存储介质 |
    | 机房/数据中心 | P1       | 机房         |
    | 边界/DMZ      | S5       | DMZ          |
    | 内部网络      | S1       | 内部网络     |

### 2.2.6 条件维度

+   条件维度（触发事件、例外）描述义务的生效边界：

-   **触发事件**：义务何时激活（满足则生效）。
-   **例外**：义务何时豁免（满足则不适用）。

+   条件与环境的区别：环境引用 IT/R 资源域词库，描述持续存在的空间背景；条件是自由文本，描述状态变化的开关。

### 2.2.7 控制机制

+   控制机制是约束行为的工具/手段，分为三类，与三域体系对应：

-   **T 技术机制**：技术工具，如加密、访问控制、审计日志。
-   **M 管理机制**：管理工具，如审批/授权、四眼原则、合同约束。参考 COSO 控制活动类型。
-   **G 治理机制**：治理工具，如职责分离、授权矩阵、考核问责。

+   控制机制与事项域的关系：事项域描述"做什么事"（归入行为维度），控制机制描述"用什么约束"（归入控制维度）。两者分属不同维度，不混用。

### 2.2.8 属性体系

+   相关方、客体、环境三个维度组均采用**身份 + 属性**结构：身份是实体的归一化标识（维度），属性是对该实体的进一步限定（属性各组独立定义）。
+   属性以结构化数组存储，每个属性项包含属性维度名（`dim`）、属性值（`value`）和是否必填（`required`）三个字段。

+   **相关方属性维度**（职责为必填，其余可选）：

    | 属性维度 | 说明                         | 举例                           |
    | -------- | ---------------------------- | ------------------------------ |
    | 职责     | 在本条义务中承担的 RACISV 责任类型 | R（执行）/ A（负责）/ S（审批）…… |
    | 规模     | 组织体量或数据处理量         | 大型平台、处理100万人以上个人信息的 |
    | 属地     | 地理管辖归属                 | 境内、境外                     |

+   **客体属性维度**（均可选）：

    | 属性维度 | 说明                           | 举例                           |
    | -------- | ------------------------------ | ------------------------------ |
    | 状态     | 义务发生时资产所处的处理阶段   | 采集、传输、存储、使用、共享、出境 |
    | 规模     | 数据量级或资产数量             | 超过100万条、大批量            |
    | 分级     | 资产的安全分级或敏感度标识     | 等保三级、重要数据、敏感个人信息 |
    | 属地     | 数据存储或产生的地理位置       | 境内存储的、境外产生的         |

+   **环境属性维度**（可选）：

    | 属性维度 | 说明             | 举例           |
    | -------- | ---------------- | -------------- |
    | 属地     | 环境的地理位置   | 境内、境外、跨境 |

# 3 词库体系

## 3.1 IT/R 资源域词库（DASPR）

+   客体和环境两个字段共用 IT/R 资源域词库。同一资产在不同条款中可充当客体或环境角色，角色由对应字段分别标注。
+   编码规则：客体字段使用 D/A/S/P/R 前缀编码；环境字段使用资产名称文本（不用编码）。

+   **D 类：数据层**

    | 代码 | 名称         | 说明                                       | 状态属性可选值                                |
    | ---- | ------------ | ------------------------------------------ | --------------------------------------------- |
    | D1   | 个人信息     | 与可识别自然人相关的各类信息               | 采集、传输、存储、使用、共享、出境、删除/销毁 |
    | D2   | 敏感个人信息 | 生物识别、金融账户、行踪轨迹等特殊类别信息 | 同 D1                                         |
    | D3   | 重要数据     | 法规定义的重要数据目录中列明的数据         | 同 D1                                         |
    | D4   | 核心数据     | 关系国家安全、国民经济命脉、重要民生的数据 | 同 D1                                         |
    | D5   | 政务数据     | 国家机关在履行法定职责中收集和产生的数据   | 同 D1                                         |
    | D6   | 一般业务数据 | 企业经营中产生的一般商业及业务数据         | 同 D1                                         |
    | D7   | 日志数据     | 操作日志、安全日志、审计日志等记录型数据   | 生成、存储、分析、归档、删除                  |
    | D8   | 鉴别信息     | 口令、密钥、证书、令牌等身份凭据           | 生成、传输、存储、使用、变更、销毁            |
    | D9   | 配置数据     | 系统配置参数、安全基线参数等配置型数据     | 创建、变更、存储、备份、恢复                  |

+   **A 类：应用层**

    | 代码 | 名称             | 说明                                       | 状态属性可选值                           |
    | ---- | ---------------- | ------------------------------------------ | ---------------------------------------- |
    | A1   | 业务应用系统     | 直接支撑业务运营的应用软件系统             | 规划、开发、测试、部署、运行、变更、下线 |
    | A2   | 基础设施平台     | 云平台、操作系统、虚拟化平台等基础运行环境 | 同 A1                                    |
    | A3   | 数据库           | 结构化或非结构化数据的存储管理系统         | 部署、运行、维护、备份、迁移、下线       |
    | A4   | 中间件与接口     | 系统间通信与集成的中间层组件及 API         | 同 A1                                    |
    | A5   | 关键信息基础设施 | 依法认定的关键信息基础设施                 | 同 A1                                    |

+   **S 类：系统层**

+   `*`：属性字段内，职责（RACISV）为必填，其余属性维度均可选。
+   动词字段的必填条件：当同一条原子要求中同时存在相关方（R角色）和客体时，动词为必填。
+   事项字段：当行为涉及 IT/M 或 IT/G 域时填写对应事项，IT/R 域行为不填事项（客体字段已承载资产）。

## 4.2 法规溯源字段

+   **法规名称**：法规/标准全称，如"中华人民共和国数据安全法"。数据库实现时，法规作为独立主表存储，原子记录通过 `regulation_id` 引用；JSON 格式展示全称。
+   **条款编号**：原始条款的层级定位符，取可独立定位的最小编号层级：

    | 文本类型               | 引用层级       | 示例                          |
    | ---------------------- | -------------- | ----------------------------- |
    | 法律/行政法规/部门规章 | 条（第X条）    | `数据安全法§21`               |
    | 国家/行业标准          | 最小数字编号节 | `GB/T 22239§8.1.4.1`          |
    | 通知/发文              | 最小编号层级   | `某通知§附件一第三条第(二)项` |

+   **效力层级**：法律、行政法规、部门规章、国家标准、行业标准、团体标准。
+   **适用行业**：引用行业清单树的节点，允许多值。行业清单树结构：

    -   第一层：行业标准分类代号（JR 金融/YD 通信/WS 卫生/NB 能源……）及 `通用`（全行业适用）
    -   第二层（可选）：监管领域，按监管机构边界划分（如 JR 下分 NFRA 监管范围、CSRC 监管范围）
    -   第三层及以后（可选）：子行业，参考 GB/T 4754 国民经济行业分类
    -   允许跨层引用：可直接引用任意层级节点，无需逐层细化
    -   行业清单树作为独立词库维护，不在本指南中展开

## 4.3 目标字段

+   **安全目标**：条款旨在达成的 COAST 安全目标，直接从 3.5 节词库中选取，格式 `{一级} > {二级} > {三级}`。尽量填到三级；跨多个三级目标时可停留二级；多个目标用分号分隔。处罚性条款通常不填。声明性安全目标条款在此字段填写目标，控制机制可留空。

## 4.4 后果字段

+   **法律后果**：违反该义务时适用的处罚，通常引用法律责任章节，如"数据安全法§48"。无则留空。

## 4.5 相关方字段

+   **身份**：条款涉及的参与方，从角色词库选取归一化类型，格式 `{归一化类型}【{类型}】`，如 `数据处理者【组织】`。一条原子要求可包含多个相关方，每个相关方独立标注身份和属性。
+   **属性**：对该参与方的限定条件，以结构化数组存储，每项包含 `dim`（属性维度）、`value`（属性值）、`required`（是否必填）：

    | 属性维度 | required | 说明                      | 取值规则                    |
    | -------- | -------- | ------------------------- | --------------------------- |
    | 职责     | true     | 在本条义务中承担的 RACISV 类型 | R / A / C / I / S / V，可多值 |
    | 规模     | false    | 组织体量或数据处理量      | 自由文本，条款未限定时不填  |
    | 属地     | false    | 地理管辖归属              | 自由文本，条款未限定时不填  |

## 4.6 客体字段

+   **资产**：义务作用的信息资产，每个资产独立标注身份和属性。资产身份使用 DASPR 编码，如 `D3 重要数据`。允许多值；无资产客体时留空。
+   **属性**：对该资产的限定条件，以结构化数组存储：

    | 属性维度 | required | 说明                         | 取值规则                    |
    | -------- | -------- | ---------------------------- | --------------------------- |
    | 状态     | false    | 义务发生时资产所处的处理阶段 | 从各资产状态集中选取        |
    | 规模     | false    | 数据量级或资产数量           | 自由文本，条款未限定时不填  |
    | 分级     | false    | 安全分级或敏感度标识         | 自由文本，条款未限定时不填  |
    | 属地     | false    | 数据存储或产生的地理位置     | 自由文本，条款未限定时不填  |

## 4.7 行为字段

+   **动词**：相关方对客体/事项执行的动作，使用归一化动词，见 3.3.1 节。必填条件：当同一条原子要求中同时存在相关方（R角色）和客体时必填，否则可留空。
+   **事项**：行为所关注的管理/治理领域，从 IT/M 或 IT/G 事项域选取（见 3.3.2、3.3.3 节）。IT/R 资源域行为不填事项（资产由客体字段承载）。

## 4.8 环境字段

+   **资产**：条款适用的背景场所/路径，从 IT/R 资源域词库选取资产名称（如"云环境"、"互联网"、"DMZ"）。多值，可同时标注多个。无显式限定时留空。
+   **属性**：对环境的限定条件，以结构化数组存储：

    | 属性维度 | required | 说明           | 取值规则                   |
    | -------- | -------- | -------------- | -------------------------- |
    | 属地     | false    | 环境的地理位置 | 自由文本，如"境内"、"跨境" |

## 4.9 条件字段

+   **触发事件**：动态事件驱动的义务激活条件——事件发生时义务从休眠变为激活。如"发现数据安全缺陷或漏洞"、"数据安全事件发生"。无则留空。
+   **例外**：义务的豁免条件——满足该条件时义务不适用。如"经中华人民共和国主管机关批准的除外"。无则留空。

## 4.10 控制字段

+   **控制机制**：具体的控制工具/手段，从 T/M/G 机制词库选取，见 3.4 节。使用前缀标明类型，格式：`T: 密码/加密; M: 审批/授权`。允许多类型混合。条文未指定具体机制时留空。
+   **义务模态**：条款的义务性质：

    | 值   | 关键词                 | 含义             |
    | ---- | ---------------------- | ---------------- |
    | 应   | 应、应当、须、必须     | 强制作为         |
    | 不得 | 不得、不应、禁止、严禁 | 强制不作为       |
    | 可以 | 可以、可               | 授权许可，非强制 |
    | 宜   | 宜、鼓励、支持         | 推荐做法，非强制 |

+   **时限**：条款明确的时间约束。参考值：立即、及时、定期（注明周期，如"每年一次"）、N 日内。无则留空。
+   **量化指标**：条款包含的具体数值约束。示例：密码长度≥8位、日志留存≥6个月、RPO≤4小时。无则留空。

# 5 标注规则

## 5.1 多值、留空与推断规则

+   **多值标注**：相关方、客体、环境、控制机制、安全目标均可标注多项。相关方和客体以数组形式承载多个实体，每个实体独立标注属性。
+   **留空规则**：当条款未显式指定某维度时，该维度留空，表示"不限/未指定"。不得填写"全部"、"不限"等文字。
+   **推断克制**：标注忠实于条款原文。仅当上下文逻辑关系明确时允许推断，不做过度解读。
+   **颗粒度就高**：标注优先使用原文表述对应的最具体分类。如原文为"敏感个人信息"，不应标注上位概念"个人信息"（D1），应标注 D2。

## 5.2 属性词标注规则

+   **属性词的来源**：属性词提取自条文中对要素的限定性描述。当条文使用"……的"定语结构修饰相关方、客体或环境时，该定语即为属性词的候选。
+   **逐维度检查**：拆解时按 2.2.8 节定义的属性维度逐项检查条文，确认每个维度是否有限定。
+   **属性词与要素的绑定**：属性词应挂在其直接限定的要素上，不应集中堆放。

    | 条文片段                       | 要素   | 属性维度 | 属性词           |
    | ------------------------------ | ------ | -------- | ---------------- |
    | 境内的组织、个人               | 相关方 | 属地     | 境内             |
    | 处理100万人以上个人信息的      | 相关方 | 规模     | 处理100万人以上  |
    | 存储于中华人民共和国境内的数据 | 客体   | 属地     | 境内存储的       |
    | 超过100万条个人信息            | 客体   | 规模     | 超过100万条      |
    | 等保三级及以上的系统           | 客体   | 分级     | 等保三级及以上   |
    | 境外                           | 环境   | 属地     | 境外             |

## 5.3 省略还原规则

+   监管条文常省略要素，拆解时需从上下文还原：

    | 省略类型     | 还原方式                       | 示例                                      |
    | ------------ | ------------------------------ | ----------------------------------------- |
    | 主体省略     | 从章节标题、适用范围条款推断   | "所有变更必须经过审批" → 还原执行者       |
    | 客体省略     | 从行为动词推断变更/处理的对象  | "应当加强风险监测" → 还原监测对象         |
    | 环境省略     | 从文档上下文推断适用的环境     | 通常默认不限环境                          |
    | 隐含义务动词 | "是……"句式还原为"应当承担……"   | "X是安全第一责任人" → X应当承担安全责任   |
    | 语法主语偏移 | 活动名称作主语时还原真正的主体 | "变更管理应当确保……" → 负责变更管理的组织 |

+   还原依据为**条文显式提及的上下文**，不做过度推断。

## 5.4 IT/R 资源域资产的角色判定

+   同一 DASPR 资产在不同条文中可充当客体或环境角色：

-   当资产作为**被管理的对象**（条款要求对其进行保护、部署、维护）时，标注为客体。
-   当资产描述**义务发生的背景**（处理/存储场所、网络分界、数据流转路径）时，标注为环境。

## 5.5 RACISV 标注规则

+   同一角色在不同条款中可承担不同 RACISV 职责，职责由条文语境判定：

    | 条文片段                           | 角色           | 职责属性 |
    | ---------------------------------- | -------------- | -------- |
    | 数据处理者应当采取加密措施         | 数据处理者     | R        |
    | 应当明确数据安全负责人             | 数据安全负责人 | A        |
    | 经安全评估机构评估后方可           | 评估/认证机构  | C        |
    | 及时告知用户                       | 用户           | I        |
    | 经中华人民共和国主管机关批准       | 监管机构       | S        |
    | 向有关主管部门报告                 | 监管机构       | I; V     |
    | 第三方服务商应在合同范围内处理数据 | 第三方服务商   | R        |

## 5.6 T 机制分层标注规则

+   技术控制机制默认标到第一层（安全能力大类），如"密码/加密"。
+   仅在条款原文明确指定具体技术手段时才标注第二层，如"传输层加密(TLS)"。

## 5.7 行为域判定规则

+   条文中的动作属于哪个域，取决于其作用对象：

    | 条文                               | 动词 | 作用对象     | 域   | 事项              |
    | ---------------------------------- | ---- | ------------ | ---- | ----------------- |
    | 数据处理者应当加密传输个人信息     | 处理 | D1 个人信息  | IT/R | —（客体承载）     |
    | 应当定期开展风险评估               | 开展 | 风险评估     | IT/M | 风险评估          |
    | 应当明确数据安全负责人             | 建立 | 岗位/角色    | IT/G | 岗位/角色设置     |
    | 运维人员对生产环境的所有变更应审批 | 变更 | 生产环境系统 | IT/R | —（客体承载）     |
    | 应当制定数据安全策略文件           | 建立 | R1 策略文件  | IT/R | —（客体承载）     |
    | 应当建立健全数据安全管理体系       | 建立 | —            | IT/M | 制度建设/文档管理 |

+   判断标准：作用对象是 DASPR 资产 → IT/R 域；作用对象是管理活动 → IT/M 域；作用对象是治理结构 → IT/G 域。

## 5.8 条文拆分规则

+   出现以下任一情形时，拆分为多条独立原子记录：

-   条文涉及多个不同的 R 角色（执行者），每个执行者单独一条记录
-   条文中义务模态混合（"应"与"不得"并存），按模态分别单独一条记录
-   条文中存在不同触发事件，每个触发事件单独一条记录
-   条文中包含证据要求（如"留存操作记录"），证据要求拆为独立的原子要求

## 5.9 不拆的条文类型

+   以下类型条文跳过，不纳入原子记录：

    | 类型       | 示例                    | 原因                         |
    | ---------- | ----------------------- | ---------------------------- |
    | 定义条款   | 第3条 数据的定义        | 无义务，仅定义术语           |
    | 政策宣示   | 第7条 国家保护数据权益  | 无可验证合规动作             |
    | 立法目的   | 第1条 制定本法目的      | 无义务                       |
    | 纯授权条款 | 第54条 军事数据另行制定 | 义务在子法规中，待子法规拆解 |

# 6 拆解步骤

+   按以下步骤对每条条文执行拆解：

-   **Step 1　识别是否需拆解**：判断条文是否属于不拆类型（见 5.9 节）。属于则跳过。
-   **Step 2　识别相关方**：条文中有哪些参与方？为每个参与方确定归一化身份（角色词库），并标注职责属性（RACISV）。多个 R 角色则准备生成多条记录。注意辨别语法主语偏移（见 5.3 节）。
-   **Step 3　识别客体与行为域**：条文针对什么资产？判断属于 IT/R（资产）、IT/M（管理事项）还是 IT/G（治理事项）。IT/R 域标注 DASPR 编码；IT/M 或 IT/G 域标注事项名称。
-   **Step 4　确定动词**：相关方和客体/事项共现时确定归一化动词。
-   **Step 5　标注环境**：条文涉及哪些背景场所/路径？从 IT/R 资源域选取资产名称填入，无则留空（见 5.4 节角色判定）。
-   **Step 6　标注属性**：检查条文中是否有对相关方、客体、环境的限定性描述，有则提取并填入对应属性维度（见 5.2 节）。
-   **Step 7　标注条件**：有无触发事件？有无例外？分别填入。如有不同触发事件，准备拆分多条记录。
-   **Step 8　标注控制**：判断义务模态（见 4.10 节）；从 T/M/G 机制词库选取控制机制（见 3.4 节）；填写时限、量化指标。
-   **Step 9　填写目标与后果**：安全目标（从 3.5 节 COAST 词库选取，尽量到三级）、法律后果、法规溯源。
-   **Step 10　归一化与检查**：对照词表归一化身份类型、映射客体编码至 DASPR 体系、规范控制机制表达。检查是否有证据要求需拆为独立记录。

## 8.2 字段说明

| JSON 字段                               | 对应字段     | 类型             | 必填 | 取值规则                                                              |
| --------------------------------------- | ------------ | ---------------- | ---- | --------------------------------------------------------------------- |
| `regulation.law_name`                   | 法规名称     | string           | 是   | 法规全称；数据库实现时通过 regulation_id 引用法规主表                 |
| `regulation.article`                    | 条款编号     | string           | 是   | 见 4.2 节引用规则，如 `数据安全法§29`、`GB/T 22239§8.1.4.1`          |
| `regulation.effect_level`               | 效力层级     | string           | 否   | 法律/行政法规/部门规章/国家标准/行业标准/团体标准                     |
| `regulation.applicable_industry`        | 适用行业     | array \| null    | 否   | 行业清单树节点 id 列表；全行业通用填 `["通用"]`；无则 null            |
| `target.security_targets`               | 安全目标     | array\<object\>  | 否   | COAST 词库；多目标时含多项；只到二级时省略 `level3`；处罚条款填 `[]`  |
| `consequence.legal_consequence`         | 法律后果     | string \| null   | 否   | 无则 null                                                             |
| `stakeholders[].identity`               | 身份         | string           | 是   | 见 3.2 节角色词库归一化类型                                           |
| `stakeholders[].category`               | 角色类型     | string           | 是   | `"组织"` / `"岗位"` / `"角色"`                                        |
| `stakeholders[].type_class`             | 主体专属性   | string           | 是   | `"通用"` / `"专属"`，见 GUIDE-REG-002 第 2.3 节                       |
| `stakeholders[].attributes`             | 相关方属性   | array            | 是   | 属性对象数组；职责项必填；格式见本节末尾说明                          |
| `object`                                | 客体         | array \| null    | 否   | 客体资产对象数组；无客体时为 null                                     |
| `object[].code`                         | 资产编码     | string           | 否   | DASPR 编码，如 `"D1"`                                                 |
| `object[].name`                         | 资产名称     | string           | 否   | 资产名称，如 `"个人信息"`                                             |
| `object[].attributes`                   | 客体属性     | array \| null    | 否   | 属性对象数组；格式见本节末尾说明；无则 null                           |
| `action.verb`                           | 动词         | string \| null   | 条件 | 归一化动词；相关方(R)+客体/事项共现时必填，否则 null                  |
| `action.domain`                         | 行为域       | string \| null   | 否   | `"IT/R"` / `"IT/M"` / `"IT/G"` / null                                |
| `action.matter`                         | 事项         | string \| null   | 否   | IT/M 或 IT/G 事项域词条；IT/R 域为 null                               |
| `environment.assets`                    | 环境资产     | array \| null    | 否   | IT/R 资源域资产名称列表；无则 null                                    |
| `environment.attributes`                | 环境属性     | array \| null    | 否   | 属性对象数组；格式见本节末尾说明；无则 null                           |
| `condition.trigger_event`               | 触发事件     | string \| null   | 否   | 动态激活条件；无则 null                                               |
| `condition.exception`                   | 例外         | string \| null   | 否   | 豁免条件；无则 null                                                   |
| `control.mechanisms.T`                  | 技术机制     | array\<string\>  | 否   | T 机制词库名称列表；空则填 `[]`                                       |
| `control.mechanisms.M`                  | 管理机制     | array\<string\>  | 否   | M 机制词库名称列表；空则填 `[]`                                       |
| `control.mechanisms.G`                  | 治理机制     | array\<string\>  | 否   | G 机制词库名称列表；空则填 `[]`                                       |
| `control.modality`                      | 义务模态     | string           | 是   | `"应"` / `"不得"` / `"可以"` / `"宜"`                                 |
| `control.degree.deadline`               | 时限         | string \| null   | 否   | `"立即"` / `"及时"` / `"定期"` / `"N日内"` / null                     |
| `control.degree.quantitative_indicator` | 量化指标     | string \| null   | 否   | 无则 null                                                             |

+   **属性对象格式**（适用于 `stakeholders[].attributes`、`object[].attributes`、`environment.attributes`）：每个属性对象包含三个键：
    -   `dim`：属性维度名，取值见各字段说明节中的属性维度表
    -   `value`：属性值，string 或 array\<string\>（职责可多值）
    -   `required`：是否必填，boolean；职责为 `true`，其余为 `false`
    -   示例：`[{"dim":"职责","value":["R"],"required":true},{"dim":"属地","value":"境外","required":false}]`

## 8.3 内规侧记录的差异

+   内规记录复用监管侧同一 schema，额外增加两个字段；`stakeholders[].type_class` 字段不适用于内规侧：

| 附加字段  | 类型   | 说明                                                            |
| --------- | ------ | --------------------------------------------------------------- |
| `doc_ref` | string | 内规来源文件编号，如 `DSP-OPS-012`                              |
| `scope`   | string | 内规适用范围，如 `"全公司"` / `"信息科技部"` / `"核心业务系统"` |

+   内规主体覆盖判断由监管侧 `stakeholders[].type_class` 驱动，见 GUIDE-REG-002 第 2.3 节。
