## 2.6 并发与幂等策略

**乐观锁：** TechnicalSolution 聚合根使用 `version` 字段做乐观锁，冲突时返回 E-40935-01（OPTIMISTIC_LOCK_CONFLICT）。

**幂等性保证：**

| 接口类型     | 幂等键生成规则                         | 存储方式         | 有效期 | 重复请求处理                  |
| ------------ | -------------------------------------- | ---------------- | ------ | ----------------------------- |
| 发起导入     | `tenantId + fileHash + requestId`      | Redis（key-val） | 24h    | 返回首次执行结果              |
| 确认导入     | `importTaskId`                         | DB 唯一索引      | -      | 返回 409 DUPLICATE_SUBMISSION |
| 方案控制关联 | `(solutionId, controlId)` 联合唯一索引 | DB               | -      | 幂等成功                      |

**异步导入锁：** 同一租户同一时刻只允许一个导入任务进行中，通过 Redis 分布式锁（key=`import:lock:{tenantId}`，TTL=10min）控制并发。

## 2.9 幂等键设计

+   SD-05的幂等键设计如下表所示

    | 接口类型         | 幂等键生成规则                         | 存储方式         | 有效期 | 重复请求处理                  |
    | ---------------- | -------------------------------------- | ---------------- | ------ | ----------------------------- |
    | 发起导入         | `tenantId + fileHash + requestId`      | Redis（key-val） | 24h    | 返回首次执行结果              |
    | 确认导入         | `importTaskId`                         | DB 唯一索引      | -      | 返回 409 DUPLICATE_SUBMISSION |
    | 方案控制关联     | `(solutionId, controlId)` 联合唯一索引 | DB               | -      | 幂等成功                      |
    | 创建技术方案     | `tenantId + solutionCode`              | DB 唯一索引      | -      | 返回 409 DUPLICATE_CODE       |
    | 更新技术方案     | `solutionId + version`                 | 乐观锁           | -      | 返回 409 OPTIMISTIC_LOCK      |
    | 删除方案控制映射 | `mappingId`                            | DB 主键          | -      | 幂等成功（已删除视为成功）    |

    表 2.9-1 幂等键设计

+   **幂等键生成规则说明**：
    +   发起导入：通过 `tenantId + fileHash + requestId` 组合保证同一租户同一文件同一请求不重复处理
    +   确认导入：通过 `importTaskId` 保证同一导入任务不重复确认
    +   方案控制关联：通过 `(solutionId, controlId)` 联合唯一索引保证同一方案不重复关联同一控制
    +   创建技术方案：通过 `tenantId + solutionCode` 保证同一租户内方案编码唯一
    +   更新技术方案：通过乐观锁 `version` 字段保证并发更新安全
    +   删除方案控制映射：通过主键 `mappingId` 保证幂等删除

## 2.10 分布式锁设计

+   SD-05的分布式锁设计如下表所示

    | 锁类型       | 锁键格式                    | 锁粒度 | 超时时间 | 适用场景                     | 获取失败处理                  |
    | ------------ | --------------------------- | ------ | -------- | ---------------------------- | ----------------------------- |
    | 导入任务锁   | `import:lock:{tenantId}`    | 租户级 | 10min    | 同一租户同时只能有一个导入   | 返回 E-42235-03 导入进行中    |
    | 方案更新锁   | `solution:lock:{solutionId}`| 方案级 | 30s      | 同一方案并发更新保护         | 返回 E-40935-01 乐观锁冲突    |
    | 批量关联锁   | `mapping:lock:{tenantId}`   | 租户级 | 5min     | 批量关联方案控制时防止并发   | 返回 E-42235-05 批量操作进行中|

    表 2.10-1 分布式锁设计

+   **分布式锁实现说明**：
    +   采用 Redis SET NX EX 命令实现分布式锁
    +   锁键格式：`sd05:{lockType}:{businessKey}`
    +   锁值：`{requestId}:{timestamp}` 用于锁持有者校验
    +   锁超时：自动过期时间，防止死锁
    +   锁释放：通过 Lua 脚本保证原子性，仅锁持有者可释放
    +   锁续期：长流程任务（如导入）支持锁续期机制

**幂等设计说明：**

+   SolutionImportTask 的幂等防重策略如下：
    -   **创建幂等**：通过 (tenantId, fileHash) 唯一索引防止重复创建。同一租户对同一文件哈希，若已存在活跃任务（status ∈ {PENDING, PARSING, VALIDATED, IMPORTING}），返回已有任务ID而非创建新任务（TS-R-03）

    | SolutionValidationService     | 逐行执行分层校验规则（L1~L4），纯计算服务          | 无（纯领域逻辑，不依赖聚合）   | P1   |

### 4.4.1 SolutionImportDomainService

+   **职责**：作为导入流程的核心编排者，依次调用解析器、校验服务，将结果写回 SolutionImportTask，并在用户确认后调用持久化流程

+   方法签名如下表所示

    | 方法签名                                                                              | 业务语义               | 所协调的聚合       | 关联规则          | 版本 |
    | ------------------------------------------------------------------------------------- | ---------------------- | ------------------ | ----------------- | ---- |
    | executeParseAndValidate(SolutionImportTask task, List\<RawRow\> rows): ImportSummary  | 执行解析与分层校验流程 | SolutionImportTask | TS-R-04~TS-R-09   | P1   |
    | persistValidSolutions(SolutionImportTask task): List\<UUID\>                          | 持久化通过校验的方案   | TechnicalSolution  | TS-R-11、TS-R-20  | P1   |

    表 4.4.1-1 SolutionImportDomainService方法签名

+   **executeParseAndValidate 协调步骤**：
    1.  调用文件解析器（ExcelParser/JsonParser）将 RawRow 提取为结构化数据
    2.  调用 SolutionValidationService.validateRows() 执行 L1~L4 分层校验
    3.  汇总生成 ImportSummary，逐行生成 ImportResultRow
    4.  调用 task.parseSuccess(summary, rows) 或 task.parseFailed(error) 更新聚合状态

+   **persistValidSolutions 协调步骤**：
    1.  从 task 获取 isValid=true 的 ImportResultRow 列表
    2.  为每行创建 TechnicalSolution 聚合根（含 importTaskId 溯源）
    3.  批量持久化至 ES，返回已入库的 solutionId 列表
    4.  调用 task.importSuccess(solutionIds) 更新任务状态

### 4.4.2 SolutionValidationService

+   **职责**：封装分层校验规则的执行逻辑，为导入行执行 L1~L4 四级校验，纯领域计算服务（无I/O副作用）

+   方法签名如下表所示

    | 方法签名                                                                        | 业务语义                     | 校验规则         | 版本 |
    | ------------------------------------------------------------------------------- | ---------------------------- | ---------------- | ---- |
    | validateRows(tenantId, rows: List\<RawRow\>): List\<ImportResultRow\>           | 对批次内所有行执行分层校验   | TS-R-04~TS-R-09  | P1   |
    | validateRow(tenantId, row: RawRow, existingNames: Set\<String\>): ImportResultRow | 对单行执行全量校验           | TS-R-04~TS-R-09  | P1   |
    | checkL1Format(row: RawRow): List\<ValidationError\>                             | L1 文件格式与结构完整性校验  | TS-R-04          | P1   |
    | checkL2Required(row: RawRow): List\<ValidationError\>                           | L2 必填字段校验              | TS-R-05, TS-R-07 | P1   |
    | checkL3Range(row: RawRow): List\<ValidationError\>                              | L3 字段范围与枚举合法性校验  | TS-R-06, TS-R-08 | P1   |
    | checkL4Uniqueness(tenantId, row, existingNames): List\<ValidationError\>        | L4 业务语义唯一性校验        | TS-R-09          | P1   |

    表 4.4.2-1 SolutionValidationService方法签名

+   **校验短路策略**：L1 失败则跳过 L2~L4；L2 失败则跳过 L3~L4（降低不必要的查询成本）

### 4.4.3 SolutionControlLinkingService

+   **职责**：通过 RPC 查询 SD-03 验证控制合法性，再调用 TechnicalSolution 聚合根的 linkControl 方法完成关联创建

+   方法签名如下表所示

    | 方法签名                                                                                     | 业务语义                       | 关联规则          | 版本 |
    | -------------------------------------------------------------------------------------------- | ------------------------------ | ----------------- | ---- |
    | linkControl(tenantId, solutionId, controlId, mappingType): SolutionControlMapping            | 验证控制合法性后建立方案关联   | TS-R-30~TS-R-34   | P1   |
    | unlinkControl(tenantId, solutionId, controlId): void                                         | 解除方案与控制的关联           | -                 | P1   |
    | listControlMappings(tenantId, solutionId): List\<SolutionControlMapping\>                    | 查询方案的全部控制关联         | -                 | P1   |

    表 4.4.3-1 SolutionControlLinkingService方法签名

+   **linkControl 协调步骤**：
    1.  通过 SD-03 RPC 接口查询 controlId 对应的控制信息，验证：控制存在、所属租户与 tenantId 一致（TS-R-31）、ControlType=TECHNICAL（TS-R-30）
    2.  加载 TechnicalSolution 聚合根，调用 aggregate.linkControl(controlId, mappingType)
    3.  聚合根执行 TS-R-32~TS-R-34 守卫条件，校验通过后创建 SolutionControlMapping 实体并持久化

## 4.5 领域事件清单

+   SD-05 领域事件清单及说明如下表所示

## 6.0 通用响应格式

+   SD-05所有接口遵循统一响应格式（引用BC总体设计约定）

```json

  "code": "SUCCESS",

```

+   说明：code 字段固定为 `"SUCCESS"`；data 字段类型因接口而异（对象/列表/null）；traceId 供链路追踪

```json
{
  "code": "E-42235-03",
  "message": "当前租户已有导入任务进行中，请等待完成",
  "timestamp": "2026-03-02T14:30:00Z",
  "traceId": "abc123",
  "details": {
    "field": "importTaskId",
    "existingTaskId": "uuid-task-001",
    "suggestion": "请等待当前任务完成后再上传"
  }
}
```

+   说明：details 字段为可选，当业务异常有可操作建议时提供；errors 字段用于批量校验失败时附带字段级错误列表

**（3）分页响应格式**

+   分页接口的 data 字段统一为以下结构：

```json
{
  "list": [],

  "pageNum": 1,

}
```

# 7 数据模型设计

## 7.1 存储架构设计

### 7.1.1 存储策略

**设计原则：**

+   **ES作为主存储**：技术方案数据（TechnicalSolution）存储在ES中，支持全文检索、复杂查询和高性能读取
+   **MySQL最小化使用**：仅用于必须的事务性操作（导入任务状态管理）
+   **数据一致性**：导入任务完成后，方案数据写入ES；任务状态在MySQL中管理

**存储分工表：**

| 数据类型           | 存储介质 | 理由                                                   |
| ------------------ | -------- | ------------------------------------------------------ |
| 技术方案主数据     | ES       | 需要全文检索、复杂过滤、高性能读取                     |
| 方案控制关联关系   | ES       | 作为方案文档的嵌套字段存储，便于关联查询               |
| 导入任务状态       | MySQL    | 需要事务保证、状态机转换、乐观锁控制                   |
| 导入校验明细       | MySQL    | 临时数据，任务完成后可清理，无需ES索引                 |

### 7.1.2 领域模型-数据模型映射

| 领域对象               | 对象类型 | 映射方式     | 目标存储                          | 说明                                              |
| ---------------------- | -------- | ------------ | --------------------------------- | ------------------------------------------------- |
| SolutionImportTask     | 聚合根   | MySQL独立表  | solution_import_task              | 事务性状态管理，1:1 直接映射                      |
| ImportResultRow        | 实体     | MySQL独立表  | solution_import_result_row        | 临时校验明细，1:N，任务完成后可定期清理           |
| TechnicalSolution      | 聚合根   | ES文档       | tech_solution（ES索引）           | 主存储，支持全文检索和复杂查询                    |
| SolutionContent（VO）  | 值对象   | ES嵌套字段   | tech_solution.content             | 配置项集合，作为ES文档的嵌套对象                  |
| SolutionControlMapping | 实体     | ES嵌套数组   | tech_solution.control_mappings    | 方案-控制关联，作为ES文档的嵌套数组               |
| TechnicalType（VO）    | 值对象   | ES字段       | tech_solution.technical_type      | 单字段枚举，直接平铺                              |

### 7.3.2 数据一致性与隔离

**MySQL与ES数据同步：**

| 场景           | 同步方式                                   | 一致性保证                               |
| -------------- | ------------------------------------------ | ---------------------------------------- |
| 方案导入完成   | 应用层同步写入ES                           | 事务内完成，失败则回滚MySQL任务状态      |
| 方案更新       | 直接更新ES文档                             | 使用version字段实现乐观锁                |
| 方案删除       | 逻辑删除（更新status为ARCHIVED）           | 仅更新ES，不物理删除                     |

**租户数据隔离：**

+   **MySQL层**：所有查询强制带tenant_id条件
+   **ES层**：使用routing key确保同租户数据在同一分片，查询时强制带tenant_id过滤
+   **应用层**：从JWT token中提取tenant_id，所有数据操作自动注入租户上下文

## 8.3 核心交互说明

**PG-SD05-02 导入向导（三步式）：**

+   **第一步 上传文件**：支持拖拽或点击选择文件（.xlsx/.xls/.json），文件大小超10MB时前端提前拦截提示；上传成功后调用 API-SD05-001 获取 importTaskId
+   **第二步 校验结果**：上传后自动轮询 API-SD05-002，轮询间隔2s；状态变为 VALIDATED 时自动跳转展示校验结果（通过行数/失败行数）；点击"查看详情"跳转 PG-SD05-03；超过60s未完成时提示"解析耗时较长，可离开并在历史页查看结果"
+   **第三步 确认导入**：展示校验摘要（通过X行/失败Y行）；validRows=0 时"确认导入"按钮置灰；可选择关联技术控制（多选）；点击"确认导入"调用 API-SD05-004

**PG-SD05-03 校验结果展示规则：**

+   错误行整行高亮（黄色背景），错误字段列标红
+   悬停错误字段显示错误原因 tooltip
+   顶部提供"只看错误行"切换开关（调用 API-SD05-003 时传 rowStatus=FAIL）
+   错误行数 > 100 时提示"可下载校验报告查看完整错误详情"（P2功能预留）

**PG-SD05-04 方案详情页交互规则：**

+   敏感配置项（isSensitive=true）的 expectedValue 显示为"***"，点击"查看"须二次鉴权（P2预留）
+   DRAFT 状态方案显示"激活"按钮；ACTIVE 显示"停用"；ARCHIVED 状态所有操作按钮隐藏
+   关联控制列表支持新增关联（跳出控制选择弹窗，仅展示 ControlType=TECHNICAL 的控制）和删除关联

**通用轮询策略：**

+   轮询间隔：2s
+   超时阈值：60s（提示后保持页面，不自动跳转）
+   终态检测：status 为 COMPLETED/FAILED/PARSE_FAILED/CANCELLED 时停止轮询

# 9 后端工程结构设计

## 9.1 工程概述

### 9.1.1 微服务归属

+   SD-05技术方案管理子领域归属于 `svc-tenant-deployment`（BC-35租户落地微服务），与 SD-03控制映射、SD-04控制评估等子领域共享同一微服务工程
+   微服务技术栈：Spring Boot 3.2 + JPA（PostgreSQL）+ Elasticsearch 8.x + Kafka + Redis + Spring Security OAuth2
+   SD-05 在共享工程中以独立包路径（`sd05.*`）与其他子领域隔离，遵循"微服务内部的子领域隔离"原则

### 9.3.4 领域事件发布机制

+   SD-05 采用 Outbox 模式（事务性发件箱）保证领域事件与业务数据的原子性

    ```
    ┌────────────────────────────────────────────────────────────────┐
    │                    事件发布流程                                │
    ├────────────────────────────────────────────────────────────────┤
    │                                                                │
    │  应用服务（同一事务）                                          │
    │    1. 更新聚合根状态 → 写入 MySQL                             │
    │    2. 将事件序列化 → 写入 domain_event_outbox 表              │
    │    3. 事务提交                                                 │
    │                                                                │
    │  Outbox Publisher（异步）                                      │
    │    4. 定时轮询 domain_event_outbox 未发送记录（每1s）          │
    │    5. 发布至 Kafka（确认ACK后标记 published=true）            │
    │    6. 消费方（BC-32）按 eventId 幂等消费                      │
    │                                                                │
    │  内部事件（ImportTaskValidatedEvent）                          │
    │    → 通过 Spring ApplicationEvent 发布（进程内，不走Kafka）    │
    │    → 应用服务监听后更新轮询缓存（Redis），前端轮询感知         │
    └────────────────────────────────────────────────────────────────┘
    ```

# 10 权限设计

## 10.1 权限模型概述

+   SD-05 权限设计基于 BC-10 用户管理子领域提供的 RBAC（基于角色的访问控制）权限模型
+   **权限粒度**：资源级权限码，格式为三段式 `{领域}:{资源}:{操作}`
+   **BC-35 权限命名空间**：`sol`（代表 tenant**sol**ution，租户落地子领域）
+   **权限码格式**：`sol:{resource}:{action}`
+   **校验时机**：在 Controller 层通过 `@PreAuthorize("hasAuthority('sol:import:create')")` 注解声明，由 Spring Security 统一拦截校验；领域层不做权限校验（领域纯净性原则）
+   **安全上下文注入**：tenantId、userId 由认证网关写入 JWT Token，应用层从 SecurityContextHolder 注入到 Command 对象，禁止前端传入

    | ---------- | ---------------------------------------------------------------------------- | ------------------------------------------------------ |

## 10.6 数据权限设计（租户隔离）

+   SD-05 的数据权限基于租户隔离（Tenant Isolation），采用应用层 + 数据库双重保障

    | 隔离层级   | 实现机制                                                                      | 适用范围                            |
    | ---------- | ----------------------------------------------------------------------------- | ----------------------------------- |
    | 应用层隔离 | tenantId 强制由 SecurityContext 注入，所有查询条件自动附加 tenantId 过滤      | 所有接口和RPC调用                   |
    | JPA层隔离  | 通过 Hibernate 多租户过滤器（TenantFilter）自动拼接 `tenant_id = ?` 条件     | MySQL 数据库查询（导入任务/状态）   |
    | ES层隔离   | ES查询 DSL 中强制追加 `term: { tenantId: "当前租户ID" }` 过滤条件            | Elasticsearch 方案查询              |
    | 数据库层   | PostgreSQL Row Level Security（RLS）策略，对 solution_import_task 表启用行级安全 | 数据库层兜底，防止 JPA 层绕过      |

    表 10.6-1 数据权限隔离机制

+   **RLS 策略示例（PostgreSQL）：**

    ```sql
    -- 启用 RLS
    ALTER TABLE solution_import_task ENABLE ROW LEVEL SECURITY;

    -- 创建租户隔离策略
    CREATE POLICY tenant_isolation ON solution_import_task
        FOR ALL
        USING (tenant_id = current_setting('app.current_tenant_id')::uuid);

    -- 应用层在事务开始时设置租户ID
    -- SET LOCAL app.current_tenant_id = '${tenantId}';
    ```

+   **跨租户操作审计**：对涉及多租户数据的 RPC 调用（如 queryBySolutionIds），基础设施层验证请求中的 tenantId 与查询结果的 tenantId 一致，不一致时记录审计日志并拒绝返回

### D.1.1 缓存键命名规范

### D.1.3 缓存防护策略

+   **缓存穿透防护**：查询不存在的 solutionId 时，在 Redis 中缓存空值（null marker，TTL=60s），避免频繁穿透数据库
+   **缓存击穿防护**：方案详情缓存失效时，使用 Redis `SETNX` 实现互斥锁（mutex lock），只允许一个请求重建缓存，其余请求等待100ms后读缓存
+   **缓存雪崩防护**：各缓存键的 TTL 在基准值上加随机抖动（±20%），避免大量缓存同时过期

    | 防护场景 | 防护策略                         | 实现方式                            | 影响范围              |
    | -------- | -------------------------------- | ----------------------------------- | --------------------- |
    | 缓存穿透 | 空值缓存（null marker）          | 查询无结果时缓存 `__NULL__`，60s TTL | solutionId 查询接口  |
    | 缓存击穿 | 互斥锁（mutex lock）             | Redis SETNX，锁TTL=5s               | 方案详情热点键重建    |
    | 缓存雪崩 | TTL 随机抖动                     | TTL = 基准值 × (0.8~1.2) 随机因子   | 所有缓存键            |

    | 分片数             | primary_shards=1（单租户数据量有限）          | 单租户方案数量预估 < 10万，1分片足够         |
    | 副本数             | replicas=1（生产），0（开发）                 | 生产环境保证高可用，开发环境节省资源         |
    | 刷新间隔           | `refresh_interval: 5s`                        | 方案导入不需要实时可见，5s 延迟可接受        |
    | 字段 keyword 索引  | solutionCode、tenantId、status 添加 keyword   | 支持精确匹配和聚合统计                       |
    | 字段 text 分词     | solutionName、description 使用 ik_max_word    | 支持中文全文检索                             |
    | 动态映射关闭       | `dynamic: false`                              | 防止意外字段自动建立索引，节省存储           |
    | source 过滤        | 查询时指定 `_source_includes` 字段列表        | 减少网络传输量，避免返回 configItems 大字段  |

### D.2.2 常见查询模式

+   SD-05 的 ES 查询场景及优化策略如下

    | 查询场景               | 查询类型                                    | 优化策略                                       | 预期响应时间 |
    | ---------------------- | ------------------------------------------- | ---------------------------------------------- | ------------ |
    | 方案列表分页查询       | term(tenantId) + range(status) + from/size  | 避免深分页（from > 1000），改用 search_after   | < 100ms      |
    | 方案关键词搜索         | match(solutionName) + filter(tenantId)      | filter 优先（利用缓存），match 仅用于评分       | < 200ms      |
    | 方案详情查询           | term(solutionId) + term(tenantId)           | 优先走 Redis 缓存，ES 作为缓存miss的回源       | < 50ms（缓存命中）|
    | 按技术类型聚合统计     | terms aggregation on TechnicalType.keyword  | 在 filter context 中执行，不影响评分计算        | < 300ms      |
    | 导入后批量写入         | Bulk API，batch_size=100                    | 异步写入，失败后重试（最多3次，指数退避）       | < 2s（批量） |
