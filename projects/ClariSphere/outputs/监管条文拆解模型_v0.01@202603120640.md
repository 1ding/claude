# 法规条款原子化拆解模型

## 1 概述

### 1.1 目标

对法规、标准的条款进行原子化拆解与结构化标注，使同一条款可通过多种维度组合被检索和聚合，支撑以下典型查询场景：

* 按客体聚合："针对数据的要求都有哪些"
* 按环境聚合："外网相关要求都有哪些"
* 按措施聚合："需要加密的场景都有哪些"
* 多维交叉筛选："重要数据 + 外网 + 传输态 + 应加密"

### 1.2 原子的定义

**原子要求**是本模型的基本记录单元，定义为：一个条款中包含的、可独立理解且可独立落地的单条要求。

若一个法条包含多个并列要求，则拆分为多条原子记录；每条原子记录独立标注全部维度。

### 1.3 原子要求的结构

每条原子要求的语义结构为：

```
场景条件（谁 + 针对什么 + 在什么环境下 + 经由什么途径）
  → 控制要求（做什么 + 做到什么程度）
```

对应到维度体系，即：

```
[责任主体] 针对 [客体/资产(状态)] 在 [环境/区域] 经由 [通道/途径] 与 [协作方]
  → 应/宜/不得 采取 [T/M/G 控制手段]，满足 [控制程度] 要求
```

## 2 维度体系总览

本模型的标注维度分为三组：

| 组别                 | 维度              | 词库来源                  | 说明                 |
| -------------------- | ----------------- | ------------------------- | -------------------- |
| **场景条件**   | 责任主体          | 角色词库                  | 条款的执行者         |
|                      | 客体/资产         | 统一实体词库（角色=客体） | 条款针对的对象       |
|                      | 环境/区域         | 统一实体词库（角色=环境） | 条款适用的场景边界   |
|                      | 通道/途径         | 统一实体词库（角色=通道） | 行为经由的方式       |
|                      | 协作方            | 角色词库（角色=协作方）   | 条款涉及的外部关系方 |
| **控制要求**   | 要求类型          | 固定枚举                  | 原子要求的性质分类   |
|                      | 控制手段（T/M/G） | 三套独立词库              | 具体控制措施         |
|                      | 控制程度          | 多子维度                  | 控制的约束条件       |
| **法规元数据** | 法规来源          | —                        | 条款的出处与效力     |
|                      | 适用范围          | —                        | 行业、业务、适用条件 |

## 3 底层支撑：词库体系

### 3.1 统一实体词库

客体、环境、通道三个维度共用一套统一实体词库。同一实体在不同条款中可扮演不同角色。

#### 3.1.1 实体结构

每个实体条目包含以下属性：

| 属性     | 说明                     | 示例                               |
| -------- | ------------------------ | ---------------------------------- |
| 实体编码 | 唯一标识                 | ENT-DATA-001                       |
| 实体名称 | 规范名称                 | 重要数据                           |
| 分类层级 | 所属大类 → 细类         | 数据 → 重要数据                   |
| 属性集   | 该实体可标注的属性       | 密级、结构化/非结构化              |

## 4 场景条件维度

### 4.1 责任主体

从角色词库中选取，标注为"主体"角色。描述条款的执行者或义务承担者。

* 允许多值（一条要求可能涉及多个主体协同）
* 部分条款主体隐含未明示，此时标注为条款上下文推断的默认主体

### 4.2 客体/资产

从统一实体词库中选取，标注为"客体"角色。描述条款针对的对象。

* 标注内容包括：实体分类 + 属性（如适用） + 状态（如适用）
* 允许多值
* 如条款未明确指定客体类型，标注为上下文可推断的最具体分类

### 4.3 环境/区域

从统一实体词库中选取，标注为"环境"角色。描述条款适用的场景边界。

* 典型值：互联网/外网、内部网络、边界/DMZ、云环境、移动环境、机房、办公场所
* 部分条款无显式环境限定，此时不标注（留空表示"不限环境"）

### 4.4 通道/途径

从统一实体词库中选取，标注为"通道"角色。描述行为经由的方式或介质。

* 典型值：互联网、专线/VPN、API接口、移动存储介质、邮件、即时通讯、纸质/物理方式
* 出现频率低于其他维度，多数条款不显式指定通道

### 4.5 协作方

从角色词库中选取，标注为"协作方"角色。描述条款涉及的外部关系方。

* 在数据共享、出境、外包管理等场景中为高频维度
* 可与责任主体同时标注同一角色（如"第三方服务商"既是协作方也可能是条款中的执行主体）

## 5 控制要求维度

### 5.1 要求类型

每条原子要求必须标注一个要求类型，作为基础分类字段。

| 类型编码 | 类型名称  | 说明                   | 对应词库     |
| -------- | --------- | ---------------------- | ------------ |
| OBJ      | 目标/原则 | 声明性的安全目标或原则 | 安全目标词库 |
| DOC      | 制度/文档 | 要求制定某类文档或制度 | 制度类型词库 |
| T        | 技术措施  | 具体技术控制要求       | T 词库       |
| M        | 管理措施  | 具体管理活动要求       | M 词库       |
| G        | 治理措施  | 组织/治理结构要求      | G 词库       |

### 5.2 控制手段词库

#### 5.2.1 T 词库（技术措施）

T 词库采用两层结构：第一层为稳定的安全能力大类，第二层为可扩展的具体技术手段。

 **标注原则** ：条款标注时默认标到第一层；仅在条款原文有明确指定时才标注第二层。场景条件（客体状态、环境等）已编码了"传输"/"存储"等信息，T 词库不重复编码这些场景维度。

| 一级（安全能力）  | 二级（具体手段，示例）                                              |
| ----------------- | ------------------------------------------------------------------- |
| 身份鉴别          | 口令认证、多因素认证、生物识别、数字证书、单点登录                  |
| 访问控制          | 自主访问控制、强制访问控制、基于角色的访问控制、最小权限、权限回收  |
| 密码/加密         | 传输层加密(TLS)、存储加密、端到端加密、数字签名、密钥管理、国密算法 |
| 安全审计/日志     | 操作审计、安全事件日志、数据库审计、日志集中管理、日志完整性保护    |
| 入侵防范          | 入侵检测(IDS)、入侵防御(IPS)、WAF、蜜罐                             |
| 恶意代码防护      | 防病毒、终端检测与响应(EDR)、沙箱检测                               |
| 网络隔离/分段     | VLAN划分、网络分区、微隔离、物理隔离、逻辑隔离                      |
| 数据脱敏/去标识化 | 静态脱敏、动态脱敏、匿名化、假名化                                  |
| 数据备份/恢复     | 全量备份、增量备份、异地备份、恢复验证                              |
| 冗余/容灾         | 双机热备、异地容灾、负载均衡、业务连续性                            |
| 安全监测/态势感知 | 流量监测、异常行为分析、安全态势感知平台、告警                      |
| 漏洞管理/补丁     | 漏洞扫描、补丁管理、渗透测试                                        |
| 安全配置/基线     | 安全基线、配置核查、最小安装、默认账户处理                          |
| 接口安全/API安全  | 接口认证、接口鉴权、传输加密、接口审计、限流/防重放                 |
| 开发安全/代码安全 | 安全编码规范、代码审计、SAST/DAST、开源组件管理                     |

| 安全目标   | 说明                     |

| 保密性     | 防止信息泄露             |

### 5.3 控制程度

控制程度是原子要求的约束条件集合，由以下子维度构成：

| 子维度           | 典型值                                                                                                      | 说明                                                   |
| ---------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 模态（义务强度） | 强制（应/必须）、禁止（不得/严禁）、推荐（宜/建议）、可选（可）、豁免（……情况下可不）                     | 条款的义务性质                                         |
| 时限/频次        | 持续性（应始终/实时）、定期（周期值：年/季/月）、触发式（触发条件 + 时效窗口）、一次性（上线前/首次使用前） | 时间维度约束                                           |
| 覆盖范围         | 全量（所有/全部）、按级别（三级及以上/重要以上）、按条件（涉及个人信息的/跨境的）                           | 适用面限定                                             |
| 量化指标         | 数值 + 单位（自由字段）                                                                                     | 具体阈值，如密码长度≥8位、日志留存≥6个月、RPO≤4小时 |
| 审批层级         | 操作员级、管理员级、管理层级、监管机构级                                                                    | 授权/审批要求                                          |
| 证据要求         | 记录、报告、备案、留存（+期限）                                                                             | 文档化与可追溯性要求                                   |

## 7 维度间关系与标注规则

### 7.1 统一实体词库的角色机制

同一实体在不同条款中可扮演不同角色：

| 实体         | 作为客体               | 作为环境                   | 作为通道                 |
| ------------ | ---------------------- | -------------------------- | ------------------------ |
| 防火墙       | 应定期更新防火墙策略   | 部署于网络边界的防火墙环境 | —                       |
| 互联网       | —                     | 通过互联网提供服务的系统   | 数据经由互联网传输       |
| VPN          | VPN设备应定期维护      | —                         | 通过VPN通道传输          |
| 移动存储介质 | 应统一管理移动存储介质 | —                         | 数据通过移动存储介质转移 |

### 7.2 角色词库的双重身份

同一角色可在同一条款中同时标注为责任主体和协作方：

* 示例："第三方服务商应在合同约定范围内处理数据" → 责任主体=第三方服务商，协作方=第三方服务商

### 7.3 标注规则

1. **多值标注** ：所有维度均允许多值标注。一条原子要求可同时涉及多个客体、多个环境、多种措施。
2. **留空规则** ：当条款未显式指定某维度时，该维度留空，表示"不限/未指定"，而非标注为"全部"。
3. **推断克制** ：标注应忠实于条款原文。仅当上下文逻辑关系明确时允许推断，不做过度解读。
4. **颗粒度就高** ：标注时优先使用条款原文表述对应的最具体分类。如原文为"敏感个人信息"，不应标注为上位概念"个人信息"。
5. **T 词库分层标注** ：技术措施默认标注到第一层（安全能力大类）；仅在条款原文明确指定具体技术手段时才标注第二层。
