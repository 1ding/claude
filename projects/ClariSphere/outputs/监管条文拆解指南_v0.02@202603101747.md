# 1 概述

+   文档编号：GUIDE-REG-001
+   文档名称：监管条文结构化拆解指南
+   文档密级：内部资料

## 1.1 目的

+   本指南定义监管条文结构化拆解的字段体系、填写规则及操作步骤，用于将法规原文转换为可跨法规聚合的结构化记录。
+   适用场景：

-   对单部法规全文进行批量结构化拆解
-   跨法规汇总同一领域的全部监管要求
-   基于结构化记录开展合规差距分析与要求映射
-   将监管义务映射到安全目标体系，识别覆盖关系

## 1.2 核心模型

+   拆解基于 DSCM（数字场景概念模型）扩展框架，以"主体对客体执行行为"为语义核心，附加义务模态、条件、时限等规范性维度，并通过目标字段与 COAST 安全目标体系建立映射。
+   一条监管义务的完整语义结构如下图所示：

```graph
┌──────────────────────────────────────────────────────────────┐
│                      监管义务语义结构                        │
│                                                              │
│   [主体:组织|岗位|角色]  ──[义务模态]──▶  [行为]  ──▶  [客体:T|M|G] │
│                                                              │
│   条件层：在 [适用条件] 下  /  当 [触发事件] 时              │
│   约束层：按照 [规则内容]，在 [时限] 内                      │
│   目的层：为了 [保护法益]                                    │
│   映射层：对应 [COAST 安全目标]                              │
└──────────────────────────────────────────────────────────────┘
```

+   每条条文按上述结构拆解为一条或多条**义务记录**，一条记录对应一个独立的监管义务。

# 2 字段体系

## 2.1 字段定义

下表列出全部字段及其说明：

| 字段     | 必填 | 说明                                                                   |
| -------- | ---- | ---------------------------------------------------------------------- |
| 来源     | 是   | 法规名称 + 条款编号，如：数据安全法§27                                 |
| 义务类别 | 是   | 操作性 / 结构性 / 资格性 / 责任归属，见 2.2 节                         |
| 主体     | 是   | 被约束的责任方，标注类型（组织/岗位/角色），使用归一化类型，见 4.1 节  |
| 行为     | 是   | 主体作用于客体的动词，使用归一化动词，见 4.3 节                        |
| 客体     | 是   | 行为作用的对象，标注类型（T/M/G），使用归一化类型，见 4.2 节           |
| 适用条件 | 否   | 限定主体范围或场景的静态前置条件                                       |
| 触发事件 | 否   | 驱动义务生效的特定动态事件                                             |
| 义务模态 | 是   | 应 / 不得 / 可以 / 宜，见 3.1 节                                       |
| 规则内容 | 是   | 具体合规要求列表，每项为一个可独立验证的合规动作                       |
| 时限     | 否   | 立即 / 及时 / 定期 / N 日内 / 无                                       |
| 保护法益 | 否   | 条文明确表述的保护目的                                                 |
| 目标     | 否   | 对应 COAST 安全目标，格式：{一级} > {二级} > {三级}，见 4.4 节         |
| 例外     | 否   | 豁免条件，如"依法不予公开的除外"                                       |
| 法律后果 | 否   | 违规处罚，通常引用法律责任章节条款                                     |

## 2.2 义务类别

+   每条义务记录按其结构特征归入以下四类：

| 义务类别 | 特征                           | 行为词示例               |
| -------- | ------------------------------ | ------------------------ |
| 操作性   | 主体执行一个具体的动作         | 处理、监测、报告、配合   |
| 结构性   | 主体建立某个组织架构或制度     | 建立、设置、明确（机构） |
| 资格性   | 主体须具备某种状态或资质       | 取得、具备、持有         |
| 责任归属 | 某主体承担某项职责或责任       | 承担、负责、担任         |

# 3 填写规则

## 3.1 义务模态判断

+   根据条文关键词判断义务模态：

| 关键词                   | 模态 | 含义             |
| ------------------------ | ---- | ---------------- |
| 应、应当、须、必须       | 应   | 强制作为         |
| 不得、不应、禁止、严禁   | 不得 | 强制不作为       |
| 可以、可                 | 可以 | 授权许可，非强制 |
| 宜、鼓励、支持           | 宜   | 推荐做法，非强制 |

## 3.2 适用条件与触发事件的区分

+   **适用条件**：静态范围限定，主体满足条件则持续适用该义务。
    +   示例："关键信息基础设施运营者……"→ 适用条件 = 主体为关键信息基础设施运营者
+   **触发事件**：动态事件驱动，事件发生时义务才生效。
    +   示例："发现数据安全缺陷或漏洞时……"→ 触发事件 = 发现安全风险
+   两者可同时存在，也可均为空（表示无条件持续义务）。

## 3.3 规则内容的粒度

+   每项规则内容应为**一个独立可验证的合规动作**，用①②③列举。
+   不可验证的抽象表述保留原文，不拆解过细。
+   示例（数据安全法§27）：

    -   ①建立健全全流程数据安全管理制度
    -   ②组织开展数据安全教育培训
    -   ③采取相应技术措施和其他必要措施

## 3.4 责任归属类条文的处理

+   中文监管条文常用"是……"代替"应当承担……"，须还原隐含动词后再填写行为字段。

| 原文句式               | 隐含义务动词 | 还原示例                       |
| ---------------------- | ------------ | ------------------------------ |
| X 是安全第一责任人     | 承担         | X 应当承担安全第一责任         |
| 应当明确安全负责人     | 建立         | 主体应建立安全职能岗位         |
| 应当具备相应资质       | 取得         | 主体应取得相应资质             |
| 应当取得行政许可       | 取得         | 主体应取得行政许可             |

## 3.5 一条条文拆分为多条记录的情形

+   出现以下任一情形时，拆分为多条独立义务记录：

-   条文涉及多个不同主体，每个主体单独一条记录
-   条文中义务模态混合（"应"与"不得"并存），按模态分别单独一条记录
-   条文中存在不同触发事件，每个触发事件单独一条记录

## 3.6 目标字段的填写

+   目标字段用于将监管义务与 COAST 安全目标体系建立映射，格式为 `{一级} > {二级} > {三级}`。
+   填写原则：

-   **尽量填到三级**；只有义务确实跨越多个三级目标时，才停留在二级
-   一条义务可对应多个目标，用分号分隔
-   处罚性条款（法律责任章节）通常不填目标

## 3.7 语法主语辨别

+   部分条文以**活动名称**作为语法主语（如"变更管理应当……"、"开发应当……"），此时：

    -   **活动本身是客体**（M 类），不是主体
    -   **真正的主体**是负责该活动的组织或岗位，需根据上下文识别
    -   若上下文未明确指定，填写最贴近的归一化角色

+   示例：

| 原文                   | 错误理解      | 正确拆解                                      |
| ---------------------- | ------------- | --------------------------------------------- |
| 变更管理应当确保……     | 主体=变更管理 | 主体=负责变更管理的组织，客体=M3.1 变更管理   |
| 开发应当遵循安全规范   | 主体=开发     | 主体=开发团队（组织/岗位），客体=M2.4 安全开发 |

## 3.8 客体类型标注

+   客体字段使用 `{代码} {名称}` 格式，如 `M3.1 变更管理`、`T1.3 个人信息`、`G2.2 安全组织架构`。
+   多个客体用分号分隔。
+   T/M/G 完整分类体系见第 4 章第 4.2 节。

## 4.2 客体词表（T/M/G 框架）

+   T/M/G 是对监管义务作用对象的语义分类：

| 类别 | 全称         | 含义                               |
| ---- | ------------ | ---------------------------------- |
| T    | 技术/设施/资源 | 被保护或被处理的技术性对象       |
| M    | 管理/活动    | 被规范或被约束的活动或过程         |
| G    | 治理/架构    | 被要求建立或维护的制度与组织结构   |

# 5 拆解步骤

+   按以下步骤对每条条文执行拆解：

-   **Step 1　识别是否需拆解**：判断条文是否属于不拆类型（见 5.1 节）。属于则跳过，不属于则继续。
-   **Step 2　识别主体**：条文中有几个主体？注意辨别语法主语（见 3.7 节），多个主体则准备生成多条记录。
-   **Step 3　确定义务类别**：该义务是操作性、结构性、资格性，还是责任归属？
-   **Step 4　还原行为动词**：如条文为"是……"句式，还原隐含动词（见 3.4 节）。
-   **Step 5　确定行为和客体**：主体对什么对象（T/M/G）执行什么动词？
-   **Step 6　判断义务模态**：关键词归类，见 3.1 节。
-   **Step 7　判断条件类型**：有无适用条件（静态）或触发事件（动态）？
-   **Step 8　拆解规则内容**：逐项列举可独立验证的合规动作，用①②③标注。
-   **Step 9　填写时限、法益、例外**：有则填，无则留空。
-   **Step 10　映射目标**：对照 4.4 节词表，选取 COAST 安全目标，尽量到三级。
-   **Step 11　归一化**：对照 4.1～4.3 节词表，标注主体类型，映射客体 T/M/G 代码。

## 5.1 不拆的条文类型

+   以下类型条文跳过，不纳入义务记录：

| 类型       | 示例                       | 原因                         |
| ---------- | -------------------------- | ---------------------------- |
| 定义条款   | 第3条 数据的定义           | 无义务，仅定义术语           |
| 政策宣示   | 第7条 国家保护数据权益     | 无可验证合规动作             |
| 立法目的   | 第1条 制定本法目的         | 无义务                       |
| 纯授权条款 | 第54条 军事数据另行制定    | 义务在子法规中，待子法规拆解 |

# 7 义务记录 JSON 格式

## 7.1 监管侧记录格式

+   完成拆解后，每条义务记录序列化为以下 JSON 格式：

```json
{
  "source": "数据安全法§29",
  "obligation_type": "操作性",
  "subject": {
    "normalized_type": "数据处理者",
    "category": "组织",
    "type_class": "通用"
  },
  "action": "处置",
  "object": [
    { "code": "M4.2", "name": "漏洞管理" }
  ],
  "applicable_condition": null,
  "trigger_event": "发现数据安全缺陷或漏洞",
  "modality": "应",
  "rules": [
    "①立即采取补救措施"
  ],
  "deadline": "立即",
  "legal_interest": "数据安全",
  "targets": [
    { "level1": "环境安全", "level2": "平台稳定性", "level3": "风险可预性" }
  ],
  "exception": null,
  "legal_consequence": null
}
```

## 7.2 字段说明

+   各字段与第 2 章字段体系的对应关系及取值规则如下：

| JSON 字段                 | 对应字段 | 类型            | 必填 | 取值规则                                                       |
| ------------------------- | -------- | --------------- | ---- | -------------------------------------------------------------- |
| `source`                  | 来源     | string          | 是   | 法规名称 + 条款编号，如 `数据安全法§29`                        |
| `obligation_type`         | 义务类别 | string          | 是   | `"操作性"` / `"结构性"` / `"资格性"` / `"责任归属"`           |
| `subject.normalized_type` | 主体     | string          | 是   | 见 4.1 节归一化类型                                                                   |
| `subject.category`        | 主体类型 | string          | 是   | `"组织"` / `"岗位"` / `"角色"`                                                        |
| `subject.type_class`      | 主体专属性 | string        | 是   | `"通用"` / `"专属"`，见 GUIDE-REG-002 第 2.3 节；通用主体按 `category` 级别匹配，专属主体需项目配置声明 |
| `action`                  | 行为     | string          | 是   | 见 4.3 节归一化动词                                            |
| `object`                  | 客体     | array           | 是   | 多客体时含多项；跨大类时 `code` 填父类如 `"M4"`                |
| `applicable_condition`    | 适用条件 | string \| null  | 否   | 无则 `null`                                                    |
| `trigger_event`           | 触发事件 | string \| null  | 否   | 无则 `null`                                                    |
| `modality`                | 义务模态 | string          | 是   | `"应"` / `"不得"` / `"可以"` / `"宜"`                         |
| `rules`                   | 规则内容 | array\<string\> | 是   | 每项一个独立可验证的合规动作，保留 `①②③` 前缀                 |
| `deadline`                | 时限     | string \| null  | 否   | `"立即"` / `"及时"` / `"定期"` / `"N日内"` / `null`           |
| `legal_interest`          | 保护法益 | string \| null  | 否   | 无则 `null`                                                    |
| `targets`                 | 目标     | array\<object\> | 否   | 多目标时含多项；只到二级时省略 `level3`；处罚条款填空数组 `[]` |
| `exception`               | 例外     | string \| null  | 否   | 无则 `null`                                                    |
| `legal_consequence`       | 法律后果 | string \| null  | 否   | 无则 `null`                                                    |

## 7.3 内规侧记录的差异

+   内规记录复用监管侧同一 schema，额外增加两个字段；`subject.type_class` 字段不适用于内规侧（主体专属性由监管侧记录携带）：

| 附加字段  | 类型   | 说明                                                            |
| --------- | ------ | --------------------------------------------------------------- |
| `doc_ref` | string | 内规来源文件编号，如 `DSP-OPS-012`                              |
| `scope`   | string | 内规适用范围，如 `"全公司"` / `"信息科技部"` / `"核心业务系统"` |

+   内规主体覆盖判断不依赖内规记录中的主体字段，而由监管侧 `subject.type_class` 驱动，见 GUIDE-REG-002 第 2.3 节。

+   `subject.regulatory_type` 填写示例：内规主体原文为"本公司"，填写 `"数据处理者"`；原文为"信息科技部"，视其承担的职责填写最贴近的归一化类型。
+   `legal_interest` 和 `legal_consequence` 在内规记录中通常为 `null`。
