# 2 概念定义

## 2.1 三个核心管理职能

+   风险管理、内控、合规是三个独立的管理职能，各自拥有完整的生命周期，从不同视角服务于同一个终极目标——**保障组织目标的实现**。

+   **风险管理**（文档标题及高层摘要中简称"风险"）：**风险**是某一事件在特定时间窗口内发生并对目标造成负面影响的可能性及其潜在后果；**风险管理**是对风险进行识别、评估、应对和监控的系统性过程。风险管理从"不确定性"视角保障组织目标，其生命周期为：风险识别 → 风险评估 → 风险应对 → 风险监控 → 风险重评估。

+   **内部控制（内控）**：为保障组织目标实现而设计和执行的控制活动集合，包括流程控制、权限控制、系统控制、审批控制等。按照 COSO 框架的经典定义，内控服务于三个层次的目标：经营的效率和效果、报告的可靠性、法律法规的遵循。内控从"控制有效性"视角保障组织目标，其生命周期为：内控设计 → 内控实施 → 内控运行 → 内控评价 → 内控优化。内控回答"控制措施有没有到位、有没有生效"。内控本身也是明确的监管要求——《商业银行内部控制指引》《企业内部控制基本规范》等法规对内控体系的建设、运行和评价提出了直接的强制性要求。本文档取内控的狭义口径，聚焦于 COSO 内部控制框架五要素中的"控制活动"要素。COSO 框架的完整五要素（控制环境、风险评估、控制活动、信息与沟通、监督活动）涵盖范围更广，其中"风险评估"和"监督活动"与本文档所述的风险管理、合规验证存在职能交叉——这正是三个职能相互协同的体现，而非定义冲突。

+   **合规管理**：对外部法规和监管要求的符合状态，以及维持该状态所开展的管理职能。合规的参照系严格限定为外部规则（法律法规、监管指引、行业标准等），不包括对内部制度的符合性检验——内部制度的执行属于内控的职责范畴。合规从"外部规则符合性"视角保障组织目标，其生命周期为：监管要求识别 → 合规审查 → 合规监测 → 合规验证 → 整改闭环。合规验证两件事：①各项业务和管理活动是否符合外部监管要求；②内控体系的建设与评价机制是否满足监管对内控的专项要求。

## 2.2 制度——书面规则的载体

+   **制度**是将管理要求固化为可执行书面规则的载体。制度本身不是独立的管理职能，而是服务于三个职能的公共表达层——风险管理、内控、合规都需要通过制度将各自的管理要求书面化。

+   制度本身不创造管理要求，只承载和固化管理要求。

+   制度的内容依据来源多元，三个职能均可直接驱动制度建设：

    -   **合规驱动制度**：将外部监管法规的要求直接转化为内部规则（如将《商业银行信息科技风险管理指引》的变更管理要求转化为《变更管理办法》）。
    -   **风险驱动制度**：将风险应对措施固化为规则（如针对高频变更故障风险，制定变更双人审核规程）。
    -   **内控驱动制度**：将控制活动的设计要求和操作规范固化为书面文本（如内控评价、报告等内控体系运行的管理要求）。

+   制度体系通常分为三个层级：管理办法（政策层，规定"管什么、谁来管"）、实施细则（标准层，规定"管到什么程度"）、操作规程（流程层，规定"具体怎么操作"）。

+   需要强调的是，制度并非管理要求落地的唯一形式。特别是在科技风险领域，内控要求同样可以通过系统配置（如权限矩阵）、自动化规则（如自动告警）、技术架构（如网络隔离）等非制度形式落地。这些技术性措施的"载体"是系统配置和技术架构本身，制度仅需规定其管理原则和变更审批要求。

## 2.3 三个职能的边界与协同

+   **风险与合规的边界**：风险管理前瞻性地应对不确定性；合规管理对标性地验证对外部监管要求的符合程度。两者均属第二道防线（详见第 3.3 节三道防线说明），但视角不同——风险管理以"损失"为核心，合规管理以"外部监管要求"为核心。两者的协同点在于：合规检验的结果可反馈为新的风险输入，驱动风险重评估。

+   **合规与内控的边界**：合规对外——其参照系是外部法规和监管要求，回答"有没有满足监管的要求"；内控对内——关注控制措施的设计和执行有效性，回答"控制措施有没有到位、有没有生效"。两者的协同点在于：监管对内控体系本身有专项要求（如《商业银行内部控制指引》），因此合规需验证内控体系是否满足这些外部要求，但合规不介入判断具体内控措施的内部执行质量——后者是内控自身的管理范畴。

+   **风险与内控的边界**：风险识别"需要防什么"，内控落实"怎么防"。两者的协同点在于：风险评估的结果是内控措施设计的重要输入，内控失效的信息又反馈到风险评估中驱动重评估。

+   **制度与三个职能的关系**：制度作为书面规则的载体，同时服务于三个职能。合规可以直接驱动制度建设（将监管要求转化为内部规则），风险可以直接驱动制度建设（将风险应对策略固化为规则），内控也可以直接驱动制度建设（将控制要求固化为操作规程）。三条路径平行存在，不存在谁必须经过谁的依赖关系。

## 2.4 目标差异与历史基因

+   三个管理职能虽然协同运作，但各自的核心目标和视角存在本质差异：

    | 职能     | 核心视角       | 核心目标                                     | 历史基因与演化                                                                                                                  |
    | -------- | -------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
    | 风险管理 | 不确定性       | 将不确定性对目标的负面影响控制在可接受范围内 | 源于保险和金融风险量化，后扩展至操作风险、科技风险等全域                                                                        |
    | 内控     | 控制有效性     | 确保控制措施有效运行，防止目标偏离           | 源于财务可靠性（COSO 框架最初为解决财务报告错报、资产流失、舞弊问题而设计），后扩展至运营安全、数据完整性、系统连续性等多维目标 |
    | 合规     | 外部规则符合性 | 确认各项活动符合外部法规和监管要求           | 源于金融监管对标，始终以外部规则为参照系                                                                                        |

+   特别说明：内控的历史基因偏财务，经典目标是"防止财务数据错报、资产流失、舞弊"。但在科技风险语境下，内控的目标已显著泛化——变更双人审核、权限最小化、灾备演练等内控措施的直接目标是保障系统稳定运行和数据完整性，已远超财务控制的范畴。合规的目标则始终聚焦于"确认符合外部要求"，不直接承担"防止风险发生"的职责——防止风险发生是风险管理的目标，合规关心的是"有没有按监管要求做"。

# 3 参考框架

## 3.1 与 COSO 内部控制框架的关系

+   COSO 内部控制框架包含五个要素：控制环境、风险评估、控制活动、信息与沟通、监督活动。本文框架对五个要素的处理如下：

-   **风险评估**：COSO 将风险评估纳入内控体系；本文框架将其独立为风险管理职能。在本文框架中，内控在设计控制活动时调用风险管理职能的评估结果作为输入——即"委托"而非"内含"。两种处理方式的差异源于视角不同：COSO 以内控为中心统摄风险评估，本文以管理职能分工为中心将二者并列。

-   **控制环境**：三个职能运作的前提条件，而非独立职能。控制环境包含两类内容：规则性内容（治理结构、职责划分、道德准则等）由制度承载；文化性内容（领导层基调、组织伦理氛围）构成三个职能有效运作的组织土壤——它解释了为什么同样的内控设计在不同组织中执行质量差异显著。

-   **控制活动**：本文内控的核心对应要素（狭义口径）。本文聚焦于此要素，即控制措施的设计与执行。

-   **信息与沟通**：贯穿三个职能的基础设施，不对应任何单一职能。本文关系结构图中三职能之间的"信息交互与反馈闭环"即对应此要素——没有有效的信息与沟通机制，三职能的协同无从实现。

-   **监督活动**：在本文框架中分两个层次处理。宏观层面对应三道防线中的第三道（内部审计）和合规管理的验证职能，负责对整体管理效果的独立评价；微观层面嵌入控制活动本身，是内控运行周期中"内控评价"环节的组成部分，即每项控制措施执行后持续跟踪其有效性。

## 3.2 与 ISO 31000 风险管理框架的关系

+   ISO 31000 提供了通用的风险管理过程框架：建立环境 → 风险识别 → 风险分析 → 风险评价 → 风险应对 → 监控与评审。本文的四个概念可映射为：风险识别与评估对应"风险识别 → 风险评价"阶段；制度建设不局限于单一阶段，可在风险应对阶段（规则固化）、监管要求识别阶段（合规要求内部化）和控制活动设计阶段（操作规程书面化）等多点触发，与制度服务于三职能的定位一致；内控执行对应"风险应对"阶段的措施落地；合规验证对应"监控与评审"阶段。

## 3.3 三道防线模型

+   三道防线是银行业风险治理的基本架构。三个核心职能在三道防线中的角色分布如下：

    | 防线   | 角色定位           | 与三个职能的关系                                                                 |
    | ------ | ------------------ | -------------------------------------------------------------------------------- |
    | 第一道 | 业务与 IT 部门     | 负责内控措施的一线落地和制度的日常执行，是风险的直接承担者                       |
    | 第二道 | 风险管理与合规部门 | 负责风险识别与评估方法论的建立，以及合规状态的独立监督                           |
    | 第三道 | 内部审计部门       | 对风险管理、内控执行、合规管理的整体有效性进行独立评价，不直接参与前两道防线工作 |

+   三道防线的核心原则是职责分离：执行风险应对措施的部门不能自我评价其有效性，合规监督部门不能替代业务部门承担执行责任。

# 4 逻辑关系

## 4.1 核心模型：三职能平行协同

+   风险管理、内控、合规是三个平行的管理职能，各自拥有独立的生命周期，从不同视角保障组织目标的实现。三者之间不是"谁驱动谁"的线性关系，而是各自独立运转、通过信息交互实现协同的并行关系。

+   下图展示三职能的平行关系与制度的定位：

## 4.2 三职能间的协同关系

+   三职能各边界的定义见第 2.3 节；本节归纳核心协同路径，作为第 5 章信息交互分析的逻辑基础。

+   **风险与内控的协同**：风险评估的结果是内控措施设计的重要输入——风险评估决定"需要控什么、控到什么程度"。反向地，内控失效的信息反馈到风险评估中，驱动风险重评估。

+   **合规与内控的协同**：合规要求（外部监管法规）是内控体系建设的重要输入——监管不仅对具体业务领域提出控制要求，还对内控体系本身的建设标准、评价机制有直接规定。反向地，内控运行的证据和效果是合规验证的核心检查对象。

+   **风险与合规的协同**：合规检验发现的缺口反馈为新的风险输入，驱动风险重评估与应对策略调整。同时，监管关注的风险领域也是风险识别的重要参考来源。

## 4.3 制度建设与三职能的关系

+   制度作为书面规则的公共载体，三个职能均可直接驱动制度建设，不存在必须经过某一职能中转的依赖关系：

    -   **合规 → 制度**：将外部监管法规的要求直接转化为内部规则（如将《商业银行信息科技风险管理指引》的变更管理要求转化为《变更管理办法》）。
    -   **风险 → 制度**：将风险应对措施固化为规则（如针对高频变更故障风险，制定变更双人审核规程）。
    -   **内控 → 制度**：将控制活动的设计要求和操作规范固化为书面文本（如内控评价流程、控制活动操作手册）。

+   一项制度的内容往往同时承载多个职能的要求。例如《变更管理办法》既承载了合规要求（监管对变更管理的强制性规定）、又承载了风险应对要求（针对变更故障风险的控制措施）、也承载了内控要求（变更审批流程和权限设计）。

+   制度并非管理要求落地的唯一形式。内控要求同样可以通过系统配置、自动化规则、技术架构等非制度形式落地。在紧急风险场景下，控制措施可以先于制度落地（措施先行、制度后补）。

# 5 依存关系分析

## 5.1 三职能的信息交互

+   三个职能通过信息交互实现协同，主要交互路径如下：

    | 信息发出方 | 信息接收方 | 交互内容                   | 作用                   |
    | ---------- | ---------- | -------------------------- | ---------------------- |
    | 风险管理   | 内控       | 风险评估结果、风险应对策略 | 内控措施设计的输入     |
    | 合规管理   | 内控       | 外部监管要求、合规检查发现 | 内控体系建设的依据     |
    | 内控       | 合规管理   | 内控运行证据、内控评价报告 | 合规验证的核心检查材料 |
    | 合规管理   | 风险管理   | 合规检验缺口、监管动态     | 风险重评估的输入       |
    | 内控       | 风险管理   | 内控失效信息、控制偏差数据 | 风险重评估的输入       |
    | 风险管理   | 合规管理   | 新识别的风险领域           | 合规监测范围的参考     |

## 5.2 反向传导与持续改进

+   三职能的协同形成持续改进闭环：

    -   合规检验发现缺口 → 反馈至风险管理（风险重评估）和内控（内控优化）
    -   内控失效 → 反馈至风险管理（暴露风险识别遗漏）→ 制度载体相应修订
    -   风险重评估 → 输出新的内控设计要求 → 内控优化 → 制度载体更新

## 5.3 常见失效模式

+   下表列出六类典型失效模式及根因定位：

    | 失效现象                           | 根因定位                             | 修复路径                                           |
    | ---------------------------------- | ------------------------------------ | -------------------------------------------------- |
    | 有制度，执行不到位                 | 内控设计不足                         | 补充控制点，增加执行检查机制                       |
    | 监管检查发现制度空白               | 风险识别遗漏                         | 重新开展风险评估，补建制度                         |
    | 合规检验通过，但事故仍发生         | 合规标准低于实际风险水位             | 提升内控严格程度，超合规管理                       |
    | 内控繁琐导致业务绕过               | 制度设计脱离业务实际                 | 风险与效率平衡，优化内控设计                       |
    | 制度更新滞后于技术演进             | 制度修订机制缺乏与技术架构变更的联动 | 建立技术变更驱动的制度评审触发机制                 |
    | 内控执行了但合规检验无法确认有效性 | 内控证据链断裂（控制留痕不足）       | 强化控制活动的证据留存要求，建立证据完整性检查机制 |

# 6 科技风险语境下的应用

## 6.1 概念在科技风险场景中的映射

+   下表以信息科技部常见场景为例，展示四个概念的具体对应：

    | 概念 | 科技风险场景示例                                         |
    | ---- | -------------------------------------------------------- |
    | 风险 | 核心系统宕机、数据泄露、IT 外包集中度过高、变更引发故障  |
    | 制度 | 变更管理办法、数据安全管理规定、业务连续性管理制度       |
    | 内控 | 变更双人审核、生产权限最小化、定期灾备演练、日志审计     |
    | 合规 | 对标《商业银行信息科技风险管理指引》《网络安全法》等要求 |

## 6.2 端到端场景贯穿示例

+   以"变更管理"为主线，展示三个职能和制度在同一场景下如何平行协同：

    | 阶段                 | 职能/环节 | 场景内容                                                                                                                                                         |
    | -------------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
    | 风险管理生命周期     | 风险管理  | 识别到"生产变更引发系统故障"是高频高影响风险场景，评估风险等级为"高"，输出风险应对策略                                                                           |
    | 合规管理生命周期     | 合规管理  | 识别到《商业银行信息科技风险管理指引》对变更管理有明确控制要求，输出合规要求清单                                                                                 |
    | 内控设计与实施       | 内控      | 综合风险评估结果和合规要求，设计控制措施：变更双人审核 → 高风险变更回退方案预审 → 变更窗口外操作须总经理级审批 → 变更实施全程录屏留痕                            |
    | 制度建设（公共载体） | 制度      | 将上述各职能要求固化为书面载体：《变更管理办法》（政策层）→《变更分类与审批细则》（标准层）→《变更操作手册》（流程层），同时承载合规要求、风险应对要求和内控要求 |
    | 合规验证             | 合规管理  | 按监管要求逐项检查内控落地情况 → 抽查变更记录与审批流程 → 输出合规检查报告                                                                                       |
    | 协同闭环             | 三职能    | 合规检查发现"紧急变更补审批率不足"→ 反馈至风险管理（风险重评估）和内控（优化控制措施）→ 更新制度载体                                                             |

## 6.3 监管评级视角

+   银行监管科技风险评级（如 ITRS，Information Technology Risk Supervision，信息科技风险监管评级）对四个维度均有考察：

    -   **风险识别能力**：是否建立完整的科技风险识别和评估机制。
    -   **制度完备性**：制度覆盖面是否对应监管要求的各控制域。
    -   **内控有效性**：制度是否真正执行，控制活动是否留有记录和证据。
    -   **合规闭环**：问题发现后是否有整改追踪机制，合规缺口是否闭环。

+   四个维度中，监管关注的重点通常是**内控有效性**——制度文件容易准备，但执行证据难以伪造，是评级区分度最高的维度。这也是本文档在失效模式中特别列出"内控证据链断裂"的原因。

## 6.4 三道防线在科技风险中的落地

+   科技风险管理中，三道防线的具体职责分工如下：

    | 防线   | 承担部门示例       | 科技风险场景下的职责                                                                       |
    | ------ | ------------------ | ------------------------------------------------------------------------------------------ |
    | 第一道 | 开发团队、运维团队 | 执行变更审批流程、落实最小权限、实施灾备演练、按操作规程执行日常运维                       |
    | 第二道 | 科技风险管理团队   | 建立科技风险评估方法论、审查制度覆盖完整性、监控关键风险指标（KRI）、开展合规检查          |
    | 第三道 | 内部审计部门       | 对科技风险管理体系整体有效性进行独立审计，评价一二道防线的履职情况，出具审计报告并跟踪整改 |

# 7 四类评估矩阵及其关系

## 7.1 矩阵定位

+   风险评估矩阵、合规评估矩阵、内控检查矩阵、制度执行检查矩阵，是三个管理职能及制度管理各自的结构化评估工具，在各自生命周期的评估环节中使用：

    | 矩阵             | 对应概念 | 在生命周期中的位置         | 核心输出                       |
    | ---------------- | -------- | -------------------------- | ------------------------------ |
    | 风险评估矩阵     | 风险管理 | 风险评估环节               | 风险等级清单、残余风险评级     |
    | 合规评估矩阵     | 合规管理 | 合规审查与验证环节         | 合规缺口清单、整改优先级       |
    | 内控检查矩阵     | 内控     | 内控评价环节               | 内控有效性评级、证据完整性状态 |
    | 制度执行检查矩阵 | 制度     | 制度执行监督（非独立职能） | 执行缺口清单、制度修订需求     |

+   注：制度执行检查矩阵虽与三职能矩阵并列呈现，但制度本身不是独立管理职能（见 2.2 节）；该矩阵是附着于三职能协同的辅助工具，其结果经流⑦汇入内控检查矩阵。

+   四类矩阵之间的信息流转，是第 5.1 节三职能信息交互在操作层的具体实现。矩阵输出结果即各职能间信息交互的载体。

## 7.2 各矩阵说明与示例

+   以下四个矩阵示例均采用同一场景（变更管理），以便对照理解各矩阵的视角差异。

### 7.2.1 风险评估矩阵

+   **用途**：对风险场景进行概率 × 影响的二维评估，输出风险等级，驱动风险应对优先级决策。
+   **核心维度**：风险场景、发生概率（1—5 级）、影响程度（1—5 级）、风险等级（概率 × 影响）、应对策略。
+   **评级规则**：

    | 风险等级 | 分值区间 | 处置要求                               |
    | -------- | -------- | -------------------------------------- |
    | 极高     | ≥ 16     | 立即应对，优先设计强内控，合规重点关注 |
    | 高       | 8—15     | 本季度内完成应对策略，纳入内控重点检查 |
    | 中       | 4—7      | 纳入常规内控覆盖范围                   |
    | 低       | ≤ 3      | 接受或记录，定期复审                   |

+   变更管理场景示例：

    | 风险场景             | 发生概率 | 影响程度 | 风险等级 | 应对策略                         |
    | -------------------- | -------- | -------- | -------- | -------------------------------- |
    | 生产变更引发系统宕机 | 3        | 5        | 高（15） | 变更双人审核、回退方案预审       |
    | 未授权变更操作       | 2        | 4        | 高（8）  | 生产权限最小化、操作日志审计     |
    | 变更窗口外操作       | 2        | 3        | 中（6）  | 审批管控、窗口时间锁             |
    | 变更文档缺失         | 3        | 2        | 中（6）  | 变更申请模板强制填写、提交前校验 |
    | 外包人员越权操作     | 1        | 5        | 中（5）  | 访问权限隔离、全程录屏、操作审批 |

### 7.2.2 合规评估矩阵

+   **用途**：将外部监管要求逐项映射至当前符合状态，识别合规缺口，确定整改优先级。
+   **核心维度**：监管要求、监管来源、符合状态（完全符合 / 部分符合 / 不符合）、缺口描述、整改优先级。
+   **整改优先级规则**：不符合 → 高；部分符合 → 中；完全符合 → 无需整改。

+   变更管理场景示例：

    | 监管要求                 | 监管来源                 | 符合状态 | 缺口描述                       | 整改优先级 |
    | ------------------------ | ------------------------ | -------- | ------------------------------ | ---------- |
    | 变更须建立书面管理流程   | 《信息科技风险管理指引》 | 完全符合 | —                              | —          |
    | 重大变更须经充分测试     | 同上                     | 部分符合 | 重大变更认定标准不统一         | 中         |
    | 紧急变更须事后补办审批   | 同上                     | 不符合   | 补审批率不足50%                | 高         |
    | 变更记录须保存至少一年   | 同上                     | 完全符合 | —                              | —          |
    | 重大变更须向监管机构报告 | 《网络安全法》           | 部分符合 | 报告触发条件未在制度中明确定义 | 中         |

### 7.2.3 内控检查矩阵

+   **用途**：对已设计的控制措施评估设计有效性（能否达到控制目标）和运行有效性（是否实际生效），并核查证据完整性。
+   **核心维度**：控制目标、控制措施、控制类型（预防性 / 检测性 / 纠正性）、设计有效性、运行有效性、证据完整性、综合评价。
+   **综合评价规则**：三个维度均充分 / 有效 / 完整 → 有效；任一维度存在缺陷 → 需改进；多个维度存在缺陷 → 无效。

+   变更管理场景示例：

    | 控制目标       | 控制措施           | 控制类型 | 设计有效性 | 运行有效性 | 证据完整性                  | 综合评价 |
    | -------------- | ------------------ | -------- | ---------- | ---------- | --------------------------- | -------- |
    | 防止未授权变更 | 变更双人审核       | 预防性   | 充分       | 有效       | 完整（审批记录可查）        | 有效     |
    | 防止窗口外操作 | 变更窗口时间锁     | 预防性   | 充分       | 部分有效   | 不完整（3次绕过无报告记录） | 需改进   |
    | 确保变更可回退 | 高风险变更回退预审 | 预防性   | 充分       | 有效       | 完整（回退方案留档）        | 有效     |
    | 检测变更异常   | 变更后监控告警     | 检测性   | 部分充分   | 部分有效   | 不完整（告警覆盖率60%）     | 需改进   |
    | 修复失控变更   | 紧急回滚流程       | 纠正性   | 充分       | 有效       | 完整（演练记录可查）        | 有效     |

### 7.2.4 制度执行检查矩阵

+   **用途**：对制度条款的实际执行情况进行抽样检查，识别执行缺口，为制度修订和内控优化提供依据。
+   **核心维度**：制度条款、制度来源、执行情况（已执行 / 部分执行 / 未执行）、抽样发现、缺口成因。
+   **与内控检查矩阵的区别**：内控检查矩阵关注控制措施的"有效性"（含设计层面），覆盖所有控制形式（制度、系统配置、技术架构等）；制度执行检查矩阵仅关注制度条款的"执行符合率"（运行层面抽样验证）。制度执行检查的结果是内控检查矩阵中"运行有效性"评估的关键输入之一。

+   变更管理场景示例（本期抽查30笔）：

    | 制度条款                       | 制度来源         | 执行情况 | 抽样发现                    | 缺口成因             |
    | ------------------------------ | ---------------- | -------- | --------------------------- | -------------------- |
    | 变更申请须提前2个工作日提交    | 《变更管理办法》 | 已执行   | 30/30符合                   | —                    |
    | 变更须经双人审核后方可实施     | 同上             | 已执行   | 29/30符合（1笔单人操作）    | 紧急情况未按规程处理 |
    | 高风险变更须总经理级审批       | 同上             | 部分执行 | 7/10符合（3笔缺总经理签字） | 审批流程不清晰       |
    | 紧急变更须48小时内补办审批     | 同上             | 部分执行 | 3/8符合（5笔超期未补审批）  | 无跟踪提醒机制       |
    | 变更记录须在实施后24小时内归档 | 同上             | 未执行   | 0/5符合（全部超期归档）     | 归档责任人未明确     |

## 7.3 矩阵间信息流转关系

+   四类矩阵之间共有七条主要信息流，是第 5.1 节三职能信息交互表在评估工具层的对应展开：

    | 编号 | 信息发出方       | 信息接收方   | 流转内容                     | 作用                               |
    | ---- | ---------------- | ------------ | ---------------------------- | ---------------------------------- |
    | ①    | 风险评估矩阵     | 内控检查矩阵 | 风险等级清单                 | 决定控制措施的检查优先级和深度     |
    | ②    | 风险评估矩阵     | 合规评估矩阵 | 新识别风险领域               | 扩展合规监测范围，补充监管关注方向 |
    | ③    | 合规评估矩阵     | 内控检查矩阵 | 监管要求、合规检查发现       | 定义控制设计标准，驱动内控改进     |
    | ④    | 内控检查矩阵     | 合规评估矩阵 | 内控运行证据、内控有效性评级 | 合规验证的核心检查材料             |
    | ⑤    | 合规评估矩阵     | 风险评估矩阵 | 合规缺口清单                 | 转化为新风险输入，触发风险重评估   |
    | ⑥    | 内控检查矩阵     | 风险评估矩阵 | 内控失效信息、控制偏差数据   | 暴露风险识别遗漏，触发风险重评估   |
    | ⑦    | 制度执行检查矩阵 | 内控检查矩阵 | 执行符合率、执行缺口         | 运行有效性评估的核心输入           |

+   七条信息流形成三条持续改进闭环，与第 5.2 节所述三条闭环一一对应：

    -   **合规驱动闭环**（对应 5.2 第1条）：合规缺口（⑤）→ 风险重评估；同时经③直接传入内控检查矩阵——两路并行驱动内控改进 → 内控改进后证据更新（④）→ 合规缺口关闭
    -   **内控失效驱动闭环**（对应 5.2 第2条）：内控失效（⑥）→ 风险等级提升 → 风险应对策略更新，驱动制度修订 → 制度执行重新抽查（⑦）→ 内控运行有效性提升
    -   **风险驱动闭环**（对应 5.2 第3条）：风险重评估（由以上闭环触发或独立触发）→ 经①重新传入内控检查矩阵 → 调整控制措施设计要求与检查优先级 → 必要时驱动制度修订

+   流②（风险评估矩阵 → 合规评估矩阵）是单向信息参考流——风险识别结果扩充合规监测范围，不形成独立反馈闭环，因此不出现在上述三条闭环路径中。
